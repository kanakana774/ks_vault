# オブジェクト指向的なクラスの作り方

新人研修向け / Java基礎

---

## 0. この資料のゴール

「クラスを **なぜ・どの単位で** 作るか」を、手順と判断基準で言語化する。
丸暗記ではなく「自分の言葉で、なぜこう分けたか説明できる」状態を目指す。

判断基準を先に一行で言うと:

> **状態（データ）を持つ概念か、純粋な処理かを見分ける。これが全ての分かれ道。**

---

## 1. クラスを作る手順（ゼロから書くとき）

### ステップ1: まず main にベタ書きして動かす

最初から綺麗に書こうとしない。一度ベタ書きで動かす。
これが後の「改善の基準点」になり、なぜ分けるのかを体感できる。

### ステップ2: メソッドに切り出す（引き金で判断）

以下のどれかを感じたら、メソッドに切り出すサイン。

- 同じ処理が2回以上出てきた（コピペした）
- main を読んでも何をしているか一目で分からない
- **`// 平均を計算` とコメントを書きたくなった**

> コメントを書きたくなったら、それは **メソッド名にできる** サイン。
> `// 平均を計算` → `average()` に変換する。

### ステップ3: クラスにまとめる（引き金で判断）

メソッドに切り出した後、**引数**を見る。

- メソッドの引数に、**毎回同じデータを渡している**
- そのデータが、複数のメソッドを引き回されている

→ その「いつも一緒にいるデータと処理」が、クラスにまとめる単位。

```java
// 切り出したが、scores を毎回渡している
double avg = average(scores);
int max = findMax(scores);
int min = findMin(scores);
```

`scores` が主役として何度も登場している。
→ `scores` を **内側に持つクラス** にすれば、引数で引き回す必要が消える。

```java
Scores scores = new Scores(values);
double avg = scores.average();
int max = scores.max();
```

---

## 2. クラスを設計する手順（慣れたら：最初から分けて書く）

ステップ1〜3は「既存コードの改善」に効く（発見的アプローチ）。
慣れたら、書く前に設計する（設計的アプローチ）。

### 名詞 → ふるまい → コード

1. **問題文から名詞（登場人物・モノ）を拾う**
   「学生の点数の平均と最高点を出す」→ 名詞は「点数の集まり」
2. **その名詞に「何を聞けるか／何ができるか」を並べる**
   点数の集まり → 「平均は？」「最高点は？」「最低点は？」
3. **名詞をクラス名、ふるまいをメソッドにする**

```java
class Scores {
    private final int[] values;
    Scores(int[] values) { this.values = values; }

    double average() { /* ... */ }
    int max()        { /* ... */ }
}
```

データ（values）が中にいて、ふるまいがそれを使う。
→ 「同じデータを後から括る」のではなく、**最初からデータとふるまいが同居する**。

## 3. クラスは1種類じゃない：3つの型

「名詞で考えろ」は強力だが万能ではない。
四則演算のように、現実世界に対応する「モノ」がない処理もある。
クラスには大きく3つの型があると理解しておく。

| 型 | 状態（データ）を持つか | 例 | 出し方 |
|---|---|---|---|
| **モノ型** | 持つ | `Scores`, `Student`, `Order` | 名詞で出す |
| **道具箱型** | 持たない（純粋処理） | `Math`, 四則演算, フォーマット | 関連処理をまとめる |
| **段取り型** | 持たない（手続きの置き場） | `〜Service` | 流れを書く場所（※2か月目で詳しく） |

### 見分ける一本の基準

> **状態（データ）を持つか?**
> 持つ → モノ型。ふるまいはそのデータのクラスに置く。
> 持たない → 道具箱型 か 段取り型。

---

## 4. 「振る舞いだけのクラス」は悪なのか？

「振る舞いだけ = util化して良くない」という勘は **半分正しい**。
良い振る舞いだけクラスと、悪い振る舞いだけクラスがある。

### 良い：純粋関数（状態を持ちようがない）

同じ入力なら必ず同じ出力。保持すべき状態が存在しない。
→ 道具箱に置いて正解。罪悪感は不要。

```java
class Calculator {
    int add(int a, int b)      { return a + b; }
    int subtract(int a, int b) { return a - b; }
}
```

### 悪い：本来データと一緒にいるべき処理が引き剥がされた util

```java
// 悪い：点数の処理なのに、点数から引き剥がされている
class ScoreUtil {
    static double average(int[] scores) { /* ... */ }
    static int max(int[] scores)        { /* ... */ }
}
```

これは「データ」と「データを使う処理」が別々＝ドメインモデル貧血症。
本来 `Scores` が持つべきふるまいが、外の Util に漏れている。

### 見分けの問い：「引数を捨ててもいいか」

```java
format(123.456)    // 引数は通りすがり → 純粋関数、Utilで良い
average(scores)    // scores が主人公で何度も登場 → Scoresクラスにすべき
```

- 引数が **通りすがり** → 純粋関数。道具箱でOK。
- 引数が **主人公**（毎回同じ顔ぶれで引き回される）→ そのデータをクラスにする合図。

> **`Util.処理(データ)` の形を見たら、そのデータがクラスになりたがっていないか疑え。**

## 5. 命名の指針

命名は「設計が正しいか」を映す鏡。名前に困る＝役割が曖昧、というサイン。

### モノ型クラス：名詞にする

- 良い：`Scores`, `Student`, `Order`, `Money`
- そのクラスが「何であるか」を表す名詞。

### メソッド：そのモノが「答えられること・できること」

- 良い：`scores.average()`, `order.total()`, `student.isPassed()`
- そのデータ自身に問いかける形で読めるのが理想。

### 命名の歯止め（危険サイン）

| 危険な名前 | なぜ危ないか |
|---|---|
| `〜Manager` | 何でも入る。責務が曖昧な証拠 |
| `〜Processor` | 「処理する」だけで中身が不明 |
| `〜Data`, `〜Info` | データだけの器になりがち（貧血症の入口） |
| `〜Util` | 純粋処理ならOK。データを引き回しているなら危険 |
| 名前に **and** が入る | 2つの責務を持っている。分割対象 |

> `〜er` / `〜Manager` という名前になったら一度立ち止まる。
> ふるまいだけでデータがない（本来モノ型にすべき）可能性。

### メソッド名にも and を入れない

- 悪い：`calculateAndPrint()`（計算して、表示もする）
- 良い：`calculate()` と `print()` に分ける。

## 6. レガシー対比：手続き + データクラス vs オブジェクト指向

レガシーコードでよく見るのが、**データだけのクラス** と **処理だけのクラス** が
分離した形。一見クラスを使っているが、中身は手続き型。

### ❌ レガシー型：データクラス + 手続き

```java
// データだけの器（getter/setter の塊）
class ScoreData {
    private int[] values;
    public int[] getValues()           { return values; }
    public void  setValues(int[] v)    { this.values = v; }
}

// 処理だけのクラス（データを外から受け取る）
class ScoreLogic {
    public double average(ScoreData data) {
        int[] v = data.getValues();          // 外からデータを取り出す
        int sum = 0;
        for (int s : v) sum += s;
        return (double) sum / v.length;
    }
}

// 呼び出し側：データと処理を自分で組み合わせる
ScoreData data = new ScoreData();
data.setValues(new int[]{80, 95, 60});
double avg = new ScoreLogic().average(data);   // 手続き的
```

**何が問題か**

- データ（`ScoreData`）と処理（`ScoreLogic`）が引き剥がされている
- 呼び出し側がデータと処理を毎回くっつける手間を負う（認知負荷が上がる）
- 「点数に対する処理」がどこにあるか追いにくい（ロジックが散らばる）
- これが **ドメインモデル貧血症** の典型

### ⭕ オブジェクト指向型：データとふるまいが同居

```java
class Scores {
    private final int[] values;

    Scores(int[] values) {
        this.values = values;
    }

    double average() {
        int sum = 0;
        for (int s : values) sum += s;     // 自分のデータを自分で使う
        return (double) sum / values.length;
    }

    int max() {
        int max = values[0];
        for (int s : values) if (s > max) max = s;
        return max;
    }
}

// 呼び出し側：scores に「聞く」だけ
Scores scores = new Scores(new int[]{80, 95, 60});
double avg = scores.average();             // 宣言的
int    max = scores.max();
```

**何が良くなったか**

- データとふるまいが同じクラスにいる（引数で引き回さない）
- 呼び出し側は `scores.average()` と **聞くだけ**。中の手続きは隠蔽される
- 点数に関する処理は全部 `Scores` を見れば分かる（凝集度が高い）
- main / 呼び出し側が **宣言的** に読める＝認知負荷が下がる

### 対比のまとめ

| 観点 | レガシー（手続き+データ） | オブジェクト指向 |
|---|---|---|
| データと処理 | 別クラスに分離 | 同じクラスに同居 |
| 呼び出し側 | データと処理を自分で組み合わせる | オブジェクトに聞くだけ |
| 読み方 | 手続き的（どうやるかが見える） | 宣言的（何をするかだけ見える） |
| ロジックの所在 | 散らばる | 1か所に集まる |
| 典型的な名前 | `〜Data` + `〜Logic`/`〜Manager` | `Scores`（名詞） |

## 7. チェックリスト（自分の言葉で説明できるか）

クラスを書いたら、以下を自問する。理由を言えれば設計はおおむね正しい。

- [ ] コメントを書きたくなった処理を、メソッド名にできているか
- [ ] 同じデータを何度も引数で渡していないか（→ クラスにまとめる合図）
- [ ] そのクラスは状態を持つか？ 持つなら、ふるまいも中にあるか
- [ ] 状態を持たないなら、それは純粋関数か？（→ 道具箱でOK）
- [ ] `Util.処理(データ)` の形になっていないか（→ データがクラスになりたがっていないか）
- [ ] クラス名は名詞になっているか。`〜Manager` `〜Data` になっていないか
- [ ] メソッド名・クラス名に **and** が入っていないか
- [ ] main / 呼び出し側を読んで、処理の流れが分かるか（宣言的か）
