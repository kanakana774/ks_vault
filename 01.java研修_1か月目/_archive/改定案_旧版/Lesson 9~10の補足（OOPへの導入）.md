### 1. 導入：メソッドのもう一つのメリット

メソッドを使うことで「同じ処理を何度も再利用できる」というメリットを学びました。実はメソッドには、もう一つ非常に大きなメリットがあります。それは、「**プログラムを人間にとって読みやすくする**」という役割です。

「これまで皆さんは`main`の中に、上から下へ手順を1つずつ並べる形で書いてきました。これを『**手続き的な書き方**』と呼ぶことにします。今はまだ短いですが、これが1万行になったらどうなるでしょうか？

例えば、銀行でお金を引き出す処理を考えてみましょう。

```java
public static void main(String[] args) {
	
	・・・
	
    int balance = br.readLine();      // 残高
    int withdrawAmount = br.readLine(); // 引き出したい金額

    // 手続き的な書き方（手順が丸見え！）
    if (withdrawAmount > 0) {
        if (balance >= withdrawAmount) {
            balance = balance - withdrawAmount;
            System.out.println("成功！残高は" + balance);
        } else {
            System.out.println("残高不足です");
        }
    }
}
```

これが巨大なプログラムのあちこちにあると、読む人は『えーっと、今の残高はいくらだっけ？』と、常に**前の数字を記憶しながら**読み進めなければならず、頭がパンクしてしまいます。

そこで昨日の『メソッド』を使い、細かい手順（How）に名前をつけて隠してみます。

```java
// 何をするか（What）だけを書く。これを「宣言的な書き方」と呼ぶことにします。
balance = withdraw(balance, withdrawAmount); 
```

これなら『引き出し処理をしているんだな』と一目で分かりますよね。
でも、1つ問題が残っています。それは<font color="#ff0000">『残高（balance）』というデータが、誰でも触れる場所に置きっぱなしになっていること</font>です。

これでは、誰かがこっそり `balance = 0;` と書き換えても防げません。これを解決するのが、今日から学ぶ**オブジェクト指向**（もっといえばカプセル化）です。」

---

### 2. オブジェクトとは「データ」と「機能」のセット

「これまでは『データ（変数）』と『処理（手順）』をバラバラに扱ってきましたが、これからはセットにします。これを**オブジェクト**と呼びます。

*   **フィールド（状態）：** そのモノが『知っていること（データ）』
*   **メソッド（振る舞い）：** そのモノが『できること（機能）』

```java
public class BankAccount {
    // 【フィールド】自分の残高は、自分が一番よく知っている
    int balance = 1000;

    // 【メソッド】自分のデータを正しく書き換える「専門家」としての振る舞い
    public void withdraw(int amount) {
        if (amount > 0 && this.balance >= amount) {
            this.balance -= amount;
        }
    }
}
```
※ 銀行口座から見て、自身に、『引き出される』という受動的な機能があることは直感に反しますが、、、
『お金を引き出される』という受動的なことでも、『**自分のデータを守り、正しく書き換える責任は自分にある**』という考え方で整理するのがオブジェクト指向の考え方です。」

---

### 3. 自律性：詳細は隠して「丸投げ」する

「オブジェクト指向にすると、使う側（main）は劇的に楽になります。

```java
public static void main(String[] args) {
    BankAccount myAccount = new BankAccount();
    
    // オブジェクトに「丸投げ」するだけ！
    myAccount.withdraw(500); 
}
```

これは『上司と部下』の関係に似ています。
上司は部下に『金庫を開けて、お札を数えて、ハンコを押して…』なんて細かい手順（手続き）は指示しません。**『500円引き出しといて』と一言お願いする**（**宣言的な指示**）だけです。**あとの細かいやり方**（**手続き的な部分**）は、専門家である部下が自分で判断してやってくれます。

このように、『**中身の細かい手順は知らないけれど、頼めばやってくれる**』という状態にすることを、**ブラックボックス化**と言います。」

スマホを操作する際にスマホの仕組みを知らなくても（ブラックボックスでも）機能を使えますよね。

### 4. 責任の所在：入口を絞るから「安心して」読める（アクセス修飾子とsetter/getter）

「なぜわざわざこんな面倒なことをするのか。最大の理由は、**『そのデータが勝手に書き換わっていない』という安心感**を得るためです。

もし、データの守りがガバガバだったら、こんな事故が起きます。

```java
myAccount.balance = -999999; // 誰かがどこかで勝手に書き換えた！
```

これでは、プログラムのどこで数字がおかしくなったのか、原因を探すのが大変です。

```java
public class BankAccount {
    // 【フィールド】残高にカギをかけます
    private int balance = 1000;

    // 【メソッド】自分のデータを正しく書き換える「専門家」としての振る舞い
    public void withdraw(int amount) {
        if (amount > 0 && this.balance >= amount) {
            this.balance -= amount;
        }
    }
}
```

そこで、データには鍵をかけ（**private**）、**『withdraw（引き出し窓口）』という入口からしか操作できない**ように制限します。withdrawには不正なデータが入らないようにチェックが入っていますので、不正なデータは入りません。このように自分のデータや機能を自分で持つように実装することを**カプセル化**と言います。カプセル化することで、自分のことは自分で責任を持つ自立したクラスにすることができます。


**ここがポイントです：**
入口を数個に絞っておけば、コードを読むときに『**この窓口（メソッド）以外で、勝手に残高が変わっているはずがない**』と確信できます。これが、読みやすさに繋がります。

**setterとgetterについて：**
実は、ロジックを持たないsetterやgetterを持ついわゆるデータクラスは、全くオブジェクト指向的ではありません。
結局、そのクラスが持つべきロジックが呼び出し側に散らばって書かれてしまうからです。そうなると似たような判定ロジックなどが溢れ、呼ぶ側からも宣言的な内容となっておらず、また、修正も困難になります。
諸説ありますが、命令型言語からの乗り換えをしやすくするために、使われてたものが現代のプロジェクトでも残ってると聞きました。。。

### 5. クラス（設計図）とインスタンス（実体）

この『自律した専門家』をたくさん生み出すために、クラスとインスタンスを使います。

*   **クラス：** 『銀行口座とはこういうものだ』と決めた**設計図**。
*   **インスタンス：** 設計図から生まれた、メモリ上の**本物の口座**。

```java
BankAccount tanakaAccount = new BankAccount(); // 田中さんの口座
BankAccount satoAccount = new BankAccount();   // 佐藤さんの口座

tanakaAccount.withdraw(500); // 田中さんの残高は減るが、佐藤さんには絶対に影響なし！
```

同じ設計図から生まれても、本物はそれぞれ別々のデータで持っています。一箇所を直しても他に影響しないことが保障されているから、大きなプログラムも怖がらずに作れるようになります。

### 6. まとめ：`main`は「作業員」から「監督」へ

「これからの皆さんの仕事は、1つの場所にすべての手順を書き込むことではありません。

1.  **役割分担：** 適切なクラスにデータと仕事を任せる。
2.  **指示を出す：** `main`の中で、専門家（オブジェクト）を呼び出し、命令を出す。

これまでは『全部自分でやる忙しい作業員』でしたが、これからは『**自律した専門家たちに指示を出す監督**』になってください。

1か月目の今は、『**現実世界のモノをクラスにする**』という感覚で慣れていきましょう。
2か月目になると、さらに『この仕事はどの担当者に任せるのが正解か？』という**専門家の役割分担**を深く考えるようになります。**モノではなく、役割でクラスを分けるようになります。**

また、プログラミング言語の進化の歴史は、人間がコードを読みやすく、管理しやすくなることを目的に進化していった歴史になります。反対に機能としては狭まっているのも面白いところです。
ただ文法として丸暗記するのも大事ですが、その機能が導入された目的を知ることで、よりその道具を適切に扱えるようになるので、そういった視点をもって勉強していってもらえればと思います。
