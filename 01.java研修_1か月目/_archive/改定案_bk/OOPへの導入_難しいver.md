### 1. 導入：なぜ「書き方」を変えるのか？（Lesson8の翌日）

昨日は「メソッド」を学びました。メソッドには同じ処理を**何度も再利用**できるという利点がありますが、実はそれ以上に大切な**「人間に優しくなる」**というメリットがあります。

「これまで皆さんは`main`メソッドの中に、上から下へ全ての処理を書いてきました。今はまだ短いですが、これが銀行のシステムのように巨大になったらどうなるでしょうか？

例えば、お金を引き出す処理を**手続き的**（手順をそのまま一歩ずつ並べる形）に書くとこうなります。

```java
public static void main(String[] args) {
    // Aさんの残高と、引き出したい金額を準備
    int balance = 1000;
    int withdrawAmount = 500;

    // 手続き的な書き方（前の値を記憶し続ける必要があり、脳が疲れる！）
    if (withdrawAmount > 0) {
        if (balance >= withdrawAmount) {
            balance = balance - withdrawAmount;
            System.out.println("引き出し成功。残高：" + balance);
        } else {
            System.out.println("残高不足です。");
        }
    }
```

これがコードのあちこちに何万行も書かれていると、読み手は常に『今の残高の最新値は何だっけ？』と前の状況をずっと記憶しながら読み進めなければならず、人間の脳はすぐに**パンク**してしまいます。これを解決するのが『メソッド』による**宣言的な書き方**です。

```java
// 手続き的な詳細を隠し、名前だけで「何をするか」を表す
balance = withdraw(balance, withdrawAmount);
```

中身の手順（How）をメソッドの中に隠して、名前（What）だけで呼び出す。これが**宣言的な書き方**です。これなら『あ、ここでは引き出しているんだな』と直感的に分かりますよね。

しかし、メソッドだけでは解決できない問題があります。それは『**変数（balance）』がまだメソッドの外側（main側）にあり、誰でも自由に触れてしまう**という点です。これを整理し、データの安全を守る究極の形が、今日から学ぶ**オブジェクト指向（OOP）**です。」

### 2. オブジェクトとは「データ」と「専門家」のセット（Lesson9～10の翌日）

「OOPでは、バラバラだった『データ』と『それを扱うメソッド』をセットにしてパッケージングします。

*   **フィールド（状態）：** そのオブジェクトが『知っていること』
*   **メソッド（振る舞い）：** そのオブジェクトが『できること』

```java
public class BankAccount {
    // フィールド：自分の状態（残高）を一番よく知っている
    int balance = 1000;

    // メソッド：このデータに責任を持つ専門家としての振る舞い
    public void withdraw(int amount) {
        if (amount > 0 && this.balance >= amount) {
            this.balance -= amount;
            System.out.println(amount + "円引き出しました。");
        } else {
            System.out.println("引き出せません。");
        }
    }
}
```
※ 現実世界では、銀行口座からすれば『引き出される』という機能は受動的な出来事で、直感的ではないですが、プログラムでは**『自分のデータ（残高）を変更するルールを自分の中に持つ』**という考え方をします。機能が能動か受動かではなく、**『そのデータに責任を持っているのは誰か』**という視点で整理します。」

### 3. 自律性：詳細は隠して「丸投げ」する

「OOPの最大の利点は、各オブジェクトが『**自律**』し、中身が『**ブラックボックス**』になることです。

```java
public static void main(String[] args) {
    // オブジェクト指向の書き方（宣言的な呼び出し）
    BankAccount myAccount = new BankAccount();
    myAccount.withdraw(500); // 500円引き出して！と命令（宣言）するだけ
```

これは上司と部下の関係に似ています。
優秀な上司は、部下に『金庫の鍵を開けて、札束を数えて、帳簿の3行目に書き込んで…』といった細かい手順（手続き的）な指示は出しません。『この500円を引き出し処理しておいて』とフワッと目的（宣言的）だけを伝えますよね。あとの細かい手順は、専門知識を持った部下が自律的に判断します。

**この『丸投げ（ブラックボックス化）』のメリット：**
1.  **中身を知らなくていい：** `main`を書く人は、口座の中の複雑な計算ルールを知らなくても、安心して使えます。
2.  **修正に強い：** もし手数料の計算ルールが変わっても、直すのは`BankAccount`の中だけ。`main`（上司）の指示の出し方を変える必要はありません。」

### 4. 責任の所在：自分の領土（データ）は自分で守る（Lesson11~13の翌日）

「なぜ『引き出し』窓口を口座自身に作らせるのか。それは、『**自分のデータを他人に直接触らせない**』というプログラミング世界の鉄則があるからです。

もしフィールドが丸見えだったら、誰かがミスをしてデータを壊すかもしれません。

```java
myAccount.balance = -999999; // 他人が勝に残高を書き換える「不正アクセス」
```

これは、他人がいきなりあなたの財布を開けて、中身を書き換えるようなものです。困りますよね。だから、フィールドには鍵（**アクセス修飾子：private**）をかけ、中身を見えないように**隠蔽**（いんぺい）します。

```java
public class BankAccount {
    // privateにして外部から操作できないように鍵をかけます。
    private int balance;
    
    public BankAccount(int balance) {
        this.balance = balance;
    }

    // 窓口（メソッド）からしかデータをいじることができない
    public void withdraw(int amount) {
        // ここに「残高不足なら引かせない」という防衛ルールを書く
        if (amount > 0 && this.balance >= amount) {
            this.balance -= amount;
        }
    }
}
```
『たとえ他人に攻撃されても、自分のデータを正しく守り、変更する責任は自分にある』。これがカプセル化の本質です。」

### 5. クラス（設計図）とインスタンス（実体）

「この自律的なパーツを量産するために『設計図』と『実物』を分けます。

*   **クラス：** 『銀行口座とは残高を持っていて、引き出しができるものだ』というルールを決めた設計図。
*   **インスタンス：** 設計図から生まれたメモリ上の本物の口座。

```java
BankAccount tanakaAccount = new BankAccount(1000); // 田中さんの口座
BankAccount satoAccount = new BankAccount(2000);   // 佐藤さんの口座

tanakaAccount.withdraw(500); // 田中さんの残高だけが減り、佐藤さんは影響なし
```

同じ設計図から生まれても、メモリの中では**別々の領土**（データ領域）を持って存在します。それぞれのインスタンスが自分の状態を自律的に管理しているのです。」

### 6. まとめ：`main`は「作業員」から「監督」へ

「これからの皆さんの仕事は、1箇所ですべての計算（手続き）を延々と書くことではありません。

1.  **責任の分離：** 適切なクラスにデータと専門知識を持たせ、仕事を任せる。
2.  **物語を作る：** `main`メソッドの中で、それらのオブジェクトを呼び出し、命令を出して、全体のストーリーを組み立てる。

```java
public static void main(String[] args) {
    BankAccount myAccount = new BankAccount(1000); // 俳優を舞台に呼ぶ
    Atm atm = new Atm();
    
    atm.insertCard(myAccount); // 監督として指示を出す
    atm.requestWithdraw(500);  // ATMが口座に引き出しを依頼する
}
```

これまでの`main`は『何でも自分でやる忙しい作業員』でしたが、これからは『**自律した専門家たちに指示を出す映画監督**』です。

プログラミング言語が進化してきた理由は、常に『**人間が楽に、ミスなく巨大なシステムを管理するため**』です。

1か月目の今は、『現実世界のモノをクラスにする』というシミュレーションの感覚で慣れていきましょう。2か月目には、さらに『業務上の役割（ドメイン）』という視点でクラスを分ける方法を学び、より高度な**責任の分離**に挑戦していきます。
