### 1. 導入：なぜ「書き方」を変えるのか？（Lesson8の翌日）

メソッドには同じ処理を**何度も再利用**できるようなるという大きなメリットがありました。しかし、それ以外にもメソッドに処理を切り出すメリットがあり、以下はそのことについて説明していきます。

「これまで皆さんは`main`メソッドの中に全ての処理を書いてきました。今はまだ短いですが、これが銀行のシステムのように巨大になったらどうなるでしょうか？

例えば、お金を引き出す処理を**手続き的**（手順をそのまま並べる形）に書くとこうなります。

```java
public static void main(String[] args) {
	// 下記を例えばコマンドで入力できるとする
    int balance = 1000;      // Aさんの残高
    int withdrawAmount = 500; // 引き出したい金額

    // 手続き的な書き方（認知負荷が高い！）
    if (withdrawAmount > 0) {
        if (balance >= withdrawAmount) {
	            balance = balance - withdrawAmount;
            System.out.println("引き出し成功。残高：" + balance);
        } else {
            System.out.println("残高不足です。");
        }
    }
    
    // これがコードのあちこちに何万行も書かれていると、
    // 『今、残高はどうなっていたっけ？』と常に前の状況を記憶しながら
    // 読み進めなければならず、人間の脳はすぐにパンクしてしまいます。
```

皆さんはこれを解決するために『メソッド』を学びました。

```java
public static void main(String[] args) {
    int balance = 1000;      // Aさんの残高（例えばコマンドで入力できるとする）
    int withdrawAmount = 500; // 引き出したい金額（例えばコマンドで入力できるとする）
    
	// 手続き的な流れを名前で切り出す（宣言的な書き方）
	balance = withdraw(balance, withdrawAmount);
```

```java
// 手続き的な詳細は隠す
int withdraw(int balance, int withdrawAmount) {
    if (withdrawAmount > 0) {
        if (balance >= withdrawAmount) {
	            balance = balance - withdrawAmount;
            System.out.println("引き出し成功。残高：" + balance);
        } else {
            System.out.println("残高不足です。");
        }
    }
}
```

中身の手順（How）をメソッドの中に隠して、名前（What）だけで呼ぶ。これを**宣言的な書き方**と表現することにします。これなら少し読みやすくなりますね。
しかし、メソッドだけでは解決できない問題があります。それは『**変数（balance）』がまだメソッドの外側にあり、誰でも自由に触れる状態にある**という点です。これを整理し、データの安全を守る方法が**オブジェクト指向（OOP）のカプセル化**です。」

### 2. オブジェクトとは「データ」と「専門家」のセット（Lesson9～10の翌日）

「OOPでは、バラバラだった『データ』と『それを扱うメソッド』をセットにしてパッケージングします。

*   **フィールド（状態）：** そのオブジェクトが『知っていること』
*   **メソッド（振る舞い）：** そのオブジェクトが『できること』

```java
public class BankAccount {
    // フィールド：自分の状態（残高）を一番よく知っている
    int balance = 1000;

    // メソッド：このデータに責任を持つ専門家としての振る舞い
    public void withdraw(int amount) {
        if (amount > 0 && this.balance >= amount) {
            this.balance -= amount;
            System.out.println(amount + "円引き出しました。");
        } else {
            System.out.println("引き出せません。");
        }
    }
}
```
※ ここで『引き出し』が口座側の機能であることに違和感があるかもしれません。しかし、オブジェクト指向の目的は『**自分のデータ（残高）を変更するルールを自分の中に持つ**』ことです。機能が受動的（引き出される）か能動的（引き出す）かは一度置いておき、『そのデータを誰が管理すべきか』という**責任の所在**で考えます。」

### 3. 自律性：詳細は隠して「丸投げ」する

「OOPの最大の利点は、各オブジェクトが『**自律**』し、中身が『**ブラックボックス**』になることです。利用する側の`main`を見てください。

```java
public static void main(String[] args) {

	// オブジェクト指向の書き方（宣言的な呼び出し）
	BankAccount myAccount = new BankAccount();
	myAccount.withdraw(500); // 500円引き出して！と依頼するだけ
	
```

これは上司と部下の関係に似ています。
上司は、部下に『金庫の鍵を開けて、札束を数えて、記帳して…』という手続き的な指示は出しません。『500円引き出しといて』と丸投げしますよね。後の細かい手順（How）は部下が自律的に判断します。つまり、上司は部下というクラスに処理の詳細（手続き的）を任せ、上司はフワッと何をして欲しいか命令（宣言的）すればいいわけです。上司は部下が具体的にどんな手順で作業したかを見えないようにします。

**この『丸投げ（ブラックボックス化）』には大きな利点があります。**
1.  **分業ができる：** 『BankAccountクラスを作る人』と『それを使うmainを書く人』に分かれて開発できます。
2.  **修正に強い：** もし『引き出し手数料を110円取る』というルールに変更されても、直すのは`BankAccount`クラスの中だけ。`main`側は呼び出し方を変えずに済みます。
3.  **複数人での開発が楽になる：** 他人が作ったクラスでも、中身を知らずに『名前（メソッド名）』だけで安心して使えます。」

### 4. 責任の所在：自分の領土（データ）は自分で守る（Lesson11~13の翌日）

「なぜ『引き出し』窓口を口座自身に作らせるのか。それは、『**自分のデータを他人に直接触らせない**』という鉄則があるからです。

もしフィールドが丸見えだったら、誰かが悪意を持って（あるいはミスで）データを壊すかもしれません。

```java
myAccount.balance = -999999; // 他人が勝に残高を書き換える「不正アクセス」
```

これは、他人がいきなりあなたの財布を開けて、中身を書き換えるようなものです。だから、フィールドには鍵（アクセス修飾子）をかけ（隠蔽）、`withdraw`という**正規の窓口**を通してもらうのです。
『たとえ自分の身に起きる出来事でも、自分のデータに責任を持ち、正しく書き換えるのは自分自身である』。これがカプセル化の本質です。」

```java
public class BankAccount {
    // privateにして外部から操作できないようにします。
    private int balance
    
    // ついでにコンストラクタで初期残高を設定できるようにします。
    pubulic BankAccount(int balance) {
	    this.balance = balance;
    }

    // 預金引き出し処理など、用意してある処理（窓口）からしか残高を弄ることができない。
    public void withdraw(int amount) {
        if (amount > 0 && this.balance >= amount) {
            this.balance -= amount;
            System.out.println(amount + "円引き出しました。");
        } else {
            System.out.println("引き出せません。");
        }
    }
}
```

### 5. クラス（設計図）とインスタンス（実体）

「この自律的なパーツを量産するために『設計図』と『実物』を分けます。

*   **クラス：** 『銀行口座とは残高を持っていて、引き出しができるものだ』というルールを決めた設計図。
*   **インスタンス：** 設計図から生まれたメモリ上の本物の口座。

```java
BankAccount tanakaAccount = new BankAccount(); // 田中さんの口座
BankAccount satoAccount = new BankAccount();   // 佐藤さんの口座

tanakaAccount.withdraw(500); // 田中さんの残高だけが減り、佐藤さんは影響なし
```

同じ設計図から生まれても、メモリの中では**別々の領土**（データ領域）を持って存在します。それぞれのインスタンスが自分の状態を自律的に管理しているのです。」

### 6. まとめ：`main`は「作業員」から「監督」へ

「これからの皆さんの仕事は、1箇所ですべての計算を行うことではありません。

1.  **責任の分離：** 適切なクラスにデータと専門知識を持たせ、仕事を任せる。
2.  **物語を作る：** `main`メソッドの中で、それらのオブジェクトを呼び出し、命令を出して、全体のストーリーを組み立てる。

```java
public static void main(String[] args) {
    // 1. 俳優（オブジェクト）を舞台に呼ぶ
    BankAccount myAccount = new BankAccount();
    Atm atm = new Atm();
    
    // 2. 監督として指示を出す（中身の手順は俳優にお任せ）
    atm.insertCard(myAccount); // キャッシュカードを入れる
    atm.requestWithdraw(500); // ATMが口座に引き出しを依頼する
}
```

これまでの`main`は『何でも自分でやる忙しい作業員』でしたが、これからは『**自律した専門家たちに指示を出す映画監督**』です。

このように、プログラミング言語の発展は、人間に読みやすいものへと進化していく過程で発明されたものになります。コンピュータは人間と違いどんなに長くなっても処理を理解することができますが、人間は多くのことを管理するのが苦手です。そのため、なぜその書き方や機能があるのかという導入の意図を知っておくことで、適切に利用できるようになります。

また、1か月目の段階では、現実世界のオブジェクト（物）をクラスで表現するという認識で構いません。しかし2か月目でアプリケーションを作る段階では、さらにそれを業務における役割という観点でクラスを分割することになりますが、それはその際に説明します。
