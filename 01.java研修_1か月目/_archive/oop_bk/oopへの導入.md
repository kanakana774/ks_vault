### 1. 導入：なぜ「書き方」を変えるのか？

「これまで皆さんは、`main`メソッドの中に全ての処理を書いてきました。今はまだ数十行ですが、これが10万行になったらどうなるでしょうか？

たとえば、RPGの戦闘シーンを作る際、手続き的に書くとこうなります。
```java
// 手続き型の書き方
int warriorHp = 100;
int warriorDef = 5;
int monsterAtk = 20;

// ダメージ計算（認知負荷が高い！）
int damage = monsterAtk - warriorDef;
if (damage < 0) {
	damage = 0;
}
warriorHp = warriorHp - damage;
if (warriorHp < 0) {
	warriorHp = 0;
}
// これを10万行のコードの至る所で「前の値を記憶しながら」追うのは限界がある
```

このように、『どう計算するか（How）』という細かな手順を延々と書き連ねるのを**手続き的**と表現することにします。しかし、コードが増えると、以前の変数の状態を全て記憶しながら読み進める必要があり、人間の脳はすぐに**パンク**してしまいます。

そこで登場するのが**オブジェクト指向**（**OOP**）です。これは複雑な**手続き的な手順**を『塊』の中に隠し、人間が理解しやすい**宣言的な言葉**でプログラミングするための整理術です。」

### 2. オブジェクトとは「データ」と「専門家」のセット

「では、どう整理するのか。これからはデータ（変数）と、それを扱う専門知識（メソッド）を一つにまとめます。

*   **フィールド（状態）：** オブジェクトが『知っていること』
*   **メソッド（振る舞い）：** オブジェクトが『できること』

```java
public class Warrior {
    // フィールド：状態
    int hp = 100;
    int def = 5;

    // メソッド：機能（このデータに責任を持つ専門家）
    public void receiveDamage(int monsterAtk) {
        int damage = monsterAtk - this.def;
        if (damage < 0) {
	        damage = 0;
	    }
        this.hp -= damage;
        if (this.hp < 0) {
	        this.hp = 0;
	    }
    }
    
    // 他にも攻撃するとか、防御するとか
}
```
※ ここで『ダメージを受ける』という機能がWarriorにあることに違和感を覚えるかもしれません。しかし、カプセル化の目的は**『自分のデータ（HP）を変更する権利を自分が持つ』**ことです。機能の能動・受動ではなく、『そのデータを誰が管理すべきか』で考えます。」

### 3. 自律性：詳細は隠して「丸投げ」する

「OOPの最大の利点は、各オブジェクトが『**自律**』し、中身が『**ブラックボックス**』になることです。

利用する側の`main`メソッドを見てください。

```java
// オブジェクト指向の書き方（宣言的）
Warrior warrior = new Warrior();
warrior.receiveDamage(20); // 10ダメージ受けて！と命令するだけ
```

*   **手続き的（前）：** HPを引いて、マイナスをチェックして…という『手順』を全部書く。
*   **宣言的（後）：** 『ダメージを受けて！』という『意図』だけを書く。

『どう計算するか（How）』という複雑な手続きはオブジェクトの中に隠されています。`main`側は中身を知らなくても、名前を見ただけで機能が使える。これが『**丸投げできる自律性**』です。

もし後で『防御力の計算式を変えたい』となっても、直すのは`Warrior`クラスの中の1箇所だけ。`main`メソッドを書き直す必要はありません。」

こうすることで、中身をブラックボックスにして、フワッとした命令を飛ばせます。例えるなら、上司が部下一人一人に仕事の手順を操り人形のように一人ずつ操りませんよね。これやっといて、裏側にはいろいろな手続きが発生するはずです。

### 4. 責任の所在：自分の領土は自分で守る

「なぜ受動的な『ダメージを受ける』ことまで自分でするのか。

それは、**『自分のデータ（領土）を他人に直接触らせない』**という鉄則があるからです。

```java
// もし他人が直接触れたら…
warrior.hp = -999; // 敵が勝手にありえない数値を代入できてしまう（データの破壊）
```

外から勝手にHPを書き換えられるのは、他人に自分の心臓を直接握らせるようなものです。だから、`hp`というフィールドには鍵をかけ、`receiveDamage`という**正規の窓口**を通してもらうのです。
『たとえ攻撃されるという嫌な出来事でも、自分のHPを正しく減らす責任は自分にある』。これがカプセル化の本質的な考え方です。」

### 5. クラス（設計図）とインスタンス（実体）

「この自律的なパーツを作るために『設計図』と『実物』を分けます。

*   **クラス：** 『Warriorとはこういうものだ』と定義した設計図。
*   **インスタンス：** 設計図から生まれた本物の実体。

```java
Warrior warrior1 = new Warrior(); // 勇者誕生（HP100）
Warrior warrior2 = new Warrior(); // 魔法使い誕生（HP50に変更可能）

warrior1.receiveDamage(20); // warrior1のHPだけが減り、warrior2は無傷
```

同じ設計図から生まれても、メモリの中では**別々の個体**として存在します。それぞれのインスタンスが自分の状態（HP）を自律的に管理しているのです。」

### 6. まとめ：`main`は「作業員」から「監督」へ

「これからの皆さんの仕事は、1箇所ですべての計算を行うことではありません。

1.  **責任の分離：** 適切なクラスにデータを分け、専門的な仕事を任せる。
2.  **物語を作る：** `main`メソッドの中で、それらを呼び出し、全体のストーリーを組み立てる。

```java
public static void main(String[] args) {
    // 1. 俳優（オブジェクト）を舞台に呼ぶ
    Warrior warrior = new Warrior();
    Monster monster = new Monster();
    
    // 2. 監督として指示を出す（中身の手順は俳優にお任せ）
    warrior.attack(monster);
    monster.receiveDamage(warrior.atk);
}
```

これまでの`main`は『何でも自分でやる作業員』でしたが、これからは**『自律した専門家たちに指示を出す映画監督』**です。

『一箇所を直しても他に影響しない』『パズルを組み合わせるように開発できる』。そんな、人間に優しいプログラミングの世界へ進んでいきましょう。」
