Javaの `ArrayList` では `add()` や `remove()` で元のリストを書き換えるのが一般的ですが、Reactの状態管理（State）では、**元の配列を一度も書き換えない「非破壊的（イミュータブル）な操作」**が絶対ルールです。

---

# 補足：配列の非破壊・破壊操作
**〜ReactのState管理で求められる「不変性」の極意〜**

## 1. 破壊的メソッド vs 非破壊的メソッド [JS]

JSの配列メソッドには、元の配列（メモリ上の実体）を直接書き換えるものと、新しい配列を生成して返すものがあります。

### 比較表：よく使うメソッド一覧
| 操作 | **破壊的 (Mutating)** <br>※ReactでNG | **非破壊的 (Non-mutating)** <br>✅ Reactで推奨 |
| :--- | :--- | :--- |
| **追加** | `push()`, `unshift()` | スプレッド構文 `[...]`, `concat()` |
| **削除** | `pop()`, `shift()`, `splice()` | `filter()`, `slice()` |
| **置換** | `arr[i] = value` | `map()` |
| **並び替え** | `sort()`, `reverse()` | `toSorted()`, `toReversed()`, `[...arr].sort()` |

---

## 2. 実践：非破壊操作のパターン集 [JS/TS]

ReactのState更新を想定した、よくある4つの操作パターンのサンプルコードです。

### ① 要素の追加
```typescript
const tags = ["React", "TS"];

// ❌ 破壊的：tags自体が変わってしまう
// tags.push("Java"); 

// ✅ 非破壊的：新しい配列を作る
const newTags = [...tags, "Java"]; 
// ["React", "TS", "Java"]
```

### ② 要素の削除
```typescript
const users = [
  { id: 1, name: "Alice" },
  { id: 2, name: "Bob" },
  { id: 3, name: "Charlie" },
];

// IDが2のユーザーを削除したい
// ✅ 非破壊的：filter を使う（条件に合うものだけを残す）
const filteredUsers = users.filter(user => user.id !== 2);
```

### ③ 要素の更新（置換）
```typescript
const items = ["Apple", "Banana", "Orange"];

// "Banana" を "Grape" に変えたい
// ✅ 非破壊的：map を使う（特定の要素だけ変換し、他はそのまま）
const updatedItems = items.map(item => 
  item === "Banana" ? "Grape" : item
);
```

### ④ 並び替え（ソート）
**注意：** `sort()` はJSの中で数少ない「破壊的」な便利メソッドなので、最もミスが起きやすいです。

```typescript
const nums = [3, 1, 4];

// ❌ 破壊的：nums自体が [1, 3, 4] に書き換わってしまう
// nums.sort(); 

// ✅ 非破壊的（従来）：コピーしてからソートする
const sortedNums = [...nums].sort((a, b) => a - b);

// ✅ 非破壊的（最新 ES2023）: toSorted を使う [JS]
const modernSorted = nums.toSorted(); 
```

## 3. なぜ「非破壊」でないといけないのか？

Reactは **「前の状態と今の状態が、メモリ上の別オブジェクトかどうか（参照が違うか）」** で再描画を判定します。

```typescript
const [list, setList] = useState(["A", "B"]);

const addBad = () => {
  list.push("C"); // 配列の中身は増えるが、listの参照先（メモリ住所）は変わらない
  setList(list);  // Reactは「住所が変わっていないから更新なし」と判断して画面が変わらない
};

const addGood = () => {
  setList([...list, "C"]); // 新しい住所の配列を渡すので、Reactが更新を検知して画面が変わる
};
```

## 4. 応用：多次元配列やオブジェクト配列の注意点 [JS]

スプレッド構文 (`[...]`) は **「浅いコピー (Shallow Copy)」** であることに注意してください。

```typescript
const users = [{ id: 1, name: "Alice" }];
const usersCopy = [...users];

// 配列自体の参照は別だが、中に入っている「オブジェクト」の参照は同じ！
usersCopy[0].name = "Bob"; 

console.log(users[0].name); // "Bob" になってしまう（元の配列も汚染）
```

**✅ 解決策：ネストした更新も非破壊で行う**
```typescript
const updatedUsers = users.map(user => 
  user.id === 1 ? { ...user, name: "Bob" } : user
);
```

## 5. ベストプラクティスとアンチパターン

### ✅ ベストプラクティス
1.  **`map`, `filter`, `reduce` を使い倒す**: これらは常に新しい配列を返すため、安全です。
2.  **ES2023の新しいメソッドを使う**: `toSorted()`, `toReversed()`, `toSpliced()`, `with()` は非破壊メソッドとして新設されました。これらを使うと意図が明確になります。
3.  **読み取り専用にする [TS]**: `readonly string[]` と型定義することで、破壊的メソッドを呼んだ瞬間にコンパイルエラーにできます。

### ❌ アンチパターン
1.  **`sort()` を直接呼ぶ**: これが原因のバグは非常に多いです。常に `[...arr].sort()` とする癖をつけましょう。
2.  **`for` ループで `push` する**: 手続き的（命令型）なコードになりやすく、ミスが入り込む隙が増えます。可能な限り `map` などの宣言的なメソッドを使いましょう。

---

### まとめ：

Javaの `Stream API` を使ったことがあるなら、**「常に `Stream` の中だけで処理を完結させ、最後に `toList()` で新しいリストを作る」**感覚が、JS/TSの配列操作に非常に近いです。

- Java: `list.stream().filter(...).collect(Collectors.toList())`
- TS: `list.filter(...)` （これだけで新しい配列が返る）
