Javaエンジニアにとって最も親しみやすいはずの「クラスと継承」ですが、**現代のTypeScript（特にReact開発）においては、その立ち位置がJavaとは大きく異なります。**

結論から言うと、**「UI（Reactコンポーネント）にはクラスを使わず、ロジックやデータモデルの定義に限定して使う」**のが現在のスタンダードです。

# 補足：クラスと継承
**〜Javaとの違いと、フロントエンドにおける現在の立ち位置〜**

## 1. 基本構文とTypeScript独自の拡張 [JS/TS]

JSのクラスはES6（2015年）で導入された「プロトタイプベースの継承」の糖衣構文（シンタックスシュガー）です。TSではそこにJavaに近いアクセス修飾子が追加されています。

### サンプルコード
```typescript
class Animal {
  // 1. プロパティの宣言 [TS] (JSにはアクセス修飾子がない)
  protected name: string;
  private id: number;

  constructor(name: string) {
    this.name = name;
    this.id = Math.random();
  }

  // 2. メソッド [JS]
  public move(distance: number = 0): void {
    console.log(`${this.name} moved ${distance}m.`);
  }
}

// 3. 継承 (Inheritance) [JS]
class Dog extends Animal {
  bark(): void {
    console.log("Woof! Woof!");
  }

  // オーバーライド
  move(distance: number = 5): void {
    console.log("Running...");
    super.move(distance); // 親クラスのメソッド呼び出し
  }
}

const myDog = new Dog("Pochi");
myDog.bark();
myDog.move();
```

## 2. Javaエンジニアが感動する「コンストラクタの省略記法」 [TS]

Javaではフィールド宣言とコンストラクタでの代入を別々に書きますが、TSには強力な短縮記法があります。

### 比較
```typescript
// ❌ 冗長な書き方
class User {
  private name: string;
  constructor(name: string) {
    this.name = name;
  }
}

// ✅ 推奨：引数プロパティ (Parameter Properties) [TS]
class UserShort {
  // コンストラクタの引数にアクセス修飾子をつけるだけで、
  // フィールド宣言と代入を自動でやってくれる
  constructor(private name: string, public readonly age: number) {}
}

const user = new UserShort("Tanaka", 25);
console.log(user.age); // 25
```

## 3. インターフェースの実現 (implements) [TS]

Javaと同様に、クラスに特定の構造を強制できます。

```typescript
interface Disposable {
  dispose(): void;
}

class Logger implements Disposable {
  dispose() {
    console.log("Resource released.");
  }
}
```

## 4. 現代のTypeScriptにおけるクラスの立ち位置

ここが最も重要なポイントです。

### ① React開発での立ち位置：**「ほぼ使わない」**
*   **Reactコンポーネント**: 以前はクラスで書いていましたが（Class Component）、現在は **関数（Function Component）** で書くのが100%正義とされています。
*   **理由**: クラスの `this` の挙動が複雑であること、コードが長くなること、Hooks（`useState`など）の方が再利用性が高いためです。

### ② 使い所：**「ドメインモデル」や「サービス層」**
UI以外の場所では依然として有用です。
*   **データモデル**: 複雑な計算ロジックを持つエンティティ（例: `Invoice` クラスに合計金額計算メソッドを持たせる）。
*   **独自のErrorクラス**: `Error` を継承して `ApiError` などを作る。
*   **サーバーサイド（NestJSなど）**: JavaのSpringに近いアーキテクチャを採用しているフレームワークでは、クラスと依存性注入（DI）が主役です。

## 5. 比較：クラス vs オブジェクトリテラル vs 関数

同じデータ構造を作る際、どれを選ぶべきかの基準です。

| 手法 | 適した場面 | 特徴 |
| :--- | :--- | :--- |
| **クラス** | 複雑な内部状態とロジックをカプセル化したい時 | `new` が必要。`this` を使う。継承ができる。 |
| **オブジェクトリテラル** | 単にデータを持ち運びたいだけの時（DTO） | `{ name: "..." }`。最も軽量。ReactのPropsはこれ。 |
| **関数（Factory関数）** | 単純な処理の結果を返したい時 | `createUserInfo(name)` のように呼び出す。 |

## 6. ベストプラクティスとアンチパターン

### ✅ ベストプラクティス
1.  **継承よりも合成 (Composition over Inheritance)**:
    Javaと同様、深い継承ツリーはJS/TSでも嫌われます。機能を共有したい場合は、共通機能を関数として切り出すか、オブジェクトをプロパティとして持つ（委譲）ようにしましょう。
2.  **`readonly` を活用する**:
    クラスのプロパティを不変にしたい場合は `readonly` をつけます。

### ❌ アンチパターン
1.  **ReactのStateにインスタンスを入れる**:
    ```typescript
    const [user, setUser] = useState(new User("Tanaka"));
    ```
    これは非推奨です。クラスインスタンスは内部でプロパティを書き換える（Mutateする）ことが多いため、Reactが変更を検知できず、再描画されないバグを招きます。**ReactのStateはプレーンなオブジェクト（`{...}`）で管理しましょう。**
2.  **何でもクラスにする**:
    Javaの癖で、ユーティリティ関数を `class StringUtils { static format() { ... } }` のようにまとめがちですが、TSでは **「単なる関数を `export` する」** のが一般的です。

---

### まとめ：

「クラスは道具の一つであり、プログラム全体の骨格ではない」と考えるのがJS/TS流です。

*   **データ構造（型）の定義**には `type` や `interface` を使う。
*   **処理（関数）**はそのまま `export` する。
*   **それらを組み合わせて状態を持たせる**必要がある時だけ `class` を使う。

この使い分けができるようになると、非常に「TSらしい」綺麗なコードが書けるようになります。
