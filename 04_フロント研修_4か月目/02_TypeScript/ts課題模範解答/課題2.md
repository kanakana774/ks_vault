今回の課題は「データのバリデーション（検証）」「例外処理」「不変性（イミュータビリティ）」といった、実務で非常に重要になる要素が含まれています。

コードを書く前に、この課題に関連する**ベストプラクティス**と**アンチパターン**を整理しましょう。

---

### 1. 型定義とデータの扱い

#### ベストプラクティス
*   **インターフェース vs 型エイリアス**: オブジェクトの形を定義する場合、拡張性が必要なら `interface`、単純な定義なら `type` を使います。最近のプロジェクトでは `type` で統一することも多いですが、一貫性が大事です。
*   **不変性（Immutability）**: 元の配列（テストデータ）を直接書き換えるのではなく、新しい配列を生成して返す設計にすると、予期せぬバグを防げます（Reactなどでは必須の考え方です）。

#### アンチパターン
*   **マジックナンバーの放置**: スコアの範囲 `0` や `100` を直接関数内に書くのではなく、定数（`MIN_SCORE = 0` など）にすると保守性が高まります。
*   **`any` の多用**: どのような場面でも `any` は避けます。

---

### 2. 例外処理（Custom Errors）

#### ベストプラクティス
*   **Errorクラスの継承**: `class InvalidScoreError extends Error { ... }` のように標準の `Error` クラスを継承します。これにより、`instanceof` を使ってエラーの種類を判別できるようになります。
*   **意味のあるメッセージ**: 単に「エラー」とするのではなく、「なぜエラーなのか（値がいくらだったのか等）」を含めるとデバッグが容易になります。

#### アンチパターン
*   **文字列を throw する**: `throw "Error!"` は NG です。必ず `Error` オブジェクト（またはその継承クラス）を throw します。
*   **何でも catch する**: `try-catch` の範囲を広げすぎると、どこでエラーが発生したか分からなくなります。

---

### 3. 関数の設計（ロジック）

#### ベストプラクティス
*   **早期リターン（ガード句）**: 関数の冒頭でエラーチェックを行い、異常があればすぐに `throw` することで、正常系の処理をネストさせずに書けます。
*   **`find` の戻り値チェック**: `array.find()` は見つからない場合に `undefined` を返すため、必ず null チェック（今回の場合は例外送出）が必要です。

#### アンチパターン
*   **副作用のある計算**: 平均スコアを出す関数の中で、ついでにスコアを追加する、といった「1つの関数で2つのことをする」設計は避けます。

---

### 補足：TypeScriptでの `catch` の注意点
最近のTypeScript（4.4以降）では、`catch(e)` の `e` は自動的に `unknown` 型になります。そのため、以下のように型ガードを使うのがベストプラクティスです。

```typescript
try {
  // 処理
} catch (e) {
  if (e instanceof StudentNotFoundError) {
    console.error(e.message);
  } else if (e instanceof Error) {
    console.error("一般的なエラー:", e.message);
  }
}
```

まずはこれらを意識して解いてみてください！解き終わったら、コードを提示いただければ、さらに具体的なレビューをさせていただきます。

これまでの議論を踏まえ、**「実務レベルのベストプラクティス」**を凝縮して全体を書き直します。

主な変更点：
1.  **不変性（イミュータビリティ）**: `push` を使わず、新しい配列を返すように変更。
2.  **責務の分離**: 計算関数は値を返すだけにし、出力は呼び出し側で行う。
3.  **エラークラスの改善**: 基底クラスを作成し、`name` が自動で正しく設定されるように変更。
4.  **定数の活用**: スコアの境界値をマジックナンバーにしない。

```typescript
// --- 1. 型定義 ---
type Student = {
  readonly id: number; // 誤って書き換えないようreadonly
  readonly name: string;
  readonly scores: number[];
};

// スコアの境界値などは定数として定義（保守性の向上）
const MIN_SCORE = 0;
const MAX_SCORE = 100;

// --- 2. 独自例外の定義 ---
class AppError extends Error {
  constructor(message: string) {
    super(message);
    this.name = this.constructor.name; // クラス名を自動的に設定
  }
}

class InvalidScoreError extends AppError {}
class StudentNotFoundError extends AppError {}
class NoScoresError extends AppError {}

// --- 3. ビジネスロジック（関数） ---

/**
 * 学生をIDで検索し、存在しなければ例外を投げる（共通処理）
 */
function findStudentOrThrow(students: Student[], id: number): Student {
  const student = students.find((s) => s.id === id);
  if (!student) {
    throw new StudentNotFoundError(`ID:${id} の学生は見つかりませんでした`);
  }
  return student;
}

/**
 * 新しいスコアを追加した「新しい学生リスト」を返す（非破壊的）
 */
function addScore(students: Student[], id: number, score: number): Student[] {
  // バリデーション
  if (score < MIN_SCORE || score > MAX_SCORE) {
    throw new InvalidScoreError(`スコア ${score} は不正です。${MIN_SCORE}〜${MAX_SCORE}の間で入力してください`);
  }

  // 対象の学生が存在するか確認
  findStudentOrThrow(students, id);

  // mapを使い、対象の学生だけスコアを更新した新しい配列を作成（イミュータブル）
  return students.map((s) =>
    s.id === id 
      ? { ...s, scores: [...s.scores, score] } 
      : s
  );
}

/**
 * 指定した学生の平均点を算出する（出力はせず値を返すだけ）
 */
function getAverage(students: Student[], id: number): number {
  const { scores } = findStudentOrThrow(students, id);

  if (scores.length === 0) {
    throw new NoScoresError("点数が登録されていません");
  }

  const sum = scores.reduce((p, c) => p + c, 0);
  return sum / scores.length;
}

// --- 4. 動作確認（テスト環境） ---

// 初期データ（テストごとにリセットできるようletにするか、都度定義）
let studentData: Student[] = [
  { id: 1, name: "John", scores: [50, 40, 35] },
  { id: 2, name: "Michel", scores: [90, 78, 100, 66] },
  { id: 3, name: "Satoshi", scores: [] },
  { id: 4, name: "Ben", scores: [50, 98] },
  { id: 5, name: "Nancy", scores: [0] },
];

function test(label: string, callback: () => void) {
  console.log(`\n=== ${label} ===`);
  try {
    callback();
  } catch (e) {
    if (e instanceof AppError) {
      console.error(`[${e.name}] ${e.message}`);
    } else {
      console.error("予期せぬエラー:", e);
    }
  }
}

// --- 実行例 ---

test("正常系：スコア追加と平均点取得", () => {
  // スコア追加（戻り値でデータを更新）
  studentData = addScore(studentData, 3, 80);
  console.log("スコアを追加しました(ID:3 に 80点)");

  const avg = getAverage(studentData, 3);
  console.log(`ID:3 の平均点: ${avg.toFixed(1)}`); // 80.0
});

test("異常系：存在しない学生ID", () => {
  // ID: 999 は存在しない
  addScore(studentData, 999, 80);
});

test("異常系：不正なスコア（101点）", () => {
  addScore(studentData, 1, 101);
});

test("異常系：点数がない学生の平均算出", () => {
  // ID: 3 は先ほど追加したので、まだ点数がない ID: 5 などで試す（Nancyは0点があるが、仮に空の場合）
  // テストデータの初期状態で空だった John(ID:1) などのケースを確認
  const emptyStudentList: Student[] = [{ id: 10, name: "Empty", scores: [] }];
  getAverage(emptyStudentList, 10);
});
```

### 修正のポイント解説

1.  **`{ ...s, scores: [...s.scores, score] }`**:
    *   これが不変性（Immutability）を保つ書き方です。元のオブジェクトを書き換えず、新しいオブジェクトを作成して配列を再構築しています。これは React や Redux などのモダンなフロントエンド開発で必須のスキルです。

2.  **`AppError` 基底クラス**:
    *   `this.constructor.name` を使うことで、`InvalidScoreError` なら自動的に `name` が `"InvalidScoreError"` になります。クラスごとに `this.name = ...` と書く手間が省け、ミスも減ります。

3.  **`getAverage` の純粋関数化**:
    *   `console.log` を関数から追い出しました。これにより、この関数は「テストがしやすい」「他の場所で再利用しやすい（例：UIのラベルに表示するだけなど）」という特性を持ちます。

4.  **`readonly` の付与**:
    *   `Student` 型のプロパティに `readonly` をつけることで、誤って `student.id = 100` のように値を書き換えてしまうコードをコンパイルエラーとして検知できます。

このコードは、型安全、保守性、再利用性の観点から見て、非常に高い品質になっています。
