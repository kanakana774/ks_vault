## クラス分割とアーキテクチャが必要な理由

### 1. 前提：なぜ私たちは「既存のコード」を触りたくないのか？

システム開発において、プログラマーが最も恐れる言葉。それは「**デグレ（デグレード）**」です。
デグレとは、修正によって、これまで正常に動いていた別の機能が動かなくなってしまうことです。

これを防ぐために、現場には鉄の掟があります。

> **「コードを1行でも変更したら、その影響を受ける可能性のある機能はすべてテスト（動作確認）し直さなければならない」**

つまり、**「修正箇所が混在している大きなクラス」**を修正するということは、たとえ1行の変更であっても、**そのクラスに関わる全機能のテストをやり直す必要がある**ことを意味します。これは膨大なコストと時間になります。

クラスを分ける最大の目的は、きれいに整理整頓することではありません。
**「修正の影響範囲を閉じ込め、テストしなければならない範囲を最小限にするため（＝楽をするため）」**です。

### 2. Step 1: 恐怖の「全部入りクラス」 (God Class)

まずは、クラス分割をしなかった場合の世界を見てみましょう。
すべての処理を1つのクラスに書いた`GodController.java`です。


```java
@RestController
public class GodController {

    // DB接続情報（本来は設定ファイルに書くべき）
    private final String DB_URL = "jdbc:mysql://localhost:3306/mydb";
    private final String DB_USER = "user";
    private final String DB_PASS = "password";

    @GetMapping("/users/{id}")
    public Map<String, Object> getUser(@PathVariable("id") int id) {
        
        Connection conn = null;
        PreparedStatement stmt = null;
        ResultSet rs = null;
        Map<String, Object> userMap = new HashMap<>();

        try {
            // ① DB接続処理
            conn = DriverManager.getConnection(DB_URL, DB_USER, DB_PASS);

            // ② SQL文の準備と実行
            String sql = "SELECT id, name, email FROM users WHERE id = ?";
            stmt = conn.prepareStatement(sql);
            stmt.setInt(1, id);
            rs = stmt.executeQuery();

            // ③ 結果の詰め替え
            if (rs.next()) {
                userMap.put("userId", rs.getInt("id"));
                userMap.put("userName", rs.getString("name"));
                userMap.put("userEmail", rs.getString("email"));
            }

        } catch (SQLException e) {
            // エラー処理...
            throw new RuntimeException(e);
        } finally {
            // ④ DB切断処理
            // ... rs, stmt, conn をクローズする処理 ...
        }

        // ⑤ レスポンスの返却
        return userMap;
    }
}
```

このコードは「動く」システムですが、「生きた心地がしない」システムです。

#### この状態で修正依頼が来たら？

**変更要求：「レスポンスに年齢(`age`)を追加してほしい」**

1.  このクラス内のSQLを書き換えます。
2.  Mapへの詰め替え処理を書き換えます。

一見簡単に見えますが、ここには罠があります。
このクラスには「DB接続」や「複雑な計算ロジック」など、今回の修正とは関係ない重要かつ繊細なコードが同居しています。誤って関係ない変数を消してしまったり、コピー＆ペーストでミスをするリスクがあります。

**結果として何が起きるか？**
*   **リスク**: SQLをいじった拍子に、無関係な検索条件のロジックを壊したかもしれない。
*   **コスト**: 不安なので、このAPIの全パターン（正常系、異常系、DB接続エラー時など）をすべてテストし直す必要がある。

**「たった1行足すだけなのに、なぜ半日もテストしているの？」**という状況は、こうして生まれます。

### 3. Step 2: 「責任」を分ければ「テスト」が減る

これを解決するために、「レイヤードアーキテクチャ」でクラスを分割します。

```mermaid
graph LR
    Controller[Controller<br>受付係] --> Service[Service<br>業務処理係] --> Mapper[Mapper<br>DB係]
```

*   **Controller**: 「受付」と「返却」だけ担当。
*   **Service**: 「計算」や「判断」だけ担当。
*   **Mapper**: 「SQLの発行」だけ担当。

#### クラスを分けたら、修正はどう変わるか？

**変更要求：「レスポンスに年齢(`age`)を追加してほしい」**

この変更でやることは以下の通りです。
1.  `Mapper`のSQLに`age`を追加。
2.  `Controller`の返却値に`age`を追加。

ここで重要なのは、**「Serviceクラスには一切触っていない」**という事実です。

#### ここが最大のメリット！
「`Service`（ビジネスロジック）」のファイルを開きもしなかったということは、**「Serviceのロジックは絶対に壊れていない」ことが保証されます。**

*   **God Classの場合**: どこが壊れたかわからないので、全テストが必要。
*   **クラスを分けた場合**: 
    *   Serviceの複雑な計算ロジックのテストは**省略してOK**（回帰テスト不要）。
    *   データが画面に出るかどうかの確認だけで済む。

**「ファイルを3つ修正する」のは手間ではありません。「修正したくない場所（Service）を安全に無視できる」ことの方が、開発においてはずっと価値があるのです。**

### 4. その他の見逃せないメリット

クラス分割には、テスト範囲の縮小以外にも、品質を保つための理由があります。

#### A. チーム開発での「衝突」を防ぐ
実際の開発はチームで行います。もし`GodController`1つしかなかったら？
*   Aさんが「バグ修正」で`GodController`を修正中。
*   Bさんが「機能追加」で`GodController`を修正中。
*   **結果**: ファイルを保存するたびに「コンフリクト（競合）」が発生し、お互いのコードを消し合う事故が起きます。

クラスが分かれていれば、「AさんはMapper（DB周り）」、「BさんはController（画面周り）」のように、**作業場所を住み分けられるため、並行して作業が進められます。**

#### B. 「部品」として使い回せる（再利用性）
「管理画面でも同じロジックを使いたい」と言われたとき、`GodController`だとコピペするしかありません。コピペ元のコードにバグが見つかったら、コピペ先も全て修正が必要です。

独立した`UserService`クラスがあれば、それを`new UserService()`して呼ぶだけです。
**「すでにテスト済みで、バグがないことが分かっている部品」**を使い回せるので、新しい機能も爆速かつ高品質で作れます。

### まとめ：クラス分割は「未来の自分への保険」

| | クラス分割なし (God Class) | クラス分割あり (アーキテクチャ) |
| :--- | :--- | :--- |
| **修正ファイル数** | 1つ (楽そうに見える) | 複数 (面倒に見える) |
| **デグレのリスク** | **極大**。関係ない機能まで壊す恐れあり。 | **最小**。変更に関係ある層しか壊れない。 |
| **必要なテスト範囲** | **クラス全体**。不安だから全部やるしかない。 | **修正した層のみ**。触っていない層はテスト不要。 |
| **チーム開発** | 常にファイルの取り合いになる。 | 分担してスムーズに進む。 |

未経験のうちは「ファイルを分ける＝書くコードが増える」と感じるかもしれません。
しかし実務では、**「コードを書く時間」よりも「コードを読み解き、バグがないか確認する時間」の方が圧倒的に長い**のです。

クラス分割は、その「確認する時間」と「バグ修正の苦しみ」を劇的に減らすための、必須のテクニックと言えますかね。
