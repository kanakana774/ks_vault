# 1. バッチ処理の基礎知識

## 1-1. バッチ処理とは
バッチ処理とは、一言で言えば「**あらかじめ定めた一定量のデータを、人の手を介さずに一括（Batch）で処理する方式**」のことです。

Web APIが「ユーザーからのリクエストに対して即座にレスポンスを返す（同期的な処理）」のに対し、バッチ処理は「特定のタイミングで、裏側でまとめて処理を行う（非同期的な処理）」という違いがあります。

### Web API（オンライン処理）との比較

| 特徴 | Web API（オンライン処理） | バッチ処理 |
| :--- | :--- | :--- |
| **開始のきっかけ** | ユーザーの操作（リクエスト） | スケジュール（時間）や特定条件 |
| **処理単位** | 1リクエスト（少量のデータ） | 大量データ（数万〜数百万件など） |
| **応答性** | リアルタイム（即時性が必要） | 非リアルタイム（完了まで時間がかかる） |
| **ユーザーとの対話** | あり（UIがある） | なし（バックグラウンドで完結） |

## 1-2. バッチ処理の特徴

1.  **一括処理（Bulk Processing）**
    *   1件ずつ処理するのではなく、大量のデータをまとめて処理します。これにより、DB接続回数の削減や計算の効率化が図れます。
2.  **スケジュール・トリガー実行**
    *   「毎日24時」「毎月月末」「特定のファイルが置かれた時」など、あらかじめ決められたルールに従って自動実行されます。
3.  **非リアルタイム性**
    *   即時性は求められません。その代わり、システム利用者が少ない夜間などにリソースを集中させて重い処理を実行できます。
4.  **自動化と確実性**
    *   一度設定すれば手動操作が不要になり、人的ミスを防げます。また、エラーが起きた際に「どこまで終わったか」を管理し、再開（リトライ）する仕組みが重要視されます。

## 1-3. 具体的なイメージ（郵便配達の例）

バッチ処理の考え方は、郵便の仕組みに例えると理解しやすくなります。

*   **オンライン処理（Web API等）**：**電話やチャット**
    *   相手とリアルタイムにやり取りし、その場で完結します。
*   **バッチ処理**：**ポストの集荷と配達**
    *   **投函（リクエストの蓄積）**: 差出人は好きな時にポストへ手紙を入れます。
    *   **集荷（バッチ実行）**: 郵便局員が「決まった時間（スケジュール）」に、ポストの中身を「まとめて（一括）」回収します。
    *   **仕分け・配送（一括処理）**: 郵便局でまとめて仕分けし、一気に各家庭へ届けます。

> [!TIP]
> ポストに手紙が届くたびに郵便局員が1軒ずつ回収に行くのは非効率です。「まとめてやるから効率が良い」のがバッチ処理の最大のメリットです。

## 1-4. メリットとデメリット

### メリット
*   **システム負荷の分散**
    *   大量のデータ更新など負荷の高い処理を、ユーザーが少ない夜間に行うことで、日中のシステム性能（レスポンス）への影響を抑えられます。
*   **リソースの有効活用**
    *   24時間フル稼働させる必要がないサーバー資源を、必要な時だけ集中的に使えます。
*   **業務の自動化**
    *   手作業で行うとミスが起きやすい定型業務（集計、バックアップ等）を確実に実行できます。

### デメリット
*   **データの鮮度（タイムラグ）**
    *   処理が完了するまで結果が反映されないため、「今現在の最新状態」が見られない期間が生じます。
*   **障害時の影響範囲が広い**
    *   大量のデータを扱うため、途中でエラーが起きると、どのデータまで処理が終わったかの把握や、リカバリ（やり直し）に手間がかかる場合があります。

## 1-5. 主な利用シーン

Web API開発でも、以下のような機能が必要になったら「バッチ処理」の導入検討タイミングです。

*   **データ集計**: 前日の売上データを計算し、集計テーブルに保存する。
*   **レポート作成**: 月末にPDFの請求書を数万件一括で生成する。
*   **外部システム連携**: 外部サービスからCSVデータを取り込んだり、逆にデータを転送したりする（ETL処理）。
*   **一括通知**: 期限が近いユーザーに対して、プッシュ通知やメールを一斉送信する。
*   **クリーニング**: 保存期間を過ぎた古いログデータや一時ファイルを削除する。

# 2. 実装の話（Spring Batchとスケジューラ）

## 2-1. Spring Batchとは
Spring Batchは、Spring Frameworkの系譜でバッチ処理を開発するためのフレームワークです。
Web API開発で使う「Dependency Injection (DI)といったSpring Bootの恩恵をそのままバッチ開発に持ち込めます。
## 2-2. 主要な構成要素
バッチ処理は、以下の4つの主要コンポーネントで成り立っています。

[公式ドキュメント](https://spring.pleiades.io/spring-batch/reference/domain.html)
![[Pasted image 20260528160256.png]]

| コンポーネント           | 役割                                  |     |
| :---------------- | :---------------------------------- | :-- |
| **Job**           | バッチ処理の「全体」を定義するコンテナ。                |     |
| **Step**          | Jobを構成する個々の「工程」。1つのJobに複数のStepを持てる。 |     |
| **JobOperator**   | Jobを実行するための起動機。                     |     |
| **JobRepository** | JobやStepの実行状態（成功・失敗・開始時刻など）を管理するDB。 |     |

### 構造のイメージ
1. **JobOperator**が「このJobを動かして」と命令する。
2. **Job**が実行され、その中の**Step**が順番に動く。
3. そのすべての経過や結果を **JobRepository** がデータベースに記録し続ける。
   - ※これにより、「失敗したところから再開（リスタート）」が可能になります。


## 2-3. Stepの2つの実装モデル
Spring Batchには、処理内容に応じて使い分ける2つのモデルがあります。

### 1. Chunk（チャンク）モデル【推奨：大量データ用】
大量のデータを一定の件数（チャンク）ごとに区切って処理するモデルです。

*   **構成要素**:
    *   **ItemReader**: データを1件ずつ読み込む（DB、CSVファイルなど）。
    *   **ItemProcessor**: 読み込んだデータを加工・フィルタリングする。
    *   **ItemWriter**: まとまった件数（チャンク）分をDB等に一括書き込みする。
*   **特徴**:
    *   **メモリに優しい**: 100万件あっても、100件ずつ処理すればメモリ不足になりません。
    *   **効率的なコミット**: 100件ごとにトランザクションを確定（コミット）するため、途中でエラーが起きても「前の100件までは完了済み」として扱えます。
*   **用途**: 大規模なDB更新、ファイル取り込みなど。
[参考](https://terasoluna-batch.github.io/guideline/5.0.0.RELEASE/ja/Ch02_SpringBatchArchitecture.html#Ch02_SpringBatchArch_Detail_ProcessFlow)

![[batch全体像.png]]


![[chunkイメージ.png]]


### 2. Tasklet（タスクレット）モデル【シンプル用】
「1つのメソッドの中にすべての処理を書く」非常にシンプルなモデルです。

*   **特徴**:
    *   自由度が高い。
    *   処理全体で1つのトランザクションになるのが一般的。
*   **用途**: ファイルの削除、シェルスクリプトの実行、1つだけのSQL発行など、定型外の処理。


## 2-4. API開発者が知っておくべき重要概念

### JobParameters（ジョブ・パラメータ）
APIの「クエリパラメータ」や「リクエストボディ」に相当します。
「何月何日のデータを処理するか」といった実行ごとの変数を、外部（起動引数）から渡す仕組みです。

### データの整合性とリスタート
APIは「失敗したらエラーを返して終わり」ですが、バッチは「失敗したところからやり直す」ことが求められます。
Spring Batchは、`JobRepository`に「どこまで終わったか」を記録しているため、大量処理の途中でエラーが起きても、**修正後に前回の続きから自動で再開する**といった高度な制御が可能です。


## 2-5. どちらのモデルを使うべきか？

| 比較項目 | Chunkモデル | Taskletモデル |
| :--- | :--- | :--- |
| **得意なこと** | 大量データの繰り返し処理 | シンプルな1回限りの処理 |
| **メモリ効率** | 非常に良い（小分けにするため） | 実装次第（一気に読み込むと危ない） |
| **実装の複雑さ** | やや高い（3つの部品を作るため） | 低い（1つのクラスで完結） |
| **リスタート** | 途中から再開しやすい | 最初からやり直しになりやすい |

**選定基準：**
- DBのレコードを1件ずつ処理して更新するなら **Chunkモデル**。
- 特定のファイルを1回移動させるだけ、といった処理なら **Taskletモデル**。

## 2.6 スケジューラ（運用担当）

ジョブの起動を担当する。JP1 / Airflow / Cron / Quartz など

具体的には下記のような役割がある。
- 毎晩 23:00 に「ジョブ」を起動
- 前段階（注文締め処理）が終わってから起動するよう依存関係を設定
- エラー発生時は Slack/メールに通知して運用者にエスカレーション
- 再実行時は同じ Spring Batch ジョブをリラン（リスタート機能活用）

⇒ 運用担当は「いつ・どの順番で実行するか」を管理する

# 3. 実例で学ぶ：Spring Batchのジョブ構成

Web APIでは「1人のリクエスト」を処理しますが、バッチでは「全ユーザーのデータ」などをまとめて処理します。

## 業務例：月額会員の決済と継続ボーナス付与ジョブ

**【要件】**
- 毎月1日の深夜に実行。
- 月額会員（サブスク）ユーザー全員に対して、月額料金の決済処理を行い、継続特典のポイントを付与する。
- 完了後、その日の売上合計をCSV出力し、完了通知を送る。

## ジョブの全体像（Step構成）

ひとつの「Job」の中に、役割の異なる「Step」を組み合わせて構築します。

### Step1：月額料金の決済とポイント付与（Chunkモデル）
**なぜChunkか？**：ユーザー数は数万人〜数百万人になる可能性があるため、一定人数ごとに決済を確定させていくのが安全だからです。
- **ItemReader**: DBから「有効な月額会員」を1件ずつ読み込む。
- **ItemProcessor**: 
    - 会員プラン（ライト/プレミアム）に応じた料金を計算する。
    - 継続月数に応じた「ボーナスポイント」を計算する。
- **ItemWriter**: 
    - クレジットカード決済を実行し、ユーザーのポイント残高を更新する。
    - （100件まとめて一括でDBを更新・コミットする）

### Step2：月額売上集計CSVの作成（Taskletモデル）
**なぜTaskletか？**：DBの集計関数（`SUM`）を使って「今回のバッチでいくら売り上げたか」を算出し、ファイルを1つ作るだけの「単発処理」だからです。
- 処理内容：今回のジョブで決済した合計金額をDBから集計し、管理用のCSVファイルに書き出す。

### Step3：運営への完了通知（Taskletモデル）
**なぜTaskletか？**：ループ処理ではなく、「メッセージを1回送る」という単一のアクションだからです。
- 処理内容：Slackやメール等で「○件の決済が完了しました」と通知を送る。
## 役割分担

役割分担は下記のようになっています。

| フェーズ       | 使うツール                    | 内容                                |
| :--------- | :----------------------- | :-------------------------------- |
| **ロジック実装** | **Spring Batch**         | 「どう処理するか」を書く。ChunkやTaskletの実装。    |
| **実行管理**   | **JP1 / Airflow / Cron** | 「いつ実行するか」を決める。前工程（バックアップ等）との順番制御。 |


## 【重要】「Chunkモデル」のメリット

なぜわざわざ `Reader / Processor / Writer` に分けるのか？ その理由は **「再試行（リスタート）」** にあります。

もし10万件の処理中、9万件目でエラーが起きた場合：
- **普通のプログラム（Tasklet等）**: どこまで終わったか分からず、最初からやり直すとデータが二重登録されるリスクがある。
- **Chunkモデル**: Spring Batchが `JobRepository` に「8万9900件まではコミット完了」と記録しているため、**エラー原因を除去して再実行するだけで、自動的に9万1件目から再開**できます。

> [!CAUTION]
> 単純にwriterでコミットするタイミングでrepositoryにも処理結果が書き込まれています。そのため、writerでコミットする前に落ちれば、その前のコミットから開始となります。
> 
> また再起動時もreaderでは、単純に以前の読み込み件数をスキップして読み込むため、結果セットが再作成されます。つまり、最初に検索した結果と再起動時に検索した結果に**冪等性**がない場合（＝途中でupdateなど挟む場合）に、処理結果が不正確なものになるかもしれません。そのため、バッチ処理は0時を超えたら起動し、最初の取得も前日のみというように条件を付けて取得する場合が多いかと思います。


# 4. まとめ：Chunk vs Tasklet の使い分けガイド

最後に、実装時に迷わないための判断基準です。

### **Chunkモデルを使うべきケース**
- **処理対象が「大量のリスト」である。**
- **1件ごとに独立したロジック（計算や変換）がある。**
- **メモリ消費を抑えたい、または途中で失敗しても続きから再開したい。**
- *例：会員全員へのメール配信、全商品の在庫同期、大量のログ解析。*

### **Taskletモデルを使うべきケース**
- **処理対象が1つ、またはまとまった1工程である。**
- **SQLを1発発行して終わり、ファイルを1つ動かして終わり、といった処理。**
- **途中で止まったら「最初からやり直し」で問題ない単純な処理。**
- *例：中間テーブルの削除（TRUNCATE）、1つのファイルの転送、完了通知。*
