## mybatis 関連

#### 戻り値の優先順位：Mapper インターフェース vs XML

XML 側の parameterType や resultType が優先されます。
Mapper インターフェースのシグネチャは 型チェックや補完のヒントとして使われますが、実際に実行されるときには MappedStatement に記録された情報（XML 由来） が使われます。

#### 処理の流れ

XML を読み込むときに MappedStatement が作られ、その中に parameterMap や resultMaps が設定されます。
Mapper インターフェースのシグネチャ（戻り値型・引数型）は MapperMethod 生成時に解析されます。
実行時は、MappedStatement（XML が元）と MapperMethod（インターフェースが元）の整合性を MyBatis がチェックします。
もし矛盾していたら ランタイムエラーになります（例: XML で resultType=User なのに、インターフェースの戻り値を int にした場合など）。

#### insert に resultType は指定できる？

結論：できません（無視されます）。
insert / update / delete の戻り値は「更新件数(int)」と決まっています。
XML に resultType を書いても意味がなく、resultMap も解釈されません。
**理由：**
XMLStatementBuilder#parseStatementNode() 内で SqlCommandType を INSERT にした場合、resultType や resultMap の設定は SELECT 以外では利用されません。
実際に実行されるのは sqlSession.insert(...) であり、戻り値は件数 (int) 固定です。

**例：**
正しい組み合わせ
```XML
<select id="selectUser" parameterType="long" resultType="User">
    SELECT \* FROM users WHERE id = #{id}
</select>
```

```java
// mapperインタフェース
User selectUser(Long id);
```

矛盾している場合（エラーになる）
```XML
<select id="selectUser" parameterType="long" resultType="User">
    SELECT \* FROM users WHERE id = #{id}
</select>
```

```java
int selectUser(Long id); // ← 戻り値型が違うので実行時にエラー
```

優先順位は XML > Mapper インターフェース
ただし整合性が取れていないとランタイムエラー
insert/update/delete は 戻り値 = 更新件数(int) 固定、resultType は使えない

#### mybatis の sql ごとの戻り値の話

**結論：**
select 以外は更新件数を戻し、select では戻り値型のものを返す。
select で戻す entity は mybatis が勝手に new するのでデフォルトコンストラクタが必要かも。

MyBatis のライブラリ内部では XML の \<select> / \<insert> / \<update> / \<delete> タグ をパースして、最終的に MappedStatement というオブジェクトに変換しています。
このとき タグ種類ごとに「SqlCommandType」（SELECT / INSERT / UPDATE / DELETE / UNKNOWN）がセットされ、実行時に戻り値処理が変わります。
##### 1. XML のタグ判定が行われる場所
MyBatis の XML パーサは org.apache.ibatis.builder.xml.XMLStatementBuilder です。
具体的にはこのメソッド 👇\
public void parseStatementNode()\
ここで \<select>, \<insert>, \<update>, \<delete> のタグ名を見て SqlCommandType を決めます。

##### 2. コードの流れ（ざっくり）
1. XMLMapperBuilder#configurationElement
   \<mapper> タグ以下を読み込む。
   各 \<select> 等を XMLStatementBuilder に渡す。

2. XMLStatementBuilder#parseStatementNode
   ノード名（select/insert/update/delete）をチェック
   SqlCommandType を決定
   MappedStatement を生成
3. Configuration#addMappedStatement
   MappedStatement を Configuration に登録
##### 3. 実行時に参照される場所
実際に Mapper メソッドを呼ぶと、
MapperMethod クラス（org.apache.ibatis.binding.MapperMethod）が動きます。
public Object execute(SqlSession sqlSession, Object[] args)
ここで command.getType()（= SqlCommandType）を見て、処理を振り分けます：
SqlCommandType.INSERT → sqlSession.insert(...) → 戻り値 int
SqlCommandType.UPDATE → sqlSession.update(...) → 戻り値 int
SqlCommandType.DELETE → sqlSession.delete(...) → 戻り値 int
SqlCommandType.SELECT → sqlSession.selectOne / selectList など → 戻り値は Entity/List

**XML パース時：**
XMLStatementBuilder#parseStatementNode() でタグ名を判定し、SqlCommandType を決定。

**実行時：**
MapperMethod#execute() が SqlCommandType を見て処理を振り分け。
これにより insert は件数(int)、select はエンティティ/リスト が返る仕様になる。

#### \<if>で注意すべきこと
```xml
<!-- 正しい -->
<if test="limit != null and limit != ''">
	limit
		#{limit}
</if>

<!-- 間違い -->
<if test="limit != null and limit = ''"><!-- ”=” になってるので代入されてる -->
	limit
		#{limit}
</if>
```
みたいに、limit\=\=のように比較演算子でなくて、代入演算子になってると、本当に代入されてしまい、#{limit}が空となってSQLが実行されてしまう事象を確認
