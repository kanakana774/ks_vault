# AI研修 — 前提と目的の整理

> 更新: 2026-08-06 / ステータス: **検討中（内容未定）**
> この文書の役割: 「何を作るか」を決める前に、**何が制約で、何のためにやるのか**を固定する。ここが揺れたまま教材を作ると作り直しになる。

---

## 1. 与件（すべて仮）

| 項目 | 現状 |
|---|---|
| 時期 | 2026年10月までに開始したい |
| 期間 | 1週間ほど |
| 位置 | 3か月目の最終週に食い込む |
| 対象 | 3か月終了時点の研修生全員 |
| 使うツール | 未定 |
| 内容 | **未定** |

前提として、**現行の1〜3か月目では研修生の生成AI利用は禁止**している。この研修は彼らにとって**初めてAIが解禁される週**になる。

---

## 2. 制約 — この研修に特有の3つ

### A. 配属先ごとに使えるツールが違う

SES事業なので、研修生は配属先の規定に従う。ツールを指定される現場もあれば、**そもそもAI禁止の現場もある**。
→ **特定ツールの操作を教える研修は空振りする。** 原理に重心を置き、ツールは「例」として1〜2種類触らせるに留める。加えて「**新しいツールが来ても自分で立ち上げられる**」というメタスキルの方が、配属先が読めない状況では価値が高い。

### B. 陳腐化が速い

モデルもツールも半年で変わる。作り込んだ教材ほど負債になる。
→ **固定するのは「型」だけにする**。何を測るか（評価軸）、どういう演習形式か（進め方）は変わらない。題材（ツール・モデル・課題のコード）は**毎期差し替える前提**で設計する。
→ 他ユニットは「教材を作り込んで使い回す」設計だが、**このユニットだけ思想を変える**。

### C. 1週間しかない。しかも一番詰まった週

3か月目の最終週は Webアプリ2 の単体テストの締めで、直後にフロント研修が立ち上がる（`03_研修カリキュラム.md` §1）。日程にも研修生の体力にも余裕がない。
→ **新しい技術領域を足す余裕はない。** すでに持っているもの（Java / API / レビュー文化）の上に載せる設計にする。フロント・クラウドなど未経験領域には手を出さない。

### D. 講師自身に AI での開発経験がない

**これは案の選択を左右する最大の制約**。研修生と同じく、講師も1〜3か月目でAIを使ってこなかった。

→ **制約Dの影響度は案ごとに全然違う**。ツール習熟を売りにする案は講師が一番詳しくないと成立せず、受講生に追い抜かれるリスクもある。逆にガバナンス中心の案は調べ物が主なので影響が小さい。**各案を「講師の習得コスト」で必ず比較する。**
→ **準備期間**: 今日が 2026-08-06、開始目標が10月なので実質2か月弱。しかもその間、2か月目API・4か月目React・SQL の研修が並行して回っている（`01_業務概要.md` §3）。**使える準備時間は細切れ**という前提で見積もる。
→ 一方で**弱みだけではない**。講師が今まさに「初めてAIを触る人」なので、**詰まりどころを実体験として教材にできる**。研修生と同じ地点から始められるのは、経験者にはない強み。学習過程そのものを記録しておく価値がある。

## 3. 目的 — 3つあり、互いに競合している

| | 目的 | 誰のため | 1週間で届くか | 何で測るか |
|---|---|---|---|---|
| **a** | SESで雇われやすい人材にする | 会社の営業 ＋ 本人の面接 | **届く** | AI活用について自分の言葉で語れるか |
| **b** | 根本的な技術力を上げる | 本人の長期 | **届かない** | — |
| **c** | 「AI研修あります」というプロモ | 会社の対外アピール | **届く**（存在自体に価値） | 対外資料に書ける中身があるか |

**競合の中身**: a と c は「短期間で見せられること」を求め、b は「時間をかけて考えさせること」を求める。**1週間なら a・c が主で、b は入口までしか作れない。**これを認めないまま設計すると、全部中途半端になる。

**ただし b を捨てる必要はない。** AIを使わせると「**自分の判断力が足りないと使いこなせない**」ことに嫌でも気づく。1週間の成果を「できるようになった」ではなく「**足りないものが分かった**」に置けば、b への強い動機づけとして機能する。配属後に伸びる人材を作るという意味では、こちらの方が本質的かもしれない。

**a と c は両立する。** 「Copilotを触りました」より「AIが書いたコードのレビュー演習をやった」「仕様を書いてAIに実装させ、テストで検証する一連をやった」の方が、営業資料としても面接の受け答えとしても強い。**中身を良くすることがそのままプロモ価値になる。**

## 4. SES と受託で必要なものが違う（時間軸を分ける）

| | 目先＝SES | 将来＝受託も取る会社 |
|---|---|---|
| 誰が開発プロセスを決めるか | 客先 | 自社 |
| 求められるもの | **個人として使えること**＋客先ルールの遵守（ガバナンス） | **チーム・プロセスとしての活用**（AI前提の見積り・品質保証） |
| 研修で扱うなら | 個人スキル＋情報漏洩/著作権/ハルシネーションの作法 | 開発プロセスの設計 |

**新人1週間で後者は早い。** 目先のSESに寄せ、受託を見据えた話は「そういう世界がある」と示す程度に留めるのが現実的。

## 5. 陳腐化するもの / しないもの

制約B への答え。**ここが「何が研修になるか」の芯**。

| 陳腐化する（教えても半年で古びる） | 陳腐化しにくい（長く効く） |
|---|---|
| 特定ツールの操作・UI | **自分が何を作りたいかを言語化する力**（仕様記述） |
| プロンプトの「コツ」「呪文」 | **出力が正しいか判断する力**（検証・レビュー） |
| 特定モデルの癖・得意不得意 | **任せる範囲と自分が責任を持つ範囲の線引き** |
| 「今のAIはここができない」という現状認識 | **必要な情報を過不足なく与える力**（コンテキスト設計） |
| ツールごとの設定・料金・制限 | **失敗の兆候に気づく力**（動くけど間違っているコードを見抜く） |
| | **新しいツールを自分で立ち上げる力** |

**理屈**: AIは能力の増幅器なので、**増幅される側（判断・設計・検証）は陳腐化せず、増幅の仕方（操作）は陳腐化する**。しかもモデルが賢くなるほどボトルネックは人間側の「指示」と「検証」に移るので、右列の価値は**上がっていく**。

調査ノート（`learning-vault/世情/...`）の Recommendation 2「AI検証・レビュー・仕様記述能力を鍛える」と同じ結論。

## 6. 研修生の出発点（`MyWork/03_研修カリキュラム.md` §6 より）

- **3か月間「自力で書く」に最適化されてきた。** AI利用は禁止。この週が初解禁
- **レビュー文化をすでに持っている** — PR運用、CheckStyle/SonarLint、DBUnit、レビュー観点資料。→ **§5右列の「検証する力」への接続線がすでに敷かれている**。ここが最短の接続点
- **仕様は常に与えられてきた。** 自分で書いたことがあるのは詳細設計から（要件定義は未経験）。→ **§5右列の「言語化する力」は弱点であり、同時に一番の伸びしろ**
- 皮肉な事実として、**彼らが3か月かけて習熟した「仕様を受け取って層に分けて実装する」作業は、AIが最も得意な領域**でもある
