# 2か月目の教材見直しの材料

> 更新: 2026-08-06 / 由来: AI研修の実験（`02_実験_プロンプト差の検証.md` P1）の副産物
> きっかけ: 講師の所感「AIの出力は**研修で扱うコードよりモダンで読みやすい**」。これが本当か調べた結果。

---

## 1. 結論: 「古い」のは一部だけで、多くは教育的単純化。むしろ研修コードの方が設計は厚い

### バージョンは古くない

| | 研修デモ | AI生成 |
|---|---|---|
| Spring Boot | **3.4.1** | 4.0.7 |
| Java | 21 | 21 |
| MyBatis Starter | 3.0.4 | 4.0.1 |
| その他 | Flyway 9.21.2 / MapStruct 1.5.5 / DBUnit / Mockito / Security / Actuator | docker-compose 同梱 |

3.4.1 は**教材を作った時点の最新**であり、通常の講義ラグ。「古い」とは言えない。AIが 4.0.7 を使ったのは「AIは常に最新で書く」という性質の表れで、**研修環境に持ち込むと壊れる方が問題**（`02_実験` §4.1 の欠陥①）。

### 「古い」と言えるのはこの2点だけ

| 箇所 | 現状 | 今なら |
|---|---|---|
| DTO / Form / Entity | class ＋ 手書き getter/setter（`TagPostFrom` / `TagEntity`） | `record`（AIは全DTOをrecordで書いた） |
| DI | 明示的コンストラクタ ＋ 「コンストラクタインジェクション」のコメント | `@RequiredArgsConstructor`（pom に Lombok はあるのに未使用） |

**ただしどちらも教育的単純化の可能性が濃厚。** 手書き getter/setter は「フィールドとアクセサの対応」を体で覚えさせる意図、明示コンストラクタは「コンストラクタインジェクションとは何か」を見せる意図だろう（実際コメントがそう示唆している）。**古さと教育的配慮を混同しないこと。**

---

## 2. 逆に、研修コードの方が優れている点（こちらが重要）

| 観点 | 研修デモ | AI生成 |
|---|---|---|
| **層の分離** | `controller / logic.service / mapper / entity / form / query / queryCondition` ＋ `util`。**検索条件を独立層に切っている** | controller で `@RequestParam` を素朴に受けるだけ |
| **エラー設計** | `ErrorCodes` enum ＋ `TodoRuntimeException` 基底クラスでエラーコード体系を管理 | `@ExceptionHandler` を並べるだけ。しかも `ex.getMessage()` を外に漏らす |
| **Javadoc** | 全メソッドに `@param` / `@return` 付き。初学者が「何を書くべきか」を型で学べる | ほぼ無し（AIは自明なコードにコメントを書かない傾向） |
| **規約の強制** | `todo_checks.xml`（CheckStyle）同梱 | lint / format 設定なし |

### 「AIのコードが読みやすい」のは、設計が浅いからでもある

層が少なく抽象が少なければ読みやすい。**読みやすさと実務的な正しさは別**。研修コードが `query`/`queryCondition` を独立層に切り、エラーコードを enum で体系化しているのは、大規模APIに近づけるための意図的な複雑さ。

→ **この非対称性はそのまま教材になる**（→ §4）。

## 2.1 ★実物の不備が2件見つかった（AIが指摘・2026-08-06）

P2b の実験で、AIが**設計書を読んで矛盾と穴を指摘してきた**（`02_実験` §4.2）。**教材の実際の不具合**なので、AI研修とは切り離して対応が要る。

### ① `content` の最大文字数が文書間で食い違っている ★要修正

| 文書 | 記載 |
|---|---|
| **要件定義書**（Todo課題1／課題2） | **30文字以内** |
| DB定義書 | `content varchar(100)` |
| OpenAPI（`todo.yaml`） | `maxLength: 100` |
| プログラム設計書（`Todo機能.md`） | 「100文字以内」 |

**3対1で100が正**と思われるが、**要件定義書だけが30**。実DBも `varchar(100)` で確認済み。

**なぜ今まで表面化しなかったか（推定）**: 研修生はDB定義とプログラム設計に従って100で実装すれば動くので、**矛盾に気づかないまま通過している**可能性が高い。逆に要件定義書を素直に読んだ研修生は30で実装し、レビューで指摘される — という理不尽が起きうる。

→ **要件定義書の記載を100に直すか、他を30に直すか。どちらが正か確認して統一する。**

### ② Tag削除時の `todo_tag` クリーンアップが未定義

Todo削除時は `todo_tag` の削除が設計書に明記されているが、**Tag削除時の記載がない**。そのままだと**孤児レコードが残る**。

→ 設計の穴。仕様として追記するか、「あえて書いていない（研修生に考えさせる）」のかを決める。

### ③ ★プログラム設計書が N+1 を指示している（最優先）

`03.API設計/プログラム設計/Todo課題2/Todo機能.md`「Todo の一覧取得」:

```
- 取得した結果が 1 件以上の場合
  - 取得した Todo 情報リスト(要素(todo))分、ループ
    - todo に紐づく Tag の情報を取得
```

登録・更新でも「`tags` の各要素についてループし、Todo と Tag の紐づきを登録」＝**ループ内 INSERT**。

**レビュー観点の筆頭項目「for 文の中で SQL を呼び出していないか」と正面から矛盾している。**

研修生に起きていること（推定）:
1. プログラム設計書に従ってループで実装する
2. レビューで N+1 を指摘される
3. **「設計書通りに書いたのに」**

→ **設計書を直すか、「設計書はナイーブな手順書であり、実装時は N+1 を避ける」と明記するか。** 後者なら「設計書の指示を鵜呑みにしない」という教育的意図として成立するが、**どこにもそう書かれていない**ので現状は単なる矛盾。

### ④ `pom.xml` に `maven-checkstyle-plugin` が無い

コーディングガイドは「レビューを投げる前に必ず Checkstyle によるプロジェクトへの解析を行うこと」と要求しているが、**`pom.xml` にプラグインが無く、CLI からは実行できない**。IDE プラグイン経由でしか動かせない状態。
→ プラグインを追加するか、ガイドに「IDEから実行する」と明記する。

### ⑤ `@MapperScan` / `@Mapper` がどこにも無い

`develop` の scaffold には `@MapperScan` も無く、Mapper インタフェースも空フォルダなので、**研修生が `@Mapper` を付けないと起動しない**。AIは起動失敗して自力で気づいた。
→ 意図的に気づかせる設計なら問題ないが、**どこにも案内がない**。`TodoApplication` に `@MapperScan` を置くか、講義で触れるかを決める。

### ⑥ `system_conf.properties` がどこからも import されていない

`todo.linkedTagLimit=5` が定義されているのに `spring.config.import` が無く、**`LimitContext` の値が 0 に解決される**。結果、タグ紐づけが常に 400 になる。**P2b・P3 の両方でAIが同じ問題を見つけて修正した**（＝確実に踏む地雷）。
→ ⑤と同じ判断。意図的なら案内を、そうでなければ scaffold を直す。

### ⑦ Tag紐づけ上限の source of truth が二重

`todo.yaml`（課題2）が `maxItems: 5` をハードコードしている一方、scaffold は `LimitContext`（`todo.linkedTagLimit`）を持っている。**どちらを正とするか設計書に書かれていない。**

### ⑧ OpenAPI の path param が `string`、DB は `Integer`

`todoId` / `tagId` が OpenAPI では `string` 型。非数値IDを渡したときの挙動が設計書に無く、**汎用の 500 ハンドラに落ちる**（400/404 にならない）。

---

### この発見のしかた自体が使える

**AIに設計書一式を読ませて「矛盾や抜けを挙げさせる」だけ**で出てきた。人間が何年も気づかなかったものが1回で出る。
→ **他ユニットの設計書（yafh-app-api など）にも同じことをやる価値がある。**
→ **研修の演習としても組める**（`01_方向性の候補.md` 案A）。研修生にもできる作業で、しかも「AIは仕様の矛盾を見つけられる」という有用性の実感になる。

## 3. 見直し候補（優先度つき）

| | 内容 | 判断 |
|---|---|---|
| **高** | DTO / Form を `record` に切り替える | Java 21 確定の教材で class＋手書きアクセサを続ける理由は薄い。ただし「record の前にまず class で構造を理解させる」回を残すなら温存も可 |
| **中** | Mapper の戻り値に `Optional` を導入（`findById` 系 ＋ `orElseThrow`） | null 安全の講義に直結する。模範解答を書くときに教材化する価値あり |
| **中** | 例外処理を二層で教える | 独自 `TodoRuntimeException` 階層は本格的だが複雑。`@RestControllerAdvice` ＋ `@ExceptionHandler` という**業界標準パターンも並行して教える**と、配属後に読むコードが分かりやすくなる |
| **低** | Lombok の使用方針を明記 | pom に依存はあるのに Tag 機能では未使用。「いつ Lombok を使ってよいか」を教材に書く |
| **低** | Spring Boot のバージョン追随ルール | 教育効果は薄いが、EOL・脆弱性管理として年1回の更新ルールを検討 |

## 4. AI研修への含意（`01_方向性の候補.md` 案Aを強める）

研修生はおそらく「**AIのコードの方が読みやすい**」と感じる。それは正しい感想だが、**読みやすさは設計の浅さでもある**。

そこで案Aの演習にこう組める。

> 自分たちが `query` / `queryCondition` を独立層に切ったのはなぜか。
> エラーコードを enum で体系化したのはなぜか。
> AIの出力にはそれが無い。**その差を説明できるか。**

**設計を理解しているかのテストになる。** しかも「AIは使えない」でも「AIの方が優秀」でもない、第三の着地になる — **AIは読みやすく浅いものを速く作る。深くするのは人間の仕事**。

## 5. この比較の限界

現在チェックアウト中のブランチは **Tag 機能のみ実装済みで、Todo 機能は `.gitkeep` のみ**（演習課題として空）。そのため日付型・コレクション操作・複雑な WHERE 句の MyBatis 記法は研修側に現物がなく、直接比較ができていない。

→ **正確な比較には `lecture_*` の段階別デモブランチか模範解答を見る必要がある。** §1〜2 の判断は Tag 機能からの類推を含む。
