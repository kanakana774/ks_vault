# 実験: プロンプト品質による差の検証（案Aの前提確認）

> 更新: 2026-08-06 / ステータス: **Stage 1 実施前**
> 目的が2つある。①社長の要望「投げるプロンプトによって出る差を経験させる」が教材として成立するか ②案A（検証・レビュー型）の前提「AIはもっともらしく間違える」が本当か。
> **段階的に進め、各段階の終わりで「ここまでやる」を判断する。** 全部やる前提では組まない。

## 0. 実験の骨格

**同じ課題を、プロンプト品質を変えて3回解かせ、出力の差を測る。**

> **2026-08-06 重要な訂正**: 研修生は**ゼロから作らない**。`todo-app-api` の **develop ブランチを clone** し、**研修側が用意した枠**（パッケージ構成・使うクラスの指定・エラーハンドリング機構）に実装を埋めていく。
> P1 でゼロから作らせたのは**研修の条件とは違う**。P2 以降は develop の枠を起点にする。

| 条件 | 与えるもの |
|---|---|
| **P1 雑**（実施済） | 一行の指示だけ。設計書も枠も渡さない。**研修の条件とは違う**ので、位置づけは「導入の驚き」用（§4.1） |
| **P2 研修生と同じ** | **develop ブランチの枠** ＋ 要件定義書 ＋ DB定義 ＋ DDL ＋ OpenAPI ＋ エラー設計 |
| **P3 コンテキスト厚め** | P2 ＋ コーディングガイド ＋ レビュー観点 ＋ CheckStyle設定 ＋ **「研修で教えた範囲だけで書く」制約**（2026-08-06改訂・§2参照） |

> **本命は P1 vs P2 ではなく P2 vs P3。** P1（雑）の出力は品質が低くならず「きれいな間違い」が出たため、品質での差が付かなかった（§4.1）。差が出るのは「**研修生が読めるコードかどうか**」で、それは規約とコンテキストを渡すかどうかで決まる。

対象は **課題1（Todo単体CRUD＋楽観ロック）→ 課題2（Tag追加・多対多）までフル**。

### 統制（守らないと実験が無意味になる）

**渡してよいもの / 絶対に渡してはいけないもの**（2026-08-06 訂正）

| | 対象 | 理由 |
|---|---|---|
| **渡してよい** | `todo-app-api` の **develop ブランチ**（＝研修生が clone する枠） | 研修生に渡っているものなので、渡さないと**研修の条件を再現できない** |
| **渡してはいけない** | **`answer-sample*` ブランチ**（`review\todo-app-api` に存在）、研修生の提出ブランチ `task/NNNNNN-氏名` | **模範解答＝配布厳禁の秘匿物**。読ませたら実験が無意味になるだけでなく、扱いとして不適切 |
| **渡してはいけない** | `MyWork\code\02-api\00.todoApiDemo\todo-app-api` の完成実装と `lecture_*` の段階別デモブランチ | 講義デモ＝実質の答え |

> `review\todo-app-api` に `lecture_*` は存在しない（デモ側のリポジトリにある）。review 側の答えは **`answer-sample*`**。ブランチ名で判断すること。

### ⚠ AIは渡していない情報源を勝手に探しに行く（2026-08-06 実測）

P2 の実行中、AIが **`C:\aevic_dev\review\docs\todo-app-api-docs\04.開発資料 / 05.講義資料 / 06.参考資料` を自分から探して読みに行った**。P2 には渡していない資料（コーディングガイド＝P3の材料、講義資料）である。

**原因**: `~/.claude/settings.json` の `permissions.additionalDirectories` に `C:\aevic_dev\review` が入っている（`bootstrap.ps1` が設定）。**このマシンのどのセッションからも review が読める。**

**より深刻な経路**: `review\todo-app-api` の `.git` には **`answer-sample*`（模範解答）** がある。`git show answer-sample:<path>` で**答えに到達できる**。

**対策（3層。上ほど確実）**

1. **`~/.claude/settings.json` の `additionalDirectories` を実験中だけ外す**（キー名を `_additionalDirectories` などに変えて無効化 → 実験後に戻す）。**これが唯一確実な手段**
2. **実験ディレクトリに `.claude/settings.json` を置き `permissions.deny` で塞ぐ**（`Read(//c/aevic_dev/**)` ／ `Documents/aevic` ／ `Documents/MyWork` ／ `Bash(git:*)`）。deny は allow に優先するはずだが、**Bash 経由の読み取りまで完全には塞げない**
3. **実験ディレクトリに `CLAUDE.md` を置いて範囲を明示**（「ここに置かれているものが渡された情報のすべて。足りなければ探さず報告せよ」）。協力的なエージェントには効くが強制力はない

**実行後は必ずログを検査**し、範囲外の読み取りがあればその試行は汚染として扱う（記録シートに明記）。

> **P1 は汚染されていない**と判断できる。AIが作ったテーブルは `todos`（`title` 200文字 / `description` 1000文字）で、実際の設計書の `todo`（`title` 30文字 / `content` 100文字）と**フィールド名も桁数も違う**。設計書を読んでいれば一致していたはず。

### この事象は研修設計上のリスクでもある（重要）

**研修生がAIを使うと、模範解答への経路が構造的に開く。**

研修生は `todo-app-api` を clone しており、その `origin` には **`answer-sample*` がある**。`git fetch origin answer-sample` → `git show` で、AIは答えを取得できる。**研修生が意図しなくても、AIが「参考になりそうな情報」として自分から取りに行きうる**（今回まさにそれが起きた）。

→ 対策は `03_研修環境とガードレール.md` §8 へ。

- 出力先はスクラッチパッドなど作業用の場所。**会社リポジトリには書き込まない。**
- develop を起点にする場合も、**別の場所にコピーして作業させる**（元の clone を汚さない）。
- やり取りの回数と、詰まった箇所をその都度メモする。**後から思い出せない。**

## 2. プロンプト文面（そのまま使う）

### P1（雑）

```
Spring Boot と MyBatis で Todo 管理の REST API を作ってください。
PostgreSQL を使います。
```

以上。追加の質問には答えず、AIが勝手に決めたことをそのまま観察する。

### P2（研修生と同じ）＝ **develop の枠を起点にする**

**先に `develop` を別の場所にコピーしてから、そこで作業させる**（元の clone を汚さない）。

```
このリポジトリは新人研修の課題用テンプレートです（todo-app-api の develop ブランチ）。
空のフォルダに実装を埋めて、Todo 管理の REST API を完成させてください。
添付の設計書に従ってください。
- 要件定義書
- DB定義書
- DDL
- OpenAPI（API設計書）
- エラー設計書（APIエラーコード）

既存のコードとフォルダ構成を確認し、それに合わせて実装してください。
設計書に書かれていないことは、書かれていないと明示してください（勝手に決めないでください）。
```

2つの仕掛けがある。

- **「設計書に書かれていないことは明示してください」** — 勝手に決めた箇所を自己申告させると後の評価が楽になる。そして**申告漏れがあること自体が観察対象**（P1 では桁数もエンドポイントも黙って決めた）
- **「既存のコードとフォルダ構成を確認し、それに合わせて」** — これだけで規約を察するかを見る。**P3 で明示するまでもなく守れるなら、それが最大の発見**

> **P2 で最も注意して見るところ**（実験の分岐点）
> ① **`core/exception` の既存機構を使うか、`@RestControllerAdvice` で自作するか。** P1 では自作した。枠を見せれば使うか
> ② **`record` / Lombok / Stream を使ってしまうか。** pom に Lombok 依存があるので使う余地がある
> ③ 7層（controller/entity/form/logic.service/mapper/query/queryCondition）に素直に従うか、勝手に簡略化するか
> ④ Flyway のマイグレーションSQL が無いことに気づいて指摘するか、勝手に作るか、Docker で立てようとするか
> ⑤ Javadoc を書くか（既存の完成品クラスには付いている）

### P3（コンテキスト厚め）＝ **研修生が読める形に縛る**

> **2026-08-06 改訂の理由**: P1 の出力は「破綻はないが、**研修生が習っていない書き方**」で埋まっていた（record / Lombok / stream / `@RestControllerAdvice` / PATCH / domainオブジェクト）。**読めないコードにレビュー演習は成立しない。**
> そこで P3 を「規約を渡す」から「**既存コードベースの規約に合わせさせる**」に変える。これは SES 現場で最も必要になる能力そのもので、「コンテキストをどう与えるか」の実演にもなる。

P2 の材料に加えて、コーディングガイド・レビュー観点・CheckStyle設定・**下記の「研修の流儀」**を渡す。

```
（P2と同じ指示に続けて）
このコードは新人研修の教材です。研修生が読めることが最優先です。
研修で教えていない機能は使わないでください。次の制約を厳守してください。

【使わないもの（研修生が未習）】
- record 型は使わない。DTO/Form/Entity は class ＋ getter/setter で書く
- Lombok は使わない（@Data / @Builder / @RequiredArgsConstructor を含む）
- Stream API は使わない。ループは for 文で書く
- PATCH は実装しない（未習のため）
- 独自の domain オブジェクトを作らない

【従うもの】
- DI は明示的なコンストラクタで書く（@RequiredArgsConstructor を使わない）
- 全メソッドに @param / @return 付きの Javadoc を書く（既存の完成品クラスと同じ体裁で）
- エラーは core/exception の既存機構を使う。
  該当する ErrorCodes を選んで NotFoundException 等を throw するだけにする
- DBは既存の PostgreSQL に接続する。Docker で新しく立てない
- コーディングガイド（添付）／CheckStyle（添付の todo_checks.xml）に違反しないこと

実装後、上記の制約を守れているか自己点検して報告してください。
```

> **P3 の制約は P2 の結果を見てから削る。** develop の枠を渡せば自動的に決まるものが多い。
> - パッケージ構成・エラーハンドリング機構・Spring Boot のバージョン → **develop に現物があるので明示不要になるはず**（P2 で守れていれば P3 から削る）
> - `record` / Lombok / Stream / PATCH / Javadoc → **既存コードに「無い」ことからは察しにくいので、明示が必要な可能性が高い**（「使っていない」は「使うな」と読めない）
>
> **この切り分けが実験の一番の収穫になる。** どこまでが「見せれば伝わる」で、どこからが「言わないと伝わらない」か。これは配属後に既存コードベースへ入るときにそのまま効く知識で、**ツールが変わっても陳腐化しない**（`00_前提と目的.md` §5）。

**この文面自体が実験対象**。守れるか、どこで破るかを見る。破った箇所が「AIに既存規約を守らせる難しさ」の教材になる。

> **P3 で確かめたいこと**: P2（読めないコードが出る）と P3（読めるコードが出る）の差が、**「研修生が読めるか読めないか」という形で劇的に出るか**。出れば、これが社長の「プロンプト差」要望に対する最良の答えになる（P1 vs P2 の差は薄かった）。

## 3. 段階と、各段階での判断

### Stage 1 — 生成させる

3条件 × 課題1 → 課題2 でコードを書かせる。

**記録するもの**: やり取りの回数 / 体感の所要時間 / 生成されたファイル数と層構造 / AIが質問してきたか、黙って決めたか / 詰まった箇所

**この段階で分かること**: AIが研修生の課題をどこまで書けるか。**研修生の1か月が何分で溶けるか。**

**判断すること**: プロンプト品質で差が出たか。差が出なければ、社長の「プロンプトによる差」案は**教材として薄い**（＝濃くしなくてよい根拠になる）。差が出れば教材になる。

---

### Stage 2 — 読んで評価する ★案Aの核心

生成物を、研修生と同じ道具で評価する。

| やること | 使うもの |
|---|---|
| 要件充足の確認 | 要件定義書の項目を1つずつ○× |
| レビュー観点を当てる | `02_API研修_2か月目\04_補足\` の既存観点 |
| 静的解析 | CheckStyle（`todo_checks.xml`）、SonarLint |
| 破綻箇所の特定 | 特に **MyBatis の XML（`resultMap`/`<collection>`）／楽観ロック（versionカラム）／バリデーション／エラーコードの対応** |

**この段階で分かること**: **AIがどう間違えるか。** 案Aの演習（欠陥探し）が成立するかは、ここで判明する。

**判断すること**: 見つかった欠陥が、研修生が自分のレビュー観点で見つけられる種類か。見つけられないほど巧妙／逆に自明すぎるなら、案Aの組み方を変える必要がある。

**成果物**: 「AI出力の欠陥カタログ」初版。これが案Aの教材の芯になる。

> **予想（外れたら記録する）**: 課題1は素直な題材なのでAIはかなり書ける。差が出るとしたら**課題2の MyBatis XML マッピング**。`<collection>` を使った1対多の取得は学習データが薄いはずで、動くが N+1 になる、あるいは重複行を潰せていない、といった形で崩れるのではないか。

---

### Stage 3 — 動かす（やるか未定）

Maven build → PostgreSQL 準備 → 起動 → Postman/ThunderClient で叩く。

**この段階で分かること**: **「動くけど間違っている」を実証できるか。** 案Aの一番強い教材はこれ。静的に読んで分かる欠陥より、動いてしまう欠陥の方が怖いと伝わる。

**判断すること**: Stage 2 の結果を見てから決める。Stage 2 で十分に欠陥が出ていれば、動作確認は研修の中でやらせればよく、講師の事前検証としては不要かもしれない。

---

### Stage 4 — テストを書かせる（やるか未定）

AIに DBUnit + JUnit のテストを書かせ、**そのテストが何を保証しているかを評価する**。

**この段階で分かること**: AIが書いたテストは通るが、**カバーしているのが自明なケースだけ**ではないか。3か月目の必須課題（テスト仕様書でのケース洗い出し）と直結する論点。

**判断すること**: 研修に入れるか。ここは「AI研修」ではなく「3か月目のテスト課題の改訂」の話になる可能性もある。

## 4.1 P1 の結果と考察（2026-08-06）

**実施条件**: Sonnet / auto モード / やり取り1回 / 約30分 / 出力 `C:\Users\kanamaru\Desktop\実験\p1\todo-api`

### 講師の所感

> 予想通り。指示していない内容は実装してこない。ただ**破綻がなく、研修で扱うコードよりむしろモダンで読みやすい**。プロジェクト構成もシンプルでよい。
> **ただし「要件を入れないとこうなりますよ」という体感が、意味のあるものかどうか怪しい。**

### 良かった点（指示していないのに満たしていた）

3層分離／**DTO と Entity の分離**（DTOは record）／**トランザクション境界が Service の public メソッド**（クラスに `@Transactional(readOnly=true)`、更新系に `@Transactional`）／**`SELECT *` を使わずカラム列挙**／`resultMap` を明示／ポートを 5433 にして既存の 5432 との衝突を回避。
**既存レビュー観点の主要項目を、指示なしで半分程度満たしている。**

### 致命的な欠陥3つ（研修生が自力で気づけない類）

| # | 欠陥 | なぜ効くか |
|---|---|---|
| 1 | **pom が Spring Boot 4.0.7**（研修は 3.4.1）。依存も `spring-boot-starter-webmvc` など Boot 4 系の名前 | 「**AIは最新版で書く**」の実証。研修環境に持ち込むと壊れ、原因が自力で分からない |
| 2 | **テストが `contextLoads()` 1本だけで実質空**。動作確認は curl で軽く叩いただけ（下記ログ参照）。それでもAIは「テストを作成し実行しました」と報告する | 「テストが通った」を信じてよいかという論点。**Stage 4 の主題が P1 で既に観測できた** |
| 3 | `@ExceptionHandler(Exception.class)` が **`ex.getMessage()` をそのままレスポンスに返す** | 情報漏洩の典型。DB由来のメッセージやテーブル名が外に出る |
| **4** | **POST のレスポンスと、直後に GET したレスポンスの `createdAt` が一致しない**（下記） | **「動くけど間違っている」の実物。** 200が返るので動作確認では気づかない |

### 欠陥④の実物（curl ログ・2026-08-06）

```
POST /api/todos → {"id":2, ... "createdAt":"2026-08-06T16:37:39.9289138", ...}
GET  /api/todos → [{"id":2, ... "createdAt":"2026-08-06T16:37:39.928914", ...}]
                                                              ↑ 7桁 → 6桁に丸められている
```

**原因**: `create()` が `TodoResponse.from(todo)` で**メモリ上のオブジェクトをそのまま返している**（DBを読み直していない）。Java の `LocalDateTime` はナノ秒（9桁）精度だが、PostgreSQL の `timestamp` はマイクロ秒（6桁）精度なので、**保存時に丸められる**。

**なぜ教材として優れているか**:
- **動作確認では絶対に気づかない**。200 が返り、値も一見同じ
- クライアントが POST のレスポンスを信じて等価判定・キャッシュすると壊れる
- **楽観ロック（version）と組み合わさるともっと厄介**になる ＝ 2か月目の講義内容に直結
- 難易度が絶妙。並べて「どこが違う？」と聞けば研修生でも気づけるが、言われなければ気づかない

→ **この欠陥は Stage 3（動かす）でしか見つからなかった。** 静的に読むだけでは出てこない。**Stage 3 の価値が実証された**ので、講師の事前検証としても研修の演習としても入れる価値がある。

### AIが自分でトラブルシュートした痕跡

curl ログを見ると、AIは日本語が化ける問題に対し「shell のエンコーディングかアプリのエンコーディングかを切り分ける」ためにJSONを**UTF-8ファイルに書き出して `--data-binary` で投げ直している**。

→ **研修生が詰まるはずの箇所を、AIが自力で回避してしまう**という観察。文字化けは1か月目からの定番の詰まりどころだが、それを学ぶ機会が消える（`01_方向性の候補.md` §0「ジュニア育成モデルの崩壊」の具体例）。

その他: `updateCompleted` が SELECT を2回している（`getOrThrow` と `findById`）／Flyway ではなく `schema.sql` + `spring.sql.init.mode: always`／楽観ロックなし／`title VARCHAR(200)` 等を勝手に決定／エンドポイントが `/api/todos`。

### 予想の答え合わせ

- **的中**: 課題1は素直なのでAIはかなり書ける。MyBatis XML の破綻は課題2まで行かないと出ない（講師の観察も同じ）
- **外れ**: レビュー観点の充足度は想定より**高かった**。目立つ欠陥は少なく、**バージョン・空テスト・情報漏洩という「見えにくいところ」に集まっている**

### 最重要の発見: 「雑だと汚いものが出る」ではない

P1 で出たのは**質の低いコードではなく、質の高い「違うもの」**だった。要件を渡していないので tag も楽観ロックも作らないが、コード自体は破綻がなく読みやすい。

→ **「プロンプトが雑だと品質が落ちる」という筋書きは成立しない。** 成立するのは「**雑だと、きれいな間違いが出る**」という筋書き。そして**質が低ければ気づけるが、質が高くて要件と違うものは気づけない**ので、教訓としてはこちらの方が怖く、価値も高い。ただし伝え方が難しい。

→ **差を測る軸を「コード品質」から「要件充足」に変える必要がある。**要件定義書の項目を1つずつ○×で数えれば、P1 は半分も満たさないことが定量的に見える。品質で比べると差が出ない。

→ **P1 の位置づけを変える**: 「雑なプロンプトの悪い例」ではなく**「導入の驚き（30分でこれが出る）」用**に使い、プロンプト差の本命は **P2 vs P3**（要件は同じで、規約とコンテキストを渡すかどうか）に置く。
