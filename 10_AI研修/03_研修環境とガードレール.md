## 1. 結論から: 案Aなら環境構築はほぼ不要

研修生は**2か月目に自分で環境を構築している** — Maven、PostgreSQL、Postman/ThunderClient、CheckStyle、SonarLint、そして自分の `todo-app-api`。3か月目の最終週なら**まだ手元にある**。

→ **新しい環境を用意しない方がよい。** 1週間しかないのに環境構築で1日溶けるのが最悪の失敗。案Aは既存環境の上に載るので、追加で要るのは**AIのアカウントだけ**。これは案の選択理由としても効く（`01_方向性の候補.md` の比較表に無かった観点）。

## 2. 最低限そろえる3つ

### ① 法人契約のAIアカウント（これは譲れない）

**個人アカウントは不可。** 理由は3つ。

- 無料・個人プランは入力が**モデルの学習に使われる**設定がデフォルトのことがある。会社のコードを投げる場に使えない
- **監査ログが残らない**ため、誰が何を投げたか後から追えない
- メンバー管理・SSOがなく、退職・異動時に止められない

法人プラン（Team / Business / Enterprise 相当）なら、学習へのオプトアウト・監査ログ・メンバー管理が付く。**どのツールにするかは未定でよいが、「法人契約であること」は先に固めておく**。ライセンス数＝研修生数＋講師分。

> SES固有の注意: 研修で使う法人アカウントは**自社契約**。配属後に客先へ持ち込めるとは限らない（`01_方向性の候補.md` 案Bのリスク欄）。研修と現場は別、と最初に言っておく。

### ② 研修用のAI利用ルール（1枚）

**研修環境は実顧客データが存在しないのでリスクは実務より低い。** だから技術的なガードレールは薄くてよい。書くべきは4点だけ。

1. 投げてよいもの: 研修用リポジトリのコード、設計書、エラーメッセージ
2. 投げてはいけないもの: 実顧客データ、個人情報、他社から預かった資料、パスワード等の資格情報
3. 出力の扱い: そのままコミットしない。**自分が読んで理解したものだけ提出する**
4. 記録: 何を投げたかを残す（下記③）

> **本質はここではない。** 研修環境が緩いことより、**「現場はもっと厳しい」というギャップを教えること**が重要。金融系の調査結果（新人が自分の判断で好きなツールを使える確率はかなり低い／申請制・指定ツール限定・全面禁止の幅）を、そのまま材料にできる。

### ③ プロンプトログを残す運用（地味だが最重要）

**何を投げたかを研修生に記録させる。** 用途が3つある。

- **評価に使える** — 成果物だけ見ても、AIに何をどう頼んだかは分からない
- **教材になる** — 「このプロンプトだとこう出た」の実例が集まる。しかも毎期更新される（陳腐化対策）
- **現場で効く** — 申請制の現場で「何に使ったか」を説明できる習慣になる

提出物には**どこをAIに書かせたかを明記させる**。大阪大学の評価指針でも「執筆・実装プロセス（下書き・編集履歴）の提出」で本人の理解度を可視化する方法が挙げられている。

## 3. コードベースをどう与えるか（設計の核心）

3つの選択肢がある。

| | 与えるもの | 得られる経験 | 実務らしさ |
|---|---|---|---|
| **ゼロから** | 仕様書だけ | プロンプト品質の差が最も出る。社長の要望に直結 | 低い |
| **既存に追加** | 自分の `todo-app-api` に機能追加させる | **既存コードをAIに読ませる／コンテキストの与え方** | 高い |
| **壊れたコードを直す** | 講師が用意した問題のあるコード | レビュー・リファクタリング。**実務で一番多い形** | 最も高い |

3つ目は研修生の未経験領域（`MyWork/03_研修カリキュラム.md` §6「既存の大きなコードを読んで直す経験」）を突けるが、**講師が「わざと問題のあるコード」を作る手間**がかかる。1週間では欲張り。

### 推し: 「自分が書いたコード vs AIが書いたコード」の比較

研修生は**同じ仕様書から自分で書いた `todo-app-api` を持っている**（課題1・2まで、`task/課題番号-氏名` ブランチ）。同じ仕様をAIに渡して出力を並べれば、

- 環境準備はゼロ
- 比較対象が**自分のコード**なので刺さり方が違う（他人のコードでは他人事になる）
- 「自分の1か月」と「AIの数分」の差が定量的に見える
- レビュー観点を当てる相手が2つあるので、**自分のコードの欠陥も同時に見つかる**（AIだけを叩く会にならない）

最後の点が効くと思う。AIの欠陥だけ探すと「AIは使えない」で終わりかねないが、自分のコードにも同じ観点を当てれば「**どちらも間違える。だからレビューが要る**」という着地になる。

## 4. 他社は何を揃えているか（調査から）

| 主体 | 環境 | ガードレール |
|---|---|---|
| **LINEヤフーコミュニケーションズ** | — | **全社共通テストを100点で合格してから、AIアシスタントの利用を許可**。段階1でAIの確率的性質（なぜ間違えるか）を理解させてから触らせる |
| **ZOZO**（新卒ハンズオン2時間） | **Cloud9 でクラウドIDEを統一**し、OpenAI API / Bedrock を叩かせた | — |
| **ベリサーブ** | Dify | **AI倫理・プロンプト設計を第1フェーズに置く**（4〜7月の4フェーズ構成の入口） |
| **サイバーエージェント**（25新卒） | AWS 等、既存のインフラ研修と共通 | e-Learning で構造化出力・Function Calling 等10項目を先に |
| **GMOペパボ** | Cursor / 各種エージェント | — |

**共通して見えるのは3つ**。①法人アカウント前提 ②**触らせる前に「なぜ間違えるか」を理解させる** ③環境は既存のものを使うか、クラウドIDEで統一する。

**LINEヤフーコミュニケーションズの「テスト合格後に利用可」は、そのまま真似できる形**。研修の初日に、AIの確率的性質とルールを教えてから解禁する、という順序にすれば、ガードレールが研修の一部になる。

## 5. 現時点の推奨

1. **法人契約のAIアカウントだけ先に確保する**（ツール選定は後でよいが、契約形態は先に固める）
2. **開発環境は2か月目のものをそのまま使う。** 新規に用意しない
3. **初日に「なぜ間違えるか」＋利用ルールをやってから解禁**（LINEヤフーコミュニケーションズ方式）
4. **プロンプトログと「どこをAIに書かせたか」の提出を必須にする**
5. 題材は**自分が2か月目に書いたコードとの比較**。講師が新規に教材コードを作らない

## 6. アカウントが揃わなかった場合のフォールバック

アカウントは会社が用意する見込み（2026-08-06 時点）。用意されなければ実装できる幅が狭まり、その分**研修の作成は楽になる**が意義も薄くなる。

重要なのは、**案Aはアカウント数に対して優雅に劣化する**という性質。

| アカウント | できること |
|---|---|
| 研修生全員分＋講師 | フル実施。**プロンプト差の体験**（社長要望）ができる。各自が自分で投げて差を見る |
| **講師の1人分だけ** | **案Aの核心は実施できる。** 講師が事前に生成した出力（P1/P2/P3の3種）を教材として配り、研修生はレビューと欠陥探しに集中する。プロンプト差は「講師が実演し、出力を配って読ませる」形に縮む |
| ゼロ | 成立しない |

→ **社長への提案では「アカウント数がプロンプト差演習の実施可否を決める」と紐付けて伝える。** 社長が入れたいと言っている部分が、まさにアカウントを要求する部分なので、そこが判断の接点になる。

→ 案B（ツール習熟型）は全員分のアカウントが無いと**そもそも成立しない**。この点も案の比較材料になる（`01_方向性の候補.md` の比較表に追記済みの観点）。

## 8. ⚠ 模範解答への経路が構造的に開く（2026-08-06 発見・要対応）

**AIは「渡していない情報源」を自分から探しに行く。** P2 の実験中、渡していない `04.開発資料`（コーディングガイド）や `05.講義資料` を勝手に読みに行った（`02_実験` §統制）。

研修に置き換えると、こうなる。

| 経路 | 中身 |
|---|---|
| 研修生の clone の `origin` | **`answer-sample*` ブランチ＝模範解答**。`git fetch origin answer-sample` → `git show` で取得できる |
| 他の研修生の `task/NNNNNN-氏名` ブランチ | 同期の提出物。丸写しできる |
| 過去期の `feature/*` ブランチ | 過去の完成品 |

**研修生が意図しなくても、AIが「参考になりそうな情報」として自分から取りに行く。** 今回まさにそれが起きた。**カンニングが事故として発生しうる。**

### 対策の候補

| | 対策 | 効果 | 手間 |
|---|---|---|---|
| **A** | **`answer-sample*` を別リポジトリに分離する**（研修生が clone するリポジトリから模範解答を物理的に消す） | **根本解決** | 中。会社側リポジトリの構成変更が要る |
| B | 研修生の環境に `CLAUDE.md` を置き、参照範囲を明示（`.git` の他ブランチを見るな、と書く） | 協力的なエージェントには効く。強制力なし | 小 |
| C | `.claude/settings.json` の `permissions.deny` で `Bash(git:*)` を塞ぐ | git を使う課題なので**現実的でない** | 小 |
| D | **プロンプトログの提出を必須にし、事後に検査する**（§2③） | 抑止力になる。事故は検知できる | 小 |
| E | 研修中だけ `origin` を外す／読み取り専用のミラーを使わせる | 効くが、PR提出の動線が壊れる | 中 |

**推奨は A ＋ D。** 模範解答を物理的に分離するのが本筋で、それまでは D（ログ提出＋事後検査）で凌ぐ。B は無料なので併用してよい。

> これは **AI研修だけの問題ではない**。既存の3か月カリキュラムでも、研修生が個人的にAIを使えば同じことが起きる。**現在「AI禁止」で成立している安全性が、解禁と同時に崩れる**という構造。社長への提案でも触れておくべき論点。
