# AI研修の芯

> 更新: 2026-08-06 / ステータス: **現時点の結論（プレゼン用の骨格）**
> 根拠は `00_前提と目的.md`（制約と目的）／`01_方向性の候補.md`（探索の記録）／`02_実験_プロンプト差の検証.md`（P1〜P3の実測）。

---

## 目的（一文）

> ### AIで作ったものを、自分の名前で出せるようにする。

SES では客先に**自分の名前で**成果物を出す。AIが書いたものでも変わらない。

---

## 構成 — 二軸 ＋ 前提

**分け方の基準は「答えがあるかどうか」。** 性質が違うので、教え方も評価も変える。

| | 中身 | 答え | 教え方 | 評価 |
|---|---|---|---|---|
| **前提: ガバナンス** | 使ってよい形で使う | **明確にある** | **教える。覚えさせる** | ○×で測れる（理解度テスト） |
| **軸①: 経験** | AIを挟んだ開発フローを一周回す | ない（体感が目的） | **やらせる** | 成果物を出したか |
| **軸②: 検証** | 出せる状態にする | **出さない** | **問いを与えてフィードバックする** | プロセスを見る（測らない） |

**順番: ガバナンス → 経験 → 検証。**

---

## 前提: ガバナンス（答えがある）

**ここだけは答えが明確にあるので、先に教えて終わらせる。**

| | 中身 |
|---|---|
| 1 | **客先のルールを確認する**（申請制・指定ツール・全面禁止の幅がある） |
| 2 | **渡してはいけないものを渡さない**（客先コード・個人情報・資格情報。著作権とライセンスもここ） |
| 3 | **何を渡したか記録する**（申請制の現場で説明できる） |
| 4 | **AIに書かせた部分を PR で明示する**（チームのルールとして） |

**作法を破ると事故（取り返せない）。だから最初に置く。**
参考: LINEヤフーコミュニケーションズは**全社共通テストを100点で合格してからAI利用を許可**している。同じ形が取れる。

---

## 軸①: 経験 — AIを挟んだ開発フローを一周回す

**目的は「どんなものかイメージできるようになること」。**

3か月で習った開発フローを、**AIを挟んでもう一周**する。

```
設計書と既存コードを読む → 実装させる → 動かす → 直させる → 差分を見る → PRを出す
```

**コンテキストの重要性は、ここで自得させる。** 教える項目にしない。
一周回せば「渡す情報が足りないと使えないものが出てくる」ことは体で分かる。**教えると陳腐化する知識になるが、体感は残る。**

> 実験の裏付け: 同じプロンプトで、渡すファイルを2つ足しただけで出力が別物になった（`02_実験` §4.3）。
> ただし**わざと情報を抜いて失敗を見せる演習にはしない。**作為的で、AIが賢くなると成立しなくなる。

**これが「語れる経験」の実体。**「AIで既存システムに機能を追加し、出力を検証して自分の名前で出した」と言えるようになる。

## 軸②: 検証 — 答えを出さない

| | 問い |
|---|---|
| 5 | **何を任せたか把握しているか** — 勝手に決められた箇所を吐き出させる／`git diff` で変更範囲を見る |
| 6 | **正しいと言えるか** — 動かす／自分のテストケース一覧と突き合わせる。**動いた ≠ 正しい** |
| 7 | **どこまでやるかを独断していないか** — 「この範囲は自分で確認、この範囲はレビューを」と言える |

### なぜ答えを出さないか

- **講師側にも唯一の答えがない。**「どこまで検証すれば十分か」は現場・案件・リスクで変わる
- **答えを配ると思考停止する。** チェックリストを渡すと、それを埋めて終わりになる
- **配属後も自分で考え続けてほしい。** 基準は現場ごとに違う

**フィードバックはする。答えは用意しない。**（講師側の判断材料は既存のレビュー観点資料がある）

### この方針の注意点2つ

1. **「答えがない」ことを明示的に伝える。** 言わないと「結局どうすればいいのか」で不満が残る。
   → **「実務でも答えは与えられない。基準は現場ごとに違う。だから考え続ける」がメッセージそのもの。**
2. **検証だけを厚くすると「AIは信用できないから全部確認しろ」になる。** それでは実務で使えない。
   → 7（独断しない）を必ず入れる。**新人が判断すべきは「基準を持っている人に確認すること」**まで。

## 漏れの確認

**三層に収まるもの**

| 論点 | 収まる先 |
|---|---|
| ハルシネーション・嘘のAPI | 検証6 |
| 著作権・ライセンス | ガバナンス2 |
| 利用コスト・トークン | ガバナンス（節度）。新人には薄いので触れる程度 |
| 車輪の再発明（既存の仕組みを使わない） | 検証5 |
| バージョン不一致（AIは最新で書く） | 検証5 |
| コンテキストの与え方 | **経験の中で自得**（教える項目にしない） |
| ツールの操作 | 経験の中で触るだけ（**軸にしない**。半年で陳腐化する） |

**三層に入らないが伝えるもの（1つ）**

| | 扱い |
|---|---|
| **自分の成長を守る判断**（任せる／自分でやる） | **演習にならない**（本人の判断）。最後に一言で伝える。ただし面接で語れる強い材料。AIが賢くなるほど重要になる |

## この構成が崩れない理由

- **フェーズ非依存** — ツール操作・プロンプト技法・コンテキスト設計はいずれ陳腐化する。**ガバナンスと検証は陳腐化しない。経験は「一周回した」事実が残る**
- **失敗を仕込まない** — 正しく使った上で成立する
- **ツール非依存** — 伝え方は抽象、触るのは具体（Claude 等）。**「これはツール固有／これは普遍」をその場で言い分ける**
- **既存カリキュラムに接続** — Git（差分）／PR・レビュー（明示）／テスト仕様書からのケース洗い出し（突き合わせ）
- **AI禁止の現場でも残る** — 客先ルールの確認・仕様を読む力は、AIの可否と無関係

## 評価の設計（性質ごとに変える）

| | 何で測るか |
|---|---|
| ガバナンス | **理解度テスト**（100点合格制も可）。答えがあるので測れる |
| 経験 | **成果物**（動くものを出したか） |
| 検証 | **プロセスの提出**（何を確認し、何を疑ったか）＋発表。**正解との一致では測らない** |

---

## ここから詰めること

1. **期間** — 体験と作法なら 2〜3日で足る（1週間は薄まる）。社長判断
2. **目的の優先順位** — 雇われやすさ／技術力／プロモ。**目的が決まらないと各層の重みが決まらない**
3. 各項目の演習の形（何をやらせ、何を提出させるか）
4. ツールと契約
5. 日程への差し込み方
