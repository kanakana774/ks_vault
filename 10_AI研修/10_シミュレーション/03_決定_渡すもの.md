## 作業9 — 書き戻しの雛形

### `決定事項.md`（リポジトリのルートに置く。研修生が埋める）

```markdown
# 決定事項

設計書に書かれていなかったことのうち、決まったものを記録する。
まだ決まっていないものは Q&A票に残す（このファイルには書かない）。

| # | 決めたこと | 出所 | 理由・回答 |
|---|---|---|---|
|   |           | 自分の判断 / 確認済み（誰に） / 暫定（未決） |      |

## やってはいけないこと

-
```

**出所を分けて書く。** 「自分で決めた」と「確認して決まった」が混ざると、**段⑥のPRで説明できない**。

### ③に振った項目の聞き方

**丸投げにしない。見立てを添える。**

```
Tag を削除したとき、その Tag に紐づいている todo_tag の行はどうしますか。
- 一緒に削除する と思いますが、Todo 側の tags の件数が変わるので確認したいです。
- 設計書（要件定義・tag.yaml・プログラム設計）には記載がありませんでした。
```

**「どうすればいいですか」だけでは実務で通らない。** ①見立て ②理由 ③どこを見たか の3点を添える。

> `#` は**Q&A票の項目番号をそのまま使う**。**欠番が「自分では決められないと判断したもの」になる**ので、
> 何を渡していないかが一目で分かる。

### `CLAUDE.md` に足す1行

```markdown
実装の前に、リポジトリルートの `決定事項.md` を必ず読むこと。
```

**指示ファイルに判断は書かない。** 規約と仕様の決定は別物。

> claudeへ
> 形式は問わない（実務環境によって多様なので）と言いましたが、なるべく寄せては行きたいかなと思ってます。
> その観点で、決定事項として別ファイルに書き、それをclaude.mdにパスを張ってというのはどうなんでしょう？研修の形態的にやりやすいからというのはあると思いますが、この辺の微妙なニュアンスで実務でのAI開発の方法を勘違いされるのは困るので、少し考えたい。
>
> **→ この形は実務の定石なので、誤解される形ではありません。** 実務での対応はこう。
>
> | 実務の呼び名 | 中身 |
> |---|---|
> | **ADR**（Architecture Decision Record）／`docs/adr/` | 決定と理由を残すファイル |
> | 指示ファイル（`CLAUDE.md` / `AGENTS.md`）の作法 | **短く保ち、詳細は別ファイルへのリンクにする**（長いと守られなくなる） |
>
> **「指示ファイルを短く保って参照を張る」こと自体が実務の作法**なので、そこは寄せられています。
>
> **ただし研修都合が入っている点が1つあり、これは言葉にしておくべきです。** 実務では決定は**チケットのコメントか設計書の追記**に入ることが多く、決定ログという独立ファイルになるのは「新人が設計書を直す権限を持たない」という研修の形が影響しています。
> → **伝え方**: 置き場は現場ごとに違う（チケット・設計書・ADR）。**変わらないのは2つだけ** — **① 規約と決定を分ける** ／ **② AIに読ませる経路を用意する**。
>
> **なお「別ファイルにする」ことには、研修都合とは別の実務的な理由があります。**
> **設計書に直接書くと、上流が決めたことと自分が決めたことが混ざる。** 決定ログなら「**これは自分が決めた**」という出所が残り、段⑥のPRで説明する材料になり、独断かどうかの検証もできる。**ここは実務でも正しい理由。**

## 作業9（後半） — 受入条件を出させるプロンプト

```
設計書・決定事項.md・DoD.md を読んで、Todo と Tag、および両者の紐づけの
受入条件（何ができたら完成と言えるか）を洗い出してください。

- 実装はしないでください。受入条件だけを出してください。
- 各条件に「テストで判定できる / 目視でしか判定できない」の区別を付けてください。
- 設計書・決定事項・DoD に書かれていないことは、書かれていないと明示してください
  （勝手に決めないでください）。ただし 実装に影響するものだけ 挙げてください。
```

**`DoD.md` も渡す**（`09_配布物/DoD.md`）。DoDを渡さないと、AIは非機能の条件を出せない。

### 照合シート（研修生が埋める）

| 自分が渡したもの | 受入条件に入っているか | 入っていなければ |
|---|---|---|
| 決定事項 #1〜#10（1件ずつ） | ○／× | **渡し漏れか、AIの落としか** |
| DoD の各項目 | ○／× | 同上 |
| **上に無いのに自分が必要だと思うもの** | **足す** | ここが本人の付加価値 |

**正常系・境界値・異常系は書き写さない。** AIが出したものをそのまま使う。

## 作業10 — 計画を出させるプロンプト

```
設計書と 決定事項.md を読んで、Todo と Tag、および両者の紐づけを
実装する計画を立ててください。

- 実装はしないでください。計画だけを出してください。
- 設計書と決定事項に書かれていないことは、書かれていないと明示してください
  （勝手に決めないでください）。ただし 実装に影響するものだけ 挙げてください。

計画には次を含めてください。
1. 作業の順序
2. 触るファイルの一覧（新規作成／変更を区別する）
3. 各段階でどう動かして確かめるか
4. コミットの区切り
```

### 研修生に配るレビュー観点（5つ）

```
□ 層の順序（Entity→Mapper→Service→Controller）になっているか
□ 触るファイル一覧は妥当か。頼んでいないものが入っていないか
□ 設計書に無い判断が混ざっていないか
□ 確認方法（どう動かして確かめるか）が書かれているか
□ 後戻りできる単位に割れているか
```

**観点を渡さないと「はい」を押すだけになる。**
**承認するまで着手させない。**
