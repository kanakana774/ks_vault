## 作業9 — 書き戻しの雛形

### `決定事項.md`（リポジトリのルートに置く。研修生が埋める）

```markdown
# 決定事項

設計書に書かれていなかったことのうち、自分で決めてよいと判断したものを記録する。
確認が必要なものは Q&A票に残す（このファイルには書かない）。

| # | 決めたこと | 理由 |
|---|---|---|
|   |           |      |

## やってはいけないこと

-
```

> `#` は**Q&A票の項目番号をそのまま使う**。**欠番が「自分では決められないと判断したもの」になる**ので、
> 何を渡していないかが一目で分かる。

### `CLAUDE.md` に足す1行

```markdown
実装の前に、リポジトリルートの `決定事項.md` を必ず読むこと。
```

**指示ファイルに判断は書かない。** 規約と仕様の決定は別物。

## 作業10 — 受入条件の書式

```markdown
## <エンドポイント> の受入条件

### テストで判定できるもの
- 正常系:
- 境界値:
- 異常系:

### 目視でしか判定できないもの
- 不変条件（頼んでいないテーブル・ファイルを変えない）:
- 非機能（クエリの本数・外に出してはいけない情報）:
```

**3〜5行でよい。** 網羅性より、**2つに分けて書くこと**が目的。
**AIには渡さない。** 自分の手元に置き、段⑤で突き合わせる。

## 作業11 — 計画を出させるプロンプト

```
設計書と 決定事項.md を読んで、Todo と Tag、および両者の紐づけを
実装する計画を立ててください。

- 実装はしないでください。計画だけを出してください。
- 設計書と決定事項に書かれていないことは、書かれていないと明示してください
  （勝手に決めないでください）。ただし 実装に影響するものだけ 挙げてください。

計画には次を含めてください。
1. 作業の順序
2. 触るファイルの一覧（新規作成／変更を区別する）
3. 各段階でどう動かして確かめるか
4. コミットの区切り
```

### 研修生に配るツッコミ観点（5つ）

```
□ 層の順序（Entity→Mapper→Service→Controller）になっているか
□ 触るファイル一覧は妥当か。頼んでいないものが入っていないか
□ 設計書に無い判断が混ざっていないか
□ 確認方法（どう動かして確かめるか）が書かれているか
□ 後戻りできる単位に割れているか
```

**観点を渡さないと「はい」を押すだけになる。**
**承認するまで着手させない。**
