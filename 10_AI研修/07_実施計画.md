## Day 1 午後 — 経験①: 読む（**2026-08-06 再設計**）

> **旧案の問題**: 「AIに設計書を読ませて矛盾を挙げさせる」は、**教材に矛盾が残っていることに依存する**。矛盾は直すべきものであり、直せばこの演習は成立しない。わざと矛盾を仕込むのも本末転倒。
> **再設計**: 焦点を「矛盾」から **「空白」** に移す。**どんなに完璧な設計書にも、確認しないと決められないことは必ず残る。** これは直しても無くならない。

### 演習: 「実装する前に、確認しないと決められないこと」を洗い出す

| | 内容 | 時間 |
|---|---|---|
| 5 | 導入デモ: **何も渡さずにAIに作らせるとどうなるか**（講師実演） | 30分 |
| 6 | **AIに設計書と既存コードを読ませ、「この仕様で実装するとき、確認しないと決められないこと」を挙げさせる** | 60分 |
| 7 | **挙がったものを自分で読んで確認する** — ①本当に書かれていないか ②自分ならどう決めるか ③誰に確認すべきか | 90分 |

**提出物**: **確認事項リスト（Q&A票）** — 実務で配属直後に作るものそのもの。

> **なぜ空白なら持続するか**: 仕様をすべて書き尽くすことは原理的にできない。実験でも矛盾だけでなく**空白**が出た — 「Tag削除時に `todo_tag` をどうするか書かれていない」「path param が非数値のときの挙動が定義されていない」。**教材を直すと矛盾が消えて、空白が際立つ。**
> **狙いは変わらない**: AIは読解を代替しない。**読んだかどうかを暴く。** 挙がったものが本当に空白かは、自分で読まないと判断できない。
> **副産物**: 矛盾が残っていればここで出る。ただし**依存はしない。**

### 代替案: この半日を廃止する

「読む」を外して **1.5日版**（ガバナンス半日 ＋ 作る半日 ＋ 検証1日）にもできる。
判断材料: Day1午後は**コードを書かない**ので、研修としての手応えは薄い。ただし**配属直後の実務に最も近い**のもここ。

### ガードレール ★要判断

**実験と同じ問題が研修でも起きる。研修生の clone の `origin` には `answer-sample*`（模範解答）がある。**
AIは「参考になりそうな情報」を自分から取りに行く（実験で実証済み）。**カンニングが事故として発生しうる。**

| 案 | 内容 | 評価 |
|---|---|---|
| **A** | **`answer-sample*` を別リポジトリに分離する** | **根本解決。**会社側リポジトリの作業が必要 |
| B | `.git` なしの配布物を渡す | 確実だが **Day3 の PR 演習が死ぬ**。不可 |
| **C** | `CLAUDE.md` で参照範囲を明示 ＋ **プロンプトログ提出で事後検査** | 手間ゼロ。抑止と検知はできるが強制力なし |

**推奨: A が本筋。10月に間に合わなければ C で凌ぐ。**（`03_研修環境とガードレール.md` §8）

### auto の可否 ★要判断

**auto（全自動）は禁止し、ステップごとに承認させる。**

理由: **経験の目的は「開発フローをイメージできるようになること」。auto だと流れが見えない。**
実験では auto で一度も確認を挟まず完走した — 実装・起動・検証・後片付けまで全部。**成果物は出るが、何が起きたかは見えない。**

> 研修では「見せる」ことが目的なので、承認を挟ませる。実務で auto を使うかは配属後の判断。

**提出物**: 動く実装。

### 使う道具 — **全部3か月で習ったもの**

| 道具 | いつ習ったか | 何に使うか |
|---|---|---|
| `git diff` | **1か月目** | 頼んでいないファイルが変わっていないか |
| Postman / ThunderClient | **2か月目** | 動かして叩く |
| CheckStyle / SonarLint | **2か月目**（PR前必須） | 規約違反 |
| レビュー観点（N+1・Service層の責務・トランザクション境界・DTO/Entity分離・`SELECT *`禁止） | **2か月目** | 設計上の問題 |
| DBUnit + JUnit、テスト仕様書からのケース洗い出し | **3か月目** | AIに書かせたテストと自分のケース一覧を突き合わせる |
| **AIへの一文**（「勝手に決めた箇所を明示せよ」＋その報告を読む） | **新規。これだけ** | AIが黙って決めたこと |

> **新しく覚えるのは一文だけ。**あとは**今まで習った道具をAIの出力に当てるだけ。**
> これは研修生にとっても分かりやすく、**「3か月の学習が無駄にならない」というメッセージ**にもなる。

### 渡す「問い」（答えは用意しない）

```
□ AIは何を勝手に決めたか。それは正しいか。
□ 頼んでいないファイルが変わっていないか。なぜ変えたのか。
□ 動いた。では正しいのか。何をもって正しいと言うのか。
□ 自分のテストケース一覧のうち、AIの実装は何を満たしていないか。
□ このコードを客先のレビューに出して「なぜこう書いたのか」と聞かれたら答えられるか。
□ どこまで自分で確認し、どこからレビューを頼むか。その線をどこに引いたか。なぜそこか。
```

**提出物**: 検証記録 —「何を確認したか」「何を疑ったか」「判断できなかったこと」。

> **フィードバックはする。答えは配らない。**（講師の判断材料は既存のレビュー観点資料）
> **必ず言うこと**: 「実務でも答えは与えられない。基準は現場ごとに違う。だから考え続ける」
> **落とさないこと**: 新人が判断すべきは**「基準を持っている人に確認すること」まで**。全部確認しろ、で終わらせない。
