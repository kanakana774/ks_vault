## 1. 前提知識：データベースの物理的な保存構造
インデックスの話をする前に、PostgreSQLがデータをどう扱っているか（物理層）を理解する必要があります。

### 前提：PCの５大装置

![[Pasted image 20251219103603.png]]

### 1-1. データは「ページ」単位で管理される
*   **HDD/SSD上の実態:** データは連続したファイルではなく、**「ページ（Page）」**（またはブロック）と呼ばれる固定長（デフォルト8KB）の区画に分割されて保存されています。
*   **タプル（Tuple）:** ページの中に実際の行データ（タプル）が詰め込まれています。

### 1-2. メモリとディスクの関係（バッファマネージャ）
*   **直接ディスクは操作しない:** CPUはHDD上のデータを直接計算できません。
*   **共有バッファ（Shared Buffer）:** PostgreSQLは、必ずディスク上のページを**メモリ上**の「共有バッファ」にコピーしてから読み書きを行います。
*   **I/Oのボトルネック:**
    *   メモリアクセス：ナノ秒単位（爆速）
    *   ディスクアクセス：ミリ秒～マイクロ秒単位（メモリの数万倍～数十万倍遅い）
*   **結論:** DBのパフォーマンスチューニングとは、突き詰めると「**いかにディスクI/O（ページの読み込み）を減らすか**」の戦いです。


## 2. 課題：インデックスがない場合（Full Table Scan）
インデックスがない状態で、`SELECT * FROM users WHERE id = 50000;` を実行するとどうなるか。

1.  **シーケンシャルスキャン:** どこに `id=50000` があるか分からないため、先頭のページから最後のページまで、順番にディスクからメモリへ読み込みます。
2.  **CPU処理:** 読み込んだページ内の全タプルをチェックします。
3.  **無駄なI/O:** たった1行を見つけるために、関係のない数万ページ（数GBのデータ）をディスクから読み込むことになります。
    *   **結果:** 応答速度が著しく低下し、ディスク負荷でシステム全体が重くなる。


## 3. 解決策：インデックスの役割
インデックスとは、**「検索対象の値」と「その行がどのページのどこにあるか（ポインタ）」だけを抽出して整列させた別のデータ構造**です。

### 3-1. CTID（物理的な住所＝ポインタ）
*   PostgreSQLのインデックスは、データの**CTID**（Block Number + Offset Number）を持っています。
    *   例：「50番目のページの、3行目」という情報。
*   インデックスを使えば、ヒープ領域を全スキャンせず、**「ピンポイントで必要なページだけ」**をバッファに読み込めます。これは**ランダムアクセス**となります。


## 4. アルゴリズム別：なぜ速いのか？
代表的な「B-Tree」と「Hash」に絞って、その速さの理由を解説します。

### 探索アルゴリズムの紹介
#### 1. 線形探索 (Linear Search)
**「端から順番に全部見る」**

*   **仕組み**: データの先頭から最後まで、一つずつ「これですか？これですか？」と確認していく方法です。
*   **日常の例**: 整理されていない書類の山から、特定の1枚を探すとき。
*   **計算量**: $O(N)$
    *   データが100万件あれば、最悪100万回チェックします。
*   **SQLでの該当**: **フルテーブルスキャン (Full Table Scan)**
    *   インデックスがない場合、SQLは必ずこれを行います。データが増えれば増えるほど遅くなります。
*   **最適・不得意**:
    *   データが未整理ならこれしか方法がない。
    *   データ量が多いと致命的に遅い。

#### 2. 二分探索 (Binary Search)
**「半分に割って絞り込む」**

*   **仕組み**: データが**「順番に並んでいる（ソート済み）」**ことが前提です。真ん中のデータを見て、探している値より「大きいか、小さいか」で探す範囲を半分、また半分と捨てていきます。
*   **日常の例**: 紙の辞書や電話帳で名前を探すとき。真ん中を開いて「あ、行き過ぎた」と思って前のページの方を開く動作。
*   **計算量**: $O(\log N)$
    *   データが100万件あっても、約20回の確認で見つかります。線形探索と比べて圧倒的に速いです。
*   **SQLでの該当**: インデックスの基礎理論
    *   インデックスを作成するとデータが裏で整列され、この探索が可能になります。
*   **最適・不得意**:
    *   **最適**: データがソートされている場合。
    *   **不得意**: データの追加・削除をするたびに並べ替え（ソート）を維持するコストがかかる。

#### 3. 木構造探索 (B-Tree / B+Tree)
**「データベース検索のデファクトスタンダード」**

*   **仕組み**: 二分探索をさらに進化させたものです。一つの分岐点（ノード）から2つだけでなく、複数の枝分かれを持つ「木」のような階層構造を作ります。
    *   データベースはハードディスク(ディスク)に保存されるため、ディスクの読み込み回数を減らすように形状が平べったく（階層を浅く）最適化されています。
*   **日常の例**: 図書館の分類。 「3階(サイエンス)に行く」→「棚番号10(数学)に行く」→「本を探す」という階層的な絞り込み。
*   **計算量**: $O(\log N)$ （二分探索と同様に非常に速い）
*   **SQLでの該当**: **B-Treeインデックス (デフォルトのインデックス)**
    *   `CREATE INDEX` すると通常これが作られます。
*   **最適・不得意**:
    *   **最適**: 「＝（等価）」検索に加え、「＞、＜（範囲）」検索も得意。
    *   **不得意**: 複雑な構造なので更新処理（INSERT/UPDATE）が少し重くなる。

#### 4. ハッシュ探索 (Hash Search)
**「計算で場所を特定するピンポイント爆撃」**

*   **仕組み**: 探したいキーワードを「ハッシュ関数」という計算式に入れると、データの格納場所（アドレス）が直接返ってきます。探索というより「計算」です。
*   **日常の例**: 本棚に「本のID」ごとの専用ボックスが決まっていて、IDを見れば即座にどの箱かわかる状態。
*   **計算量**: $O(1)$
    *   データが100万件あろうが1億件あろうが、計算一発（1回）で見つけます。理論上最速です。
*   **SQLでの該当**: **ハッシュインデックス**
*   **最適・不得意**:
    *   **最適**: 「ID = 100」のような**完全一致**検索。
    *   **不得意**: 「価格 > 1000」のような**範囲検索が不可能**（計算結果がバラバラになるため）。また、ソート順も保持しません。


#### まとめ：どのアルゴリズムがいつ最適か？

| アルゴリズム     | 速度イメージ    | SQLでの用途        | 得意な検索                                               | 苦手な検索                              |
| :--------- | :-------- | :------------- | :-------------------------------------------------- | :--------------------------------- |
| **線形探索**   | 遅い (数に比例) | インデックスなし       | なし (強いて言えば全件取得)                                     | 全て                                 |
| **二分探索**   | 速い        | B-Treeの基礎理論    | -                                                   | -                                  |
| **B-Tree** | **速い**    | **一般的なインデックス** | **範囲検索 (BETWEEN, <, >)**<br>並べ替え (ORDER BY)<br>完全一致 | 特になし (万能型)                         |
| **ハッシュ**   | **最速**    | 特殊なインデックス      | **完全一致 (=)** のみ                                     | **範囲検索 (>, <)**<br>並べ替え (ORDER BY) |

---

### 4-1. B-Tree インデックス（デフォルト・汎用）
PostgreSQLの標準インデックスです。「バランス木」構造を持ちます。

*   **構造:**
    *   **Root/Branchノード:** データの範囲（例: 1〜50は左、51〜100は右）を持ち、階層構造になっています。
    *   **Leafノード:** 最下層。ここに実際のキー値とCTID（データへのポインタ）があります。
*   **なぜ速いのか（計算量 $O(\log N)$）:**
    *   **二分探索の応用:** 100万件データがあっても、木の深さ（階層）は通常3〜4階層程度に収まります。収まるように平らな木を作ります。
    *   つまり、100万件の中から1件を探すのに、たった3〜4ページのインデックスページを読むだけでデータの場所にたどり着けます。
*   **強み:** 等価検索（`=`）だけでなく、範囲検索（`<`, `>`, `BETWEEN`）やソート（`ORDER BY`）にも利用可能。

### 4-2. Hash インデックス
ハッシュ関数を用いたインデックスです。

*   **構造:**
    *   検索キーを「ハッシュ関数」に通し、ハッシュ値（32bit整数のバケットID）に変換します。
    *   そのバケットの中に、CTIDが格納されています。
*   **なぜ速いのか（計算量 $O(1)$）:**
    *   **計算一発:** 木構造のようにルートから辿る必要がありません。「値Aの場所はここ！」と数式で即座に算出されます。
    *   データ量が増えても、理論上アクセス速度は変わりません（衝突が少ない場合）。
*   **なぜB-Treeより限定的なのか:**
    *   **順序がない:** ハッシュ値は元の値の大小関係を保持しません。そのため、範囲検索（`>`）やソートには使えません。
    *   **等価検索専用:** `WHERE col = 'abc'` のような完全一致のみで最強の速度を出します。



## 5. まとめ：物理層から見た全体像フロー


1.  **クエリ受信:** `SELECT * FROM table WHERE id = 100`
2.  **プランナ判断:** 「全ページ読むよりインデックス見たほうがI/O少ないな」と判断。
3.  **インデックス走査（Index Scan）:**
    *   ディスク上の**インデックスページ**（軽量）を数ページだけ読む。
    *   `id=100` のCTID（住所）を取得（例: Page 55, Offset 2）。
4.  **ヒープアクセス（Heap Fetch）:**
    *   ディスク上の**データページ**（Page 55）**だけ**をピンポイントで読み込む。
5.  **結果返却:** 高速に応答。



## 6. おまけ：インデックスの代償（トレードオフ）
「じゃあ全部にインデックス貼ればいいの？」という問いへの回答です。

1.  **書き込みコスト増:**
    *   `INSERT/UPDATE/DELETE` を行う際、テーブル（ヒープ）だけでなく、付与されている**全てのインデックスも更新**しなければなりません。
    *   インデックスが多いほど、更新処理は遅くなります。
2.  **ディスク容量:**
    *   インデックス自体もディスク容量（ページ）を消費します。
3.  **メンテナンス:**
    *   頻繁な更新でインデックスも断片化するため、`REINDEX` や `VACUUM` などのメンテナンスが必要です。
