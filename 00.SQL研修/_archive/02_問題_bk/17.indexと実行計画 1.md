### **問題 1: 単一列インデックスとスキャン方式（Bitmap Scan）**
- **問題目的**: インデックス作成による効果と、PostgreSQL特有の「Bitmap Scan」の挙動（物理配置とI/O効率の関係）を理解する。

#### **準備（データ作成）**
まず以下のSQLを実行して、検証用データを準備してください。
```SQL
-- 既存データがある場合は削除（必要に応じて）
-- TRUNCATE TABLE customers;

-- ダミーデータを2万件追加（cityは1000種類、物理的に散らばるように生成）
INSERT INTO customers (customer_id, name, email, phone, city, join_date, membership_id)
SELECT
	gs AS customer_id,
	'Customer_' || gs AS name,
	'test@tmail.com' AS email,
	'090-1234-5678' AS phone,
	'City_' || (gs % 1000) AS city, -- 1000種類の都市名（例：City_1, City_1001...と散らばる）
	NOW() AS join_date,
	1 AS membership_id
FROM
	GENERATE_SERIES(1, 20000) AS gs;
```

#### **問題**
1. `city` 列にインデックスがない状態で、`city = 'City_1'` の顧客を検索するクエリの実行計画を確認してください。
2. `city` 列に単一列インデックス `idx_customer_city` を作成してください。
3. インデックス作成後、再度同じクエリの実行計画を確認してください。どのようなスキャン方式が表示されますか？また、なぜその方式が選ばれたのか考察してください。

```SQL
-- 1. インデックスなしでの確認
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM Customers WHERE city = 'City_1';

-- 2. インデックス作成
CREATE INDEX idx_customer_city ON Customers (city);

-- 統計情報を更新（オプティマイザが正しい判断をするために必須）
ANALYZE customers;

-- 3. インデックスありでの確認
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM Customers WHERE city = 'City_1';
```

#### **解答例と解説**

**1. インデックス作成前**
*   **出力例**: `Seq Scan on customers ...`
*   **解説**: 全件走査（シーケンシャルスキャン）。条件に合う行を探すために、テーブルの先頭から最後まで全てのページを読み込みます。データ量に比例して遅くなります。

**2. インデックス作成後**
*   **出力例**:
```SQL
	"QUERY PLAN"
	"Bitmap Heap Scan on customers  (cost=4.44..67.26 rows=20 width=63) (actual time=0.135..0.157 rows=20 loops=1)"
	"  Recheck Cond: ((city)::text = 'City_1'::text)"
	"  Heap Blocks: exact=20"
	"  Buffers: shared hit=20 read=2"
	"  ->  Bitmap Index Scan on idx_customer_city  (cost=0.00..4.44 rows=20 width=0) (actual time=0.083..0.083 rows=20 loops=1)"
	"        Index Cond: ((city)::text = 'City_1'::text)"
	"        Buffers: shared read=2"
	"Planning:"
	"  Buffers: shared hit=16 read=1"
	"Planning Time: 0.588 ms"
	"Execution Time: 1.791 ms"
```
**3. なぜ「Index Scan」ではなく「Bitmap Heap Scan」なのか？**
この実行計画は2段階で処理されています。

1.  **Bitmap Index Scan (下段)**:
    *   インデックス `idx_customer_city` だけを読み、条件に合う行の**位置情報（TID）**を探し、メモリ上に「ビットマップ（地図）」を作成します。
    *   ここではまだテーブル本体のデータは読みません。
2.  **Bitmap Heap Scan (上段)**:
    *   作成されたビットマップに従ってテーブル本体（Heap）からデータを取得します。
    *   **重要**: 通常の `Index Scan` は見つかった順にデータを読みに行きますが、今回は対象データ（City_1）が「1件目、1001件目、2001件目...」と**物理的に離れた場所に散らばっています**。
    *   そのままアクセスするとディスクのヘッドがあちこちに移動（ランダムアクセス）して遅くなるため、PostgreSQLは**「物理的に近い順にアクセス順序をソート」してからまとめて読み込む** `Bitmap Heap Scan` を選択しました。これによりI/O効率が最適化されます。
    * Heap Blocksは実際に読み込んだページ数です。

### **問題 2: 複合インデックスと左側プレフィックス**
- **問題目的**: 複合インデックスの列の順番の重要性（左側プレフィックスの原則）を理解する。

#### **準備（データ作成）**
```SQL
-- ダミーデータを2万件追加
INSERT INTO products (product_id, product_name, category_id, price)
SELECT
	gs AS product_id,
	'product_' || gs AS name,
	(gs % 4) + 1,
	gs % 1000 AS price
FROM
	GENERATE_SERIES(101, 20000) AS gs;
```

#### **問題**
1. `Products` テーブルに `product_name` と `price` の複合インデックス `idx_product_name_price` を作成してください（`product_name` が先頭）。
2. 以下の3つのクエリについて実行計画を確認し、インデックスが使われるか確認してください。
    *   a) `product_name = 'product_101' AND price > 100`
    *   b) `product_name = 'product_101'`
    *   c) `price > 10000`

```SQL
CREATE INDEX idx_product_name_price ON Products (product_name, price DESC);

ANALYZE products;

-- a) 両方指定
EXPLAIN SELECT * FROM Products WHERE product_name = 'product_101' AND price > 100;
-- b) 先頭列のみ指定
EXPLAIN SELECT * FROM Products WHERE product_name = 'product_101';
-- c) 2列目のみ指定
EXPLAIN SELECT * FROM Products WHERE price > 10000;
```

#### **解答例と解説**

*   **a) 両方指定**: **Index Scan**
    *   インデックスがフル活用されます。まず `product_name` で場所を特定し、その範囲内で `price` をチェックできるため高速です。
    * また、`product_name` の一意性が高く（カーディナリティが高い）、ヒットする行数が極端に少ない（今回の場合は1件）ため、最もオーバーヘッドの少ない Index Scan が選ばれたと思われます。
*   **b) 先頭列のみ**: **Index Scan**
    *   使われます。辞書で「最初の文字」だけ分かっている状態と同じで、インデックスのソート順を利用して検索可能です。
*   **c) 2列目のみ**: **Seq Scan (インデックス不使用)**
    *   **左側プレフィックスの原則**: 辞書で「2文字目が 'a' の単語」を探すのが大変なのと同様、先頭列（`product_name`）の条件がないと、インデックスの並び順を利用できないため、全件走査になります。

### **問題 3: カバリングインデックス (Index Only Scan)**
- **問題目的**: テーブルへのアクセスを完全に省略する「Index Only Scan」の効果と、`INCLUDE` 句の使い方を理解する。

#### **準備（データ作成）**
```SQL
INSERT INTO orders (order_id, customer_id, order_date, status)
SELECT
	gs AS order_id,
	gs AS customer_id, -- customer_idを一意にする
	NOW() AS order_date,
	'dummy' AS status
FROM
	GENERATE_SERIES(1, 20000) AS gs;
```

#### **問題**
1. `customer_id = 101` の注文の `order_id` と `order_date` を取得するクエリを考えます。
2. 検索条件(`customer_id`)だけでなく、取得したい列(`order_id`, `order_date`)もカバーするインデックスを作成してください。
3. 実行計画を確認し、「Index Only Scan」になっていることを確認してください。

```SQL
-- カバリングインデックス作成 (INCLUDE句を使用)
CREATE INDEX idx_orders_covering ON Orders (customer_id) INCLUDE (order_date, order_id);

-- 実行計画確認
EXPLAIN SELECT order_id, order_date FROM Orders WHERE customer_id = 101;

ANALYZE orders;

-- 実行計画確認
EXPLAIN SELECT order_id, order_date FROM Orders WHERE customer_id = 101;
```

#### **解答例と解説**

*   **出力例**: `Index Only Scan using idx_orders_covering ...`
*   **解説**:
    *   **Index Only Scan**: クエリが必要とする全てのデータ（`customer_id`, `order_date`, `order_id`）がインデックスの中にコピーとして存在しています。
    *   そのため、インデックスを見るだけで結果を返せます。テーブル本体（Heap）を見に行く「ブックマークルックアップ（ランダムアクセス）」が完全に発生しないため、究極的に高速なアクセス方法です。
    *   PostgreSQLの `INCLUDE` 句を使うと、検索キーではないが付加情報として持たせたいカラムを効率的にインデックスに追加できます。

### **問題 4: 関数インデックス**
- **問題目的**: カラムに関数を適用すると通常のインデックスが効かなくなることと、その対策を理解する。

#### **問題**
1. `product_name` を小文字にして検索するクエリ `WHERE LOWER(product_name) = 'smartwatch'` を実行します。
2. 既存の `idx_product_name_price`（先頭が product_name）があるにも関わらず、Seq Scanになることを確認してください。
3. `LOWER(product_name)` に対する関数インデックスを作成し、改善されるか確認してください。

```SQL
-- 1. Seq Scanになることを確認
EXPLAIN SELECT * FROM Products WHERE LOWER(product_name) = 'product_101';

-- 2. 関数インデックス作成
CREATE INDEX idx_product_name_lower ON Products (LOWER(product_name));

-- たぶんこれないとbitmapscanとかになるが、商品名は1つしかないのでindexscanが正しく、統計情報を更新してもらわないとそれにならないかも
analyze Products;

-- 3. Index Scanになることを確認
EXPLAIN SELECT * FROM Products WHERE LOWER(product_name) = 'product_101';
```

#### **解答例と解説**

*   **解説**:
    *   B-Treeインデックスは「元の値」順に並んでいます。`LOWER()` などの関数を通すと、元の並び順とは関係ない値になるため、DBMSはインデックスを使えません。
    *   **関数インデックス**: 計算結果（小文字化した値など）をあらかじめ計算してインデックスに格納しておく機能です。これにより、複雑な条件でも高速化が可能になります。

### **問題 5: JOINと実行計画 (Nested Loop)**
- **問題目的**: JOINのアルゴリズム（特にNested Loop）がどのような時に選ばれるか理解する。

#### **問題**
以下のクエリの実行計画を確認してください。Customers（データ少・絞り込みあり）と Orders（データ多・インデックスあり）を結合します。

```SQL
EXPLAIN ANALYZE
SELECT
    c.name,
    o.order_id
FROM
    Customers c
JOIN
    Orders o ON c.customer_id = o.customer_id
WHERE
    c.city = 'City_1'; -- 絞り込み条件
```

#### **解答例と解説**

*   **出力例**: `Nested Loop ...`
*   **解説**:
    *   **Nested Loop Join (NLJ)**: プログラミングの「二重ループ」と同じ動きです。
        1.  外側ループ（Outer）：`Customers` から `City_1` の人を抽出（今回は約20件）。
        2.  内側ループ（Inner）：抽出された20件の各 `customer_id` を使い、`Orders` テーブルのインデックスを引く。
    *   **なぜ選ばれたか**: Outer側の行数が少なく、Inner側に効率的なインデックスがある場合、NLJは最速です。逆に、Outer側の行数が数万件になると、ループ回数が膨大になるため、DBMSは `Hash Join` や `Merge Join` に切り替えます。

---

```SQL
"QUERY PLAN"
"Nested Loop  (cost=4.73..145.56 rows=20 width=18) (actual time=0.071..0.152 rows=20 loops=1)"
"  ->  Bitmap Heap Scan on customers c  (cost=4.44..67.26 rows=20 width=18) (actual time=0.063..0.091 rows=20 loops=1)"
"        Recheck Cond: ((city)::text = 'City_1'::text)"
"        Heap Blocks: exact=20"
"        ->  Bitmap Index Scan on idx_customer_city  (cost=0.00..4.44 rows=20 width=0) (actual time=0.044..0.044 rows=20 loops=1)"
"              Index Cond: ((city)::text = 'City_1'::text)"
"  ->  Index Only Scan using idx_orders_covering on orders o  (cost=0.29..3.90 rows=1 width=8) (actual time=0.003..0.003 rows=1 loops=20)"
"        Index Cond: (customer_id = c.customer_id)"
"        Heap Fetches: 0"
"Planning Time: 0.325 ms"
"Execution Time: 0.183 ms"
```

#### 1. 実行計画の詳細説明

実行計画は「内側（インデントが深い方）」から「外側」へ、そして「上」へと読んでいきます。

##### **Step 1: Customersテーブルの絞り込み (Bitmap Scan)**
まず、`WHERE c.city = 'City_1'` の条件で `Customers` テーブルから対象行を探しています。

1.  **`Bitmap Index Scan on idx_customer_city`**
    *   インデックス `idx_customer_city` を使い、`city = 'City_1'` に該当する行の位置情報（TID）を取得します。
    *   ここではまだテーブルのデータ本体（Heap）にはアクセスせず、「どのページのどこに行があるか」という地図（ビットマップ）を作ります。
2.  **`Bitmap Heap Scan on customers c`**
    *   作成された地図を使い、実際に `Customers` テーブルのデータにアクセスします。
    *   **Recheck Cond:** 条件が合っているか再確認し、必要なカラム（`name`, `customer_id`）を取得します。
    *   **Heap Blocks: exact=20:** 該当する20行を取得するために、物理的に20ブロック（ページ）を読み込みました。データ生成のロジック（`gs % 1000`）により、該当データが物理的にバラバラに散らばっているため、20行のために20ブロック読む必要があったことがわかります。

##### **Step 2: Ordersテーブルとの結合 (Index Only Scan)**
次に、見つかった `Customers` の行（20行）に対して、`Orders` テーブルを結合します。

*   **`Index Only Scan using idx_orders_covering on orders o`**
    *   結合条件 `o.customer_id = c.customer_id` を満たすデータをインデックス `idx_orders_covering` から探します。
    *   **Index Only Scan:** ここが重要です。必要な情報である `order_id` がインデックスの `INCLUDE` 部分に含まれているため、**`Orders` テーブル本体（Heap）を見に行く必要がありません。** インデックスを見るだけでデータが揃います。
    *   **Heap Fetches: 0:** テーブル本体へのアクセスが0回であることを示しています。
    * `"  ->  Index Only Scan using idx_orders_covering on orders o  (cost=0.29..3.90 rows=1 width=8) (actual time=0.003..0.003 rows=1 loops=20)"`
      左側の駆動表`Customers`一行ごとに、右側の`Orders`をindex検索する×20回
	    - **loops=20:** 確かにこの処理は **20回** 実行されています（左側の行数が20行だから）。
		- **rows=1:** しかし、1回の実行あたり **1行** しかヒットしていません（全行見ていない証拠です）。
		- **Index Only Scan:** 「全行走査(Seq Scan)」ではなく「インデックス検索」を使っています。

##### **Step 3: 結合の実行 (Nested Loop)**
最後に、上記2つの結果を合わせます。

*   **`Nested Loop`**
    *   外側のループ（`Customers` の結果20行）を1行ずつ回し、その都度内側（`Orders` のインデックス検索）を実行します。
    *   左側の行数が少ない（20行）ため、このループ処理は一瞬で終わります。

---

#### 2. なぜこの計画が選択されたのか？

PostgreSQLのオプティマイザがこの計画を選んだ理由は、主に以下の3点です。

##### **理由①：高い選択率（Selectivity）によるNested Loopの採用**
*   全20,000行のうち、`city = 'City_1'` に該当するのは20行（0.1%）だけです。
*   左側（駆動表）の行数が極端に少ない場合、巨大なハッシュテーブルを作る「Hash Join」や、ソートが必要な「Merge Join」よりも、単純にループを回す「Nested Loop」の方が圧倒的に低コストだからです。

##### **理由②：データが散らばっているため Bitmap Scan を採用**
*   単なる `Index Scan` ではなく `Bitmap Heap Scan` が選ばれました。
*   データ生成条件 `gs % 1000` により、`City_1` のデータはテーブル全体に飛び飛び（物理的に離れた場所）に存在します。
*   通常の `Index Scan` だと「インデックス→テーブル」「インデックス→テーブル」とランダムアクセスが多発しますが、`Bitmap Scan` は「読むべき場所をリストアップしてソートしてからテーブルを見に行く（シーケンシャルに近いアクセスにする）」ため、I/O効率が良いと判断されました。
    *   ※行数が極端に少ない（20行）ため、通常のIndex Scanとコスト差は僅差ですが、物理配置を考慮してBitmapが勝った形です。

##### **理由③：カバリングインデックスによる Index Only Scan**
*   `Orders` テーブルへのアクセスに `idx_orders_covering` が使われています。
*   このインデックスは `(customer_id) INCLUDE (order_date, order_id)` と定義されています。
*   クエリで必要な `o.order_id` がインデックスに含まれているため、オプティマイザは「わざわざ重いテーブル本体を見に行かなくても、インデックスだけで仕事を終えられる」と判断し、最も高速な **Index Only Scan** を選択しました。

#### **まとめ：パフォーマンスチューニングのワークフロー**

実務で「クエリが遅い」と言われたら、以下の手順で調査しましょう。

1.  **現状把握 (`EXPLAIN ANALYZE`)**:
    *   推測ではなく、必ず事実を確認します。
    *   `Seq Scan` が出ていないか？ `rows` の予測と実際(`actual`)に大きなズレがないか？
2.  **インデックス検討**:
    *   検索条件(`WHERE`)、結合条件(`JOIN`)、ソート(`ORDER BY`)に使われる列にインデックスはあるか？
    *   **複合インデックス**: 左側プレフィックスを守れているか？
    *   **関数適用**: 列に関数を使っていないか？
3.  **スキャン方式の評価**:
    *   **Bitmap Scan**: データの散らばりを考慮してくれている証拠。悪くない。
    *   **Index Only Scan**: 最高のパフォーマンス。頻出クエリなら狙う価値あり。
4.  **統計情報の更新 (`ANALYZE`)**:
    *   データが増減したのに実行計画がおかしい場合は、統計情報が古い可能性があります。
