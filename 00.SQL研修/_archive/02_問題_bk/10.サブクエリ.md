## 問5について補足

**同率（タイ）の扱いを含めて「順位」に基づいた抽出を行う場合、ウィンドウ関数を使うのがベスト（現代のSQL標準）**です。

単純な `LIMIT 3` や `TOP 3` では、「3位が複数人いた場合に誰かが漏れてしまう」という問題が発生するため、業務要件としては不正確になることが多いです。

以下に、「同率順位」の扱いに合わせた2つのベストな書き方（`DENSE_RANK` と `RANK`）を提示します。

### 1. 【推奨】順位を詰める書き方（DENSE_RANK）
「1位、2位、2位、**3位**」のように、**同率がいても順位番号を飛ばさずにトップ3グループを取得したい場合**はこちらです。
（例：オリンピックの表彰台のように、銀メダルが2人いても、次は銅メダルという考え方）

```sql
WITH OrderStats AS (
    -- まず注文ごとの支払合計額を計算
    SELECT
        order_id,
        SUM(amount) AS sum_amount
    FROM
        payments
    GROUP BY
        order_id
),
RankedOrders AS (
    SELECT
        order_id,
        sum_amount,
        -- 同率がいても順位を飛ばさない（1, 1, 2, 3...）
        DENSE_RANK() OVER (ORDER BY sum_amount DESC) as ranking
    FROM
        OrderStats
)
SELECT
    ranking,
    order_id,
    sum_amount
FROM
    RankedOrders
WHERE
    ranking <= 3
ORDER BY
    ranking, order_id;
```

**結果のイメージ:**
もし金額が `1200, 1200, 1000, 800` だった場合、**4件すべて**がヒットします。
*   1位: 1200
*   1位: 1200
*   2位: 1000
*   3位: 800


### 2. 順位を飛ばす書き方（RANK）
「1位、2位、2位、**4位**」のように、**同率がいる場合に順位を飛ばす場合**はこちらです。
（例：テストの順位などで、上位が詰まっていると3位が存在しなくなるケース）

```sql
WITH OrderStats AS (
    SELECT
        order_id,
        SUM(amount) AS sum_amount
    FROM
        payments
    GROUP BY
        order_id
),
RankedOrders AS (
    SELECT
        order_id,
        sum_amount,
        -- 同率がいると順位が飛ぶ（1, 1, 3, 4...）
        RANK() OVER (ORDER BY sum_amount DESC) as ranking
    FROM
        OrderStats
)
SELECT
    ranking,
    order_id,
    sum_amount
FROM
    RankedOrders
WHERE
    ranking <= 3;
```

**結果のイメージ:**
もし金額が `1200, 1200, 1000, 800` だった場合、**3件**がヒットします。
*   1位: 1200
*   1位: 1200
*   3位: 1000
*   (4位: 800 は除外される)


### ウィンドウ関数を使わない場合（非推奨）
もし古い環境でウィンドウ関数が使えない場合、同率取得を実現するには以下のような非常に読みにくく重いクエリ（相関サブクエリ）を書く必要があります。**現代では避けるべき書き方**ではある。。。

```sql
SELECT
	p_main.order_id,
	SUM(p_main.amount) AS sum_amount
FROM
	payments p_main
GROUP BY
	p_main.order_id
HAVING
	-- 外側の行（注文ごとの合計金額＝SUM(p_main.amount)）より金額が高い注文の「distinctな金額の数」が3つ未満であればトップ3に入る
	(
		SELECT
			COUNT(DISTINCT sub_sum)
		FROM
			(
				SELECT
					SUM(amount) AS sub_sum
				FROM
					payments
				GROUP BY
					order_id
			) AS sub
		WHERE
			sub.sub_sum > SUM(p_main.amount)
	) < 3
ORDER BY
	sum_amount DESC;
```

### 結論
同率順位を考慮する要件であれば **`WINDOW関数` (CTE + RANK/DENSE_RANK) が唯一の正解** と言えます。シンプルに `LIMIT 3` を使うと、データ次第でランダムに結果が変わってしまう（同額のどちらが表示されるか保証されない）リスクあり。

## 問題6について補足

### 【推奨】ベストな書き方（ウィンドウ関数）
前の質問と同様、**「同率1位も含める」**なら、ウィンドウ関数（`RANK`）を使うのが、計算が1回で済み、可読性も高いため**ベスト**。

```sql
WITH ProductSales AS (
    -- 商品ごとの販売数を集計
    SELECT
        p.product_id,
        p.product_name,
        SUM(oi.quantity) AS total_qty
    FROM
        products p
        JOIN orderitems oi ON p.product_id = oi.product_id
    GROUP BY
        p.product_id,
        p.product_name
),
RankedSales AS (
    -- 販売数でランキング付け（同率は同じ順位に）
    SELECT
        product_id,
        product_name,
        total_qty,
        RANK() OVER (ORDER BY total_qty DESC) as rnk
    FROM
        ProductSales
)
SELECT
    product_id,
    product_name,
    total_qty
FROM
    RankedSales
WHERE
    rnk = 1; -- 1位（同率含む）のみ取得
```
これなら「最大値を求めるサブクエリ」を書く必要がありません。


### 【簡易版】同率を考慮しなくて良い場合
もし仕様が「とりあえず一番売れてるものを1つ出せばいい（同率の場合はどれでもいい）」であれば、これが一番シンプルで高速です。

```sql
SELECT
    p.product_id,
    p.product_name,
    SUM(oi.quantity) AS total_qty
FROM
    products p
    JOIN orderitems oi ON p.product_id = oi.product_id
GROUP BY
    p.product_id,
    p.product_name
ORDER BY
    total_qty DESC
LIMIT 1;
```


### 【重要】業務的な落とし穴（キャンセル注文）
今回のテーブル定義とデータを見ると、**「キャンセルされた注文 (Status = 'Cancelled')」** が含まれています。
単純に `OrderItems` だけで集計すると、**キャンセルされた注文の個数も「売れた」とカウントされてしまう。

データでは：
*   **Laptop (id:1):** 2個 (Order 1, 5)
*   **Novel (id:3):** 2個 (Order 1)
*   **T-shirt (id:4):** 3個 (Order 4) ← **キャンセル済み**

単純集計だと「キャンセルされたTシャツ」が1位になってしまいます。
「有効な売上」を集計したい場合は、`ORDERS` テーブルを `JOIN` してステータスを見る必要があります。

**キャンセルを除外した完成形（ウィンドウ関数版）:**

```sql
WITH ValidSales AS (
    SELECT
        p.product_id,
        p.product_name,
        SUM(oi.quantity) AS total_qty
    FROM
        products p
        JOIN orderitems oi ON p.product_id = oi.product_id
        JOIN orders o ON oi.order_id = o.order_id -- 注文ステータス確認のためJOIN
    WHERE
        o.status != 'Cancelled' -- キャンセルを除外
    GROUP BY
        p.product_id,
        p.product_name
),
RankedSales AS (
    SELECT
        product_id,
        product_name,
        total_qty,
        RANK() OVER (ORDER BY total_qty DESC) as rnk
    FROM
        ValidSales
)
SELECT * FROM RankedSales WHERE rnk = 1;
```

**結果:**
キャンセルを除外すると、Laptop(2個) と Novel(2個) が同率1位になります。この要件まで含めるかどうかが、SQL作成時の重要なポイントになります。

## 問 8：==相関サブクエリ==

平均より高い価格の商品だけを購入したことがある顧客の名前を取得してください

```SQL
SELECT
	C.CUSTOMER_ID,
	C.NAME
FROM
	CUSTOMERS C
WHERE
	NOT EXISTS ( -- 平均より低い価格の商品を買った履歴が存在しない
		SELECT
			1
		FROM
			ORDERS O
			INNER JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
			INNER JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
		WHERE
			O.CUSTOMER_ID = C.CUSTOMER_ID
			AND P.PRICE <= (
				SELECT
					AVG(PRICE)
				FROM
					PRODUCTS
			)
	);
```

==⇒ただこれだと一度も購入したことがない顧客も出てしまうので間違い。。。==


① NOT EXISTS + EXISTS

「平均以下の商品を買ったことがない」＋「少なくとも 1 回は購入している」

```SQL
SELECT C.customer_id, C.name
FROM Customers C
WHERE EXISTS ( -- 模範解答では一度も購入したことがない顧客も出てしまっているので、注文テーブルに存在してるか（＝購入履歴があるか）を条件に入れておく
    SELECT 1
    FROM Orders O
    JOIN OrderItems OI ON O.order_id = OI.order_id
    WHERE O.customer_id = C.customer_id
)
AND NOT EXISTS (
    SELECT 1
    FROM Orders O
    JOIN OrderItems OI ON O.order_id = OI.order_id
    JOIN Products P ON OI.product_id = P.product_id
    WHERE O.customer_id = C.customer_id
      AND P.price <= (SELECT AVG(price) FROM Products)
);
```

長所: 安全で意図が明確、実務でよく使われる
短所: サブクエリが 2 つありやや冗長

② MIN(price) を使う方法

「その顧客が買った商品の最小価格が平均より大きい」

```SQL
SELECT C.customer_id, C.name
FROM Customers C
WHERE (
    SELECT MIN(P.price)
    FROM Orders O
    JOIN OrderItems OI ON O.order_id = OI.order_id
    JOIN Products P ON OI.product_id = P.product_id
    WHERE O.customer_id = C.customer_id
) > (SELECT AVG(price) FROM Products);
```

長所: すっきりして読みやすい
短所: 「購入が 1 件もない場合 → MIN() = NULL → 比較不可」で自動的に除外される（逆にこれが利点に）

③ HAVING + 集約（JOINとGROUP BYで解決する方法）

顧客ごとにまとめてから判定する方法。

```SQL
SELECT O.customer_id, C.name
FROM Orders O
JOIN Customers C ON O.customer_id = C.customer_id
JOIN OrderItems OI ON O.order_id = OI.order_id
JOIN Products P ON OI.product_id = P.product_id
GROUP BY O.customer_id, C.name
HAVING MIN(P.price) > (SELECT AVG(price) FROM Products);
```

長所: 集計ベースのレポートなどと組み合わせやすい
短所: JOIN が多く、全件集計するのでパフォーマンス的にはやや重い

⇒joinで解決するとサブクエリの課題にならないので今回はNGかな

④ NOT IN（非相関サブクエリで書いてしまう）

平均以下を買った顧客を除外する方法。

```SQL
SELECT C.customer_id, C.name
FROM Customers C
WHERE C.customer_id NOT IN (
    SELECT O.customer_id
    FROM Orders O
    JOIN OrderItems OI ON O.order_id = OI.order_id
    JOIN Products P ON OI.product_id = P.product_id
    WHERE P.price <= (SELECT AVG(price) FROM Products)
);
```

長所: シンプルで短い
短所: サブクエリ結果に NULL が含まれると全件返らなくなる（危険）
実務では非推奨（NULL 安全性のため）
⇒ただ、customer_idはpkなのでnullにはならないから問題ないのでは？

```SQL
SELECT C.customer_id, C.name
FROM Customers C
WHERE C.customer_id NOT IN (
    SELECT O.customer_id
```

実務観点での推奨順位

1. パターン ①（EXISTS + NOT EXISTS） … 一番安全で意図も明確
2. パターン ②（MIN 比較） … 条件が最小/最大値で表せるときはスッキリ
3. パターン ③（HAVING） … 集計レポート系の場面で便利
4. パターン ④（NOT IN） … 実務では避けるのが無難
