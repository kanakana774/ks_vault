「**全称量化**（すべての〜が条件を満たす）」という、SQLの中でも論理的落とし穴にはまりやすい典型的な例。
「平均以下の商品を買ったことがない（NOT EXISTS）」だけでは「一度も買ったことがない人」が含まれてしまうのが最大の罠。

### 解法パターン整理

#### 1. 【王道】EXISTS + NOT EXISTS
**論理：** 「高い商品を買ったことがある」かつ「安い商品を買ったことがない」

```SQL
SELECT C.CUSTOMER_ID, C.NAME
FROM CUSTOMERS C
WHERE EXISTS (
    -- ① 平均より高い商品を買ったことがある
    SELECT 1
    FROM ORDERS O
    JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
    JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
    WHERE O.CUSTOMER_ID = C.CUSTOMER_ID
      AND P.PRICE > (SELECT AVG(PRICE) FROM PRODUCTS)
)
AND NOT EXISTS (
    -- ② 平均以下の商品を買ったことがない
    SELECT 1
    FROM ORDERS O
    JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
    JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
    WHERE O.CUSTOMER_ID = C.CUSTOMER_ID
      AND P.PRICE <= (SELECT AVG(PRICE) FROM PRODUCTS)
);
```
*   **相関サブクエリ度：** ★★★（二重に使っており、練習として最適）
*   **特徴：** 「高いのを買った」かつ「安いのを買ってない」＝「高いもの**だけ**買った」というロジックが明確。
*   **未購入者の扱い：** ①がFalseになるため、自然に除外されます。

#### 2. 【スマート】スカラサブクエリでの比較 (MIN利用)
**論理：** 「その人が買った最も安い商品の価格」が「全体の平均価格」より高い。

```SQL
SELECT C.CUSTOMER_ID, C.NAME
FROM CUSTOMERS C
WHERE (
    SELECT MIN(P.PRICE)
    FROM ORDERS O
    JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
    JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
    WHERE O.CUSTOMER_ID = C.CUSTOMER_ID
) > (SELECT AVG(PRICE) FROM PRODUCTS);
```
*   **相関サブクエリ度：** ★★★
*   **特徴：** 非常に簡潔です。
*   **未購入者の扱い：** 購入履歴がない場合、`MIN(PRICE)` は `NULL` になります。SQLにおいて `NULL > 数値` の判定は `UNKNOWN` (False扱い) となるため、**追加の条件なしで未購入者を自動的に除外できます。** これが最もバグの少ない書き方と言えます。

#### 3. 【集合演算】EXCEPT を使う (PostgreSQL推奨)
**論理：** 「平均より高い商品を買った顧客IDの集合」引く「平均以下の商品を買った顧客IDの集合」。

```SQL
SELECT C.CUSTOMER_ID, C.NAME
FROM CUSTOMERS C
WHERE C.CUSTOMER_ID IN (
    -- 平均より高い商品を買った人
    SELECT O.CUSTOMER_ID
    FROM ORDERS O
    JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
    JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
    WHERE P.PRICE > (SELECT AVG(PRICE) FROM PRODUCTS)
    
    EXCEPT
    
    -- 平均以下の商品を買った人
    SELECT O.CUSTOMER_ID
    FROM ORDERS O
    JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
    JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
    WHERE P.PRICE <= (SELECT AVG(PRICE) FROM PRODUCTS)
);
```
*   **相関サブクエリ度：** ★☆☆ (非相関サブクエリ + 集合演算)
*   **特徴：** SQLらしい集合思考の解法です。PostgreSQLなど `EXCEPT` (OracleならMINUS) が使える環境では非常に可読性が高いです。
*   **未購入者の扱い：** 最初の集合（高い商品を買った人）に含まれないため、自動的に除外されます。

#### 4. 【非推奨】IN + NOT IN
**論理：** 「何か買ったことがある」かつ「安い商品を買った人リストに含まれない」。

```SQL
SELECT C.CUSTOMER_ID, C.NAME
FROM CUSTOMERS C
WHERE C.CUSTOMER_ID IN (
    -- 何か買ったことがある
    SELECT O.CUSTOMER_ID FROM ORDERS O
)
AND C.CUSTOMER_ID NOT IN (
    -- 安い商品を買った人リスト
    SELECT O.CUSTOMER_ID
    FROM ORDERS O
    JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
    JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
    WHERE P.PRICE <= (SELECT AVG(PRICE) FROM PRODUCTS)
    -- ※本来はここで WHERE O.CUSTOMER_ID IS NOT NULL が必要だがPKなので省略可
);
```
*   **相関サブクエリ度：** ★☆☆ (非相関サブクエリ)
*   **特徴：** 直感的ですが、`NOT IN` はNULLが含まれると全滅するリスクがあるため、実務では敬遠されがちです（今回はPKなので安全だが、教育上は注意が必要）。

 **NOT INにnullが含まれると、なぜ全滅するのか？**
```sql
SELECT
	*
FROM
	customers
WHERE
	name not IN ('Alice', '存在しない名前', NULL)
```
例えば上記は、`name <> 'Alice' and name <> '存在しない名前' and name <> null`と展開されるが、`name <> null`の結果がunknownとなり、and条件で結合されてる条件がtrueを返すことがなくなる。（＝全滅する）

```sql
SELECT
	*
FROM
	customers
WHERE
	name IN ('Alice', '存在しない名前', NULL)
```
この場合は、`name = 'Alice' or name = '存在しない名前' or name = null`と展開され、`name = null`はunknownとなるが、orで結合されてるため、他の評価式がtrueを返せばtrueとなる。

#### 5. 【参考】HAVING (集約)
**論理：** グルーピングして最小値を比較。

```SQL
SELECT C.CUSTOMER_ID, C.NAME
FROM CUSTOMERS C
JOIN ORDERS O ON C.CUSTOMER_ID = O.CUSTOMER_ID
JOIN ORDERITEMS OI ON O.ORDER_ID = OI.ORDER_ID
JOIN PRODUCTS P ON OI.PRODUCT_ID = P.PRODUCT_ID
GROUP BY C.CUSTOMER_ID, C.NAME
HAVING MIN(P.PRICE) > (SELECT AVG(PRICE) FROM PRODUCTS);
```
*   **相関サブクエリ度：** ☆☆☆ (HAVING句内の非相関サブクエリ)
*   **特徴：** 「結合と集約」の問題としては正解ですが、「相関サブクエリ」の出題意図からは外れます。

#### 6.【参考】(HAVING COUNT 条件付き集約)
##### パターンA：減点方式（NGな商品が0個）

```SQL
-- countのパターン
SELECT
    c.customer_id,
    c.name
FROM
    customers c
    JOIN orders o ON c.customer_id = o.customer_id
    JOIN orderitems oi ON o.order_id = oi.order_id
    JOIN products p ON oi.product_id = p.product_id
GROUP BY
    c.customer_id,
    c.name
HAVING
    -- 平均価格以下の商品数が0個であること
    COUNT(CASE WHEN p.price <= (SELECT AVG(price) FROM products) THEN 1 END) = 0;
```
##### パターンB：加点方式（全数 ＝ OKな商品数）

```SQL
-- countのパターン
SELECT
	c.customer_id,
	c.name
FROM
	customers c
	JOIN orders o ON c.customer_id = o.customer_id
	JOIN orderitems oi ON o.order_id = oi.order_id
	JOIN products p ON oi.product_id = p.product_id
GROUP BY
	c.customer_id,
	c.name
HAVING
	-- 顧客ごとに全ての明細と値段が平均以上の明細が同数の顧客のみ絞る
	COUNT(*) = COUNT(CASE WHEN p.price > (SELECT AVG(price) FROM products) THEN 1 END)
```

### まとめ・比較表

問題の意図（相関サブクエリの理解）と、エッジケース（未購入者）への対応を考慮した比較です。

| パターン    | SQL構文                   | 相関サブクエリ度 |   未購入者判定    | メリット                          | デメリット                         |
| :------ | :---------------------- | :------: | :---------: | :---------------------------- | :---------------------------- |
| **1**   | **EXISTS + NOT EXISTS** |  **高**   |   OK (手動)   | **意図が明確で安全**。「相関サブクエリ」の練習に最適。 | コードが長くなる。                     |
| **2**   | **WHERE (MIN > AVG)**   |  **高**   | **OK (自動)** | **最もスマート**。NULLの性質をうまく利用している。 | 初学者は「なぜ未購入者が消えるか」で混乱する可能性がある。 |
| **3**   | EXCEPT (集合演算)           |    低     |   OK (自動)   | 可読性が非常に高い。                    | 相関サブクエリの練習にならない。              |
| **4**   | IN + NOT IN             |    低     |   OK (手動)   | シンプル。                         | NULL安全性の問題があり、教育的推奨度が下がる。     |
| **5、6** | HAVING                  |    低     |   OK (自動)   | 分析クエリとして実用的。                  | JOINが主役になってしまう。               |

### 結論（模範解答としてどうするか）

**「相関サブクエリ」の問題として出題するなら、パターン2 (MIN利用) が最も美しく、かつパターン1 (EXISTS) が論理的に丁寧。かな？**

サブクエリの問題ということを鑑みて模範解答としての優先度は暫定で下記としますかね、、、

1.  **模範解答（スマートな解法）:** パターン2 (`WHERE (SELECT MIN...) > AVG`)
    *   解説：「未購入の場合はNULLになり、比較がFalseになるため除外される」点に触れると学びが深いです。
2.  **別解（論理的な解法）:** パターン1 (`EXISTS 高` AND `NOT EXISTS 低`)
    *   解説：「高いのを買った履歴があり、かつ、安いのを買った履歴がない」と分解して考えるアプローチ。

# おまけ（全称量化子について）


数学的な「集合論・論理学」の概念と、それを「SQL」という言語がどう実装しているか（あるいはしていないか）という観点でまとめる。
SQLは**「集合」**を扱う言語ですが、**「論理（Logic）」**の扱いにおいて少しクセがあります。特に「全称量化（すべて）」は、そのクセが最も強く出る部分です。

---

## 1. 概念の対比：論理学 vs SQL

まず、3つの基本的な概念が、SQLでどう表現されるかを見ます。

| 概念       |     記号      | 意味                | SQLでの表現                     |
| :------- | :---------: | :---------------- | :-------------------------- |
| **存在量化** |  $\exists$  | **「少なくとも1つ存在する」** | **`EXISTS`** <br> (直感的に書ける) |
| **全称量化** |  $\forall$  | **「すべてについて〜である」** | **直接的な構文なし** <br> (工夫が必要)   |
| **空虚な真** | $\emptyset$ | 「対象が0件なら、命題は真」    | SQLの実務要件と矛盾しやすい             |

SQLには `FOR ALL` がないため、全称量化を実現するには「論理学的アプローチ」か「集合論的アプローチ」のどちらかを使って翻訳する必要があります。

---

## 2. 全称量化への2つのアプローチ

「購入した商品が **すべて** 1000円以上である」という条件を例にします。

### A. 論理学的アプローチ（二重否定）
**定義：** $\forall x, P(x) \iff \neg \exists x, \neg P(x)$
（すべて $P$ である $\iff$ $P$ でないものは存在しない）

論理学の法則（ド・モルガン）をそのままSQLに翻訳する方法です。

*   **思考プロセス:**
    1.  「すべて1000円以上」と言いたい。
    2.  裏を返せば「1000円未満のものは**存在しない**」。
    3.  SQLにする: `NOT EXISTS (... < 1000)`
*   **SQLの特徴:**
    *   どんな条件（数値、文字列、複合条件）でも記述できる**万能型**。
    *   **「空虚な真」の問題:** 一度も購入していない（対象が空集合）場合、「1000円未満は存在しない」は **真 (TRUE)** になります。なので「購入履歴あり」という条件 (`AND EXISTS`) を追加して補正する必要があります。

### B. 集合論的アプローチ（部分集合・特徴量）
**定義：** $A \subseteq B$
（集合Aの要素は、すべて集合Bに含まれる）

集合そのものの「形」や「境界値」を評価する方法です。SQLはこれを得意とします。

*   **思考プロセス (境界値評価):**
    1.  集合 $A$ = {その人が買った商品の価格たち}
    2.  「すべての要素 $\geqq$ 1000」であるためには、「集合 $A$ の**最小値** $\geqq$ 1000」であれば十分である。
*   **SQLの特徴:**
    *   `MIN(price) >= 1000` や `COUNT(*) = SUM(case...)` を使う。
    *   **「空集合」の自動除外:** SQLの集約関数は、空集合に対して `NULL` を返します。`NULL >= 1000` は `UNKNOWN` (False扱い) になるため、**補正なしで「購入者のみ」に限定できます。**

---

## 3. 「空虚な真 (Vacuous Truth)」の罠

全称量化を扱う際、数学と実務で最も乖離するのがこの概念です。

*   **数学/論理学:** 「空集合のすべての要素は条件を満たす」＝ **TRUE**
    *   例：「私の飼っているユニコーンはすべてピンク色である」（一匹もいないので、反証できず真となる）
*   **SQL (ALL演算子):** 数学に忠実
    *   `PRICE > ALL (SELECT ... FROM 空集合)` は **TRUE** を返す。
*   **実務:** 「何も買ってない人は対象外にしたい」
    *   **FALSE** になってほしい。

このギャップを埋めるために、各アプローチで以下の対応が必要になります。

| アプローチ            | 空集合(0件)の判定       | 実務で必要な対応                   |
| :--------------- | :--------------- | :------------------------- |
| **`NOT EXISTS`** | **TRUE** (論理通り)  | 別途 `AND EXISTS` (履歴あり) を足す |
| **`ALL` 演算子**    | **TRUE** (論理通り)  | 別途 `AND EXISTS` を足す        |
| **集約 (`MIN`)**   | **NULL** (SQL独自) | 対応不要 (NULL比較でFalseになる)     |

---

# 4. まとめ：SQLにおける正解ルート

集合と論理の性質を踏まえると、SQLで全称量化を扱う際の「解法ルート」は以下のようになります。

### ルート①：数値・日付など「順序」がある場合
**→ 集合論的アプローチ (`MIN`, `MAX`) を使う**
*   理由： `NULL` による空集合の排除が、実務の直感（買ったことない人は除外）と一致してバグらないから。
*   クエリ：
    ```SQL
    WHERE (SELECT MIN(price) FROM ...) >= 1000
    ```

### ルート②：文字列・属性など「順序」がない場合
**→ 論理学的アプローチ (`NOT EXISTS`) を使う**
*   理由： 「最小のカテゴリ」などは定義できないため、集合の境界値を使えない。二重否定の論理で攻めるしかない。
*   クエリ：
    ```SQL
    WHERE NOT EXISTS (SELECT 1 ... WHERE category != 'Furniture')
      AND EXISTS (SELECT 1 ...) -- 空集合対策
    ```

### ルート③：`ALL` 演算子
**→ 使わない**
*   理由： 論理学的な「空虚な真」の挙動と、SQL特有の「NULLの伝播（3値論理）」の悪いところ取りになりやすく、危険だから。




# 簡単まとめ

exists = 1つは存在する
not exists = １つも存在しない
### この世の馬はすべて白い＝NOT（白ではない馬が存在する）＝白ではない馬が１匹も存在し`ない`
`この世の馬はすべて白い`という全称命題的な表現はSQLには存在しないので、`白ではない馬が少なくとも１匹は存在する`という反例（存在命題的）を`否定`することで表現する。⇒反例が一つも存在しない。
ただし、馬がこの世に存在しない場合も`白ではない馬が１匹も存在しない`は真となるため注意！

### この世のユニコーンはすべて白い＝NOT（白ではないユニコーンが存在する）＝白ではないユニコーンが１匹も存在し`ない`

`白ではないユニコーンが１匹も存在しない`はユニコーンが一匹も存在しない場合も真となる。

### 平均以上の買い物しかしたことがない＝NOT（平均以下の買い物をしたことがある）＝平均以下の買い物をしたことが`ない`


|         | 全称命題        | 存在命題の否定                       |
| ------- | ----------- | ----------------------------- |
| 命題      | この世の馬はすべて白い | NOT（白ではない馬が存在する）＝白ではない馬が存在しない |
| SQLでの表現 | 直接的な表現がない   | NOT　EXISTS                    |
