### 問題3：未発送注文の一括発送バッチ（分割コミット実装）
現在、システム内には「支払い済み（Processing）」の注文が複数あります。これらを一括で「出荷済み（Shipped）」に更新するバッチ処理 `proc_batch_shipping` を作成してください。

**仕様：**
1.  **対象抽出**: `ORDERS` テーブルから `STATUS = 'Processing'` の注文をすべて抽出する。
2.  **ループ処理**: 抽出した注文を1件ずつループで処理する。
3.  **更新内容**: 
    *   `SHIPMENTS` テーブルに新規レコードを作成（Status: 'In Transit', Shipped_Date: 当日）。
    *   `ORDERS` テーブルの `STATUS` を 'Shipped' に更新。
4.  **分割コミット**: **1件処理が終わるたびに `COMMIT` を実行**してください。

#### 体験の手順

このプロシージャを実行して、挙動を確認しましょう。
##### 1. 事前データの確認
現在、`STATUS = 'Processing'` の注文は ID 7 と ID 13 です。
```sql
SELECT order_id, status FROM orders WHERE status = 'Processing';
-- 結果： 7, 13
```
##### 2. プロシージャの実行
```sql
CALL proc_batch_shipping();
```

**実行時の出力ログ（イメージ）：**
> NOTICE: 注文ID: 7 の発送処理に成功しました。
> WARNING: 注文ID: 13 でエラーが発生しました。この件をスキップします。エラー: ID:13で予期せぬエラーが発生しました！

##### 3. 結果の確認
ここが**「手戻りがない」ことを確認する重要ポイント**です。

```sql
SELECT order_id, status FROM orders WHERE order_id IN (7, 13);
```

| order_id | status | 備考 |
| :--- | :--- | :--- |
| 7 | **Shipped** | **成功！COMMITされたので変更が残っている** |
| 13 | **Processing** | **失敗。この件だけ元の状態に戻っている** |

#### 解説：なぜこの処理が重要なのか

1.  **長時間ロックの回避**:
    100万件のデータを一つの `BEGIN...COMMIT` で処理すると、その間ずっとテーブルにロックがかかり、他のユーザーが操作できなくなります。1件ずつ、あるいは1,000件ずつ COMMIT することで、ロックをこまめに解放できます。

2.  **リスタート（再送）の効率化**:
    もし1,000件中900件目でサーバーがダウンした場合、一括コミットだと1件目からやり直しになります。分割コミットしていれば、**「すでに Shipped になったものは飛ばして、900件目から再開する」**という運用が可能です。

3.  **注意点：プロシージャの呼び出し方**:
    `COMMIT` を含むプロシージャを呼び出すときは、**「呼び出し側でトランザクションを開始していないこと」**が条件です。
    （例：`BEGIN; CALL ...; COMMIT;` の中では実行できず、単独で `CALL` する必要があります）
