パッケージ導入における具体的な業務内容を、SQLの活用シーンとセットで深掘り。
この手の案件では、プログラム（C#やJava等）を直接書き換えるよりも、**「データベースの中身をどうにかする」**作業が圧倒的に多くなります。

---

### 1. 旧システムからのデータ移行（移行フェーズ）
最もSQLを酷使し、かつ重要な業務です。病院が以前使っていた古いシステムから、新しいパッケージにデータを移します。

*   **具体的な作業：**
    *   旧DBから「患者基本情報」「過去の病名」「アレルギー情報」などを抽出。
    *   パッケージ側のテーブル構造に合わせてデータを変換し、取り込む。
*   **SQLの使われ方：**
    *   **マッピング処理：** `CASE`文を多用します。
        *   例：旧DBで性別が「1:男, 2:女」だったものを、新DBの「M:Male, F:Female」に変換して`INSERT`する。
    *   **重複排除：** `GROUP BY`や`DISTINCT`、`ROW_NUMBER()`を使って、二重登録されている古いデータを整理します。
    *   **データクレンジング：** `TRIM`で余計な空白を消したり、`COALESCE`でNULLを空文字に置換したりして、インポートエラーを防ぎます。

### 2. 病院独自の統計・レポート作成（導入・運用フェーズ）
パッケージの標準機能では足りない「病院独自の集計」を求められた際に、SQLで対応します。

*   **具体的な作業：**
    *   「先月の診療科ごとの手術件数一覧」や「特定薬剤の投与患者リスト」などの帳票作成。
    *   経営層向けのデータ抽出。
*   **SQLの使われ方：**
    *   **複雑な結合（JOIN）：** 電カルのDBはテーブル数が数百〜数千あります。「患者テーブル」「受付テーブル」「オーダーテーブル」「病名テーブル」「医師マスタ」などを5枚も10枚も`LEFT JOIN`して1つの表を作ります。
    *   **集計関数：** `COUNT`, `SUM`, `AVG` などの集計はもちろん、期間を絞り込むための複雑な `WHERE` 句を書きます。
    *   **ビュー（VIEW）作成：** 頻繁に使う集計をSQLとして保存しておき、BIツール（グラフ表示ソフト）から呼び出せるようにします。

### 3. マスタ設定の流し込み（環境構築フェーズ）
病院ごとに異なる「数千種類の薬品」「検査項目」「セット入力（いつもの処方のセット）」を登録します。

*   **具体的な作業：**
    *   病院からExcelでもらったマスタ一覧を、DBに一括登録する。
*   **SQLの使われ方：**
    *   **一括更新（BULK INSERT/UPDATE）：** 画面から1つずつ登録すると数週間かかるため、SQLファイルを作成して一気に`INSERT`します。
    *   **整合性チェック：** `EXISTS` や `IN` を使って、「マスタに登録しようとしている薬品コードが、実は既に存在していないか」「参照先のコードが正しいか」を事前にチェックします。

### 4. 障害調査・データメンテナンス（保守フェーズ）
「画面にエラーが出る」「計算がおかしい」といった問い合わせに対し、裏側から調査します。

*   **具体的な作業：**
    *   ユーザーの操作ログを追い、どのタイミングでデータがおかしくなったか突き止める。
    *   プログラムのバグで汚れてしまったデータを正しい状態に修正する。
*   **SQLの使われ方：**
    *   **特定レコードの抽出：** `SELECT * FROM Orders WHERE PatientID = '12345' AND OrderDate = '2023-10-01'` のように、特定の患者の特定の瞬間のデータを抜き出します。
    *   **修正パッチの作成：** `UPDATE` 文を書きます。※一歩間違えると全患者のデータが書き換わるため、`WHERE` 句に主キーを指定し、事前に `BEGIN TRANSACTION` でロールバックできるようにしてから実行するような、慎重な作業が求められます。

### 5. なぜ「少しのカスタマイズだけ」という風潮なのか
あなたが聞いた「統一されたもので少しのカスタマイズ」という点は、SQLの仕事にこう影響します。

*   **「アドオン開発」がメインになる：**
    パッケージの心臓部（本体プログラム）はいじらせてもらえません。その代わり、**「パッケージからデータだけ抜いてきて別の画面（サブシステム）で表示する」**ような、SQLメインの周辺機能開発が仕事の中心になります。
*   **「パラメータ設計」が重要：**
    「プログラムを書き換える」のではなく、「DBの設定テーブル（フラグ）をSQLで `0` から `1` に変えることで、機能をON/OFFする」といった、設定値の管理が主なカスタマイズ手法になります。

### まとめ：この案件で求められるSQLレベル
*   単純な `SELECT / INSERT / UPDATE / DELETE` は当然。
*   **複数テーブルの複雑な `JOIN`**（外部結合、自己結合）。
*   **サブクエリや共通テーブル式 (WITH句)** を使った階層的なデータ抽出。
*   **実行速度を意識したクエリ作成**（数百万件のレセコンデータから瞬時に集計するため）。

「エンジニア」というよりは、半分「データアナリスト」や「DBA（データベース管理者）」に近いような動き方をイメージしておくと、ギャップが少ないかもしれません。



---

おっしゃる通り、本番DBを直接叩いて `UPDATE` や `DELETE` をするのは、エンジニアとしては「生きた心地がしない」作業ですよね。しかし、パッケージ導入や保守の現場では、どうしてもこれが必要になる場面があります。

不安に思われている「仕組み」や「ツールの実態」について、より現場に近い目線で解説します。

---

### 1. 手動更新のリスクヘッジはどうしているか？

「個人の裁量で `BEGIN TRANSACTION` してね」という放任主義な現場は、今の医療IT業界（特に大手）ではほぼありません。以下のような**「組織的な仕組み」**でミスを防いでいます。

*   **「本番作業手順書」の作成とダブルチェック：**
    実行するSQLを事前にテキストファイルに書き出し、別のベテランエンジニアが「この条件で本当に正しいか？」をレビューします。本番当日は、その**承認済みファイルをコピペするだけ**にします。
*   **検証環境（ステージング）でのリハーサル：**
    本番と全く同じデータ（または匿名化したデータ）が入った検証環境で、そのSQLを先に実行し、結果が正しいか（件数や内容）を1件ずつ確認します。
*   **エビデンス（証跡）の取得：**
    実行前に `SELECT COUNT(*)` で件数を確認し、実行後も `COUNT` を取って、ログをすべて保存します。
*   **新人の立ち位置：**
    新人がいきなり本番DBの更新権限をもらうことはまずありません。最初は「検証環境用のデータ作成SQLを書く」ことや「本番用の手順書を作成し、先輩にレビューしてもらう」ことからスタートします。数ヶ月〜1年ほどして、業務とデータの構造が完璧に理解できたと判断されてから、横で先輩が見守る中で本番実行ボタンを押す、という流れが一般的です。

### 2. 「もっとうまい仕組み」はないのか？

Web開発（RailsやDjangoなど）のような「マイグレーションツール」で自動化できない理由は、医療パッケージ特有の事情があります。

*   **「一品物」のデータ変換が多い：**
    A病院から移すデータとB病院から移すデータは、元々の形式がバラバラです。共通のプログラムで自動化しきれず、結局「SQL職人」がその病院専用の変換スクリプトを書くことになります。
*   **パッケージのバージョン管理：**
    パッケージソフト自体は、アップデート時に自動でテーブル定義を変える仕組みを持っていますが、**「中身のデータ（患者の病名など）を業務ロジックに合わせて微調整する」**のは、現場のエンジニアがSQLで書くしかないのが実態です。

### 3. クライアントツール（GUI）か、コマンド（CLI）か？

これは現場のセキュリティポリシーと、採用しているデータベースによります。

*   **よく使われるGUIツール：**
    *   **SQL Server (Microsoft) の場合：** `SQL Server Management Studio (SSMS)` がデファクトスタンダードです。非常に多機能で使いやすいです。
    *   **PostgreSQL の場合：** `pgAdmin` や `DBeaver` が使われます。
    *   **Oracle の場合：** `SQL Developer` など。
*   **現場のルール：**
    *   **開発環境：** GUIツールを自由に使い、テーブル構造を見ながら作業します。
    *   **本番環境：** セキュリティ上、GUIツールのインストールが禁止されている場合があります。その場合は、**「踏み台サーバー」と呼ばれる保守用サーバーにログインし、黒い画面（コマンドライン）からSQLファイルを読み込ませて実行**します。

### 4. 医療IT業界ならではの「慎重さ」

あなたが感じた「怖いな」という感覚は、医療ITエンジニアとして非常に大切です。

*   **ログを必ず残す：** どのGUIツールを使っても、「ログ出力（スプール）」機能を使って、自分が打ったコマンドとDBからのレスポンスを全てテキストに残します。
*   **SELECTで確認してからUPDATE：**
    `UPDATE patients SET name = '...' WHERE id = 100;` と打つ前に、
    まず `SELECT * FROM patients WHERE id = 100;` を実行して、「今からこの1件を変えるんだな」ということを目で見て確認する癖を徹底させられます。

### アドバイス
もし面談などで「SQLの作業に不安がある」と伝えるなら、**「手動での更新作業において、どのようなダブルチェック体制や手順書の運用をされていますか？」**と逆質問してみると良いですよ。
しっかりしたプロジェクトであれば、「うちは手順書を二重チェックして、検証環境で試してから本番に行くから大丈夫だよ」と教えてくれるはずです。

この慎重なプロセスを経験すると、**「絶対にミスが許されない環境での正確な作業スキル」**が身につくので、エンジニアとしての信頼性は爆上がりします。

ご指摘の通り、数百万件、数千万件というオーダーの医療データを扱う場合、通常の「1件ずつINSERTするSQL」では終わらなくなります。

現場で使われる**「大量データ処理の仕組み」**と**「高速化のテクニック」**を、よりエンジニア視点で詳しく解説します。

---

### 1. 「夜通しのデータ変換」はどう実装されているか？

単一のクエリを投げっぱなしにするのではなく、**「バッチ処理のパイプライン」**を組むのが一般的です。

*   **制御の仕組み（Shell / PowerShell / バッチ）：**
    OSレベルのスクリプト（ShellやPowerShell）が全体の司令塔になります。「旧DBからCSV抽出 → ワークテーブルへロード → 変換SQL実行 → エラーログ出力」といったステップを順番に実行させます。
*   **DB内ロジック（PL/SQL / T-SQL）：**
    複雑な変換ロジック（例えば、1つの処方データから複数の会計データを作るなど）が必要な場合は、ストアドプロシージャ（OracleならPL/SQL、SQL ServerならT-SQL）を書きます。
    *   **理由：** アプリサーバーとDBサーバーの間でデータを往復させるとネットワークがボトルネックになるため、DB内で処理を完結させるのが最速だからです。
*   **中間テーブル（Staging Table）の活用：**
    本番テーブルにいきなり入れるのではなく、まずは「何でも入る緩い制約の中間テーブル」にバサッと入れます。そこでSQLを使って「データクレンジング」を行い、最後に一括で本番テーブルへ移す、という多段構えで行います。

---

### 2. 大量データ挿入（Bulk Insert）のテクニック

Excelで`INSERT`文を作って流すのは、数千件程度のマスタデータまでです。数百万件のトランザクションデータ（投薬履歴など）では、以下の手法が取られます。

#### ① DB製品ごとの「高速ロードツール」を使う
これが最も速いです。SQL文を通さず、バイナリ形式でDBに直接書き込むような仕組みです。
*   **SQL Server:** `bcp` コマンド、または `BULK INSERT` 命令。
*   **Oracle:** `SQL*Loader` (sqlldr) 。
*   **PostgreSQL:** `COPY` コマンド。
これらは、通常の`INSERT`よりも数倍〜数十倍速いです。

#### ② インデックスと制約の「一時削除」
DBにインデックス（索引）や外部キー制約があると、1件入れるたびにDBが「整合性チェック」や「索引の並び替え」を行うため、激重になります。
*   **技法：** 挿入前にインデックスを `DROP` または `DISABLE`（無効化）し、全データを入れた後に一気に `REBUILD`（再構築）します。これで劇的に速くなります。

#### ③ トランザクションログの制御
大量の`INSERT`をすると、DBは「万が一の復旧用」にログを書き溜めますが、これがディスクを圧迫し、速度を低下させます。
*   **技法：** 移行作業中だけDBのログモードを「簡易（Loggingを最小限にする）」に切り替える、あるいは一定件数（例：1万件）ごとに `COMMIT` を刻むといった制御をスクリプトで行います。

#### ④ パラレル（並列）処理
1つのプロセスで頑張るのではなく、データを「2020年度分」「2021年度分」のように分割し、4つや8つのスレッドで同時にSQLを走らせてDBのCPUを使い切ります。

### 3. エディタやツールの使い分け（現場のリアル）

「新人がどうやって作業するか」という点では、以下のような使い分けが多いです。

*   **マスタデータ（数千件）：**
    ExcelのA列に旧コード、B列に名称…と並べて、C列に `="INSERT INTO TABLE_A (ID, NAME) VALUES ('" & A1 & "', '" & B1 & "');"` と関数を書いて、生成されたSQLをテキストエディタ（VSCodeや秀丸など）に貼り付けて実行。
*   **大量の履歴データ（数百万件）：**
    PythonやShellスクリプトなどで、旧データを「ロード用CSV」に変換。それを前述の `bcp` や `sqlldr` の設定ファイル（コントロールファイル）を書いて、コマンドラインから実行。

### 4. 「夜通し」の正体

なぜ時間がかかるかというと、**「整合性チェック（検証）」**に時間がかかるからです。

SQLでデータを変換したあと、
「合計金額が合っているか？」
「処方箋の枚数と、患者の数が旧システムと一致するか？」
といった**「検算SQL」**を何百本も走らせます。ここで不整合が見つかると、原因を調査してSQLを書き直し、最初からやり直します。この試行錯誤を「リハーサル」の期間中に何度も繰り返します。

### まとめ：新人がやること
おそらく最初は、
1.  **「このマスタをExcelでSQLにして流しておいて」**という簡単な作業。
2.  **「このSQLを実行して、出てきた件数をExcelにメモして」**という検証補助。
3.  **「この変換SQL（先輩が書いたもの）を、2024年度分のデータに対して実行してみて」**というオペレーション。
このあたりからスタートし、徐々に「自分でShellやPL/SQLを組んで、100万件を1時間で終わらせる」ようなチューニングを任されるようになる…というイメージです。

かなり泥臭いですが、**「巨大なデータを意のままに操る」**という点では、エンジニアとしての基礎体力が非常に付く仕事ですよ。



---

電子カルテシステムのデータベース構造は非常に複雑で、テーブル数は1,000を超えることも珍しくありませんが、中心となるのは**「患者マスタ」「病名」「オーダ（処方や検査）」**の3点です。

具体的にどんなテーブル構造で、どんなSQLを書くことになるのか、現場でよくあるケースを想定して再現します。

### 1. 想定される主要なテーブル構造（簡略版）

#### ① マスタ系（M_で始まることが多い）
*   **M_PATIENT（患者マスタ）**: `patient_id(PK)`, `kanji_name`, `kana_name`, `birth_date`, `sex_code`, `zip_code`
*   **M_DRUG（薬品マスタ）**: `drug_code(PK)`, `drug_name`, `unit`, `unit_price`（厚労省のコードに基づく）

#### ② トランザクション系（T_で始まる、日々増え続けるデータ）
*   **T_DIAGNOSIS（病名テーブル）**: `diagnosis_id`, `patient_id(FK)`, `disease_code`, `start_date`, `outcome_flag`（継続中か治癒したか）
*   **T_ORDER（オーダテーブル）**: `order_id`, `patient_id(FK)`, `doctor_id`, `order_type`（処方・注射・検査などの区別）, `order_date`
*   **T_ORDER_DRUG（処方詳細）**: `order_id`, `drug_code`, `dosage`（分量）, `usage_code`（飲み方）

### 2. 具体的に書くSQLのパターン

#### ケースA：データ移行（旧システムから新システムへ）
旧システムでは性別が「1, 2」、新システム（パッケージ）では「M, F」で管理している場合。

```sql
-- 旧システムのテンポラリテーブル(WORK_PATIENT)から本番マスタへ移行
INSERT INTO M_PATIENT (patient_id, kanji_name, birth_date, sex_code)
SELECT 
    old_id, 
    kanji_name, 
    -- '19800101' という文字列を日付型に変換
    CAST(old_birthday AS DATE),
    -- 性別コードの変換
    CASE 
        WHEN old_sex = '1' THEN 'M' 
        WHEN old_sex = '2' THEN 'F' 
        ELSE 'U' -- Unknown
    END
FROM WORK_PATIENT;
```

#### ケースB：病院独自の統計レポート（SQLによるデータ抽出）
「特定の期間に、特定の病名の患者に対して、どんな薬が処方されたか」を抽出してExcelで出したいと言われた場合。

```sql
SELECT 
    p.patient_id,
    p.kanji_name,
    d.disease_name,
    o.order_date,
    dr.drug_name,
    od.dosage
FROM T_ORDER o
INNER JOIN M_PATIENT p ON o.patient_id = p.patient_id
INNER JOIN T_DIAGNOSIS dg ON o.patient_id = dg.patient_id
INNER JOIN T_ORDER_DRUG od ON o.order_id = od.order_id
INNER JOIN M_DRUG dr ON od.drug_code = dr.drug_code
WHERE o.order_date BETWEEN '2023-10-01' AND '2023-10-31'
  AND dg.disease_code = 'D123' -- 特定の病名コード
  AND o.order_type = 'Prescription'; -- 処方オーダのみ
```
※このように、4枚も5枚もテーブルを `JOIN` するのは日常茶飯事です。

#### ケースC：マスタの一括修正（本番メンテナンス）
「あるメーカーの薬品100種類の名称が一斉に変更になったが、パッケージの画面から1つずつ直すのは無理」と言われた場合。

1.  まずExcelで変更リストをもらう。
2.  Excelの関数を使って `UPDATE` 文を100行生成する。
    `="UPDATE M_DRUG SET drug_name = '" & B2 & "' WHERE drug_code = '" & A2 & "';"`
3.  生成されたSQLをエディタに貼り付け、慎重に実行。

```sql
-- 実際の手順イメージ
BEGIN TRANSACTION; -- 怖すぎるので必ずトランザクション開始

-- 1行だけ試して影響範囲を確認
UPDATE M_DRUG SET drug_name = '新しい薬名A' WHERE drug_code = '111222333';

-- 期待通り1件だけ更新されたか確認
SELECT * FROM M_DRUG WHERE drug_code = '111222333';

-- 問題なければ残りの99行を貼り付けて実行
...

COMMIT; -- 最後に確定
```

    *   SQL生成器として使います。VLOOKUPや文字列結合を使って、移行データの紐付け案を作ります。

### 4. 仕事の「風潮」としての補足

「統一されたもので少しのカスタマイズ」という風潮の場合、仕事は以下のようになります。

1.  **「その要望、SQLでデータだけ抜けば解決しませんか？」**と提案する（プログラム改修を避ける）。
2.  **「パッケージの標準テーブルの『予備カラム1』にこのデータを入れよう」**といった、データのパズルをする。
3.  パッケージの本体をいじらない代わりに、**「外付けのBIツールや帳票ツール（SQLで動く）」**を駆使して病院の要望に応える。

「ソースコードを書く時間」よりも、**「テーブル定義書を読み、SQLを組み立て、データの整合性をチェックしている時間」**の方が長くなるはずです。これがこの案件の「エンジニアリング」の本質です。

実際の電子カルテシステム（国内パッケージ）でよく見られる、代表的なテーブル構造をいくつか再現してみます。

本物のシステムは数千テーブルありますが、改修や移行で必ず触ることになる**「患者」「来院」「病名」「処方」**の4つの領域に絞って解説します。

---

### 1. 患者基本マスタ (`M_PATIENT`)
病院に登録されている全患者の情報です。

| カラム名 | 型 | 説明 |
| :--- | :--- | :--- |
| `patient_id` | `VARCHAR(20)` | **PK** 患者番号（カルテ番号） |
| `kanji_name` | `VARCHAR(100)` | 氏名（漢字） |
| `kana_name` | `VARCHAR(100)` | 氏名（カナ） |
| `birth_date` | `DATE` | 生年月日 |
| `sex_type` | `CHAR(1)` | 性別 (1:男, 2:女, 9:不明) |
| `zip_code` | `VARCHAR(7)` | 郵便番号 |
| `address` | `VARCHAR(200)` | 住所 |
| `tel_no` | `VARCHAR(15)` | 電話番号 |
| `update_at` | `DATETIME` | 最終更新日時 |
| `delete_flg` | `INT` | 削除フラグ (0:有効, 1:削除) |

*   **ポイント:** 医療系では「削除（DELETE）」はまず行わず、`delete_flg` による**論理削除**が基本です。また、氏名は漢字・カナの両方が必須です。

---

### 2. 来院・受付情報 (`T_VISIT`)
「いつ、誰が、どの科に来たか」という、全ての診療の起点となるテーブルです。

| カラム名 | 型 | 説明 |
| :--- | :--- | :--- |
| `visit_id` | `BIGINT` | **PK** 来院管理番号 |
| `patient_id` | `VARCHAR(20)` | **FK** 患者番号 |
| `dept_code` | `VARCHAR(10)` | 受診科コード（内科、外科など） |
| `doctor_id` | `VARCHAR(10)` | 担当医ID |
| `visit_date` | `DATE` | 受診日 |
| `visit_time` | `TIME` | 受付時刻 |
| `visit_status` | `INT` | 状態 (1:待ち, 2:診察中, 3:会計待ち, 4:完了) |

*   **ポイント:** 移行作業では、旧システムの「受付履歴」をこのテーブルに流し込む必要があります。

---

### 3. 患者病名テーブル (`T_DIAGNOSIS`)
患者が現在かかっている病気のリストです。レセプト（診療報酬明細書）に直結するため、非常に厳格に管理されます。

| カラム名 | 型 | 説明 |
| :--- | :--- | :--- |
| `diag_id` | `BIGINT` | **PK** 病名管理番号 |
| `patient_id` | `VARCHAR(20)` | **FK** 患者番号 |
| `disease_code` | `VARCHAR(10)` | 疾病コード（ICD-10等の標準コード） |
| `disease_name` | `VARCHAR(200)` | 病名（標準病名または病院独自の名称） |
| `start_date` | `DATE` | 診療開始日 |
| `end_date` | `DATE` | 診療終了日（治癒・死亡・転院など） |
| `main_flg` | `INT` | 主病名フラグ (1:主病名) |
| `outcome_type` | `CHAR(1)` | 転帰区分 (1:治癒, 2:中止, 3:死亡, 4:継続) |

*   **ポイント:** ここにある病名データが正しくないと、病院は国に診療代を請求（レセプト請求）できなくなります。移行で最もミスが許されないテーブルの一つです。

---

### 4. 処方オーダテーブル (`T_ORDER_DRUG`)
医師が出したお薬の指示データです。

| カラム名 | 型 | 説明 |
| :--- | :--- | :--- |
| `order_id` | `BIGINT` | **PK** オーダ番号 |
| `visit_id` | `BIGINT` | **FK** 来院管理番号 |
| `drug_code` | `VARCHAR(20)` | 薬品コード（HOTコードやYJコード） |
| `drug_name` | `VARCHAR(200)` | 薬品名 |
| `dosage` | `NUMERIC(10,3)` | 1回または1日あたりの分量 |
| `unit_name` | `VARCHAR(10)` | 単位（錠、mL、gなど） |
| `usage_code` | `VARCHAR(10)` | 用法コード（食後、就寝前など） |
| `days` | `INT` | 処方日数 |

*   **ポイント:** 単位や用法のコードは病院ごとに独自のものを使っている場合があり、移行時には「旧システムの『食後』は新システムの『コード001』にする」といった**コード変換SQL**が大量に発生します。

### 5. 実際によくやる操作（SQLイメージ）

改修や調査で、以下のようなSQLをよく書くことになります。

#### 例：特定の薬（A）を処方されているが、特定の病名（B）が登録されていない患者を抽出する
（※これは「不適切な処方（査定リスク）」を見つけるための調査です）

```sql
SELECT
    P.patient_id,
    P.kanji_name,
    O.drug_name
FROM T_ORDER_DRUG O
JOIN M_PATIENT P ON O.patient_id = P.patient_id
WHERE O.drug_code = 'DRUG_A_CODE' -- 特定の薬
  AND NOT EXISTS (
      SELECT 1 FROM T_DIAGNOSIS D
      WHERE D.patient_id = P.patient_id
        AND D.disease_code = 'DISEASE_B_CODE' -- 必要な病名
        AND D.delete_flg = 0
  );
```

#### 例：移行時に「未完了の病名」だけを新システムに移すSQL
（※過去に治った病名は移さず、現在治療中のものだけ移すケース）

```sql
INSERT INTO NEW_SYSTEM.T_DIAGNOSIS (...)
SELECT ...
FROM OLD_SYSTEM.PATIENT_BYOMEI
WHERE TENKI_FLG = '0' -- 継続中
  AND DELETE_DATE IS NULL -- 削除されていない
  AND START_DATE >= '2015-01-01'; -- あまりに古すぎるものは切り捨てる、などの条件
```

### このようなテーブルを扱う際の心構え
1.  **カラム名が日本語（ローマ字）のこともある:** `KANJI_NAME` ではなく `SNAME_KJ` のような、古い慣習の名前がついているパッケージも多いです。
2.  **マスタ依存が激しい:** ほぼ全てのテーブルが何らかのマスタ（科、医師、場所、薬品、病名…）を参照しているため、`JOIN` の嵐になります。
3.  **日付の扱いがシビア:** 「和暦（元号）」を扱う処理や、日付を `INT` 型（20231001）で持っている古い設計のパッケージもまだ残っており、SQLでの型変換に苦労することがあります。

いかがでしょうか？「あ、これなら今のSQL知識でいけそう」とか「JOINが大変そうだな」といったイメージが湧いてきましたか？

### 1. テーブル定義 (DDL)

```sql
-- 既存テーブルの削除（初期化用）
DROP TABLE IF EXISTS t_order_drug;
DROP TABLE IF EXISTS t_diagnosis;
DROP TABLE IF EXISTS t_visit;
DROP TABLE IF EXISTS m_department;
DROP TABLE IF EXISTS m_patient;

-- 1. 患者マスタ
CREATE TABLE m_patient (
    patient_id VARCHAR(20) PRIMARY KEY,     -- 患者番号
    kanji_name VARCHAR(100) NOT NULL,       -- 氏名（漢字）
    kana_name VARCHAR(100) NOT NULL,        -- 氏名（カナ）
    birth_date DATE NOT NULL,               -- 生年月日
    sex_type CHAR(1) CHECK (sex_type IN ('1', '2', '9')), -- 1:男, 2:女, 9:不明
    zip_code CHAR(7),                       -- 郵便番号
    address TEXT,                           -- 住所
    delete_flg INT DEFAULT 0                -- 削除フラグ (0:有効)
);

-- 2. 診療科マスタ
CREATE TABLE m_department (
    dept_code VARCHAR(10) PRIMARY KEY,      -- 診療科コード
    dept_name VARCHAR(50) NOT NULL          -- 診療科名
);

-- 3. 来院・受付テーブル
CREATE TABLE t_visit (
    visit_id SERIAL PRIMARY KEY,            -- 来院ID（自動採番）
    patient_id VARCHAR(20) REFERENCES m_patient(patient_id),
    dept_code VARCHAR(10) REFERENCES m_department(dept_code),
    visit_date DATE NOT NULL DEFAULT CURRENT_DATE,
    visit_status INT DEFAULT 1              -- 1:待ち, 2:診察中, 3:会計待, 4:完了
);

-- 4. 患者病名テーブル
CREATE TABLE t_diagnosis (
    diag_id SERIAL PRIMARY KEY,             -- 病名管理ID
    patient_id VARCHAR(20) REFERENCES m_patient(patient_id),
    disease_code VARCHAR(10) NOT NULL,      -- ICD10コード等
    disease_name VARCHAR(200) NOT NULL,     -- 病名
    start_date DATE NOT NULL,               -- 診療開始日
    end_date DATE,                          -- 診療終了日
    outcome_type CHAR(1)                    -- 1:治癒, 4:継続
);

-- 5. 処方オーダテーブル
CREATE TABLE t_order_drug (
    order_id SERIAL PRIMARY KEY,            -- オーダID
    visit_id INT REFERENCES t_visit(visit_id),
    drug_code VARCHAR(20) NOT NULL,         -- 薬品コード
    drug_name VARCHAR(200) NOT NULL,        -- 薬品名
    dosage NUMERIC(10,3) NOT NULL,          -- 用量
    unit_name VARCHAR(10),                  -- 単位
    days INT NOT NULL                       -- 日数
);
```

### 3. このデータで試せる「移行・改修」の練習例

作成したテーブルを使って、以下のようなクエリを書いてみると、実業務のイメージが掴めます。

#### ① 統計・レポート業務の練習
「2024年1月に来院した患者の、氏名、受診科、処方された薬、病名を一覧で出せ」
（※4枚のテーブルを結合する練習）
```sql
SELECT 
    p.kanji_name,
    d.dept_name,
    diag.disease_name,
    od.drug_name
FROM t_visit v
JOIN m_patient p ON v.patient_id = p.patient_id
JOIN m_department d ON v.dept_code = d.dept_code
LEFT JOIN t_diagnosis diag ON p.patient_id = diag.patient_id
LEFT JOIN t_order_drug od ON v.visit_id = od.visit_id
WHERE v.visit_date BETWEEN '2024-01-01' AND '2024-01-31';
```

#### ② 移行作業（クレンジング）の練習
「旧システムから持ってきたデータの性別が `1, 2` ではなく `M, F` だった場合、どう `INSERT` するか？」のシミュレーション。
```sql
-- ワークテーブル（旧システムを想定）
CREATE TEMPORARY TABLE work_old_data (old_id VARCHAR(10), old_sex VARCHAR(10));
INSERT INTO work_old_data VALUES ('00004', 'M'), ('00005', 'F');

-- 変換しながらマスタに入れる
INSERT INTO m_patient (patient_id, kanji_name, kana_name, birth_date, sex_type)
SELECT 
    old_id, '移行テスト', 'イコウテスト', '2000-01-01',
    CASE WHEN old_sex = 'M' THEN '1' WHEN old_sex = 'F' THEN '2' ELSE '9' END
FROM work_old_data;
```

#### ③ 整合性チェック
「薬は出ているのに、病名が登録されていない（レセプト落ちリスク）患者をみつける」
```sql
SELECT v.patient_id, p.kanji_name
FROM t_visit v
JOIN m_patient p ON v.patient_id = p.patient_id
WHERE EXISTS (SELECT 1 FROM t_order_drug od WHERE od.visit_id = v.visit_id) -- 薬あり
  AND NOT EXISTS (SELECT 1 FROM t_diagnosis dg WHERE dg.patient_id = v.patient_id AND dg.outcome_type = '4'); -- 継続中の病名なし
```

### 1. PostgreSQL用 テーブル定義 (DDL)

移行案件では、まず「受け皿」となるテーブルを作る必要があります。CSVのヘッダーに合わせて型を定義します。
※SyntheaのIDはUUID形式（長い英数字）なので `VARCHAR(100)` や `UUID` 型を使います。

```sql

CREATE TABLE encounters (

    code VARCHAR(20),
    description TEXT,
    reasoncode VARCHAR(20),
    reasondescription TEXT
);

-- 3. 病名・状態（現在かかっている病気）
CREATE TABLE conditions (
```

### 1. patients (患者マスタ)

| カラム名 | 説明 | 備考 |
| :--- | :--- | :--- |
| **id** | 患者一意識別子 (UUID) | **PK**（主キー）。他テーブルから参照されるID |
| **birthdate** | 生年月日 | `DATE` 型 |
| **deathdate** | 死亡日 | 生存している場合は `NULL` |
| **ssn** | 社会保障番号 | 米国のマイナンバーに相当。重複チェックによく使う |
| **drivers** | 運転免許証番号 | 本人確認用 |
| **passport** | パスポート番号 | 同上 |
| **prefix** | 敬称 | Mr., Ms., Dr. など |
| **first_name** | 名 | 名前（下の名前） |
| **last_name** | 姓 | 名字 |
| **suffix** | 接尾辞 | Jr., Sr.（ジュニア、シニア）など |
| **maiden** | 旧姓 | 結婚前の名字 |
| **marital** | 既婚区分 | S:独身, M:既婚, D:離婚 など |
| **race** | 人種 | White, Asian, Black など（米国特有） |
| **ethnicity** | 民族 | Hispanic, Non-Hispanic など |
| **gender** | 性別 | M:男, F:女 |
| **birthplace** | 出生地 | 生まれた場所 |
| **address** | 住所 | 現住所のテキスト |

### 2. encounters (来院・受診記録)
「いつ、誰が、何の目的で病院に来たか」を管理するハブとなるテーブルです。

| カラム名 | 説明 | 備考 |
| :--- | :--- | :--- |
| **id** | 来院一意識別子 | **PK**。診察ごとに発行されるID |
| **date** | 来院日時 | `TIMESTAMP`（日付＋時刻） |
| **patient_id** | 患者ID | **FK**（外部キー）。`patients.id` に紐付く |
| **code** | 受診形態コード | 標準コード（SNOMED-CT等） |
| **description** | 受診内容説明 | 「一般外来」「救急」「健康診断」などの名称 |
| **reasoncode** | 来院理由コード | なぜ来たかを示すコード |
| **reasondescription** | 来院理由説明 | 「腹痛」「定期検診」などのテキスト |

### 3. conditions (病名・状態)
患者が診断された病気（傷病名）を管理します。

### SES案件で役立つ「データの見方」のコツ

*   **PKとFKを意識する**: `encounters.id` が、`conditions` や `medications` の `encounter_id` に繋がっていることを常に意識してクエリを書きます。
*   **NULLの意味を考える**: `deathdate` や `stop_date` が `NULL` であることは、「今も生きている」「今もその病気が続いている」という重要な意味を持ちます。
*   **値の型に注意**: `observations.value` は数値が入ることが多いですが、型が `VARCHAR` なので、計算する時は `CAST(value AS NUMERIC)` する必要があります（ただし数値以外の文字が入っているとエラーになるので注意）。

### 第1問：データ移行タスク
**【シミュレーション】**
旧システムからインポートした `patients` テーブルのデータを、新しいパッケージソフトの「患者管理テーブル（仮に `new_patients`）」に移行します。新しいパッケージには以下の制約があります。
1.  `gender`（性別）は 'M'/'F' ではなく、'1'（男）、'2'（女）に変換すること。
2.  `first_name` と `last_name` を結合して一つの `full_name` カラムに入れること。
3.  住所が空（NULL）の場合は、'住所不明' という文字列を入れること。

#### 解答例と解説
**パターンA：標準的な `CASE` 文と文字列結合**
```sql
INSERT INTO new_patients (patient_id, full_name, gender_code, address)
SELECT 
    id,
    first_name || ' ' || last_name, -- 文字列結合
    CASE 
        WHEN gender = 'M' THEN '1'
        WHEN gender = 'F' THEN '2'
        ELSE '9' 
    END,
    COALESCE(address, '住所不明') -- NULLを置換
FROM patients;
```

*   **優れている点:** `COALESCE` を使ってスマートにNULL処理をしている点。
*   **注意点:** `||` で結合する際、どちらかがNULLだと結果もNULLになるため、名前の欠損があり得る場合は `CONCAT_WS(' ', first_name, last_name)` を使う方が安全です。

### 第2問：病院独自の統計レポートタスク
**【シミュレーション】**
病院の経営層から、「2010年以降に『Diabetes（糖尿病）』と診断（Conditions）された患者の中で、実際に『Metformin』という薬（Medications）を処方された患者の割合を知りたい」という依頼を受けました。まずは該当する「患者ID、氏名、診断名、処方薬名」をリストアップしてください。

#### 解答例と解説
**パターンA：`INNER JOIN` を活用する（一般的）**
```sql
SELECT DISTINCT
    p.id,
    p.first_name || ' ' || p.last_name AS patient_name,
    c.description AS condition_name,
    m.description AS medication_name
FROM patients p
JOIN conditions c ON p.id = c.patient_id
JOIN medications m ON p.id = m.patient_id
WHERE c.description LIKE '%Diabetes%'
  AND m.description LIKE '%Metformin%'
  AND c.start_date >= '2010-01-01';
```

*   **メリット:** 構造が分かりやすく、他の項目（処方日など）も追加しやすい。
*   **デメリット:** `JOIN` によってデータが重複（1人の患者に複数回の処方がある場合など）するため、`DISTINCT` が必須になり、データ量が多いと少し重くなる。

**パターンB：`EXISTS` を活用する（実務で好まれる）**
```sql
SELECT 
    p.id,
    p.first_name || ' ' || p.last_name AS patient_name
FROM patients p
WHERE EXISTS (
    SELECT 1 FROM conditions c 
    WHERE c.patient_id = p.id AND c.description LIKE '%Diabetes%' AND c.start_date >= '2010-01-01'
)
AND EXISTS (
    SELECT 1 FROM medications m 
    WHERE m.patient_id = p.id AND m.description LIKE '%Metformin%'
);
```
*   **メリット:** 「条件に合う人がいるかいないか」だけを判定するため、**実行速度が速い**。また、`DISTINCT` を使わなくても重複が発生しない。
*   **デメリット:** 抽出できる項目が「患者マスタ」にあるものに限定される（薬の具体的な処方日などは出せない）。

### 第3問：マスタの一括修正タスク
**【シミュレーション】**
保守作業の一環です。薬剤マスタ（今回は `medications` テーブル内のデータ）を確認したところ、特定の薬品コード（CODE: '860975'）の名称が、古い「Metformin」のままになっています。これを一斉に「Metformin 500 MG Oral Tablet」に更新してください。ただし、**「過去に一度でも処方された記録があるデータのみ」**を正確に更新する必要があります。

#### 解答例と解説
**パターンA：安全なトランザクションを用いた更新**
```sql
BEGIN; -- 必ずトランザクションを開始

-- 更新前に件数を確認（重要！）
SELECT COUNT(*) FROM medications WHERE code = '860975';

-- 更新実行
UPDATE medications
SET description = 'Metformin 500 MG Oral Tablet'
WHERE code = '860975';

-- 更新後の内容を10件ほど見て確認
SELECT * FROM medications WHERE code = '860975' LIMIT 10;

-- 問題なければ確定
COMMIT; 
-- もし件数がおかしければ
-- ROLLBACK;
```

*   **優れている点:** SESの現場で最も評価される「慎重な」手順。件数確認をしてからコミットする流れは「分かっているエンジニア」の動きです。

**パターンB：サブクエリを使った更新（条件が複雑な場合）**
※もし「特定の受診科で処方されたものだけ変えたい」などの条件がある場合：
```sql
UPDATE medications m
SET description = 'Metformin 500 MG Oral Tablet'
WHERE m.code = '860975'
  AND EXISTS (
      SELECT 1 FROM encounters e 
      WHERE e.id = m.encounter_id 
        AND e.description = 'Wellness Request' -- 例：特定の来院理由のみ
  );
```
*   **メリット:** 関連テーブルの条件を見て更新できる。
*   **デメリット:** `UPDATE` 文の `WHERE` 句にサブクエリを入れると処理が重くなることがあるため、大規模データでは実行計画（EXPLAIN）の確認が必要。

### SES案件での立ち回りアドバイス
これらの問題を解く際に、以下のことを意識すると「現場でデキる人」と思われます。

1.  **いきなりUPDATE/INSERTしない:** まずは `SELECT` で対象件数を確認する。
2.  **`LIKE` 検索の使い所:** 医療データは名称が長いため `= 'Metformin'` だとヒットしないことが多いです。`LIKE '%Metformin%'` を使う癖をつけておきましょう。
3.  **NULLへの恐怖:** 医療データは「生年月日が入っていない」「住所がない」ことがザラにあります。常に `COALESCE` や `IS NOT NULL` を意識しましょう。
