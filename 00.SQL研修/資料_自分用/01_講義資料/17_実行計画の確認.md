### 0. 準備：テストデータの作成
まずは、比較用の `users`（1万件）と `orders`（20万件）テーブルを作成します。

```sql
-- 既存のテーブルがあれば削除（NOTICEは無視して大丈夫です）
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS users;

-- テーブル作成
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name TEXT,
    region TEXT,
    created_at TIMESTAMP
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT,
    amount INT,
    status TEXT,
    created_at TIMESTAMP
);

-- データ挿入（1万ユーザー）
INSERT INTO users (name, region, created_at)
SELECT 
    'user_' || i,
    CASE WHEN i % 10 = 0 THEN 'Tokyo' ELSE 'Other' END,
    now() - (i * interval '1 hour')
FROM generate_series(1, 10000) AS s(i);

-- データ挿入（20万注文）
INSERT INTO orders (user_id, amount, status, created_at)
SELECT 
    (random() * 9999 + 1)::int,
    (random() * 20000)::int,
    CASE WHEN random() < 0.01 THEN 'pending' ELSE 'shipped' END,
    now() - (i * interval '2 minutes')
FROM generate_series(1, 200000) AS s(i);

-- 統計情報を最新にする
ANALYZE users;
ANALYZE orders;
```

### 1. スキャンノードの比較（選択率の変化）
データの絞り込み条件（選択率）によって、スキャンの種類が変わる様子を確認します。

```sql
-- (1) Index Scan：非常に少ない行数（1%）を引く場合
-- まずはインデックスを作成
CREATE INDEX idx_orders_status ON orders(status);
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM orders WHERE status = 'pending';
```

```sql
"Index Scan using idx_orders_status on orders  (cost=0.29..291.03 rows=2140 width=28) (actual time=0.017..0.698 rows=2061 loops=1)"
"  Index Cond: (status = 'pending'::text)"
"  Buffers: shared hit=1116"
"Planning Time: 0.052 ms"
"Execution Time: 0.785 ms"
```

```sql
-- (2) Seq Scan：多くの行数（99%）を引く場合
-- インデックスがあっても、全体を読む方が早いと判断される
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM orders WHERE status = 'shipped';
```

```sql
"Seq Scan on orders  (cost=0.00..3971.00 rows=197860 width=28) (actual time=0.010..11.289 rows=197939 loops=1)"
"  Filter: (status = 'shipped'::text)"
"  Rows Removed by Filter: 2061"
"  Buffers: shared hit=1471"
"Planning Time: 0.053 ms"
"Execution Time: 16.178 ms"
```

```sql
-- (3) Bitmap Scan：中程度の行数を引く場合（例：amountで絞り込み）
CREATE INDEX idx_orders_amount ON orders(amount);
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM orders WHERE amount < 2000;
```

```sql
"Bitmap Heap Scan on orders  (cost=252.89..1976.47 rows=20206 width=28) (actual time=0.761..3.209 rows=20198 loops=1)"
"  Recheck Cond: (amount < 2000)"
"  Heap Blocks: exact=1471"
"  Buffers: shared hit=1495"
"  ->  Bitmap Index Scan on idx_orders_amount  (cost=0.00..247.84 rows=20206 width=0) (actual time=0.641..0.642 rows=20198 loops=1)"
"        Index Cond: (amount < 2000)"
"        Buffers: shared hit=24"
"Planning:"
"  Buffers: shared hit=6"
"Planning Time: 0.062 ms"
"Execution Time: 3.739 ms"
```


> [!example]- 詳解
> 1. 【下段】Bitmap Index Scan（インデックスで地図を作る）
> まずはここから始まります。
> 動作: idx_orders_amount インデックスを使い、amount < 2000 に該当する行が「どのページのどのあたりにあるか」を調べ、メモリ上に**地図（ビットマップ）**を作成しました。
> Buffers (shared hit=24): インデックスのページを 24ページ 読みました。
> actual rows=20198: 条件に合う行が 20,198行あることを突き止めました。
> 2. 【上段】Bitmap Heap Scan（地図を元にテーブルを読む）
> 次に、作成した地図を使ってテーブル本体（Heap）にアクセスします。
> 動作: 地図を見て、必要なテーブルページだけを**「前から順番に」**読みに行きます。これにより、Index ScanよりもディスクI/Oが効率化されます。
> Heap Blocks (exact=1471):
> 1471: 実際に読みに行ったテーブル本体のページ数です。
> exact: work_mem（作業用メモリ）が十分だったため、行単位の「正確な」地図を使えたことを示します。
> 3. Buffers の内訳（累積の計算）
> 全体の shared hit=1495 は、このノード以下の合計値です。
> 全体 (1495) － インデックス分 (24) ＝ テーブル分 (1471)
> この 1471 という数字が、Heap Blocks: exact=1471 と完全に一致しています。
> つまり、**「インデックス24枚、テーブル1471枚、計1495枚のページを全てメモリ（shared buffers）から読み込んだ」**ことが分かります。
> 4. Recheck Cond（再確認）
> 意味: 「テーブルから持ってきた行が、本当に amount < 2000 を満たしているか」を念のためチェックしています。
> なぜ必要か: もしメモリが足りず地図が「大雑把（lossy）」になった場合、余計な行まで読み込んでしまうため、この再チェックで振り落とす必要があるからです。（今回は exact なので、実際には全ての行がパスしています）
> 5. 性能評価（サマリー）
> 推定と実測の乖離: rows=20206（推定）に対し actual rows=20198（実測）と、ほぼ完璧に一致しています。統計情報が新しく、プランナの判断が非常に正確です。
> キャッシュ効率: 全て shared hit であり、ディスク読み込み（read）が 0 なので、物理I/Oによる遅延が発生していません。
> 実行時間: 2万件のデータ抽出を約 3.7ms で完了しており、非常に高速です。

### 2. Index Only Scan と Visibility Map の関係
`VACUUM` を行う前後で `Heap Fetches` がどう変わるかを確認します。

```sql
-- インデックス作成
CREATE INDEX idx_orders_user_amount ON orders(user_id, amount);

-- (1) VACUUM前：Index Only Scan だが Heap Fetches が発生する可能性がある
-- （挿入直後なのでVMが更新されていないため）
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, amount FROM orders WHERE user_id = 100;

-- (2) VACUUM後：Heap Fetches が 0 になる
VACUUM ANALYZE orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT user_id, amount FROM orders WHERE user_id = 100;
```

```sql
"  Buffers: shared hit=6"
```

### 4. work_mem 不足による Disk Spill（temp written）
`work_mem` を極端に小さくして、ディスクソートが発生する様子を確認します。

```sql
-- 並列処理をこのセッションだけオフにする
SET max_parallel_workers_per_gather = 0;
```

```sql
-- (A) メモリ内ソート：quicksort（全件ソート）
-- LIMITを付けずにソートさせると、全件をメモリに展開してソートします
SET work_mem = '64MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY amount + 0 DESC; -- indexを使わせない
```

```sql
"Sort  (cost=21580.64..22080.64 rows=200000 width=32) (actual time=55.861..73.488 rows=200000 loops=1)"
"  Sort Key: ((amount + 0)) DESC"
"  Sort Method: quicksort  Memory: 17082kB"
"  Buffers: shared hit=1471"
"  ->  Seq Scan on orders  (cost=0.00..3971.00 rows=200000 width=32) (actual time=0.013..12.611 rows=200000 loops=1)"
"        Buffers: shared hit=1471"
"Planning Time: 0.046 ms"
"Execution Time: 84.163 ms"
```

```sql
-- (B) 最適化ソート：top-N heapsort（上位抽出）
-- LIMITを付けると、全部を並べ替えない「椅子取りゲーム」方式に変わります
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY amount + 0 DESC LIMIT 100;
```

```sql
"  Buffers: shared hit=1471"

"Execution Time: 33.529 ms"
```

> > 動作: リーダーとワーカーの計2人で、1471ページのテーブルデータを全件読み込みました。
> > rows=100000 loops=2: 合計で20万行（10万行×2人）を処理しています。
> > 速度: わずか 6.6ms で読み込みを終えています。
> > 2. Sort
> > メモリ内に収まっています。
> > Sort Method: top-N heapsort (リーダー担当):
> > LIMIT 50000 があるため、**「上位5万件だけを保持する特別なソート（ヒープソート）」**を行いました。
> > 全データを並び替えるより遥かに効率的です。
> > Memory: 9017kB（約9MB）を使用。
> > Worker 0: Sort Method: quicksort (ワーカー担当):
> > 助手（ワーカー）の方は quicksort という一般的なメモリ内ソートを行いました。
> > Memory: 10087kB（約10MB）を使用。
> > 3. Gather Merge（合流と整理）
> > 動作: リーダーのソート結果（top-N）と、ワーカーのソート結果を、順番を崩さないように（Merge）合流させています。
> > Buffers: shared hit=1507: 読み込みは全てメモリ（shared buffers）上のキャッシュで済んでいます。

### 実習のポイント
実行したあと、以下の値をガイドと照らし合わせてみてください：

1.  **`actual time * loops`**: 特に Nested Loop の内側で、1回あたりの時間は短くても loops が多いと総時間が肥大化することを確認。
2.  **`Rows Removed by Filter`**: インデックスが使われず、Seq Scan で大量の行が捨てられていないか。
3.  **`shared hit` vs `shared read`**: 2回目に同じクエリを投げた時、`read` が `hit` に変わる（キャッシュが効く）様子を確認。
4.  **`Sort Method`**: `quicksort` なのか `external merge`（ディスク使用）なのか。

これらのサンプルを実行することで、SQLチューニング時に「なぜこのプランが選ばれたのか」「どうすれば改善するか」の感覚が掴めるはずです。
