# PL/pgSQL 実践講座：第7章 高度なトピック

第7章では、PL/pgSQLの真骨頂とも言える3つの高度な機能、**「トリガー」**、**「カーソル」**、そして**「動的SQL」**を解説します。これらは大規模・複雑なシステムにおいて、自動化、パフォーマンス最適化、そして柔軟なロジック実装を実現するための必須スキルです。

## 7.1 トリガー (Triggers)：データベースの自動化

トリガーは、特定のテーブルに対するDML（INSERT, UPDATE, DELETE）を検知して自動実行される仕組みです。

### 7.1.1 押さえておくべき特殊変数
トリガー関数内では、以下の特殊変数が自動的に用意されます。
*   `NEW`: INSERT/UPDATE時の新しい行データ。
*   `OLD`: UPDATE/DELETE時の古い行データ。
*   `TG_OP`: 操作内容（`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`）。
*   `TG_WHEN`: タイミング（`BEFORE`, `AFTER`, `INSTEAD OF`）。

### 実演：自動監査ログとバリデーション
`BEFORE`トリガーでデータの正規化を行い、`AFTER`トリガーでログを記録するパターンを実装します。

```sql
-- 準備：監査用テーブル
CREATE TABLE IF NOT EXISTS audit_log (
    audit_id    serial PRIMARY KEY,
    table_name  text,
    operation   text,
    old_data    jsonb,
    new_data    jsonb,
    changed_by  text DEFAULT current_user,
    changed_at  timestamptz DEFAULT now()
);

-- 1. BEFOREトリガー関数：データのクレンジングと制約チェック
CREATE OR REPLACE FUNCTION fn_employees_before_save()
RETURNS trigger AS $$
BEGIN
    -- 名前の前後の空白を自動削除
    NEW.name := trim(NEW.name);

    -- 給与の異常な下げ幅（20%以上）をチェック
    IF TG_OP = 'UPDATE' THEN
        IF NEW.salary < (OLD.salary * 0.8) THEN
            RAISE EXCEPTION '給与の急激な減額（20%%以上）は許可されていません。'
                USING HINT = '人事部へ確認してください。';
        END IF;
    END IF;

    RETURN NEW; -- 変更を反映させるためにNEWを返す
END;
$$ LANGUAGE plpgsql;

-- 2. AFTERトリガー関数：監査ログの記録
CREATE OR REPLACE FUNCTION fn_employees_after_save()
RETURNS trigger AS $$
BEGIN
    INSERT INTO audit_log (table_name, operation, old_data, new_data)
    VALUES (
        TG_TABLE_NAME,
        TG_OP,
        to_jsonb(OLD),
        to_jsonb(NEW)
    );
    RETURN NULL; -- AFTERトリガーの戻り値は無視される
END;
$$ LANGUAGE plpgsql;

-- トリガーの登録
CREATE OR REPLACE TRIGGER trg_employees_before
    BEFORE INSERT OR UPDATE ON employees
    FOR EACH ROW EXECUTE FUNCTION fn_employees_before_save();

CREATE OR REPLACE TRIGGER trg_employees_after
    AFTER INSERT OR UPDATE OR DELETE ON employees
    FOR EACH ROW EXECUTE FUNCTION fn_employees_after_save();

-- 実行テスト
UPDATE employees SET name = '  Ichiro Sato  ', salary = 640000 WHERE emp_id = 3;

-- 結果確認
SELECT name, salary FROM employees WHERE emp_id = 3; -- 空白が消えている
SELECT * FROM audit_log ORDER BY audit_id DESC LIMIT 1; -- ログが残っている
```

## 7.2 カーソル (Cursors)：巨大データへの効率的なアクセス

第4章の `FOR record IN SELECT` も内部的にはカーソルを使っていますが、明示的なカーソル操作が必要な場面（結果セットを別の関数に渡す、一行ずつ複雑な更新をかける等）があります。

### 7.2.1 カーソル変数 (`REFCURSOR`) の返却
関数から巨大な結果セットを「開いたまま」呼び出し元に返し、呼び出し側で必要な分だけフェッチする手法です。

### 実演：カーソルによる一行更新 (`WHERE CURRENT OF`)
```sql
DO $$
DECLARE
    -- 1. カーソルの宣言
    cur_emp CURSOR FOR 
        SELECT emp_id, name, salary FROM employees FOR UPDATE;
    r_emp RECORD;
BEGIN
    -- 2. カーソルを開く
    OPEN cur_emp;
    
    LOOP
        -- 3. 一行取得
        FETCH cur_emp INTO r_emp;
        EXIT WHEN NOT FOUND;
        
        -- 特定の条件で、カーソルが「今」指している行を更新
        IF r_emp.salary < 500000 THEN
            UPDATE employees 
            SET salary = salary + 50000 
            WHERE CURRENT OF cur_emp; -- プライマリキーを指定し直す必要がない
            
            RAISE NOTICE 'Updated: %', r_emp.name;
        END IF;
    END LOOP;
    
    -- 4. カーソルを閉じる
    CLOSE cur_emp;
END;
$$ LANGUAGE plpgsql;
```

## 7.3 動的SQL (Dynamic SQL)：柔軟なクエリの構築

「テーブル名が引数で決まる」「検索条件の列が動的に変わる」といった場合、`EXECUTE` 文を使用します。

### 7.3.1 【重要】SQLインジェクション対策
動的SQLを扱うエンジニアの最大の責務はセキュリティです。
*   **`format()` 関数**: 識別子（テーブル名等）には `%I`、値には `%L` を使います。
*   **`USING` 句**: 実行時に値を安全にバインドします。

### 実演：動的な統計取得関数
```sql
DO $$
DECLARE
    v_table_name text := 'employees';
    v_col_name   text := 'salary';
    v_min_val    numeric := 500000;
    v_result     numeric;
    v_sql        text;
BEGIN
    -- format関数で安全にSQLを組み立て
    -- %I: Identifier (テーブル名、列名用)
    -- %L: Literal (値用)
    -- $1: USING句で渡すプレースホルダ
    v_sql := format(
        'SELECT avg(%I) FROM %I WHERE %I > $1', 
        v_col_name, v_table_name, v_col_name
    );

    RAISE NOTICE 'Executing SQL: %', v_sql;

    -- 動的SQLの実行
    EXECUTE v_sql 
    INTO v_result -- 結果を受け取る
    USING v_min_val; -- $1 に値をバインド

    RAISE NOTICE 'Average %: %', v_col_name, v_result;
END;
$$ LANGUAGE plpgsql;
```

## 7.4 実践：INSTEAD OF トリガーによる更新可能ビュー

ビュー（View）は通常、JOINが含まれると更新できませんが、`INSTEAD OF` トリガーを使えば、ビューへの更新を背後の複数テーブルへ振り分ける「仮想テーブル」を構築できます。

### 実演：ビュー経由での複数テーブル更新
```sql
-- 複雑なビューの作成
CREATE OR REPLACE VIEW v_employee_details AS
SELECT e.emp_id, e.name, d.dept_name, e.salary
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id;

-- INSTEAD OF トリガー関数
CREATE OR REPLACE FUNCTION fn_v_employee_upd()
RETURNS trigger AS $$
DECLARE
    v_dept_id integer;
BEGIN
    -- 部署名からIDを逆引き
    SELECT dept_id INTO v_dept_id FROM departments WHERE dept_name = NEW.dept_name;
    
    IF NOT FOUND THEN
        RAISE EXCEPTION '部署 % は存在しません。', NEW.dept_name;
    END IF;

    -- 元のテーブルを更新
    UPDATE employees SET 
        name = NEW.name,
        salary = NEW.salary,
        dept_id = v_dept_id
    WHERE emp_id = OLD.emp_id;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- ビューにトリガーを紐付け
CREATE TRIGGER trg_v_employee_upd
    INSTEAD OF UPDATE ON v_employee_details
    FOR EACH ROW EXECUTE FUNCTION fn_v_employee_upd();

-- 実行テスト：ビューに対してUPDATE
UPDATE v_employee_details 
SET dept_name = 'Sales', salary = 900000 
WHERE emp_id = 2;

-- 結果確認：背後のemployeesテーブルが更新されている
SELECT * FROM employees WHERE emp_id = 2;
```

## 7.5 まとめとエンジニア向けのベストプラクティス

1.  **トリガーの `WHEN` 句を活用せよ**: 
    `CREATE TRIGGER ... WHEN (OLD.col IS DISTINCT FROM NEW.col)` のように条件を書くことで、無駄なトリガー関数の起動を抑え、大幅にパフォーマンスを改善できます。
2.  **動的SQLでは `USING` を第一選択に**: 文字列連結で値を埋め込むのは「悪」です。常に `USING` でバインドするか `format(..., %L)` を使用してください。
3.  **カーソルは「バッチ処理」の武器**: 
    100万行を超えるような処理で、全データを一度に取得してメモリを使い果たすような事態は、明示的なカーソル操作（または `FOR IN SELECT`）で回避しましょう。
4.  **INSTEAD OF トリガーでAPIを隠蔽せよ**: 
    複雑なテーブル設計を隠し、シンプルなビューに対してDMLを許可することで、アプリケーション側の実装を劇的に簡略化できます。
