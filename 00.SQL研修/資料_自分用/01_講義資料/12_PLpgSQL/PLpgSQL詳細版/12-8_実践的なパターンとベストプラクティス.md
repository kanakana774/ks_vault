## 8.0 準備：実践用シミュレーション環境

本章では、外部システムから届いた「未加工のデータ」を既存のマスターテーブルに同期（同期・マージ）するシナリオを想定します。

```sql
-- 1. 外部システムから届いた最新データを一時的に保持するワークテーブル
CREATE TABLE IF NOT EXISTS staging_employees (
    emp_id   integer,
    name     text,
    dept_id  integer,
    salary   numeric
);

-- 2. サンプルデータの投入 (一部は更新、一部は新規)
TRUNCATE staging_employees;
INSERT INTO staging_employees VALUES
(1, 'Taro Tanaka (Updated)', 1, 600000), -- 既存の更新
(5, 'New User A', 2, 400000),           -- 新規追加
(2, 'Hanako Suzuki', 2, 750000);         -- 既存の更新
```

## 8.1 高度な同期パターン：Bulk UPSERT と削除のハンドリング

第3章の単純な `ON CONFLICT` を超えて、実務では「ステージングテーブルとマスターテーブルを比較し、差分だけを同期する」というロジックが頻出します。

### 実演：PL/pgSQLによるインテリジェント・シンクロナイザー
```sql
DO $$
DECLARE
    v_inserted_count integer := 0;
    v_updated_count  integer := 0;
    v_deleted_count  integer := 0;
BEGIN
    -- 1. UPSERT (更新と挿入を一括で処理)
    -- CTE (WITH句) を組み合わせて、更新された件数をカウントするテクニック
    WITH upsert_res AS (
        INSERT INTO employees (emp_id, name, dept_id, salary)
        SELECT emp_id, name, dept_id, salary FROM staging_employees
        ON CONFLICT (emp_id) DO UPDATE 
        SET name = EXCLUDED.name,
            dept_id = EXCLUDED.dept_id,
            salary = EXCLUDED.salary
        WHERE (employees.name, employees.dept_id, employees.salary) 
              IS DISTINCT FROM (EXCLUDED.name, EXCLUDED.dept_id, EXCLUDED.salary)
        RETURNING (xmax = 0) AS is_insert -- xmax=0 なら INSERT、それ以外は UPDATE
    )
    SELECT 
        count(*) FILTER (WHERE is_insert),
        count(*) FILTER (WHERE NOT is_insert)
    INTO v_inserted_count, v_updated_count
    FROM upsert_res;

    -- 2. 同期対象に含まれていない古い従業員を削除（論理削除やアーカイブなど）
    -- ここでは単純削除の例
    DELETE FROM employees 
    WHERE emp_id NOT IN (SELECT emp_id FROM staging_employees)
    AND created_at < now() - interval '1 hour'; -- 登録直後のデータは除外する等の安全策
    
    GET DIAGNOSTICS v_deleted_count = ROW_COUNT;

    RAISE NOTICE '同期が完了しました。';
    RAISE NOTICE '新規挿入: % 件 / 更新: % 件 / 削除: % 件', 
        v_inserted_count, v_updated_count, v_deleted_count;

END;
$$ LANGUAGE plpgsql;
```

## 8.2 パフォーマンス・エンジニアリング：バルク処理とメモリ管理

「100万行のデータをPL/pgSQLでループ処理したら、DBが重くなった（あるいは止まった）」というのは現場でよくある失敗です。

### 鉄則
1.  **可能な限り純粋なSQL（集合演算）で書く**: ループ内での `INSERT/UPDATE` は、SQLエンジンとPL/pgSQLエンジンの切り替え（コンテキストスイッチ）を大量に発生させるため、非常に遅いです。
2.  **どうしてもループが必要な場合はプロシージャで分割コミット**: 第5章で学んだ通り、一つの巨大なトランザクションは、ロックの保持や `UNDO/REDO` ログ（WAL）の圧迫を招きます。

### 実演：性能重視の「配列を用いた一括処理」
一行ずつSQLを投げるのではなく、PL/pgSQL内で一度配列に溜め込み、最後に `UNNEST` を使って一括更新するテクニックです。

```sql
DO $$
DECLARE
    v_ids    integer[] := '{}';
    v_salaries numeric[] := '{}';
    v_batch_size constant integer := 1000;
    r RECORD;
BEGIN
    FOR r IN SELECT emp_id, salary FROM employees LOOP
        -- 配列にデータを蓄積
        v_ids := v_ids || r.emp_id;
        v_salaries := v_salaries || (r.salary * 1.05); -- 5%アップ

        -- バッチサイズに達したら一括更新
        IF array_length(v_ids, 1) >= v_batch_size THEN
            UPDATE employees AS e
            SET salary = t.new_sal
            FROM unnest(v_ids, v_salaries) AS t(id, new_sal)
            WHERE e.emp_id = t.id;
            
            v_ids := '{}';
            v_salaries := '{}';
            COMMIT; -- プロシージャならここでコミット（DOブロックでは不可）
        END IF;
    END LOOP;

    -- 残りのデータを処理
    IF array_length(v_ids, 1) > 0 THEN
        UPDATE employees AS e
        SET salary = t.new_sal
        FROM unnest(v_ids, v_salaries) AS t(id, new_sal)
        WHERE e.emp_id = t.id;
    END IF;
END;
$$ LANGUAGE plpgsql;
```

## 8.3 スキーマ変更への対応とバージョン管理

現場で最も「痛い」のは、関数の引数や戻り値の型を変更した際に、`CREATE OR REPLACE` が効かずに依存関係が壊れることです。

### ベストプラクティス
*   **関数のシグネチャ（引数の数・型）を変える際は、明示的に `DROP FUNCTION` する**: 
    古い関数が残ったまま新しい関数が作られると、多重定義（オーバーロード）状態になり、アプリケーションがどちらを呼んでいるか混乱する原因になります。
*   **引数が多い場合は「名前付き引数」または「JSONB/RECORD」を検討する**: 
    将来的に引数が増えそうな場合は、最初から `JSONB` 一つで受け取るように設計しておくと、DBオブジェクトを再定義せずにロジックだけをアップデートできます。

## 8.4 現場で守るべき「PL/pgSQL 命名・設計規約」

バリバリ書くエンジニアであれば、チーム内での規約を徹底しましょう。以下は一般的な推奨例です。

### 1. 命名規則
*   変数名: `v_column_name` (一般変数), `c_constant_name` (定数)
*   引数名: `p_parameter_name` (引数)
*   カーソル名: `cur_name`
*   レコード名: `rec_name` または `r_name`
*   これらにより、`#variable_conflict use_column` 等に頼らずとも、SQL内の列名との衝突を視覚的に回避できます。

### 2. 関数・プロシージャのヘッダーコメント
関数の先頭には、必ず以下の情報を記述する癖をつけましょう。

```sql
/*
 * 目的: [処理の概要]
 * 引数: 
 *   p_id - 従業員ID
 * 戻り値:
 *   更新後の合計給与額
 * 例外:
 *   P0001 - 指定されたIDが存在しない場合
 * 作成者: [名前]
 * 更新履歴: 2026-02-02 新規作成
 */
```

## 8.5 パフォーマンス・プロファイリング

PL/pgSQL関数が遅いと感じた場合、内部のどのSQLが遅いのかを特定する必要があります。

1.  **`auto_explain` 拡張機能**: `auto_explain.log_nested_statements = on` に設定すると、関数内部で実行された個別のSQLの実行計画がログに出力されます。
2.  **`pg_stat_statements`**: どの関数が何回呼ばれ、平均でどれくらい時間がかかっているかの統計を取得できます。
3.  **`plpgsql_check` (外部拡張)**: コード内の列名のタイポや型変換の矛盾を、実行前に静的解析してくれます。

## 8.6 最後に：注意

PL/pgSQLは非常に強力なツールですが、**「何でもPL/pgSQLで書こうとしないこと」**が最も重要です。

*   **1層目（SQL）**: 単一のSQL文で書けるなら、それが最も速く、最適化され、読みやすい。
*   **2層目（PL/pgSQL）**: 複雑な分岐、データの逐次処理、複数テーブルにまたがる一貫性が必要な場合に採用する。
*   **3層目（アプリケーション）**: DBの外部にあるAPIとの連携、複雑なUI制御、高度な計算ライブラリが必要な場合はアプリ側で処理する。

このバランスを正しく判断する。
