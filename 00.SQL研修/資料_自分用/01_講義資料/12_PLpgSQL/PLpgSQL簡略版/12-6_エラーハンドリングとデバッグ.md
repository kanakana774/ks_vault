# PL/pgSQL 実践講座：第6章 エラーハンドリングとデバッグ

運用されるシステムにおいて、正常系と同等、あるいはそれ以上に重要なのが「異常系」の処理です。PL/pgSQLにおけるエラーハンドリング（例外処理）を正しく理解していないと、不完全なデータ更新を残してしまったり、原因特定に膨大な時間を費やすことになります。

第6章では、意図的なエラーの発生、例外の捕捉、そして実行時の診断情報を取得する高度なテクニックを解説します。


## 6.0 準備：エラーログ記録用テーブルの作成

エラーハンドリングの実演として、エラー情報をテーブルに永続化するパターンを多用するため、専用のログテーブルを作成しておきます。

```sql
CREATE TABLE IF NOT EXISTS error_logs (
    log_id      serial PRIMARY KEY,
    log_time    timestamptz DEFAULT now(),
    user_name   text DEFAULT current_user,
    sql_state   text,
    message     text,
    context     text
);
```

## 6.1 メッセージの通知とエラーの発生 (`RAISE`)

`RAISE` 文は、ユーザーへの通知、警告、および処理の中断（例外の送出）に使用されます。

### 6.1.1 ログレベルの使い分け
*   `DEBUG`, `LOG`, `INFO`, `NOTICE`, `WARNING`: 処理を続行し、クライアントまたはサーバーログにメッセージを送ります。
*   `EXCEPTION`: **現在のトランザクションをアボート（ロールバック）し、例外を投げます。**

### 6.1.2 構造化されたエラー情報 (`USING` 句)
単なるメッセージだけでなく、`DETAIL`（詳細）や `HINT`（ヒント）、そして**独自の `ERRCODE`（SQLSTATE）**を付与すべきです。

**実演：詳細な情報を伴う例外の送出**
```sql
DO $$
DECLARE
    v_salary_limit CONSTANT numeric := 1000000;
    v_input_salary numeric := 1500000;
BEGIN
    IF v_input_salary > v_salary_limit THEN
        RAISE EXCEPTION '給与額が上限を超えています'
            USING 
                DETAIL = format('入力された額 %s は上限 %s を超えています。', v_input_salary, v_salary_limit),
                HINT = '1,000,000以下の値を入力してください。',
                ERRCODE = 'P0001'; -- 独自のSQLSTATE (5桁の文字列)
    END IF;
END;
$$ LANGUAGE plpgsql;
```

## 6.2 例外の捕捉 (`EXCEPTION` ブロック)

`BEGIN ... END` ブロックに `EXCEPTION` 句を追加することで、エラーをキャッチして代替処理を行うことができます。

### 6.2.1 特定の例外と `OTHERS`
PostgreSQLには `unique_violation` や `foreign_key_violation` といった標準的な例外名が定義されています。

**実演：一意制約違反をキャッチして無視する（またはログに書く）**
```sql
DO $$
BEGIN
    -- 重複するIDで挿入を試みる (一意制約違反を発生させる)
    INSERT INTO departments (dept_id, dept_name) VALUES (1, 'Duplicate Dept');

EXCEPTION
    WHEN unique_violation THEN
        RAISE NOTICE '既に存在する部署IDのため、挿入をスキップしました。(SQLSTATE: %)', SQLSTATE;
    WHEN OTHERS THEN
        RAISE NOTICE '予期せぬエラー: % (%)', SQLERRM, SQLSTATE;
END;
$$ LANGUAGE plpgsql;
```

## 6.3 診断情報の取得 (`GET STACKED DIAGNOSTICS`)

例外が発生した際、`SQLSTATE`（エラーコード）と `SQLERRM`（エラーメッセージ）以外にも、**「どこで（Context）」**エラーが起きたかなどの詳細情報が必要になります。`EXCEPTION` ブロック内でのみ使える `GET STACKED DIAGNOSTICS` を使用します。

**実演：エラーの詳細をログテーブルに記録する**
```sql
DO $$
DECLARE
    v_state   text;
    v_msg     text;
    v_context text;
BEGIN
    -- ゼロ除算エラーを発生させる
    PERFORM 1 / 0;

EXCEPTION
    WHEN OTHERS THEN
        -- スタックされた診断情報を取得
        GET STACKED DIAGNOSTICS 
            v_state   = RETURNED_SQLSTATE,
            v_msg     = MESSAGE_TEXT,
            v_context = PG_EXCEPTION_CONTEXT;

        -- ログテーブルに保存（副作用：このDOブロックが正常終了すれば保存される）
        INSERT INTO error_logs (sql_state, message, context)
        VALUES (v_state, v_msg, v_context);

        RAISE NOTICE 'エラーをログに記録しました。内容: %', v_msg;
END;
$$ LANGUAGE plpgsql;

-- ログを確認
SELECT * FROM error_logs ORDER BY log_id DESC LIMIT 1;
```

## 6.4 トランザクションと例外の重要な関係

PL/pgSQLにおいて、`EXCEPTION` 句を持つ `BEGIN ... END` ブロックは、内部的に **「サブトランザクション（セーブポイント）」** を作成します。

1.  `BEGIN` ブロックに入った際にセーブポイントが作成される。
2.  エラーが発生すると、そのブロック内の変更は **自動的にロールバック** される。
3.  `EXCEPTION` 句の処理が実行される。
4.  その後の処理は続行可能（コミットも可能）。

**実演：一部の失敗を許容して全体をコミットする**
```sql
DO $$
BEGIN
    -- 1. 正常な更新
    UPDATE employees SET salary = salary + 1 WHERE emp_id = 1;

    -- 2. エラーが起きるブロック
    BEGIN
        INSERT INTO employees (name, dept_id, salary) VALUES (NULL, 1, 0); -- nameはNOT NULLなのでエラー
    EXCEPTION
        WHEN OTHERS THEN
            RAISE WARNING '2番目の処理は失敗しましたが、継続します。';
            -- ここでこのブロック内の INSERT はロールバックされている
    END;

    -- 3. 別の正常な更新
    UPDATE employees SET salary = salary + 1 WHERE emp_id = 2;
    
    -- DOブロック全体が正常終了すれば、1 と 3 の更新はコミットされる
END;
$$ LANGUAGE plpgsql;
```

## 6.5 デバッグ手法

### 6.5.1 RAISE NOTICE による「変数値のトレース」
現場での最も基本的なデバッグは `RAISE NOTICE` です。複雑な文字列を組み立てる際は `format()` 関数を使いましょう。

```sql
RAISE NOTICE 'Debug: 変数 v_target_id = %, 現在の時刻 = %', v_id, now();
```

### 6.5.2 ASSERT による「前提条件の検証」
「この時点でこの変数は絶対にNULLではないはずだ」というエンジニアの意図をコードに組み込めます。

```sql
-- 事前に設定が必要（セッション単位）
SET plpgsql.check_asserts = on;

DO $$
DECLARE
    v_emp_count integer;
BEGIN
    SELECT count(*) INTO v_emp_count FROM employees;
    
    -- 従業員が一人もいない場合は異常とみなす
    ASSERT v_emp_count > 0, '従業員テーブルが空です。データを確認してください。';
END;
$$ LANGUAGE plpgsql;
```

## 6.6 まとめ

1.  **独自のSQLSTATEを定義せよ**: アプリケーション側で「どのエラーか」を判別しやすくするため、`ERRCODE = 'P0001'` のように独自のコードを付与すると、運用監視が楽になります。
2.  **`EXCEPTION` は最小限の範囲に**: ブロックを大きくしすぎると、どこでエラーが起きたか特定しにくくなります。また、パフォーマンスへの影響も考慮してください。
3.  **`SQLSTATE` と `SQLERRM` は必ずセットで出力**: エラーコードだけ、あるいはメッセージだけでは原因特定に不十分なケースが多いです。
4.  **`RAISE` 後に再スローするか検討せよ**: `EXCEPTION` ブロックでエラーをキャッチしてログを書いた後、そのまま処理を終わらせると呼び出し元は「成功した」と誤認します。本当に中断すべきなら、最後に引数なしの `RAISE;` を実行してエラーを再スローしてください。
