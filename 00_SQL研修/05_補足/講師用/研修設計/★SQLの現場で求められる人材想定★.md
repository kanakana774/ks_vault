# SQLの現場で求められる人材像 — 研修の設計基準

> 更新: 2026-08-21 / 位置づけ: **講師用の設計基準**（研修生に配る文書ではない）
> 目的: 「現場が求めるもの」を、**研修のどこで踏ませるか／踏ませないと決めるか**まで落とす
> 現場の姿そのもの（案件の型・使う技術・タスク例）は [[★常駐先の想定業務★]] が正本。この文書は**そこから人物像と研修要件を導く**役
> 幹／ハッチの定義と作業ルールは [[00_見直しの進め方]] が正本。個別トピックの網羅は [[トピック網羅チェックリスト]]
> 研修生に伝える言い方は [[研修生に伝えること]]（読者が違うので分離した）

---

## 0. 一言でいうと

求められているのは「**単にSQLが書ける人**」ではなく、「**SQLという道具を使って、ビジネス上の課題を正確かつ効率的に解決してくれる人**」。

研修の言葉に翻訳すると:

> **構文を教え切ることがゴールではない。「データの意味を考える」「自分が出した結果を疑う」「遅い理由を説明できる」の3つの癖をつけて送り出す。**

構文の網羅は手段であって目的ではない、というのがこの文書の唯一の主張。

## 1. 求められる5つの資質 → 研修のどこで踏ませるか

**「担保」ではなく「踏ませる」**と書く。合否判定はしないので、到達を保証しているわけではない（「解けたかではなく**踏んだ経験として残ったか**」が実態）。

| # | 資質 | 現場での現れ方 | 研修で踏ませる場所 |
|---|---|---|---|
| 1 | **データの意味を考えられる** | 仕様書どおりに書くだけでなく、業務背景を理解しようとする。だから**仕様の矛盾に気づける** | 実務想定問題の「思考プロセス」節／マスタとトラン／ER図からの経路選択 |
| 2 | **正確性と品質を担保できる** | 販売管理・会計では1円の誤差も許されない。**自分のSQLを疑ってテストする慎重さ**とレビューを受け入れる素直さ | 罠ベースの追加問題群（01〜07章）／実務想定問題の事前検証ステップ |
| 3 | **パフォーマンスを意識できる** | 開発環境の少量データでは通るクエリが本番の数百万件で死ぬ。`EXPLAIN` を読み、インデックスの重要性を理解している | 17章（物理構造・EXPLAIN実測・効かない落とし穴・結合アルゴリズム） |
| 4 | **周辺技術に柔軟に対応できる** | Shell / Python / Java からSQLが呼ばれ、BIツールと繋がる。SQL以外にも抵抗がない | **踏ませない**（§2で割り切り）。地図だけ渡す |
| 5 | **粘り強く原因を追究できる** | 障害調査＝探偵仕事。ログを読み、SQLでデータを追い、絡んだ事象から原因を突き止める | 実務想定問題「障害調査」／ロック調査／アンチジョインでの突合 |

### 二層で見た状態

トピック単位の網羅度では測れないので、**幹／ハッチ(a)／ハッチ(b) の3列に開く**（→ [[00_見直しの進め方]] §2）。

| # | 資質 | 幹（原理を導出させる） | ハッチ(a) 暗記と明示 | ハッチ(b) パターン提示 |
|---|---|---|---|---|
| 1 | データの意味 | ◎ マスタとトラン／正規化／ER図からの経路選択 | — 該当が少ない | ✗ |
| 2 | 正確性と品質 | △ **罠ベースの演習はあるが、検証手順の原理が無い**（§3-1） | ✗ | ✗ |
| 3 | パフォーマンス | ◎ ページ・I/O・B-Tree から説明できる | △ `Index Cond` と `Filter` はあるが**暗記対象と明示していない** | ✗ |
| 4 | 周辺技術 | ✗ 意図的に踏ませない | — | — |
| 5 | 原因追究 | △ 道具立てが未整備（[[トピック網羅チェックリスト]] A-3・A-6） | ✗ 方言表・カタログ名が無い（同 B-3・A-6） | ✗ |

◎=ある ／ △=部分的 ／ ✗=無い ／ —=該当なし

**ハッチ(b) が全部 ✗。** 導出についてこれなかった人向けの「このパターンを思い出して」が一つも無い。**項目数では最大の欠落。**

### 1-1. データの意味を考えられる人

ただ仕様書通りにクエリを書くだけでなく、「**このデータは何を表しているのか**」「**なぜこの集計が必要なのか**」といった業務背景を理解しようと努める人材は重宝される。データの意味を理解することで、**仕様の矛盾に気づいたり**、より良い集計方法を提案したりできるから。

**踏ませている場所（既にできている）**

- [[01_RDBMSとDDL]] のコラム「マスタとトラン」＝テーブルを見て役割を判断する語彙
- [[00_なぜテーブルを分けるのか]]・[[00_補足_正規化の詳細]] ＝なぜこの形なのかを説明できる
- [[08_補足_結合]] §3「宣言的視点でルートを探す」＝ER図から**意味の正しい経路**を選ぶ。同じ結果に見えて意味が違う結合を区別させる、この教材の要
- 実務想定問題の各問に付いている **「【システム上の目的】」と「思考プロセス」** ＝「何のための集計か」を先に読ませる形式になっている

**この資質は現行教材の設計思想そのもの**なので、追加は不要。むしろ**削らないよう守る**対象。完全に製品非依存なので移植可能性の問題も無い。

### 1-2. 正確性と品質を担保できる人

業務システム、特に販売管理や会計システムでは1円の誤差も許されない。自分が書いたSQLが本当に正しい結果を返すか、**あらゆるケースを想定してテストできる慎重さ**や、他者のレビューを真摯に受け入れる素直さが求められる。

**踏ませている場所（強い）** — 01〜07章の追加問題は、ほぼ全部この資質のための教材になっている。

- 「〜ではない」で絞ったら件数が合わない（NULL）／`||` と `CONCAT` のNULL差／目に見えない空白／`COUNT(*)` と `COUNT(列)`／整数除算／`WHEN` の書き順／`TIMESTAMP` への `BETWEEN`／`LIMIT`・`OFFSET` の重複と欠落／年跨ぎで壊れる月次集計
- `WHERE` は「対象を選ぶ」だけでなく「**対象外を守る**」ために書く（03_UPDATE 問題11）

**穴**: → §3-1（**書いたSQLを自分で検証する手順**が講義に無い）

### 1-3. パフォーマンスを意識できる人

開発環境の少量データでは問題なく動いたクエリが、本番環境の数百万件のデータでは非常に遅くなる、というのはよくある話。`EXPLAIN`（実行計画）で非効率な処理を見つけたり、インデックスの重要性を理解している人材は高く評価される。

**踏ませている場所（この研修の強み）** — 17章はここに正面から答えている。

- [[17-1_導入_物理構造とスキャン方式]] ＝なぜ速いのかを物理層（ページ・I/O・B-Tree）から説明できる。**ここは製品非依存の幹**
- [[17-2_実践_EXPLAINの読み方]] ＝`Index Cond` と `Filter` の違い、**同じインデックスでも値によって計画が変わる**、効かない落とし穴7種。**すべて実測**
- 結合アルゴリズム（Nested Loop / Hash / Merge）は **17-2 §3-2 で「引く／計算する／並走する」の一言まで**。実測での比較は講義では扱わず、[[17-3_補足_結合アルゴリズム_詳細]]（詳細版・非配布）に置いてある

「開発環境では出ない」という人材想定の核心そのものが、**ケース4（値によって計画が変わる）**として教材化できている。

**穴**: 17章には **🐘（PostgreSQL固有）の切り分けが1つも無い**（15章にはある）。`Bitmap Scan`・`Buffers`・`Heap Fetches` は固有名で、原理は移植可能。**幹とハッチ(a)が混ざったまま。**

### 1-4. 周辺技術にも柔軟に対応できる人

SQLはあくまでシステムの一部。Shellスクリプトや Python からSQLが実行されたり、BIツールと連携したりすることが多いため、SQL以外の技術にも抵抗なく学んでいける姿勢が重要。

**判断: 研修では踏ませない。** → §2

### 1-5. 粘り強く原因を追究できる人

「障害調査・原因分析」はまさに探偵の仕事。ログを読み、SQLでデータを一つひとつ追いかけ、複雑に絡み合った事象の中から原因を突き止めるには、論理的思考力と粘り強さが不可欠。

**踏ませている場所（部分的）**

- 実務想定問題「問題2：障害調査 - 顧客からの問い合わせ対応」＝この資質のための唯一の演習
- [[15-2_実践_ロックとMVCC]] §1-3「誰が誰を待っているのかを調べる」＝止まっている原因を突き止める
- [[シーケンスが飛ぶ現象]]（`05_補足/過去にあった質問/`）＝「なぜそうなるか」を追う型の資料。この蓄積を増やすこと自体がこの資質の教材になる

**穴**: 調査の**道具**が揃っていない。孤児レコード検出・件数突合（アンチジョイン、[[トピック網羅チェックリスト]] A-3）と、既存テーブル構造をSQLで調べる手段（同 A-6）。さらに「既存の長いSQLを読む」演習が無い（同 B-1）。**この3つは全部この資質に紐づく**ので、優先度を上げる根拠になる。

とくに **A-6（`information_schema`）は配属先DBで最初にやること**。配属先が不定なので、ここは最優先級。

## 2. 研修で踏ませないと決めるもの（割り切り）

設計基準として大事なのは「やること」より「**やらないと決めたこと**」。求められているのは事実だが、SQL単体の研修では扱わない。

**理由を期間やカリキュラムの月数に依拠させない。** かつて「実質数日〜数週だから」「2か月目のAPI研修が担保するから」と書いていたが、期間は1か月（約20日）で、**外部研修生に2か月目は無い**。理由が前提の変化で無効になると、表ごと信用できなくなる。

| 求められているが扱わない | 理由 | 代わりに渡すもの |
|---|---|---|
| Shell / Python / Java からのSQL実行 | **研修生が他のプログラミング言語に触っているかも怪しい。** SQL単体の研修として設計している | 「SQLは呼ばれる側」という位置づけの説明だけ |
| BIツール（Tableau / Power BI） | 案件で入ってから覚えれば足りる。汎用性が低い | — |
| DWH系（BigQuery / Snowflake / dbt / Airflow） | [[★常駐先の想定業務★]] の②だが、①業務システム系が主戦場 | [[バックエンドDBカオスマップ_2025末]]。**位置づけは「DWHを切る代わり」ではなく「配属先DBが何であってもよいことの説明装置」** |
| 論理設計を自分でやる演習 | 正規化は読み物どまり。設計は実務の中で身につく領域 | [[00_なぜテーブルを分けるのか]]・[[08_補足_結合]] で読解まで |
| 要件定義 | **要件は与えられる前提**で演習を設計している | — |
| クラウド・コンテナ・CI/CD | SQL単体の研修の範囲外 | — |
| パーティショニング・行レベルセキュリティ | 研修範囲としては過剰（[[トピック網羅チェックリスト]] C） | — |
| 設定値チューニング（`work_mem`・`random_page_cost`） | **設定値を決めるのは配属直後の役割ではない。** ただし「依頼できることを知っている」のは役割の内 | トラブルの語彙として一言 |

**この表の意味**: 「求められている＝研修に入れる」ではない。入れない判断をここに書いておかないと、**毎回同じ検討をやり直すことになる**。

## 3. この整理で見つかった抜け（人材想定から導かれるのに教材が無いもの）

[[トピック網羅チェックリスト]] は「構文」の網羅を見た。こちらは「資質」から見た抜けで、**構文の一覧には出てこない**種類のもの。

### 3-1. 書いたSQLを自分で検証する作法が、講義にも通常演習にも無い【最重要】

資質#2（正確性）の核心。「あらゆるケースを想定してテストできる慎重さ」を**具体的な手順**として教えている場所が無い。

現状ある場所は**実務想定問題の解説の中だけ**:

> 「`UPDATE` を実行する前に、必ず『どのような値に更新されるのか』を `SELECT` で確認するのが鉄則です。この**『事前検証』プロセスを研修で徹底させます**」
> （[[業務システムを意識した問題_回答付]] 問題3の講師向け解説）
> 「件数確認をしてからコミットする流れは『分かっているエンジニア』の動き」（[[電子カルテの業務想定]]）

**自分で「研修で徹底させます」と書いているのに、それを教える教材が無い。** 実務想定問題は最後にやる発展問題なので、そこまで到達しない研修生には一度も伝わらない。

**なぜ最優先か**

- **完全に製品非依存。** 配属先DBが何であっても通じる（原則5に最も強い）
- **1ページで足りる。** 作るコストが最も低い
- **合否判定をしない方針と噛み合う。** 渡すのは作法であって、正解を採点するものではない
- 資質#2 が「幹 △」なのは、罠ベースの演習は踏ませているが**原理を導出させていない**から。ここを埋めると △ → ◎ になる

**教える中身は教材側に持つ。** → 置き場: `01_講義資料/00_SQLを検証する.md`（[[00_SQLを書く時の注意]] の隣。**書き方の作法**と**検証の作法**の対）。この文書は「なぜ要るか」だけを持つ。

### 3-2. 業務担当者との連携が人材想定に入っていない

[[★常駐先の想定業務★]] の「SES案件としての特徴」には**書いてある**:

> 「業務担当者との連携が多い（仕様確認・抽出条件相談など）」

しかしこの文書の5資質には入っていない。実際には**現場で最も評価が分かれる部分**（「言われたものを作る人」と「条件の曖昧さを潰してから作る人」の差）。資質#1（データの意味）の裏返しでもある。

研修で踏ませられる範囲は限られるが、**問題文の曖昧さを意図的に残して「何を確認しますか？」と問う**形なら演習にできる。

> なお [[改善案]] には受講生の声として「問題文がわかりにくい ⇒ 実務で必要ない日本語能力が求められるのは無駄」がある。**曖昧さは減らすべきだが、「業務仕様として本質的に曖昧なもの」は別**。前者は直し、後者は演習の材料にする、という切り分けをしておくと両方立つ。

### 3-3. 本番データを触る怖さ・作業手順が体系化されていない

「1円の誤差も許されない」の実務的な意味は、**事故らない手順を持っていること**。

- `WHERE` 無し `UPDATE` / `DELETE` の事故 → 03_UPDATE 問題11・問題13 が部分的にカバー
- 自動コミットのツール差 → [[15-1_導入_トランザクションとACID]] §2-2 でカバー済み（良い）
- 長時間ロック・大量更新の分割 → [[15-2_実践_ロックとMVCC]] と PL/pgSQL 章に散在
- 作業前の退避・戻し方 → **無い**

散在している上記を「本番作業の作法」として1枚に集約する価値がある（§3-1 と同じノートでよい）。

## 4. 研修方針との整合（迷ったら見るところ）

| 論点 | この文書が言っていること | 現状 | 結論 |
|---|---|---|---|
| ウィンドウ関数・CTE | 「使えると市場価値が大きく上がる」 | 発展問題での使用制限があった | **制限の正体は「先出し禁止」**（→ [[00_見直しの進め方]] 原則6）。講義していない構文を課題で求めないという話で、**範囲そのものの禁止ではない**。18章を講義した後は使ってよい。段階的に解禁する |

## 5. この文書の使い方

- 新しいトピックを入れるか迷ったら、**§1のどの資質に効くか**を言えるかで判断する。言えないものは入れない
- 入れると決めたら、次に **幹か／ハッチ(a)か／ハッチ(b)か**を決める（→ [[00_見直しの進め方]] §4）。「入れる／入れない」の二値で止めない
- 幹に置くなら、**ハッチ(b)（このパターンを思い出して）も一緒に作る**。習熟速度の差はハッチで受ける
- 「求められている」だけでは入れる理由にならない。**§2の割り切り表**に足して閉じる
- 個別の構文の網羅は [[トピック網羅チェックリスト]]、作業項目は [[改善案]]、進め方は [[00_見直しの進め方]]。この文書は**判断基準**だけを持つ
