# 関数の属性と最適化

## 〜`VOLATILE` / `PARALLEL` / `COST` / `ROWS` が実行計画を決める〜

講義版では `CREATE FUNCTION` に `LANGUAGE plpgsql` しか書きませんでした。実は `CREATE FUNCTION` には**オプティマイザに渡すヒント**を書く場所がいくつもあり、そこを埋めるかどうかで実行計画がまるごと変わります。研修生が「関数にまとめたのに遅い」と言ってきたとき、原因はほぼここにあります。

この資料では、関数に付けられる属性を一つずつ実測で確かめます。あわせて、講義版でまったく触れなかった **`LANGUAGE sql` との違い**、**明示カーソル**、**`CREATE OR REPLACE` が失敗する条件**を扱います。

> **この資料の前提**
> - PostgreSQL 17.5 で動作確認しています。掲載している出力・実行時間・エラーメッセージは**すべて実測**です。
> - **これは講師用の資料です。研修生には配りません。** 講義で説明する必要はありませんが、質問されたときに答えられるようにしておく範囲です。
> - 対応する講義版: [[12-4_関数とプロシージャと例外処理|12-4 関数とプロシージャと例外処理]]（特に §1-2「行数ぶん呼ばれる」と §10「片付け」）
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] のものです。性能比較のためだけに `demo_nums`（20 万行）・`demo_big`（200 万行）を作っています。

## 1. 変動性（Volatility）

### 1-1. 3 つの区分は「オプティマイザへの約束」

| 区分 | 意味 | 破ったときに困る人 |
|:---|:---|:---|
| `VOLATILE`（既定） | 同じ引数でも呼ぶたび結果が変わりうる。テーブルを更新してもよい | — |
| `STABLE` | **1 つの SQL 文の中では**同じ引数に同じ結果を返す。テーブルは読めるが書けない | オプティマイザ |
| `IMMUTABLE` | データベースの状態に**まったく依存しない**。引数が同じなら永遠に同じ結果 | オプティマイザとインデックス |

重要なのは、**PostgreSQL はこの宣言を検証しない**ということです。`IMMUTABLE` と書いた関数がテーブルを読んでいても、作成時にはエラーになりません（§1-8 で壊してみます）。これは「型」ではなく「約束」です。

### 1-2. 【実測】`WHERE` 句で何回呼ばれるか

中身が同じで変動性だけ違う 3 つの関数を作り、`RAISE NOTICE` で呼ばれた回数を数えます。

```sql
CREATE OR REPLACE FUNCTION f_vol(p_x integer) RETURNS integer
LANGUAGE plpgsql VOLATILE AS $$
BEGIN
    RAISE NOTICE 'f_vol が呼ばれた';
    RETURN p_x;
END;
$$;

CREATE OR REPLACE FUNCTION f_stb(p_x integer) RETURNS integer
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RAISE NOTICE 'f_stb が呼ばれた';
    RETURN p_x;
END;
$$;

CREATE OR REPLACE FUNCTION f_imm(p_x integer) RETURNS integer
LANGUAGE plpgsql IMMUTABLE AS $$
BEGIN
    RAISE NOTICE 'f_imm が呼ばれた';
    RETURN p_x;
END;
$$;
```

`memberships` は 4 行です。この 4 行のテーブルに対して、同じ条件を 3 通りで実行します。

```sql
SELECT count(*) FROM memberships WHERE membership_id > f_vol(0);
SELECT count(*) FROM memberships WHERE membership_id > f_stb(0);
SELECT count(*) FROM memberships WHERE membership_id > f_imm(0);
```

```
--- VOLATILE ---
NOTICE:  f_vol が呼ばれた
NOTICE:  f_vol が呼ばれた
NOTICE:  f_vol が呼ばれた
NOTICE:  f_vol が呼ばれた
 count
-------
     4
(1 row)

--- STABLE ---
NOTICE:  f_stb が呼ばれた
NOTICE:  f_stb が呼ばれた
NOTICE:  f_stb が呼ばれた
NOTICE:  f_stb が呼ばれた
NOTICE:  f_stb が呼ばれた
 count
-------
     4
(1 row)

--- IMMUTABLE ---
NOTICE:  f_imm が呼ばれた
 count
-------
     4
(1 row)
```

- `VOLATILE` … **4 回**（行数ぶん）
- `STABLE` … **5 回**（行数ぶん ＋ 1 回）
- `IMMUTABLE` … **1 回**

`IMMUTABLE` が 1 回で済んでいるのは、**プラン作成時に定数へ畳み込まれた**（constant folding）からです。`STABLE` の「＋1 回」の正体は次節で分かります。

### 1-3. 【実測】`EXPLAIN` だけでも呼ばれる

実行せず、計画を立てるだけにしてみます。

```sql
EXPLAIN (COSTS OFF) SELECT count(*) FROM memberships WHERE membership_id > f_vol(0);
EXPLAIN (COSTS OFF) SELECT count(*) FROM memberships WHERE membership_id > f_stb(0);
EXPLAIN (COSTS OFF) SELECT count(*) FROM memberships WHERE membership_id > f_imm(0);
```

```
--- VOLATILE ---
                 QUERY PLAN
--------------------------------------------
 Aggregate
   ->  Seq Scan on memberships
         Filter: (membership_id > f_vol(0))
(3 rows)

--- STABLE ---
NOTICE:  f_stb が呼ばれた
                 QUERY PLAN
--------------------------------------------
 Aggregate
   ->  Seq Scan on memberships
         Filter: (membership_id > f_stb(0))
(3 rows)

--- IMMUTABLE ---
NOTICE:  f_imm が呼ばれた
             QUERY PLAN
-------------------------------------
 Aggregate
   ->  Seq Scan on memberships
         Filter: (membership_id > 0)
(3 rows)
```

3 点読み取れます。

1. **`VOLATILE` は `EXPLAIN` では 1 回も呼ばれない。** 実行しない限り呼べないからです。
2. **`STABLE` は `EXPLAIN` で 1 回呼ばれる。** オプティマイザが**選択率の見積もりのために引数を実際に評価**します。これが §1-2 の「＋1 回」です。
3. **`IMMUTABLE` は `EXPLAIN` で 1 回呼ばれ、その結果がプランに焼き付く。** `Filter:` が `f_imm(0)` ではなく **`0`** になっています。関数呼び出しがプランから消えました。

> ⚠️ **「`EXPLAIN` は安全だから本番で叩いていい」は正確ではありません。**
> `STABLE` / `IMMUTABLE` な関数が定数引数で使われていると、`EXPLAIN` だけでもその関数は実行されます。副作用のある処理を `STABLE` と偽って宣言していると、`EXPLAIN` で発火します。

### 1-4. 【実測】実行計画が変わる（インデックスを使えるかどうか）

20 万行のテーブルで見ると、差は計画の形に出ます。

```sql
CREATE TABLE demo_nums (id integer PRIMARY KEY, val integer);
INSERT INTO demo_nums SELECT i, i % 1000 FROM generate_series(1, 200000) AS i;
ANALYZE demo_nums;

EXPLAIN SELECT count(*) FROM demo_nums WHERE id > f_vol(199990);
EXPLAIN SELECT count(*) FROM demo_nums WHERE id > f_stb(199990);
EXPLAIN SELECT count(*) FROM demo_nums WHERE id > f_imm(199990);
```

```
--- VOLATILE ---
                              QUERY PLAN
-----------------------------------------------------------------------
 Aggregate  (cost=53551.67..53551.68 rows=1 width=8)
   ->  Seq Scan on demo_nums  (cost=0.00..53385.00 rows=66667 width=0)
         Filter: (id > f_vol(199990))
(3 rows)

--- STABLE ---
NOTICE:  f_stb が呼ばれた
                                         QUERY PLAN
--------------------------------------------------------------------------------------------
 Aggregate  (cost=8.87..8.88 rows=1 width=8)
   ->  Index Only Scan using demo_nums_pkey on demo_nums  (cost=0.67..8.84 rows=10 width=0)
         Index Cond: (id > f_stb(199990))
(3 rows)

--- IMMUTABLE ---
NOTICE:  f_imm が呼ばれた
                                         QUERY PLAN
--------------------------------------------------------------------------------------------
 Aggregate  (cost=8.62..8.63 rows=1 width=8)
   ->  Index Only Scan using demo_nums_pkey on demo_nums  (cost=0.42..8.59 rows=10 width=0)
         Index Cond: (id > 199990)
(3 rows)
```

**これが変動性のいちばん重要な帰結です。**

- `VOLATILE` … 行ごとに値が変わりうるので、**インデックスの検索条件（`Index Cond`）にできない**。全件走査して `Filter` で捨てるしかない
- `STABLE` … 文の中では一定なので **`Index Cond` にできる**。見積もり行数も `66667` → `10` と正確になった
- `IMMUTABLE` … 定数に置き換わるので、そもそも関数がない状態と同じ

`Index Cond` になると、**その値の評価は 1 回だけ**になります（スキャンキーを組み立てるときの 1 回）。実測すると `EXPLAIN` 時の 1 回と合わせて 2 回です。

```sql
SELECT count(*) FROM demo_nums WHERE id > f_stb(199990);
```

```
NOTICE:  f_stb が呼ばれた
NOTICE:  f_stb が呼ばれた
 count
-------
    10
(1 row)
```

### 1-5. 【実測】速度差

`RAISE NOTICE` を除いた同じ 3 つの関数（`g_vol` / `g_stb` / `g_imm`）で計ります。

```sql
\timing on
SELECT count(*) FROM demo_nums WHERE id > g_vol(199990);
SELECT count(*) FROM demo_nums WHERE id > g_stb(199990);
SELECT count(*) FROM demo_nums WHERE id > g_imm(199990);
```

```
--- 1回目 ---
VOLATILE  : Time: 64.479 ms
STABLE    : Time:  0.658 ms
IMMUTABLE : Time:  0.274 ms

--- 2回目 ---
VOLATILE  : Time: 52.512 ms
STABLE    : Time:  0.673 ms
IMMUTABLE : Time:  0.392 ms
```

**同じ結果（10 行）を返すのに 80〜200 倍の差**です。中身がまったく同じ関数で、`CREATE FUNCTION` に単語 1 つ書き足すかどうかだけの違いです。

### 1-6. `STABLE` は「1 回しか評価されない」保証ではない

ここは誤解しやすいところです。**`STABLE` は「オプティマイザが定数扱いしてよい」という許可であって、「1 回しか呼ばない」という保証ではありません。** 実際の評価回数は選ばれた計画次第です。

同じ `f_stb(0)` が、

- `Index Cond` になった計画（§1-4）では **実行時 1 回**
- `Filter` になった計画（§1-2 の `memberships`）では **行ごとに 1 回**（4 行なら 4 回）

でした。**「`STABLE` にしたから中の `SELECT` は 1 回で済む」と考えて重い処理を入れるのは危険です。**

### 1-7. 【実測】関数インデックスは `IMMUTABLE` でないと作れない

```sql
CREATE OR REPLACE FUNCTION name_key_vol(p_name text) RETURNS text
LANGUAGE plpgsql VOLATILE  AS $$ BEGIN RETURN upper(p_name); END; $$;
CREATE OR REPLACE FUNCTION name_key_stb(p_name text) RETURNS text
LANGUAGE plpgsql STABLE    AS $$ BEGIN RETURN upper(p_name); END; $$;
CREATE OR REPLACE FUNCTION name_key_imm(p_name text) RETURNS text
LANGUAGE plpgsql IMMUTABLE AS $$ BEGIN RETURN upper(p_name); END; $$;

CREATE INDEX idx_pv ON products (name_key_vol(product_name));
CREATE INDEX idx_ps ON products (name_key_stb(product_name));
CREATE INDEX idx_pi ON products (name_key_imm(product_name));
```

```
--- VOLATILE でインデックスを作る ---
ERROR:  functions in index expression must be marked IMMUTABLE
--- STABLE でインデックスを作る ---
ERROR:  functions in index expression must be marked IMMUTABLE
--- IMMUTABLE でインデックスを作る ---
CREATE INDEX
```

**`STABLE` でも拒否されます。** インデックスは「一度書いたら、あとで読み直したときも同じ値であること」を要求するので、文をまたいで値が変わりうる `STABLE` では足りません。

### 1-8. 【実測】`IMMUTABLE` の約束を破るとインデックスが嘘をつく

PostgreSQL は宣言を検証しません。だから**テーブルを読む関数を `IMMUTABLE` と書いてもインデックスが作れてしまいます**。そして壊れます。

```sql
CREATE TABLE demo_rate (id integer PRIMARY KEY, rate numeric);
INSERT INTO demo_rate VALUES (1, 0.10);

CREATE OR REPLACE FUNCTION bad_taxed(p_price numeric) RETURNS numeric
LANGUAGE plpgsql IMMUTABLE AS $$          -- ★ 嘘の IMMUTABLE
DECLARE
    v_rate numeric;
BEGIN
    SELECT rate INTO v_rate FROM public.demo_rate WHERE id = 1;   -- 実は DB を読んでいる
    RETURN round(p_price * (1 + v_rate), 2);
END;
$$;

CREATE TABLE demo_price (id integer PRIMARY KEY, price numeric);
INSERT INTO demo_price VALUES (1, 1000), (2, 2000);
CREATE INDEX idx_bad ON demo_price (bad_taxed(price));   -- 通ってしまう
ANALYZE demo_price;
```

税率を変えてから、関数を直接呼ぶ場合とインデックスを使う場合を比べます。

```sql
UPDATE demo_rate SET rate = 0.20 WHERE id = 1;   -- demo_price は一切変更していない

SELECT bad_taxed(1000) AS now_taxed;

SET enable_seqscan = off;
EXPLAIN (COSTS OFF) SELECT id FROM demo_price WHERE bad_taxed(price) = 1100;
SELECT id FROM demo_price WHERE bad_taxed(price) = 1100;
SELECT id FROM demo_price WHERE bad_taxed(price) = 1200;
```

```
 now_taxed
-----------
   1200.00
(1 row)

                     QUERY PLAN
----------------------------------------------------
 Index Scan using idx_bad on demo_price
   Index Cond: (bad_taxed(price) = '1100'::numeric)
(2 rows)

 id
----
  1
(1 row)

 id
----
(0 rows)
```

**関数を直接呼べば 1200 なのに、インデックス経由で 1100 を探すと当たり、1200 を探すと当たりません。** インデックスは作成時の値（税率 0.10）を保存したままで、`UPDATE demo_rate` はインデックスの再構築を引き起こしません。PostgreSQL は `demo_price` の行が変わっていないので、更新する理由がないのです。

> ⚠️ **「たまに 1 件だけ検索結果が合わない」という不具合の典型的な原因です。**
> `REINDEX` すればその瞬間は直りますが、原因は関数の宣言なので必ず再発します。**`IMMUTABLE` は「テーブルもシーケンスも設定パラメータも一切参照しない」ときだけ書いてください。** タイムゾーン依存の日付関数（`timestamptz` → `date` のキャストなど）も `IMMUTABLE` ではありません。

### 1-9. 既定値は `VOLATILE`

何も書かないと `VOLATILE` になります。カタログで確認できます。

```sql
CREATE OR REPLACE FUNCTION def_pl(p_x integer) RETURNS integer
LANGUAGE plpgsql AS $$ BEGIN RETURN p_x; END; $$;

SELECT proname, provolatile, proparallel, prosecdef, proleakproof, procost, prorows
  FROM pg_proc WHERE proname = 'def_pl';
```

```
 proname | provolatile | proparallel | prosecdef | proleakproof | procost | prorows
---------+-------------+-------------+-----------+--------------+---------+---------
 def_pl  | v           | u           | f         | f            |     100 |       0
(1 row)
```

`provolatile` の `v` が `VOLATILE`（`s` = `STABLE`、`i` = `IMMUTABLE`）です。**つまり、講義版で作った関数はすべて `VOLATILE` として扱われています。** 参考に組み込み関数を見ると、方針の違いがはっきりします。

```sql
SELECT proname, provolatile, proparallel, procost FROM pg_proc
 WHERE proname IN ('upper','now','random','length') AND pronargs <= 1 ORDER BY proname;
```

```
 proname | provolatile | proparallel | procost
---------+-------------+-------------+---------
 length  | i           | s           |       1
 now     | s           | s           |       1
 random  | v           | r           |       1
 upper   | i           | s           |       1
(抜粋)
```

`now()` が `STABLE` なのは「同じ文の中では同じ時刻を返す」からです。`random()` は `VOLATILE` かつ `PARALLEL RESTRICTED` です。

## 2. 並列実行の安全性（`PARALLEL`）

### 2-1. 3 つの区分

| 区分 | 意味 |
|:---|:---|
| `PARALLEL SAFE` | 並列ワーカーの中で実行してよい |
| `PARALLEL RESTRICTED` | リーダープロセスでなら実行してよい（＝その部分は並列化されない） |
| `PARALLEL UNSAFE`（既定） | 並列実行そのものを禁止する |

`UNSAFE` にすべきなのは、テーブルを書き換える、一時テーブルを触る、シーケンスを進める、`SET` でパラメータを変える、などの関数です。

### 2-2. 【実測】並列実行が消える

200 万行（100 MB）のテーブルで比べます。

```sql
CREATE TABLE demo_big (id integer, val integer, txt text);
INSERT INTO demo_big SELECT i, i % 1000, 'row ' || i FROM generate_series(1, 2000000) AS i;
ANALYZE demo_big;

CREATE OR REPLACE FUNCTION p_safe(p_x integer) RETURNS integer
LANGUAGE plpgsql IMMUTABLE PARALLEL SAFE       AS $$ BEGIN RETURN p_x % 7; END; $$;
CREATE OR REPLACE FUNCTION p_restricted(p_x integer) RETURNS integer
LANGUAGE plpgsql IMMUTABLE PARALLEL RESTRICTED AS $$ BEGIN RETURN p_x % 7; END; $$;
CREATE OR REPLACE FUNCTION p_unsafe(p_x integer) RETURNS integer
LANGUAGE plpgsql IMMUTABLE PARALLEL UNSAFE     AS $$ BEGIN RETURN p_x % 7; END; $$;

EXPLAIN (COSTS OFF) SELECT count(*) FROM demo_big WHERE p_safe(val) = 3;
EXPLAIN (COSTS OFF) SELECT count(*) FROM demo_big WHERE p_restricted(val) = 3;
EXPLAIN (COSTS OFF) SELECT count(*) FROM demo_big WHERE p_unsafe(val) = 3;
```

```
--- PARALLEL SAFE ---
                   QUERY PLAN
-------------------------------------------------
 Finalize Aggregate
   ->  Gather
         Workers Planned: 2
         ->  Partial Aggregate
               ->  Parallel Seq Scan on demo_big
                     Filter: (p_safe(val) = 3)
(6 rows)

--- PARALLEL RESTRICTED ---
               QUERY PLAN
-----------------------------------------
 Aggregate
   ->  Seq Scan on demo_big
         Filter: (p_restricted(val) = 3)
(3 rows)

--- PARALLEL UNSAFE ---
             QUERY PLAN
-------------------------------------
 Aggregate
   ->  Seq Scan on demo_big
         Filter: (p_unsafe(val) = 3)
(3 rows)
```

時間も測ります。

```
PARALLEL SAFE   : Time: 393.610 ms / 281.258 ms
PARALLEL UNSAFE : Time: 897.198 ms / 809.869 ms
```

**約 2.5〜2.9 倍**（`max_parallel_workers_per_gather = 2` の環境）。ワーカー数を増やせる環境なら差はもっと開きます。

### 2-3. 既定は `PARALLEL UNSAFE`

§1-9 の `proparallel` が `u` でした。**つまり、自分で書いた PL/pgSQL 関数を `WHERE` 句に置いた瞬間、そのクエリは並列実行できなくなります。** 「集計クエリに自作関数を 1 つ足したら急に遅くなった」の原因はこれです。

> 💡 **`RESTRICTED` と `UNSAFE` の使い分け**
> 実行計画上、この 2 つの結果はしばしば同じ（並列なし）になります。違うのは、クエリの**他の部分**が並列化できるかどうかです。`RESTRICTED` なら他の枝は並列化されえますが、`UNSAFE` はクエリ全体の並列化を禁止します。**読むだけの関数なら `SAFE` を明示するのが基本**です。

## 3. `COST` と `ROWS`

### 3-1. 何を表す数字か

| 属性 | 意味 | 既定値 |
|:---|:---|:---|
| `COST` | **1 回の呼び出しの見積もりコスト**。単位は `cpu_operator_cost`（既定 0.0025） | 100（C 言語以外） |
| `ROWS` | 集合を返す関数が**返す行数の見積もり** | 1000（集合を返す関数のみ） |

`COST 100` は「1 回の呼び出しが基本的な演算子 100 個ぶん」という申告です。§1-4 の `VOLATILE` の計画で `Seq Scan` のコストが `53385` と大きかったのは、この 100 が 20 万行ぶん足されているからです。

### 3-2. 【実測】`COST` で条件の評価順が変わる

オプティマイザは `WHERE` の条件を**安い順に並べ替えます**。中身が同じで `COST` だけ違う 2 つの関数で確かめます。

```sql
CREATE OR REPLACE FUNCTION c_cheap(p_x integer) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE PARALLEL SAFE COST 1     AS $$ BEGIN RETURN p_x % 7 = 3; END; $$;
CREATE OR REPLACE FUNCTION c_pricey(p_x integer) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE PARALLEL SAFE COST 10000 AS $$ BEGIN RETURN p_x % 7 = 3; END; $$;

EXPLAIN SELECT count(*) FROM demo_big WHERE c_cheap(val)  AND id = 12345;
EXPLAIN SELECT count(*) FROM demo_big WHERE c_pricey(val) AND id = 12345;
```

```
--- COST 1 ---
                                   QUERY PLAN
---------------------------------------------------------------------------------
 Aggregate  (cost=26238.10..26238.11 rows=1 width=8)
   ->  Gather  (cost=1000.00..26238.10 rows=1 width=0)
         Workers Planned: 2
         ->  Parallel Seq Scan on demo_big  (cost=0.00..25238.00 rows=1 width=0)
               Filter: (c_cheap(val) AND (id = 12345))
(5 rows)

--- COST 10000 ---
                                     QUERY PLAN
------------------------------------------------------------------------------------
 Aggregate  (cost=20857488.10..20857488.11 rows=1 width=8)
   ->  Gather  (cost=1000.00..20857488.10 rows=1 width=0)
         Workers Planned: 2
         ->  Parallel Seq Scan on demo_big  (cost=0.00..20856488.00 rows=1 width=0)
               Filter: ((id = 12345) AND c_pricey(val))
(5 rows)
```

`Filter:` の**順序が入れ替わっています**。`COST 10000` の側では安い `id = 12345` が先に評価され、`AND` の短絡評価で関数はほとんど呼ばれません。

**つまり `COST` を正しく申告すると、重い関数を「呼ばれないように」してもらえます。** 中で `SELECT` を投げる関数に既定の 100 を放置するのは過小申告です。中でクエリを 1 本投げるなら数千〜数万のオーダーが実態に近くなります。

### 3-3. 【実測】`ROWS` を誤ると実行計画が崩れる

## 4. `LANGUAGE sql` と `LANGUAGE plpgsql` の決定的な違い

### 4-1. インライン展開されるかどうか

**`LANGUAGE sql` の関数は、条件を満たすと呼び出し元のクエリに展開されて消えます（インライン展開）。** `LANGUAGE plpgsql` の関数は**絶対に展開されません**。オプティマイザから見て中身が見えないブラックボックスです。

インライン展開の主な条件（スカラー関数の場合）:

- `LANGUAGE sql` である
- 本体が単一の `SELECT` である
- `SECURITY DEFINER` でない、`SET` 句を持たない
- 呼び出し元より変動性が緩くない（`IMMUTABLE` 宣言なのに中身が `VOLATILE` だと展開されない）

### 4-2. 【実測】集合を返す関数

```sql
CREATE OR REPLACE FUNCTION nums_gt_sql(p_min integer) RETURNS SETOF demo_nums
LANGUAGE sql STABLE AS $$
    SELECT * FROM demo_nums WHERE id > p_min;
$$;

CREATE OR REPLACE FUNCTION nums_gt_pl(p_min integer) RETURNS SETOF demo_nums
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RETURN QUERY SELECT * FROM demo_nums WHERE id > p_min;
END;
$$;

EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF) SELECT count(*) FROM nums_gt_sql(199990);
EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF) SELECT count(*) FROM nums_gt_pl(199990);
```

```
--- LANGUAGE sql ---
                                                     QUERY PLAN
---------------------------------------------------------------------------------------------------------------------
 Aggregate  (cost=4.62..4.63 rows=1 width=8) (actual rows=1 loops=1)
   ->  Index Only Scan using demo_nums_pkey on demo_nums  (cost=0.42..4.59 rows=10 width=0) (actual rows=10 loops=1)
         Index Cond: (id > 199990)
         Heap Fetches: 0
 Planning Time: 6.390 ms
 Execution Time: 0.062 ms
(6 rows)

--- LANGUAGE plpgsql ---
                                            QUERY PLAN
--------------------------------------------------------------------------------------------------
 Aggregate  (cost=12.75..12.76 rows=1 width=8) (actual rows=1 loops=1)
   ->  Function Scan on nums_gt_pl  (cost=0.25..10.25 rows=1000 width=0) (actual rows=10 loops=1)
 Planning Time: 0.029 ms
 Execution Time: 0.503 ms
(4 rows)
```

**`LANGUAGE sql` 版は関数がプランから消え、`Index Only Scan` になっています。** `LANGUAGE plpgsql` 版は `Function Scan` で、見積もりは §3-4 の既定値 `rows=1000`（実測 10 行）です。

### 4-3. 【実測】`LIMIT` が中まで届くか

これがインライン展開の効き目としていちばん分かりやすい実験です。20 万行返す関数に `LIMIT 1` を付けます。

```sql
SELECT id FROM nums_gt_sql(0) LIMIT 1;
SELECT id FROM nums_gt_pl(0)  LIMIT 1;
```

```
--- LANGUAGE sql ---
 id
----
  1
(1 row)
Time: 0.411 ms

--- LANGUAGE plpgsql ---
 id
----
  1
(1 row)
Time: 22.784 ms
```

**`LANGUAGE sql` 版は 0.4 ミリ秒、`LANGUAGE plpgsql` 版は 23 ミリ秒。** plpgsql 版は `LIMIT 1` があっても 20 万行すべてを作ってからその 1 行を返しています（§6-3 で裏を取ります）。**外側の `LIMIT` / `WHERE` は plpgsql 関数の中には届きません。**

### 4-4. 【実測】スカラー関数

```sql
CREATE OR REPLACE FUNCTION half_sql(p_x integer) RETURNS integer
LANGUAGE sql     IMMUTABLE PARALLEL SAFE AS $$ SELECT p_x / 2 $$;
CREATE OR REPLACE FUNCTION half_pl(p_x integer)  RETURNS integer
LANGUAGE plpgsql IMMUTABLE PARALLEL SAFE AS $$ BEGIN RETURN p_x / 2; END; $$;

EXPLAIN (COSTS OFF) SELECT count(*) FROM demo_nums WHERE half_sql(id) = 5;
EXPLAIN (COSTS OFF) SELECT count(*) FROM demo_nums WHERE half_pl(id) = 5;
```

```
--- LANGUAGE sql ---
           QUERY PLAN
--------------------------------
 Aggregate
   ->  Seq Scan on demo_nums
         Filter: ((id / 2) = 5)
(3 rows)

--- LANGUAGE plpgsql ---
                                  QUERY PLAN
------------------------------------------------------------------------------
 Finalize Aggregate
   ->  Gather
         Workers Planned: 2
         ->  Partial Aggregate
               ->  Parallel Index Only Scan using demo_nums_pkey on demo_nums
                     Filter: (half_pl(id) = 5)
(6 rows)
```

`LANGUAGE sql` 版の `Filter:` は **`((id / 2) = 5)`** です。関数が式そのものに置き換わりました。

```
half_sql : Time: 8.154 ms / 9.543 ms
half_pl  : Time: 426.179 ms / 147.926 ms
（参考）関数を使わず id / 2 = 5 と直接書いた場合: Time: 9.362 ms
```

**16〜45 倍の差**。しかも `LANGUAGE sql` 版は「関数を使わずに直接式を書いた場合」と同じ速度です。展開されて完全に同一のクエリになったからです。

### 4-5. 講義版 12-4 §1-2 との接続

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §1-2 に「SQL の中で呼べるということは、行数ぶん呼ばれるということです」と書きました。**その根拠がここです。**

- `discounted_price()` は `LANGUAGE plpgsql` なので、インライン展開されない
- 既定で `VOLATILE` なので、定数畳み込みもされず、`Index Cond` にもならない
- 中の `SELECT` 2 本が、外側のクエリの行数ぶん実行される

研修生に「では速くするには？」と聞かれたら、答えは 3 段階です。

1. **そもそも関数にせず、JOIN 1 文で書く。** これがいちばん速い
2. どうしても関数にしたいなら、**`LANGUAGE sql` の 1 文で書いて `STABLE` を付ける**（インライン展開されうる）
3. plpgsql が必要な処理なら、**`STABLE` / `PARALLEL SAFE` / 実態に合った `COST` を明示する**

## 5. セキュリティ属性

### 5-1. 【実測】`SECURITY INVOKER` と `SECURITY DEFINER`

| 属性 | 誰の権限で動くか |
|:---|:---|
| `SECURITY INVOKER`（既定） | **呼び出した人** |
| `SECURITY DEFINER` | **関数を作った人（所有者）** |

権限の弱いロールを作って確かめます。

```sql
CREATE ROLE demo_low;
GRANT USAGE ON SCHEMA public TO demo_low;

CREATE TABLE secret_salary (staff_id integer PRIMARY KEY, salary numeric);
INSERT INTO secret_salary VALUES (1, 500000), (2, 600000);
REVOKE ALL ON secret_salary FROM PUBLIC;

CREATE OR REPLACE FUNCTION total_salary_invoker() RETURNS numeric
LANGUAGE plpgsql SECURITY INVOKER AS $$
DECLARE v_total numeric;
BEGIN
    SELECT sum(salary) INTO v_total FROM secret_salary;
    RETURN v_total;
END;
$$;

CREATE OR REPLACE FUNCTION total_salary_definer() RETURNS numeric
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE v_total numeric;
BEGIN
    SELECT sum(salary) INTO v_total FROM secret_salary;
    RETURN v_total;
END;
$$;

GRANT EXECUTE ON FUNCTION total_salary_invoker(), total_salary_definer() TO demo_low;

SET ROLE demo_low;
SELECT sum(salary) FROM secret_salary;   -- 直接
SELECT total_salary_invoker();
SELECT total_salary_definer();
RESET ROLE;
```

```
--- demo_low になって直接読む ---
ERROR:  permission denied for table secret_salary

--- SECURITY INVOKER 関数経由 ---
ERROR:  permission denied for table secret_salary
CONTEXT:  SQL statement "SELECT sum(salary)              FROM secret_salary"
PL/pgSQL function total_salary_invoker() line 4 at SQL statement

--- SECURITY DEFINER 関数経由 ---
 total_salary_definer
----------------------
              1100000
(1 row)
```

`SECURITY DEFINER` の使いどころは「**テーブルへの直接アクセスは禁じたいが、決まった集計だけは見せたい**」というケースです。実質的にストアドプロシージャを API にする設計です。

### 5-2. 【実測】`search_path` を固定しないと乗っ取られる

**`SECURITY DEFINER` 関数の中で参照するテーブル名を修飾しないと、呼び出し側が `search_path` を変えるだけで別のテーブルを読ませられます。**

```sql
CREATE TABLE bonus_rate (id integer PRIMARY KEY, rate numeric);
INSERT INTO bonus_rate VALUES (1, 0.05);
REVOKE ALL ON bonus_rate FROM PUBLIC;

CREATE OR REPLACE FUNCTION apply_bonus(p_staff_id integer) RETURNS numeric
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
    v_rate numeric;
    v_sal  numeric;
BEGIN
    SELECT rate INTO v_rate FROM bonus_rate WHERE id = 1;   -- ★ 修飾していない
    UPDATE secret_salary SET salary = round(salary * (1 + v_rate))
     WHERE staff_id = p_staff_id
    RETURNING salary INTO v_sal;
    RETURN v_sal;
END;
$$;
GRANT EXECUTE ON FUNCTION apply_bonus(integer) TO demo_low;
GRANT CREATE ON DATABASE :"DBNAME" TO demo_low;   -- psql が現在のDB名に展開する
```

正常な呼び出しでは 5% 増（500000 → 525000）です。ここで `demo_low` が偽の `bonus_rate` を用意します。

```sql
BEGIN;
SET ROLE demo_low;
CREATE SCHEMA evil;
CREATE TABLE evil.bonus_rate (id integer PRIMARY KEY, rate numeric);
INSERT INTO evil.bonus_rate VALUES (1, 10);
SET search_path = evil, public;
SELECT apply_bonus(1) AS new_salary;
RESET ROLE;
ROLLBACK;
```

```
=== 正常な呼び出し（rate = 0.05）===
 new_salary
------------
     525000
(1 row)

=== demo_low が偽の bonus_rate を用意して呼ぶ ===
 new_salary
------------
    5500000
(1 row)
```

**`demo_low` は `bonus_rate` を読む権限も `secret_salary` を書く権限も持っていないのに、給与を 11 倍にできました。** `apply_bonus` が所有者権限で動くので、攻撃者は「関数がどのテーブルを読むか」を差し替えるだけで済みます。

対策は関数自身に `search_path` を固定することです。

```sql
ALTER FUNCTION apply_bonus(integer) SET search_path = public, pg_temp;
SELECT proname, proconfig FROM pg_proc WHERE proname = 'apply_bonus';
```

```
   proname   |            proconfig
-------------+---------------------------------
 apply_bonus | {"search_path=public, pg_temp"}
(1 row)
```

同じ攻撃をもう一度試すと、

```
 new_salary
------------
     525000
(1 row)
```

**5% 増に戻りました。**

> ⚠️ **`pg_temp` を最後に書くのが定石です。**
> `pg_temp`（一時テーブルのスキーマ）は明示的に書かないと**暗黙に先頭**に置かれます。攻撃者が一時テーブルで `bonus_rate` を作る手が残ってしまうので、末尾に明示して優先度を下げます。
> より徹底するなら `SET search_path = ''` にして関数内のすべての名前を `public.xxx` と修飾します。

### 5-3. 【実測】PostgreSQL 17 では `CREATE INDEX` の中の `search_path` が制限される

§1-8 で `public.demo_rate` と修飾したのには理由があります。修飾しないとこうなります。

```sql
CREATE OR REPLACE FUNCTION sp_taxed(p_price numeric) RETURNS numeric
LANGUAGE plpgsql IMMUTABLE AS $$
DECLARE v_rate numeric;
BEGIN
    SELECT rate INTO v_rate FROM sp_rate WHERE id = 1;   -- 修飾なし
    RETURN p_price * (1 + v_rate);
END;
$$;

SHOW search_path;
SELECT sp_taxed(1000);                          -- ふつうに呼ぶ
CREATE INDEX idx_sp ON sp_price (sp_taxed(price));   -- インデックス式として呼ぶ
```

```
   search_path
-----------------
 "$user", public
(1 row)

 sp_taxed
----------
  1100.00
(1 row)

ERROR:  relation "sp_rate" does not exist
LINE 1: SELECT rate             FROM sp_rate WHERE id = 1
                                     ^
QUERY:  SELECT rate             FROM sp_rate WHERE id = 1
CONTEXT:  PL/pgSQL function sp_taxed(numeric) line 4 at SQL statement
```

**同じ関数が、普通に呼べば通り、`CREATE INDEX` の中では「テーブルがない」と言われます。** PostgreSQL 17 で、`ANALYZE` / `CLUSTER` / `CREATE INDEX` / `CREATE MATERIALIZED VIEW` / `REFRESH MATERIALIZED VIEW` / `REINDEX` / `VACUUM` の**保守操作は安全な `search_path`（`pg_catalog, pg_temp`）で関数を実行する**ようになりました（[PostgreSQL 17 リリースノート](https://www.postgresql.org/docs/release/17.0/)）。

つまり、**PostgreSQL 16 以前で動いていた式インデックスが、17 に上げた瞬間に `REINDEX` や `VACUUM FULL` で落ちる**可能性があります。バージョンアップの事前確認項目です。対策は関数側に `SET search_path` を書くか、名前を完全修飾することです。

### 5-4. 【実測】`LEAKPROOF`

`LEAKPROOF` は「**この関数は引数の中身を、返り値以外の手段で漏らさない**」という宣言です。エラーメッセージにも `RAISE NOTICE` にも引数を出さない、という約束です。

何の役に立つのか。行単位のアクセス制御（`security_barrier` 付きビュー、行レベルセキュリティ）を使っているとき、オプティマイザは**アクセス制御の条件より先にユーザーの条件を評価してよいか**を `LEAKPROOF` で判断します。

```sql
CREATE OR REPLACE FUNCTION leaky(p_x numeric) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE AS $$
BEGIN
    RAISE NOTICE '関数が見た値: %', p_x;     -- ★ 引数を漏らしている
    RETURN p_x > 0;
END;
$$;

CREATE OR REPLACE FUNCTION lp_ok(p_x numeric) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE LEAKPROOF AS $$   -- ★ 中身は同じなのに LEAKPROOF と宣言
BEGIN
    RAISE NOTICE '関数が見た値: %', p_x;
    RETURN p_x > 0;
END;
$$;

CREATE TABLE secret_pay (staff_id integer PRIMARY KEY, dept text, salary numeric);
INSERT INTO secret_pay VALUES (1,'A',500000),(2,'A',520000),(3,'B',900000),
                              (4,'B',950000),(5,'C',1200000),(6,'C',1500000);
REVOKE ALL ON secret_pay FROM PUBLIC;

-- dept = 'A' の行だけ見せるビュー
CREATE VIEW v_dept_a WITH (security_barrier) AS SELECT * FROM secret_pay WHERE dept = 'A';
GRANT SELECT ON v_dept_a TO demo_low;
```

関数を「とても安い」と申告して、ビューの条件より先に評価させます。

```sql
ALTER FUNCTION lp_ok(numeric)  COST 0.0001;
ALTER FUNCTION leaky(numeric)  COST 0.0001;
SET ROLE demo_low;
EXPLAIN (COSTS OFF) SELECT staff_id FROM v_dept_a WHERE leaky(salary);
SELECT staff_id FROM v_dept_a WHERE leaky(salary);
EXPLAIN (COSTS OFF) SELECT staff_id FROM v_dept_a WHERE lp_ok(salary);
SELECT staff_id FROM v_dept_a WHERE lp_ok(salary);
RESET ROLE;
```

```
--- LEAKPROOF ではない関数（安いと申告しても外側から動かせない）---
             QUERY PLAN
------------------------------------
 Subquery Scan on v_dept_a
   Filter: leaky(v_dept_a.salary)
   ->  Seq Scan on secret_pay
         Filter: (dept = 'A'::text)
(4 rows)

NOTICE:  関数が見た値: 500000
NOTICE:  関数が見た値: 520000
 staff_id
----------
        1
        2
(2 rows)

--- LEAKPROOF な関数（ビューの条件より先に評価される）---
                       QUERY PLAN
--------------------------------------------------------
 Subquery Scan on v_dept_a
   ->  Seq Scan on secret_pay
         Filter: (lp_ok(salary) AND (dept = 'A'::text))
(3 rows)

NOTICE:  関数が見た値: 500000
NOTICE:  関数が見た値: 520000
NOTICE:  関数が見た値: 900000
NOTICE:  関数が見た値: 950000
NOTICE:  関数が見た値: 1200000
NOTICE:  関数が見た値: 1500000
 staff_id
----------
        1
        2
(2 rows)
```

**結果は 2 行のままなのに、`LEAKPROOF` 版の `NOTICE` には見えてはいけない B 部門・C 部門の給与（900000〜1500000）が全部出ています。**

`LEAKPROOF` ではない関数は `Subquery Scan` の外側でしか評価できないので、ビューが絞った 2 行しか見えません。`LEAKPROOF` と宣言した瞬間、オプティマイザは「この関数は漏らさないから中に入れてよい」と判断し、全 6 行を渡しました。

だから `LEAKPROOF` は superuser 専用です。

```sql
SET ROLE demo_low;
CREATE FUNCTION lp_by_low(p_x numeric) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE LEAKPROOF AS $$ BEGIN RETURN true; END; $$;
```

```
ERROR:  only superuser can define a leakproof function
```

> ⚠️ **`LEAKPROOF` は「速くなるおまじない」ではありません。** 付けてよいのは、`RAISE` もエラーも出さず、引数の値によって挙動が変わる箇所が返り値以外にない関数だけです。判断がつかないなら付けないのが正解です。

## 6. 集合を返す関数

### 6-1. 3 通りの書き方

| 書き方 | 返るもの |
|:---|:---|
| `RETURNS SETOF <型>` | 1 列の集合。`<型>` にテーブル名を書けば行型の集合 |
| `RETURNS TABLE (列名 型, …)` | 列名付きの集合。**内部的には `OUT` 引数と同じ** |
| `OUT` 引数 ＋ `RETURNS SETOF record` | `RETURNS TABLE` の古い書き方 |

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §1-3 では `RETURNS TABLE` だけを扱いました。

### 6-2. 【実測】`RETURN NEXT` と `RETURN QUERY`

| 文 | 何をするか |
|:---|:---|
| `RETURN NEXT <値>` | 結果に 1 行足す。ループの中で使う |
| `RETURN QUERY <クエリ>` | クエリの結果を**まとめて**結果に足す |
| `RETURN QUERY EXECUTE <文字列>` | 動的 SQL の結果をまとめて足す |

**どちらも「そこで関数を抜ける」わけではありません。** `RETURN`（値なし）に達するか `END` に到達したときに返ります。

```sql
CREATE OR REPLACE FUNCTION setof_next(p_n integer) RETURNS SETOF integer
LANGUAGE plpgsql STABLE AS $$
DECLARE
    r_row RECORD;
BEGIN
    FOR r_row IN SELECT id FROM demo_nums WHERE id <= p_n LOOP
        RETURN NEXT r_row.id;
    END LOOP;
    RETURN;
END;
$$;

CREATE OR REPLACE FUNCTION setof_query(p_n integer) RETURNS SETOF integer
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RETURN QUERY SELECT id FROM demo_nums WHERE id <= p_n;
    RETURN;
END;
$$;

SELECT count(*) FROM setof_next(200000);
SELECT count(*) FROM setof_query(200000);
```

```
--- RETURN NEXT を 20万回 ---
Time: 69.324 ms / 78.150 ms
--- RETURN QUERY で一度に ---
Time: 41.111 ms / 67.614 ms
```

**1.2〜1.7 倍程度**。「`RETURN NEXT` は 1 行ずつだから極端に遅い」というほどではありません。どちらも行を貯める先は同じだからです（次節）。**読みやすさで選んでよい**、が実測から言える結論です。1 行ずつ加工が必要なら `RETURN NEXT`、クエリの結果をそのまま返すなら `RETURN QUERY` です。

### 6-3. 【実測】メモリ挙動：PL/pgSQL の集合関数は全件をいったん貯める

PL/pgSQL の集合を返す関数は、**結果を全部タプルストア（メモリまたは一時ファイル）に書き出してから返します**。呼び出し側に 1 行ずつ流す仕組み（value-per-call）は使えません。§4-3 で `LIMIT 1` が効かなかったのはこれが理由です。

一時ファイルの発生を `pg_stat_database` で観測します。

```sql
CREATE OR REPLACE FUNCTION setof_txt(p_n integer) RETURNS SETOF text
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RETURN QUERY SELECT txt FROM demo_big WHERE id <= p_n;
END;
$$;

SELECT temp_files, pg_size_pretty(temp_bytes) AS temp_bytes
  FROM pg_stat_database WHERE datname = current_database();
SELECT count(*) FROM setof_txt(1000000);
SELECT temp_files, pg_size_pretty(temp_bytes) AS temp_bytes
  FROM pg_stat_database WHERE datname = current_database();

-- 同じ件数を素の SQL で
SELECT count(*) FROM (SELECT txt FROM demo_big WHERE id <= 1000000) t;
SELECT temp_files, pg_size_pretty(temp_bytes) AS temp_bytes
  FROM pg_stat_database WHERE datname = current_database();
```

```
--- 関数を呼ぶ前 ---
 temp_files | temp_bytes
------------+------------
         23 | 85 MB
(1 row)

--- PL/pgSQL の集合関数で100万行 ---
  count
---------
 1000000
(1 row)
Time: 3923.789 ms (00:03.924)

 temp_files | temp_bytes
------------+------------
         24 | 105 MB
(1 row)

--- 同じ100万行を素の SQL で数えた場合 ---
  count
---------
 1000000
(1 row)
Time: 200.240 ms

 temp_files | temp_bytes
------------+------------
         24 | 105 MB
(1 row)
```

**PL/pgSQL 関数の側では一時ファイルが 1 個・20 MB 増え、素の SQL では 1 バイトも増えていません。** 時間も 3924 ms 対 200 ms（約 20 倍）です。

`work_mem`（この環境では 4 MB）を超えた分がディスクに落ちています。**「100 万行返す関数」を書くと、その 100 万行ぶんのディスク書き込みが発生します。** 集合を返す PL/pgSQL 関数を大きなデータに使わない理由がこれです。

> 💡 対策は 3 つです。
> 1. **関数にせずビューにする**（[[00_SQL研修/01_講義資料/99_補足_viewについて|99_補足_viewについて]]）
> 2. **`LANGUAGE sql` の 1 文で書く**（インライン展開されて `LIMIT` が届く。§4-3）
> 3. **引数で絞ってから返す**（`LIMIT` を関数の引数にして中で使う）

### 6-4. 【実測】`LATERAL` と `ROWS FROM`

集合を返す関数は `FROM` に置けるので、**行ごとに引数を変えて呼ぶ**（`LATERAL`）ことができます。

```sql
CREATE OR REPLACE FUNCTION recent_orders(p_customer_id integer, p_limit integer)
RETURNS TABLE (order_id integer, order_date date, status text)
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RETURN QUERY
    SELECT o.order_id, o.order_date, o.status::text
      FROM orders o
     WHERE o.customer_id = p_customer_id
     ORDER BY o.order_date DESC, o.order_id DESC
     LIMIT p_limit;
END;
$$;

SELECT c.name, r.order_id, r.order_date
  FROM customers c
  CROSS JOIN LATERAL recent_orders(c.customer_id, 2) r
 WHERE c.customer_id IN (1, 2)
 ORDER BY c.customer_id, r.order_id;
```

```
 name  | order_id | order_date
-------+----------+------------
 Alice |        6 | 2022-02-10
 Alice |        7 | 2022-03-01
 Bob   |        9 | 2022-02-20
 Bob   |       10 | 2022-03-10
(4 rows)
```

```sql
EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF, COSTS OFF)
SELECT c.name, r.order_id FROM customers c
  CROSS JOIN LATERAL recent_orders(c.customer_id, 2) r WHERE c.customer_id IN (1, 2);
```

```
                           QUERY PLAN
----------------------------------------------------------------
 Nested Loop (actual rows=4 loops=1)
   ->  Seq Scan on customers c (actual rows=2 loops=1)
         Filter: (customer_id = ANY ('{1,2}'::integer[]))
         Rows Removed by Filter: 7
   ->  Function Scan on recent_orders r (actual rows=2 loops=2)
 Planning Time: 0.045 ms
 Execution Time: 0.099 ms
(7 rows)
```

**`Function Scan ... loops=2` — 顧客 1 人につき 1 回、関数がまるごと実行されています。** 便利ですが、これは講義版 12-3 §7 で叩いた N+1 そのものです。顧客が 10 万人なら 10 万回です。

なお、**関数を `FROM` にカンマで並べても、PostgreSQL では自動的に `LATERAL` として扱われます**（`LATERAL` を明示しなくても相関できる）。上の例は `FROM customers c, recent_orders(c.customer_id, 2) r` と書いても同じ結果でした。可読性のために明示することをすすめます。

0 件の顧客（`customer_id = 6` の Grace）を残したいなら `LEFT JOIN LATERAL ... ON true` です。

```sql
SELECT c.name, r.order_id
  FROM customers c
  LEFT JOIN LATERAL recent_orders(c.customer_id, 2) r ON true
 WHERE c.customer_id IN (1, 6)
 ORDER BY c.customer_id, r.order_id;
```

```
 name  | order_id
-------+----------
 Alice |        6
 Alice |        7
 Grace |
(3 rows)
```

`ROWS FROM (...)` は複数の集合関数を**横に並べる**構文です。行数が違う場合は短い側が NULL で埋まります。

```sql
SELECT * FROM ROWS FROM (top_products(3), generate_series(1, 5)) AS t(product_name, seq);
```

```
 product_name | seq
--------------+-----
 Laptop       |   1
 Smartphone   |   2
 Luxury Sofa  |   3
              |   4
              |   5
(5 rows)
```

### 6-5. 【実測】`RETURNS TABLE` の列名は変数になる

`RETURNS TABLE (…)` に書いた列名は、関数の中では **`OUT` 引数（＝変数）** です。だから同名の列を修飾せずに使うと衝突します。

```sql
CREATE OR REPLACE FUNCTION t_conflict() RETURNS TABLE (product_name text, price numeric)
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RETURN QUERY SELECT product_name::text, price FROM products ORDER BY product_id LIMIT 2;
END;
$$;
SELECT * FROM t_conflict();
```

```
ERROR:  column reference "product_name" is ambiguous
LINE 1: SELECT product_name::text, price FROM products ORDER BY prod...
               ^
DETAIL:  It could refer to either a PL/pgSQL variable or a table column.
QUERY:  SELECT product_name::text, price FROM products ORDER BY product_id LIMIT 2
CONTEXT:  PL/pgSQL function t_conflict() line 3 at RETURN QUERY
```

**`CREATE FUNCTION` は成功し、呼んだときに初めて落ちます。** PL/pgSQL の「コンパイル」が初回実行時であることの現れです（→ [[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]]）。

対策はテーブルに別名を付けることです。

```sql
CREATE OR REPLACE FUNCTION t_conflict_ok() RETURNS TABLE (product_name text, price numeric)
LANGUAGE plpgsql STABLE AS $$
BEGIN
    RETURN QUERY SELECT p.product_name::text, p.price FROM products p ORDER BY p.product_id LIMIT 2;
END;
$$;
SELECT * FROM t_conflict_ok();
```

```
 product_name |  price
--------------+---------
 Laptop       | 1200.00
 Smartphone   |  800.00
(2 rows)
```

> 💡 講義版で `RETURNS TABLE` の列名を `category_name` / `order_count` / `total_amount` にして、クエリ側は `c.category_name` と修飾していたのは、この衝突を避けるためです。研修生が「なぜ `c.` を付けるのか」と聞いてきたら、ここが答えです。**`RETURNS TABLE` を使うときは、クエリ側の列を必ず別名で修飾する**をルールにしてください。

`RETURN NEXT NULL` は NULL 行を 1 行足します（エラーにはなりません）。

```sql
CREATE OR REPLACE FUNCTION nulls_srf() RETURNS SETOF integer LANGUAGE plpgsql AS $$
BEGIN
    RETURN NEXT 1;
    RETURN NEXT NULL;
    RETURN NEXT 3;
END;
$$;
SELECT * FROM nulls_srf();
```

```
 nulls_srf
-----------
         1

         3
(3 rows)
```

## 7. 明示カーソル

### 7-1. なぜ講義から外したか

講義版では明示カーソル（`DECLARE ... CURSOR` / `OPEN` / `FETCH` / `CLOSE`）を**一切扱っていません**。研修生に聞かれたときの答えを用意しておきます。

**理由は 4 つです。**

1. **`FOR r_x IN SELECT ... LOOP` で 99% 足りる。** `FOR` ループは内部でカーソルを使っており（[[12詳解-6_性能とアンチパターン|12詳解-6]] §2 で実測）、`OPEN` / `FETCH` / `CLOSE` / `NOT FOUND` の判定を自動でやってくれます。研修生が書くのは前者だけで済みます。
2. **`CLOSE` 漏れという新種のバグを教えることになる。** 明示カーソルは `EXIT WHEN NOT FOUND` の位置を間違えると 1 行余分に処理したり、無限ループになったりします。制御構造を覚えたばかりの段階でこれを足す利益がありません。
3. **「メモリ節約のためにカーソルを使う」という説明はこの研修の題材では嘘になる。** `FOR ... IN SELECT` も同じくカーソル経由です。明示カーソルにしてもメモリは減りません。
4. **明示カーソルが本当に必要な場面は、研修の到達点より外にある。** `refcursor` を関数の戻り値にしてアプリ側でフェッチする、`WITH HOLD` でトランザクションをまたぐ、`SCROLL` で前後に動く — いずれも設計判断を伴う話です。

**教えるべき代替は「1 文で書く」「`FOR ... IN SELECT` で書く」の 2 つだけ**、という判断です。

### 7-2. 【実測】基本形

```sql
DO $$
DECLARE
    cur_p CURSOR (p_cat integer) FOR
        SELECT product_id, product_name FROM products WHERE category_id = p_cat ORDER BY product_id;
    r_p RECORD;
BEGIN
    OPEN cur_p(p_cat := 1);
    LOOP
        FETCH cur_p INTO r_p;
        EXIT WHEN NOT FOUND;
        RAISE NOTICE 'カテゴリ1: % %', r_p.product_id, r_p.product_name;
    END LOOP;
    CLOSE cur_p;
END;
$$;
```

```
NOTICE:  カテゴリ1: 1 Laptop
NOTICE:  カテゴリ1: 2 Smartphone
NOTICE:  カテゴリ1: 6 Monitor
NOTICE:  カテゴリ1: 13 Headphones
```

- カーソルは引数を取れます（`CURSOR (p_cat integer) FOR ...` → `OPEN cur_p(p_cat := 1)`）
- `FETCH` の後に **`EXIT WHEN NOT FOUND`** が必須です。これを忘れると無限ループになります
- カーソル変数の命名は `cur_` です（コーディング規約）

### 7-3. 【実測】`WHERE CURRENT OF`

明示カーソルにしかできない唯一の実用的な機能がこれです。**「いま `FETCH` した行」を主キーを書き直さずに更新できます。**

```sql
BEGIN;
DO $$
DECLARE
    cur_inv CURSOR FOR
        SELECT product_id, warehouse_id, stock_quantity
          FROM inventory
         WHERE warehouse_id = 1
         ORDER BY product_id
           FOR UPDATE;
    r_inv RECORD;
BEGIN
    OPEN cur_inv;
    LOOP
        FETCH cur_inv INTO r_inv;
        EXIT WHEN NOT FOUND;

        IF r_inv.stock_quantity < 100 THEN
            UPDATE inventory
               SET stock_quantity = stock_quantity + 1
             WHERE CURRENT OF cur_inv;       -- ★ 主キーを書き直さない
            RAISE NOTICE '商品% を +1（%→%）',
                r_inv.product_id, r_inv.stock_quantity, r_inv.stock_quantity + 1;
        END IF;
    END LOOP;
    CLOSE cur_inv;
END;
$$;
SELECT product_id, stock_quantity FROM inventory WHERE warehouse_id = 1 ORDER BY product_id;
ROLLBACK;
```

```
NOTICE:  商品1 を +1（50→51）
NOTICE:  商品2 を +1（30→31）
NOTICE:  商品6 を +1（40→41）
NOTICE:  商品7 を +1（10→11）
NOTICE:  商品9 を +1（2→3）
NOTICE:  商品10 を +1（20→21）
NOTICE:  商品13 を +1（20→21）
 product_id | stock_quantity
------------+----------------
          1 |             51
          2 |             31
          3 |            100
          6 |             41
          7 |             11
          9 |              3
         10 |             21
         13 |             21
(8 rows)
```

在庫 100 の商品 3 だけが増えていません。`WHERE CURRENT OF` の制約は 2 つです。

- カーソルのクエリが**単一テーブルの単純なクエリ**であること（`GROUP BY`・`JOIN`・`DISTINCT` は不可）
- `FOR ... IN SELECT` のループ変数には使えない（**明示カーソル専用**）

> 💡 それでも実務では `WHERE 主キー = r_x.主キー` と書く方が多いです。読む人にとって「どの行を更新しているか」が明示的で、カーソルの状態に依存しないからです。**`WHERE CURRENT OF` は「複合主キーが長くて書くのが苦痛」なときの選択肢**という位置づけです。

### 7-4. 【実測】`SCROLL` と `MOVE`

```sql
DO $$
DECLARE
    cur_s SCROLL CURSOR FOR SELECT product_id, product_name FROM products ORDER BY product_id;
    r_s RECORD;
BEGIN
    OPEN cur_s;
    FETCH cur_s INTO r_s;                 RAISE NOTICE 'NEXT      : %', r_s.product_name;
    FETCH LAST FROM cur_s INTO r_s;       RAISE NOTICE 'LAST      : %', r_s.product_name;
    FETCH PRIOR FROM cur_s INTO r_s;      RAISE NOTICE 'PRIOR     : %', r_s.product_name;
    FETCH ABSOLUTE 3 FROM cur_s INTO r_s; RAISE NOTICE 'ABSOLUTE 3: %', r_s.product_name;
    MOVE FORWARD 2 FROM cur_s;
    FETCH cur_s INTO r_s;                 RAISE NOTICE '2つ飛ばして: %', r_s.product_name;
    CLOSE cur_s;
END;
$$;
```

```
NOTICE:  NEXT      : Laptop
NOTICE:  LAST      : Headphones
NOTICE:  PRIOR     : Socks
NOTICE:  ABSOLUTE 3: Novel
NOTICE:  2つ飛ばして: Monitor
```

`SCROLL` を付けないと後方への移動はできません。`MOVE` は「行を取らずにカーソルを動かす」文です。

### 7-5. 【実測】`refcursor` を返す

**関数から「開いたままのカーソル」を返し、呼び出し側で必要なぶんだけ取る**やり方です。名前付き `refcursor` を渡すと、その名前で `FETCH` できます。

```sql
CREATE OR REPLACE FUNCTION open_products(p_cursor refcursor, p_cat integer)
RETURNS refcursor
LANGUAGE plpgsql AS $$
BEGIN
    OPEN p_cursor FOR
        SELECT product_id, product_name, price FROM products
         WHERE category_id = p_cat ORDER BY product_id;
    RETURN p_cursor;
END;
$$;

BEGIN;
SELECT open_products('cur_a', 1);
FETCH 2 FROM cur_a;
FETCH ALL FROM cur_a;
CLOSE cur_a;
COMMIT;
```

```
 open_products
---------------
 cur_a
(1 row)

 product_id | product_name |  price
------------+--------------+---------
          1 | Laptop       | 1200.00
          2 | Smartphone   |  800.00
(2 rows)

 product_id | product_name | price
------------+--------------+--------
          6 | Monitor      | 300.00
         13 | Headphones   | 150.00
(2 rows)

CLOSE CURSOR
COMMIT
```

**`BEGIN` … `COMMIT` で囲む必要があります。** 名前を渡さない場合は自動生成名になり、返ってきた名前を引用符で囲んで使うことになります。

```sql
BEGIN;
SELECT open_products2(1) AS cname \gset
\echo :cname
FETCH ALL FROM :"cname";
COMMIT;
```

```
<unnamed portal 1>
 product_id
------------
          1
          2
          6
         13
(4 rows)
```

**`<unnamed portal 1>` のように空白を含む名前なので、必ず引用符で囲む必要があります。** 呼び出し側で名前を決めて渡すほうが扱いやすいです。

### 7-6. 【実測】`WITH HOLD`

カーソルは既定でトランザクション終了時に閉じます。`WITH HOLD` を付けると `COMMIT` をまたいで生き残ります。

```sql
-- WITH HOLD なし
BEGIN;
DECLARE cur_nohold CURSOR FOR SELECT product_id FROM products ORDER BY product_id;
FETCH 2 FROM cur_nohold;
COMMIT;
FETCH 2 FROM cur_nohold;
```

```
 product_id
------------
          1
          2
(2 rows)

COMMIT
ERROR:  cursor "cur_nohold" does not exist
```

```sql
-- WITH HOLD あり
BEGIN;
DECLARE cur_hold CURSOR WITH HOLD FOR SELECT product_id FROM products ORDER BY product_id;
FETCH 2 FROM cur_hold;
COMMIT;
FETCH 2 FROM cur_hold;
CLOSE cur_hold;
```

```
 product_id
------------
          1
          2
(2 rows)

COMMIT
 product_id
------------
          3
          4
(2 rows)

CLOSE CURSOR
```

**`WITH HOLD` は PL/pgSQL の `DECLARE` では書けません。**

```sql
DO $$
DECLARE
    cur_x CURSOR WITH HOLD FOR SELECT 1;
BEGIN
    NULL;
END;
$$;
```

```
ERROR:  syntax error at or near "WITH"
LINE 3:     cur_x CURSOR WITH HOLD FOR SELECT 1;
                         ^
```

PL/pgSQL の中で保持カーソルが必要なら `EXECUTE 'DECLARE … CURSOR WITH HOLD FOR …'` と動的 SQL で書きます。

> ⚠️ **`WITH HOLD` は `COMMIT` の時点で残りの行を全部タプルストアにコピーします。** 100 万行のカーソルを保持すると、`COMMIT` がその場で重くなり、一時ファイルも作られます。「トランザクションを短く保つため」に `WITH HOLD` を使うと、かえって遅くなることがあります。

## 8. `CREATE OR REPLACE` とオーバーロード

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §10 で「`CREATE OR REPLACE` は引数や戻り値の型を変えると失敗する」「`DROP FUNCTION` は名前が一意なら引数を省略できる」と書きました。境界を実測で確認します。

### 8-1. 【実測】何を変えると失敗するか

```sql
CREATE OR REPLACE FUNCTION f_sig(p_a integer) RETURNS integer
LANGUAGE plpgsql AS $$ BEGIN RETURN p_a; END; $$;

-- (a) 戻り値の型を変える
CREATE OR REPLACE FUNCTION f_sig(p_a integer) RETURNS text
LANGUAGE plpgsql AS $$ BEGIN RETURN p_a::text; END; $$;

-- (b) 引数名だけを変える
CREATE OR REPLACE FUNCTION f_sig(p_b integer) RETURNS integer
LANGUAGE plpgsql AS $$ BEGIN RETURN p_b; END; $$;

-- (c) 引数を1つ足す
CREATE OR REPLACE FUNCTION f_sig(p_b integer, p_c integer) RETURNS integer
LANGUAGE plpgsql AS $$ BEGIN RETURN p_b + p_c; END; $$;
```

```
--- (a) 戻り値の型を変える ---
ERROR:  cannot change return type of existing function
HINT:  Use DROP FUNCTION f_sig(integer) first.
--- (b) 引数名だけを変える ---
ERROR:  cannot change name of input parameter "p_a"
HINT:  Use DROP FUNCTION f_sig(integer) first.
--- (c) 引数を1つ足す（＝別の関数になる＝オーバーロード）---
CREATE FUNCTION
```

| 変更内容 | `CREATE OR REPLACE` | 理由 |
|:---|:---|:---|
| 本体だけ | ○ | シグネチャが同じ |
| 変動性・`COST`・`PARALLEL` など属性 | ○ | シグネチャに含まれない |
| **戻り値の型** | ✕ | `cannot change return type of existing function` |
| **引数名**（型はそのまま） | ✕ | `cannot change name of input parameter` |
| 引数の型 | ✕（別関数として作られる） | シグネチャが違う＝別関数 |
| 引数の個数 | ✕（別関数として作られる） | 同上 |

**(b) の「引数名だけを変える」が失敗するのは意外に思われます。** PL/pgSQL では引数名が本体から参照されるので、名前を変えると呼び出し側の名前付き記法（`f_sig(p_a => 1)`）が壊れるためです。

### 8-2. 【実測】`DROP FUNCTION` の引数省略

```sql
\df f_sig
DROP FUNCTION f_sig;
```

```
                          List of functions
 Schema | Name  | Result data type |   Argument data types    | Type
--------+-------+------------------+--------------------------+------
 public | f_sig | integer          | p_a integer              | func
 public | f_sig | integer          | p_b integer, p_c integer | func
(2 rows)

ERROR:  function name "f_sig" is not unique
HINT:  Specify the argument list to select the function unambiguously.
```

一意なら省略できます。

```sql
CREATE OR REPLACE FUNCTION f_out2(p_a integer, OUT p_r integer)
LANGUAGE plpgsql AS $$ BEGIN p_r := p_a; END; $$;
DROP FUNCTION f_out2;
```

```
DROP FUNCTION
```

**講義版のルール（「`DROP` には引数の型まで書く」）は、オーバーロードが後から増えても片付けコードが壊れないようにするためです。**

### 8-3. 【実測】`DEFAULT` を足すと呼び出しが曖昧になる

オーバーロードとデフォルト値を混ぜると、**作れるが呼べない**関数ができます。

```sql
CREATE OR REPLACE FUNCTION f_sig(p_b integer, p_c integer DEFAULT 0) RETURNS integer
LANGUAGE plpgsql AS $$ BEGIN RETURN p_b + p_c; END; $$;
SELECT f_sig(1), f_sig(1, 2);
```

```
CREATE FUNCTION
ERROR:  function f_sig(integer) is not unique
LINE 1: SELECT f_sig(1), f_sig(1, 2);
               ^
HINT:  Could not choose a best candidate function. You might need to add explicit type casts.
```

`f_sig(integer)` と `f_sig(integer, integer DEFAULT 0)` の両方が `f_sig(1)` に一致してしまいました。**`DROP FUNCTION` した後でも `CREATE FUNCTION` は通ります。エラーは呼んだときに出ます。** 実務では「オーバーロードとデフォルト値は混ぜない」が安全です。

### 8-4. 【実測】`OUT` 引数はシグネチャに含まれない

```sql
CREATE OR REPLACE FUNCTION f_out(p_a integer, OUT p_r integer)
LANGUAGE plpgsql AS $$ BEGIN p_r := p_a; END; $$;
CREATE OR REPLACE FUNCTION f_out(p_a integer) RETURNS integer
LANGUAGE plpgsql AS $$ BEGIN RETURN p_a; END; $$;
\df f_out
```

```
CREATE FUNCTION
CREATE FUNCTION
                       List of functions
 Schema | Name  | Result data type | Argument data types | Type
--------+-------+------------------+---------------------+------
 public | f_out | integer          | p_a integer         | func
(1 row)
```

**2 つ作ったつもりが 1 つになっています。** `f_out(p_a integer, OUT p_r integer)` のシグネチャは `f_out(integer)` なので、2 回目の `CREATE OR REPLACE` が 1 回目を**上書きしました**。`OUT` 引数の型を変えると戻り値の型変更として拒否されます。

```sql
CREATE OR REPLACE FUNCTION f_out2(p_a integer, OUT p_r integer)
LANGUAGE plpgsql AS $$ BEGIN p_r := p_a; END; $$;
CREATE OR REPLACE FUNCTION f_out2(p_a integer, OUT p_r text)
LANGUAGE plpgsql AS $$ BEGIN p_r := p_a::text; END; $$;
```

```
CREATE FUNCTION
ERROR:  cannot change return type of existing function
HINT:  Use DROP FUNCTION f_out2(integer) first.
```

**エラーメッセージが `f_out2(integer)` と、`OUT` を含まない形で出ている**ことに注目してください。

## 9. `OUT` 引数を持つプロシージャの呼び出し規則

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §2-1 で `OUT` 引数を扱いました。**`CALL` の書き方が SQL からと PL/pgSQL からで違う**ので、そこを整理します。

```sql
CREATE OR REPLACE PROCEDURE customer_summary(
    p_customer_id IN  integer,
    p_name        OUT text,
    p_order_count OUT bigint)
LANGUAGE plpgsql AS $$
BEGIN
    SELECT c.name, count(o.order_id) INTO p_name, p_order_count
      FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id
     WHERE c.customer_id = p_customer_id GROUP BY c.name;
END;
$$;
```

### 9-1. 【実測】SQL から `CALL` する

```sql
CALL customer_summary(1, NULL, NULL);
CALL customer_summary(1);
CALL customer_summary(1, 'x', 0);
```

```
--- (1) OUT の位置に NULL を書く ---
 p_name | p_order_count
--------+---------------
 Alice  |             4
(1 row)

--- (2) OUT を省略して呼ぶ ---
ERROR:  procedure customer_summary(integer) does not exist
LINE 1: CALL customer_summary(1);
             ^
HINT:  No procedure matches the given name and argument types. You might need to add explicit type casts.

--- (3) OUT の位置に定数を書く ---
 p_name | p_order_count
--------+---------------
 Alice  |             4
(1 row)
```

- **`OUT` 引数のぶんも引数を書かなければなりません。** 省略すると「そんなプロシージャはない」と言われます
- `OUT` に渡した値は評価されないので、`NULL` でも `'x'` でも結果は同じ
- 結果は**1 行の表として返ってきます**

公式ドキュメントの記述（[CALL](https://www.postgresql.org/docs/17/sql-call.html)）:

> Arguments must be supplied for all procedure parameters that lack defaults, including `OUT` parameters. However, arguments matching `OUT` parameters are not evaluated, so it's customary to just write `NULL` for them. (Writing something else for an `OUT` parameter might cause compatibility problems with future PostgreSQL versions.)

**「`NULL` 以外を書くと将来のバージョンで問題になるかもしれない」と明記されています。** `NULL` を書いてください。

`INOUT` にすると値がちゃんと渡されます。

```sql
CREATE OR REPLACE PROCEDURE double_it(p_x INOUT integer)
LANGUAGE plpgsql AS $$ BEGIN p_x := p_x * 2; END; $$;
CALL double_it(21);
```

```
 p_x
-----
  42
(1 row)
```

### 9-2. 【実測】PL/pgSQL から `CALL` する

```sql
-- (4) 変数を渡す
DO $$
DECLARE v_name text; v_cnt bigint;
BEGIN
    CALL customer_summary(1, v_name, v_cnt);
    RAISE NOTICE '% / %', v_name, v_cnt;
END;
$$;

-- (5) OUT の位置に定数を書く
DO $$
BEGIN
    CALL customer_summary(1, 'x', 0);
END;
$$;

-- (6) OUT を省略する
DO $$
BEGIN
    CALL customer_summary(1);
END;
$$;
```

```
--- (4) 変数を渡す ---
NOTICE:  Alice / 4

--- (5) OUT の位置に定数を書く ---
ERROR:  procedure parameter "p_name" is an output parameter but corresponding argument is not writable
CONTEXT:  PL/pgSQL function inline_code_block line 3 at CALL

--- (6) OUT を省略する ---
ERROR:  procedure customer_summary(integer) does not exist
LINE 1: CALL customer_summary(1)
             ^
HINT:  No procedure matches the given name and argument types. You might need to add explicit type casts.
QUERY:  CALL customer_summary(1)
CONTEXT:  PL/pgSQL function inline_code_block line 3 at CALL
```

**PL/pgSQL からは「書き込める変数」を渡さなければなりません。** `not writable`（書き込めない）というエラーメッセージが出ます。名前付き記法も使えます。

```sql
DO $$
DECLARE v_name text; v_cnt bigint;
BEGIN
    CALL customer_summary(p_customer_id => 1, p_name => v_name, p_order_count => v_cnt);
    RAISE NOTICE '% / %', v_name, v_cnt;
END;
$$;
```

```
NOTICE:  Alice / 4
```

公式ドキュメント（[41.6.3 Calling a Procedure](https://www.postgresql.org/docs/17/plpgsql-control-structures.html)）に「PL/pgSQL は `CALL` の出力パラメータを SQL と違う扱いにする。各 `OUT` / `INOUT` パラメータは `CALL` 文の中の変数に対応していなければならず、戻ったあとにその変数へ代入される」と書かれています。

### 9-3. PostgreSQL 14 での変更

**PostgreSQL 14 で「プロシージャが `OUT` パラメータを持てる」ようになりました。** リリースノートの記述は次のとおりです（[PostgreSQL 14 Release Notes](https://www.postgresql.org/docs/release/14.0/)）。

> Stored procedures can now return data via `OUT` parameters.
> Allow procedures to have `OUT` parameters (Peter Eisentraut)

つまり **PostgreSQL 13 以前のプロシージャで値を返すには `INOUT` を使う必要があった**、ということです。講義版 §2-1 で `OUT` を使っている書き方は PostgreSQL 14 以降の書き方です。

- PostgreSQL 14 のリリースノートの「Migration to Version 14」（非互換一覧）には、この件は載っていません。**新機能の追加であり、既存コードを壊す変更ではない**と読めます。
- **PostgreSQL 13 以前で `OUT` がどのようなエラーになるかは、この環境（17.5 のみ）では実測できていないので未確認です。** 「13 以前は `INOUT` を使う」という説明にとどめてください。

## まとめ

| 属性 | 既定値 | 誤ると何が起きるか |
|:---|:---|:---|
| 変動性 | `VOLATILE` | インデックスが使われず、行数ぶん呼ばれる（実測 80〜200 倍） |
| `IMMUTABLE` の嘘 | — | 関数インデックスが古い値を返し続ける（実測） |
| `PARALLEL` | `UNSAFE` | クエリ全体の並列実行が止まる（実測 2.5〜2.9 倍） |
| `COST` | 100 | 重い関数が先に評価される。`WHERE` の評価順が変わる（実測） |
| `ROWS` | 1000 | Nested Loop が選ばれて内側が何万回も回る（実測 2〜3.7 倍） |
| `LANGUAGE` | — | plpgsql はインライン展開されない。`LIMIT` が中に届かない（実測 16〜45 倍） |
| `SECURITY DEFINER` ＋ `search_path` 未固定 | — | 呼び出し側に挙動を乗っ取られる（実測 11 倍のボーナス） |
| `LEAKPROOF` | 付かない | 隠していたはずの行の値が関数に渡る（実測） |

**講師として押さえておく要点**

- **既定値はすべて「安全側だが最適化されない側」に振ってある。** `VOLATILE` ＋ `PARALLEL UNSAFE` ＋ `COST 100` ＋ `ROWS 1000` は「何も分からない関数」への保守的な仮定です
- **「関数にまとめたのに遅い」の答えは、ほぼ「属性を書いていないから」と「plpgsql はインライン展開されないから」の 2 つ。** 研修生に説明するときは、まず「そもそも 1 文で書けないか」を確認し、その次にこの話をしてください
- **`IMMUTABLE` は検証されない約束。** 破るとインデックスが静かに壊れます
- **PL/pgSQL の集合関数は全件をタプルストアに貯める。** 大きなデータで使わせないこと（実測 20 倍・一時ファイル 20 MB）
- **明示カーソルを講義から外したのは、`FOR ... IN SELECT` で足りるから。** `WHERE CURRENT OF` だけが明示カーソル専用の機能です
- **`OUT` 引数の `CALL` は SQL と PL/pgSQL で書き方が違う。** SQL からは `NULL` を並べ、PL/pgSQL からは変数を渡します
