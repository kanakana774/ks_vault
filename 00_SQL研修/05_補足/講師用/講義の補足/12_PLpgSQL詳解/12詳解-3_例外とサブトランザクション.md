# 例外とサブトランザクションの深掘り

## 〜`EXCEPTION` 句が本当に作っているもの〜

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §7 では「`EXCEPTION` 句を足すとエラーを捕まえられる」、§9 では「再スローするとログの `INSERT` も巻き戻る」ところまでを扱いました。[[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] は「`EXCEPTION` 句がセーブポイントを作るので `COMMIT` できない」を扱っています。

**この資料は、その「セーブポイントを作る」を観測できる形にすることから始めます。** そのうえで、64 個問題の実体、例外を捕まえるコストの実測、`SQLSTATE` の設計規則、`RAISE` と `GET STACKED DIAGNOSTICS` の全形、そして「エラーログを DB に残したい」という要求に対する実務上の選択肢を整理します。

> **この資料の前提**
> - PostgreSQL 17.5 で動作確認しています。掲載しているエラーメッセージ・出力は**すべて実測**です。
> - **これは講師用の資料です。研修生には配りません。**
> - 対応する講義版: [[12-4_関数とプロシージャと例外処理|12-4]] §4〜§9 ／ [[12-1_PLpgSQLの基礎とDOブロック|12-1]] §6
> - **`COMMIT` / `ROLLBACK` が書ける場所の規則は [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] で扱っています。この資料では繰り返しません。** 15-3 を読んでいることを前提にします。
> - サブトランザクションの観測には 2 つのセッションを使っています（自分自身の状態は見えないため。→ §2-2）。

---

## 1. サブトランザクションの実体を観測する

### 1-1. 15-3 との分担

[[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §4-2 は、`EXCEPTION` 句付きのブロックの動きをこう整理しています。

1. ブロックに入る → `SAVEPOINT` を自動作成
2. 内部の SQL を実行
3. エラー発生 → そのセーブポイントまで自動ロールバックし、`EXCEPTION` 節へ
4. 正常終了 → セーブポイントを自動解放（`RELEASE`）

**この資料が足すのは「本当にそうなっているか」を外から見る方法と、4 の『解放』が何を解放していないか**です。

### 1-2. 実測：`xmin` で「別のトランザクション」を見る

行の `xmin` システム列には、その行を挿入したトランザクション ID が入ります。**`EXCEPTION` 句のあるブロックで挿入した行と、ない場所で挿入した行の `xmin` を比べれば、別のトランザクションかどうかが分かります。**

```sql
CREATE TABLE demo_sub (id integer, label text);

BEGIN;
SELECT pg_current_xact_id() AS main_xid;

INSERT INTO demo_sub VALUES (1, 'EXCEPTION 句なしのブロックで INSERT');

DO $$
BEGIN
    INSERT INTO demo_sub VALUES (2, 'EXCEPTION 句ありのブロックで INSERT');
EXCEPTION WHEN OTHERS THEN
    NULL;
END;
$$;

DO $$
BEGIN
    INSERT INTO demo_sub VALUES (3, 'EXCEPTION 句なしのブロックで INSERT（DO）');
END;
$$;

SELECT id, label, xmin FROM demo_sub ORDER BY id;
COMMIT;
```

```
 main_xid 
----------
    19551
(1 row)

 id |                   label                   | xmin  
----+-------------------------------------------+-------
  1 | EXCEPTION 句なしのブロックで INSERT       | 19551
  2 | EXCEPTION 句ありのブロックで INSERT       | 19552
  3 | EXCEPTION 句なしのブロックで INSERT（DO） | 19551
(3 rows)
```

**メイントランザクションは 19551。`EXCEPTION` 句を持つブロックの中の `INSERT` だけが 19552 という別の ID になっています。** `DO` ブロックそれ自体は新しい ID を消費していません（id=3 は 19551）。

**つまり「`EXCEPTION` 句を書いた」という事実だけが、新しいトランザクション ID（サブトランザクション ID = subxid）を消費させています。**

### 1-3. 実測：ネストするたびに増える

```sql
BEGIN;
SELECT pg_current_xact_id() AS main_xid;
DO $$
BEGIN
    INSERT INTO demo_sub VALUES (10, 'depth1');
    BEGIN
        INSERT INTO demo_sub VALUES (11, 'depth2');
        BEGIN
            INSERT INTO demo_sub VALUES (12, 'depth3');
        EXCEPTION WHEN OTHERS THEN NULL; END;
    EXCEPTION WHEN OTHERS THEN NULL; END;
EXCEPTION WHEN OTHERS THEN NULL; END;
$$;
SELECT id, label, xmin FROM demo_sub WHERE id >= 10 ORDER BY id;
ROLLBACK;
```

```
 main_xid 
----------
    19553
(1 row)

 id | label  | xmin  
----+--------+-------
 10 | depth1 | 19554
 11 | depth2 | 19555
 12 | depth3 | 19556
(3 rows)
```

**3 段ネストすると 3 つの subxid（19554/19555/19556）が消費されました。** ブロック 1 つにつき 1 つです。

### 1-4. 実測：書き込まないブロックは subxid を消費しない

サブトランザクションは常に ID を取るわけではありません。**書き込みをして初めて ID が割り当てられます。** これは §2 の 64 個問題を理解するための鍵です。§2-3 で測ります。

## 2. サブトランザクション 64 個問題

### 2-1. 何が 64 なのか

各バックエンドは共有メモリ上に `PGPROC` という構造体を持ち、そこに**「自分が現在持っている未確定のサブトランザクション ID」のキャッシュ**を置いています。**この配列の長さが 64 です**（PostgreSQL のソースで `PGPROC_MAX_CACHED_SUBXIDS = 64`）。

他のセッションが「ある行が見えるか」を判定するとき、その行の `xmin` が誰かの未確定トランザクションに属するかを調べます。**キャッシュに収まっていれば共有メモリを見るだけで済みますが、溢れると `pg_subtrans`（ディスク上の構造）を引きに行くことになります。**

`pg_stat_get_backend_subxact()`（PostgreSQL 17 で利用可能）で、この状態を観測できます。

### 2-2. 実測：64 と 65 の境目

**自分自身のバックエンドの subxact 状態は見えません**（観測用の値はクエリ開始時点のものなので 0 のままになります）。そこで 2 つのセッションを使います。

- **保持側**：`application_name = 'subxact_demo'` を設定し、トランザクションを開いて N 個のサブトランザクションを作り、`pg_sleep(6)` でその状態を保持する
- **観測側**：別接続から `pg_stat_get_backend_subxact()` を読む

観測側のクエリ：

```sql
SELECT a.pid, s.subxact_count, s.subxact_overflowed
  FROM pg_stat_get_backend_idset() AS b(bid),
       pg_stat_get_backend_subxact(b.bid) AS s,
       pg_stat_activity a
 WHERE pg_stat_get_backend_pid(b.bid) = a.pid
   AND a.application_name = 'subxact_demo';
```

保持側（`SAVEPOINT` を明示的に使う版。**セーブポイントの中で書き込むのが要点**です）：

```sql
SET application_name = 'subxact_demo';
BEGIN;
INSERT INTO demo_sub VALUES (100, 'main');
SAVEPOINT sp1;  INSERT INTO demo_sub VALUES (201, 'sp1');
SAVEPOINT sp2;  INSERT INTO demo_sub VALUES (202, 'sp2');
--  … N 個まで繰り返す …
SELECT pg_sleep(6);
ROLLBACK;
```

N を変えて観測しました。


**64 個までは `subxact_count = N` / `overflowed = f`。65 個目で `count` が 64 で止まり `overflowed = t` に変わります。** 70 個でも 64 のままです。**「64」がキャッシュの容量であることが、そのまま見えています。**

`SAVEPOINT` ではなく PL/pgSQL の `EXCEPTION` 句付きブロックをネストさせても、まったく同じ結果になります。

```sql

BEGIN;

INSERT INTO demo_sub VALUES (1, 'depth1');
BEGIN
INSERT INTO demo_sub VALUES (2, 'depth2');
--  … N 段まで繰り返す …
PERFORM pg_sleep(6);

--  … N 段ぶん閉じる …
END

```


**`BEGIN ... EXCEPTION ... END` は `SAVEPOINT` とまったく同じものを作っている**——これが実測での確認です。

### 2-3. 実測：ループ内の `EXCEPTION` は「成功すると溜まる」

ここが本題です。[[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §4-2 は「ループの中に `EXCEPTION` ブロックを置くと、回るたびにセーブポイントが作られる」と警告しています。**では、ループを抜けるとき（各回で `RELEASE` されるはず）に subxid は解放されるのでしょうか。**

3 通りのループを 100 回ずつ回して観測しました。

```sql
-- (A) 毎回 EXCEPTION ブロック・中で INSERT・エラーは起きない
BEGIN;
DO $do$
DECLARE i integer;
BEGIN
    FOR i IN 1..100 LOOP
        BEGIN
            INSERT INTO demo_sub VALUES (i, 'ok');
        EXCEPTION WHEN OTHERS THEN NULL;
        END;
    END LOOP;
    PERFORM pg_sleep(6);
END
$do$;
ROLLBACK;

-- (B) 毎回 EXCEPTION ブロックの中でエラーが起きる（INSERT の後に RAISE EXCEPTION）
-- (C) EXCEPTION ブロックの中で書き込まない（SELECT count(*) だけ）
```

```
###### (A) ループ 100 回・毎回 EXCEPTION ブロック・エラーは起きない
  pid  | subxact_count | subxact_overflowed 
-------+---------------+--------------------
 22880 |            64 | t
(1 row)

###### (B) ループ 100 回・毎回 EXCEPTION ブロックの中でエラーが起きる
  pid  | subxact_count | subxact_overflowed 
-------+---------------+--------------------
 16864 |             0 | f
(1 row)

###### (C) ループ 100 回・EXCEPTION ブロックの中で書き込まない（XID を消費しない）
  pid  | subxact_count | subxact_overflowed 
-------+---------------+--------------------
 18260 |             0 | f
(1 row)
```

**結果は直感と逆です。**

| | subxid | 理由 |
|:---|:---|:---|
| (A) 成功して抜ける | **100 個ぶん消費 → 溢れる** | サブトランザクションがコミットしても、その変更は親が確定するまで未確定。**subxid はキャッシュに残り続ける** |
| (B) エラーで抜ける | 0 | サブトランザクションが中止された時点で、その subxid はキャッシュから**取り除かれる**（もう誰も見なくてよいため） |
| (C) 書き込まない | 0 | 書き込みがないので subxid が**割り当てられない** |

**「失敗したときの方が安全」という、覚えにくい形の結論です。** 15-3 §5 のバッチテンプレートが「内側ブロックの外で `COMMIT` する」形になっているのは、**(A) の蓄積を `COMMIT` で切るため**です。テンプレート末尾の「この形にすると、内側ブロックのセーブポイントは毎回 `COMMIT` で解放されるので、§4-2 のサブトランザクション増加も起きません」は、この実測と整合しています。

### 2-4. 15-3 の警告を精密化する

15-3 §4-2 の書き方（「ループの中に `EXCEPTION` を置くと、回るたびにセーブポイントが作られる → 64 個を超えると性能が落ちる」）は結論として正しいのですが、**理由の説明としては (B)(C) を説明できません。** 講師が突っ込まれたときは次のように補ってください。

- 数えているのは「同時に存在するブロックの深さ」ではなく、**「そのトランザクションが割り当てた subxid の総数」**である
- subxid は**書き込みをしたときにだけ**割り当てられる
- 一度割り当てられた subxid は、**そのサブトランザクションが成功した場合は最上位の `COMMIT` / `ROLLBACK` まで残る**
- 中止された場合はその時点で取り除かれる

**したがって「ループの中で `EXCEPTION` ブロックを使い、その中で更新する」処理は、正常に流れるほど subxid が溜まります。** 1 万件処理すれば 1 万個です。

### 2-5. 溢れると何が遅くなるか（この環境では性能差の再現は未確認）

`overflowed = t` になると、他のセッションが可視性判定をするときに `pg_subtrans` を参照するようになります。理屈の上では次が遅くなります。

- **他のセッションによる読み取り**（その行が見えるかの判定に `SubTransGetTopmostTransaction()` が必要になる）
- 溢れた側のセッションではなく、**周りのセッションが遅くなる**のが特徴

**この検証環境（単一マシン・接続数も少ない）では、`overflowed = t` の状態で他セッションの読み取りが有意に遅くなることを再現できませんでした＝未確認です。** 影響が観測できるのは「高い同時実行数」「長時間開いたトランザクション」「多数のサブトランザクション」が揃った場合で、それを作るのはこの環境では現実的ではありません。

> ⚠️ **研修生に「64 を超えると急に遅くなる」と数値付きで断言しないでください。**
> 測って見せられるのは「64 でキャッシュが溢れる」ところまでです。性能への影響は同時実行の条件に依存し、この環境では再現できていません。**「64 という上限が実在し、超えると別の（遅い）仕組みに切り替わる」までが実測で言えることです。**

## 3. 例外を捕まえるコスト

### 3-1. ベンチマークの設計

`EXCEPTION` 句のコストは 2 つに分かれます。

1. **ブロックに入る／出るときのセーブポイント操作**（例外が起きなくても払う）
2. **例外が実際に発生したときの巻き戻しとハンドラ起動**

これを切り分けるため、4 通りの書き方で同じ回数まわします。

```sql
-- ① ブロックなし
FOR i IN 1..p_n LOOP
    v_r := 100.0 / (i % 5 + 1);
END LOOP;

-- ② EXCEPTION 句あり／例外は起きない
FOR i IN 1..p_n LOOP
    BEGIN
        v_r := 100.0 / (i % 5 + 1);
    EXCEPTION WHEN division_by_zero THEN
        v_r := 0;
    END;
END LOOP;

-- ③ 毎回 例外を捕まえる
FOR i IN 1..p_n LOOP
    BEGIN
        v_r := 100.0 / 0;
    EXCEPTION WHEN division_by_zero THEN
        v_r := 0;
    END;
END LOOP;

-- ④ IF で事前チェック
FOR i IN 1..p_n LOOP
    v_d := 0;
    IF v_d = 0 THEN
        v_r := 0;
    ELSE
        v_r := 100.0 / v_d;
    END IF;
END LOOP;
```

いずれも `clock_timestamp()` の差を返す関数にして、**20 万回を 3 セット**測ります。**DB への書き込みを含めていないのは、§2-3 の subxid 蓄積を混ぜないためです。**

### 3-2. 実測

```
       pattern        |       t1        |       t2        |       t3        
----------------------+-----------------+-----------------+-----------------
 ブロックなし         | 00:00:00.057058 | 00:00:00.036826 | 00:00:00.034401
(1 row)

             pattern              |       t1        |       t2        |       t3       
----------------------------------+-----------------+-----------------+----------------
 EXCEPTION 句あり／例外は起きない | 00:00:00.103046 | 00:00:00.107688 | 00:00:00.09936
(1 row)

       pattern        |       t1        |       t2        |       t3        
----------------------+-----------------+-----------------+-----------------
 毎回 例外を捕まえる  | 00:00:04.821996 | 00:00:06.587012 | 00:00:06.441212
(1 row)

       pattern        |       t1       |       t2        |       t3        
----------------------+----------------+-----------------+-----------------
 IF で事前チェック    | 00:00:00.07506 | 00:00:00.045224 | 00:00:00.031147
(1 row)
```

20 万回あたりに整理します。

| 書き方 | 20 万回 | 1 回あたり | ①比 |
|:---|---:|---:|---:|
| ① ブロックなし | 約 0.035 秒 | 約 0.18 μs | 1.0 |
| ② `EXCEPTION` 句あり／例外なし | 約 0.10 秒 | 約 0.50 μs | 約 3 倍 |
| ③ 毎回 例外を捕まえる | 約 6.0 秒 | 約 30 μs | **約 170 倍** |
| ④ `IF` で事前チェック | 約 0.035 秒 | 約 0.18 μs | 1.0 |

### 3-3. 読み方

- **`EXCEPTION` 句を「書いただけ」のコストは 1 回あたり 0.3μs 程度。** 20 万回まわしてやっと 0.07 秒の差です。**「`EXCEPTION` 句があるだけで重い」という言い方は誇張です。**
- **例外が実際に飛ぶと 2 桁変わります**（0.5μs → 30μs、約 60 倍）。セーブポイントまでの巻き戻しとエラーオブジェクトの構築が入るためです。
- **`IF` の事前チェックは①と区別できない速さ。** つまり**「起きることが分かっているエラー」を例外で処理するのが高い**のであって、例外機構そのものが高いのではありません。

**したがって指針はこうなります。**

| 状況 | 書き方 |
|:---|:---|
| 起きることが予期できる（在庫不足、未入力、0 除算になり得る） | **`IF` で事前チェック**。例外を飛ばさない |
| 事前チェックが原理的に書けない（一意制約違反の競合など） | `EXCEPTION` 句で捕まえる |
| ループの中で 1 件ごとに失敗を許容したい | `EXCEPTION` 句（＋§2-3 の subxid 蓄積に注意し、`COMMIT` で切る） |

> 💡 **「一意制約違反は `IF EXISTS` で事前チェックすればいい」は誤りです。**
> チェックした瞬間と `INSERT` する瞬間の間に他のセッションが入り込めるので（TOCTOU）、事前チェックでは防げません。**競合するものは例外で捕まえるしかありません。** 講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §7 で `unique_violation` を例に選んだのは、これが「例外でしか扱えない」典型だからです。

## 4. `SQLSTATE` の設計

### 4-1. 5 桁の構造

`SQLSTATE` は 5 文字です。**先頭 2 文字がクラス、残り 3 文字がサブクラス**で、サブクラスが `000` のものはそのクラス全体を表します。

| 例 | 意味 |
|:---|:---|
| `23000` | `integrity_constraint_violation`（クラス 23 全体） |
| `23505` | `unique_violation` |
| `22012` | `division_by_zero` |
| `P0001` | `raise_exception` |

PostgreSQL のソースツリーの `src/backend/utils/errcodes.txt` がこの一覧の正本で、そこから条件名・マクロ・ドキュメントの表が生成されています。

### 4-2. 【よくある誤解】実測：`P0001` は「独自コード」ではない

旧版の教材には `USING ERRCODE = 'P0001'` を「独自の SQLSTATE を定義する例」として示しているものがあります。**`P0001` は `RAISE EXCEPTION` が何も指定しなかったときの既定値です。**

```sql
DO $$
BEGIN
    BEGIN
        RAISE EXCEPTION 'ただのメッセージ';
    EXCEPTION WHEN OTHERS THEN
        RAISE NOTICE 'SQLSTATE = % / 条件名で捕まえられるか →', SQLSTATE;
    END;

    BEGIN
        RAISE EXCEPTION 'ただのメッセージ';
    EXCEPTION WHEN raise_exception THEN
        RAISE NOTICE 'raise_exception で捕まえられた。SQLSTATE = %', SQLSTATE;
    END;
END;
$$;
```

```
NOTICE:  SQLSTATE = P0001 / 条件名で捕まえられるか →
NOTICE:  raise_exception で捕まえられた。SQLSTATE = P0001
```

**`ERRCODE` を何も書かない `RAISE EXCEPTION` の SQLSTATE が `P0001` で、条件名 `raise_exception` に対応しています。**

これを「独自コード」に使うと何が壊れるかを実測します。

```sql
DO $$
BEGIN
    BEGIN
        -- 業務エラーのつもりで P0001 を指定
        RAISE EXCEPTION '在庫が足りません' USING ERRCODE = 'P0001';
    EXCEPTION WHEN SQLSTATE 'P0001' THEN
        RAISE NOTICE '捕まえた: % （でもこれは既定値と同じコード）', SQLERRM;
    END;

    BEGIN
        -- まったく無関係なうっかりミス（メッセージだけの RAISE）
        RAISE EXCEPTION 'デバッグ用に置いたまま忘れた RAISE';
    EXCEPTION WHEN SQLSTATE 'P0001' THEN
        RAISE NOTICE 'これも同じハンドラに落ちる: %', SQLERRM;
    END;
END;
$$;
```

```
NOTICE:  捕まえた: 在庫が足りません （でもこれは既定値と同じコード）
NOTICE:  これも同じハンドラに落ちる: デバッグ用に置いたまま忘れた RAISE
```

**「在庫不足」を処理するハンドラが、無関係な `RAISE EXCEPTION` まで拾ってしまいました。** `ERRCODE` を書かない `RAISE EXCEPTION` はコードのどこにでもあり得るので、**`P0001` で分岐する設計は最初から壊れています。**

### 4-3. 実測：`P` は PostgreSQL の予約領域

`P` クラスは PostgreSQL 自身が使っています。すでに使われているものを確認します。

```sql
DO $$
DECLARE v_x text;
BEGIN
    BEGIN
        SELECT name INTO STRICT v_x FROM customers WHERE customer_id = 999;
    EXCEPTION WHEN OTHERS THEN
        RAISE NOTICE 'no_data_found  = %', SQLSTATE;
    END;
    BEGIN
        SELECT name INTO STRICT v_x FROM customers;
    EXCEPTION WHEN OTHERS THEN
        RAISE NOTICE 'too_many_rows  = %', SQLSTATE;
    END;
END;
$$;

DO $$
BEGIN
    BEGIN
        ASSERT 1 = 2, 'ASSERT が失敗した';
    EXCEPTION WHEN assert_failure THEN
        RAISE NOTICE 'assert_failure = %', SQLSTATE;
    END;
END;
$$;
```

```
NOTICE:  no_data_found  = P0002
NOTICE:  too_many_rows  = P0003
NOTICE:  assert_failure = P0004
```

**`P0001` から `P0004` まで埋まっています。** 将来のバージョンで `P0005` 以降が追加される可能性があるので、**`P` クラスに独自コードを置いてはいけません。**

### 4-4. 実測：独自コードの正しい選び方

SQL 標準は「実装定義（implementation-defined）」のクラスとして、**先頭文字が `5`〜`9` または `I`〜`Z` の範囲**を空けています。`errcodes.txt` もこの規則に従っています。PostgreSQL 自身が使っているクラスは `00`〜`4x` と `5x` の一部（`53` `54` `55` `57` `58`）、`F0` `HV` `P0` `XX` なので、**`S` で始まるコードは安全に使えます。**

```sql
DO $$
BEGIN
    BEGIN
        RAISE EXCEPTION '在庫が足りません' USING ERRCODE = 'S0001';
    EXCEPTION WHEN SQLSTATE 'S0001' THEN
        RAISE NOTICE 'S0001 で捕まえた: %', SQLERRM;
    END;

    BEGIN
        RAISE EXCEPTION '与信限度を超えました' USING ERRCODE = 'S0002';
    EXCEPTION
        WHEN SQLSTATE 'S0001' THEN RAISE NOTICE '在庫の話として処理';
        WHEN SQLSTATE 'S0002' THEN RAISE NOTICE '与信の話として処理: %', SQLERRM;
    END;
END;
$$;
```

```
NOTICE:  S0001 で捕まえた: 在庫が足りません
NOTICE:  与信の話として処理: 与信限度を超えました
```

**業務エラーの種類ごとに別のコードを割り当てられました。** 実務では次のように決めておくとよいです。

| コード | 意味 |
|:---|:---|
| `S0001` | 在庫不足 |
| `S0002` | 与信限度超過 |
| `S0003` | 締め処理済みの期間への更新 |
| … | （一覧をリポジトリの 1 ファイルで管理する） |

> ⚠️ **`SQLSTATE` に業務の意味を持たせるかどうかは設計判断です。**
> アプリ側が `SQLSTATE` で分岐する必要があるなら独自コードを付ける価値があります。**メッセージを人が読むだけなら `P0001`（既定）のままでよく、そのときは `USING ERRCODE` を書かないのが正しい**です。「なんとなく `ERRCODE` を書く」のがいちばんよくありません。

### 4-5. 実測：受け付けられる書式・られない書式

```sql
DO $$ BEGIN RAISE EXCEPTION 'x' USING ERRCODE = 'ABC';   END; $$;
DO $$ BEGIN RAISE EXCEPTION 'x' USING ERRCODE = 'ab001'; END; $$;
DO $$
BEGIN
    BEGIN
        RAISE EXCEPTION 'x' USING ERRCODE = 'AB001';
    EXCEPTION WHEN OTHERS THEN
        RAISE NOTICE '小文字は? SQLSTATE = %', SQLSTATE;
    END;
END;
$$;
```

```
ERROR:  unrecognized exception condition "ABC"
CONTEXT:  PL/pgSQL function inline_code_block line 3 at RAISE
ERROR:  unrecognized exception condition "ab001"
CONTEXT:  PL/pgSQL function inline_code_block line 3 at RAISE
NOTICE:  小文字は? SQLSTATE = AB001
```

**`ERRCODE` に渡した文字列は、まず「条件名」として解釈が試みられます。** 5 文字の大文字英数字なら SQLSTATE として通り、そうでなければ条件名の表を引いて、なければ `unrecognized exception condition` になります。**`'ABC'`（3 文字）も `'ab001'`（小文字）も条件名として存在しないので落ちます。**

### 4-6. 実測：条件名を投げる／クラスで捕まえる

`ERRCODE` には条件名も書けます。

```sql
DO $$
BEGIN
    BEGIN
        RAISE EXCEPTION 'これは一意制約違反のふりをする' USING ERRCODE = 'unique_violation';
    EXCEPTION WHEN unique_violation THEN
        RAISE NOTICE '条件名指定で投げて条件名で捕まえた。SQLSTATE = %', SQLSTATE;
    END;
END;
$$;
```

```
NOTICE:  条件名指定で投げて条件名で捕まえた。SQLSTATE = 23505
```

また、**サブクラスが `000` のコード（クラスコード）で捕まえると、そのクラス全体を捕まえます。**

```sql
DO $$
BEGIN
    BEGIN
        INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
        VALUES (900, 1, 1, 5, 'dup', CURRENT_DATE);
    EXCEPTION
        WHEN SQLSTATE '23000' THEN RAISE NOTICE 'クラス 23000 で捕まえた';
        WHEN OTHERS          THEN RAISE NOTICE 'クラスでは捕まらず OTHERS: %', SQLSTATE;
    END;

    BEGIN
        INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
        VALUES (900, 1, 1, 5, 'dup', CURRENT_DATE);
    EXCEPTION
        WHEN integrity_constraint_violation THEN
            RAISE NOTICE '条件名 integrity_constraint_violation で捕まえた: %', SQLSTATE;
    END;
END;
$$;
```

```
NOTICE:  クラス 23000 で捕まえた
NOTICE:  条件名 integrity_constraint_violation で捕まえた: 23505
```

**発生したのは `23505` ですが、`23000` でも `integrity_constraint_violation` でも捕まりました。** 「一意制約・外部キー・NOT NULL・CHECK のどれでも同じ扱いにしたい」ときは、クラスで書くと 4 つ並べる必要がなくなります。ただし**「どれで落ちたか」が分からなくなるので、`SQLSTATE` をログに出すことは必須です。**

## 5. `RAISE` の全形

### 5-1. 5 つの形

| 形 | 例 | 用途 |
|:---|:---|:---|
| `RAISE level 'format', 引数…` | `RAISE NOTICE 'id=%', v_id` | 通常 |
| `RAISE level 条件名` | `RAISE division_by_zero` | 既存の条件名を投げる |
| `RAISE level SQLSTATE 'コード'` | `RAISE SQLSTATE 'S0001'` | コードを直接投げる |
| `RAISE level USING キー = 値, …` | `RAISE USING MESSAGE = '…'` | すべてを `USING` で書く |
| `RAISE;`（引数なし） | ハンドラ内での再スロー | 捕まえたエラーを投げ直す |

`level` を省略すると `EXCEPTION` になります。

**なお `RAISE NOTICE;` のように「レベルだけ」は書けません。**

```sql
DO $$
BEGIN
    RAISE NOTICE;
END;
$$;
```

```
ERROR:  syntax error at or near ";"
LINE 3:     RAISE NOTICE;
                        ^
```

`USING MESSAGE` で本文を渡すのが正しい形です。

```sql
DO $$
BEGIN
    RAISE NOTICE USING MESSAGE = 'USING MESSAGE で本文を書いた';
END;
$$;
```

```
NOTICE:  USING MESSAGE で本文を書いた
```

条件名・`SQLSTATE` を直接投げた場合、**メッセージを指定しなければ条件名そのものが `SQLERRM` になります。**

```sql
DO $$
BEGIN
    BEGIN
        RAISE division_by_zero;
    EXCEPTION WHEN division_by_zero THEN
        RAISE NOTICE 'SQLSTATE=% / SQLERRM=%', SQLSTATE, SQLERRM;
    END;

    BEGIN
        RAISE division_by_zero USING MESSAGE = '割る数が 0 でした';
    EXCEPTION WHEN division_by_zero THEN
        RAISE NOTICE 'SQLSTATE=% / SQLERRM=%', SQLSTATE, SQLERRM;
    END;

    BEGIN
        RAISE SQLSTATE 'S0001' USING MESSAGE = '独自コードを直接投げた';
    EXCEPTION WHEN SQLSTATE 'S0001' THEN
        RAISE NOTICE 'SQLSTATE=% / SQLERRM=%', SQLSTATE, SQLERRM;
    END;
END;
$$;
```

```
NOTICE:  SQLSTATE=22012 / SQLERRM=division_by_zero
NOTICE:  SQLSTATE=22012 / SQLERRM=割る数が 0 でした
NOTICE:  SQLSTATE=S0001 / SQLERRM=独自コードを直接投げた
```

**`RAISE;` はハンドラの中でしか書けません。**

```sql
DO $$
BEGIN
    RAISE;
END;
$$;
```

```
ERROR:  RAISE without parameters cannot be used outside an exception handler
CONTEXT:  PL/pgSQL function inline_code_block line 3 at RAISE
```

### 5-2. 実測：`USING` の全キーワード

```sql
DO $$
BEGIN
    RAISE EXCEPTION 'メッセージ本体'
        USING ERRCODE   = 'S0009',
              DETAIL    = '詳細：何が起きたか',
              HINT      = 'ヒント：どうすれば直るか',
              COLUMN    = 'price',
              CONSTRAINT= 'products_price_positive',
              DATATYPE  = 'numeric',
              TABLE     = 'products',

$$;
```

```
ERROR:  メッセージ本体
DETAIL:  詳細：何が起きたか
HINT:  ヒント：どうすれば直るか
CONTEXT:  PL/pgSQL function inline_code_block line 3 at RAISE
```

**`COLUMN` / `CONSTRAINT` / `DATATYPE` / `TABLE` / `SCHEMA` は画面に出ていません。** これらはクライアントに表示される項目ではなく、**プロトコル上のフィールドとして運ばれ、`GET STACKED DIAGNOSTICS` やドライバの API から読むもの**です。実際に取れることを確認します。

```sql
DO $$
DECLARE
    v_col text; v_con text; v_dt text; v_tab text; v_sch text;
BEGIN
    BEGIN
        RAISE EXCEPTION '価格が負です'
            USING ERRCODE = 'S0009', COLUMN = 'price', CONSTRAINT = 'products_price_positive',
                  DATATYPE = 'numeric', TABLE = 'products', SCHEMA = 'public';
    EXCEPTION WHEN SQLSTATE 'S0009' THEN
        GET STACKED DIAGNOSTICS
            v_col = COLUMN_NAME, v_con = CONSTRAINT_NAME, v_dt = PG_DATATYPE_NAME,
            v_tab = TABLE_NAME,  v_sch = SCHEMA_NAME;
        RAISE NOTICE 'COLUMN=[%] CONSTRAINT=[%] DATATYPE=[%] TABLE=[%] SCHEMA=[%]',
            v_col, v_con, v_dt, v_tab, v_sch;
    END;
END;
$$;
```

```
NOTICE:  COLUMN=[price] CONSTRAINT=[products_price_positive] DATATYPE=[numeric] TABLE=[products] SCHEMA=[public]
```

**取れました。** 「アプリのフォームで、どの項目にエラーを表示するか」を DB 側から伝えたい場合に使えます。ただし**アプリ側がこのフィールドを読む実装になっていなければ意味がありません。** 使うなら両側で決めてから使ってください。

### 5-4. 実測：`WHEN OTHERS` が捕まえないもの

```sql
DO $$
BEGIN
    BEGIN
        ASSERT 1 = 2, 'assert';
    EXCEPTION WHEN OTHERS THEN
        RAISE NOTICE 'OTHERS で捕まえた';
    END;
END;
$$;
```

```
ERROR:  assert
CONTEXT:  PL/pgSQL function inline_code_block line 15 at ASSERT
```

**`WHEN OTHERS` を書いてあるのに、`ASSERT` の失敗は素通りしました。** 専用の条件名なら捕まります（§4-3 の実測、`assert_failure` = `P0004`）。

**`OTHERS` は `assert_failure` と `query_canceled` を捕まえません。** 前者は「プログラムのバグを示すもの」、後者は「利用者やタイムアウトによる中断」で、どちらも業務ロジックが握りつぶしてよいものではないためです。

> 💡 **これは `ASSERT` の使いどころを決めます。**
> 「あり得ないはずの状態」の検出に `ASSERT` を使えば、上流の `WHEN OTHERS` に握りつぶされずに必ず外へ出ます。**`RAISE EXCEPTION` は `OTHERS` に捕まりますが、`ASSERT` は捕まりません。** 講義版では `ASSERT` を扱っていないので、研修生には出さないでください。

## 6. `GET STACKED DIAGNOSTICS`

### 6-1. 実測：全 10 項目

`reviews` の一意制約違反で、取れる項目をすべて表示します。

```sql
DO $$
DECLARE
    v_returned_sqlstate    text;
    v_column_name          text;
    v_constraint_name      text;
    v_pg_datatype_name     text;
    v_message_text         text;
    v_table_name           text;
    v_schema_name          text;
    v_pg_exception_detail  text;
    v_pg_exception_hint    text;
    v_pg_exception_context text;
BEGIN
    BEGIN
        INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
        VALUES (901, 1, 1, 5, 'dup', CURRENT_DATE);
    EXCEPTION WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS
            v_returned_sqlstate    = RETURNED_SQLSTATE,
            v_column_name          = COLUMN_NAME,
            v_constraint_name      = CONSTRAINT_NAME,
            v_pg_datatype_name     = PG_DATATYPE_NAME,
            v_message_text         = MESSAGE_TEXT,
            v_table_name           = TABLE_NAME,
            v_schema_name          = SCHEMA_NAME,
            v_pg_exception_detail  = PG_EXCEPTION_DETAIL,
            v_pg_exception_hint    = PG_EXCEPTION_HINT,
            v_pg_exception_context = PG_EXCEPTION_CONTEXT;

        RAISE NOTICE 'RETURNED_SQLSTATE   = [%]', v_returned_sqlstate;
        RAISE NOTICE 'COLUMN_NAME         = [%]', v_column_name;
        RAISE NOTICE 'CONSTRAINT_NAME     = [%]', v_constraint_name;
        RAISE NOTICE 'PG_DATATYPE_NAME    = [%]', v_pg_datatype_name;
        RAISE NOTICE 'MESSAGE_TEXT        = [%]', v_message_text;
        RAISE NOTICE 'TABLE_NAME          = [%]', v_table_name;
        RAISE NOTICE 'SCHEMA_NAME         = [%]', v_schema_name;
        RAISE NOTICE 'PG_EXCEPTION_DETAIL = [%]', v_pg_exception_detail;
        RAISE NOTICE 'PG_EXCEPTION_HINT   = [%]', v_pg_exception_hint;
        RAISE NOTICE 'PG_EXCEPTION_CONTEXT= [%]', v_pg_exception_context;
    END;
END;
$$;
```

```
NOTICE:  RETURNED_SQLSTATE   = [23505]
NOTICE:  COLUMN_NAME         = []
NOTICE:  CONSTRAINT_NAME     = [reviews_product_id_customer_id_key]
NOTICE:  PG_DATATYPE_NAME    = []
NOTICE:  MESSAGE_TEXT        = [duplicate key value violates unique constraint "reviews_product_id_customer_id_key"]
NOTICE:  TABLE_NAME          = [reviews]
NOTICE:  SCHEMA_NAME         = [public]
NOTICE:  PG_EXCEPTION_DETAIL = [Key (product_id, customer_id)=(1, 1) already exists.]
NOTICE:  PG_EXCEPTION_HINT   = []
NOTICE:  PG_EXCEPTION_CONTEXT= [SQL statement "INSERT INTO reviews (review_id, product_id, customer_id, rating, comment, review_date)
        VALUES (901, 1, 1, 5, 'dup', CURRENT_DATE)"
PL/pgSQL function inline_code_block line 15 at SQL statement]
```

| 項目 | この例での値 | 使いどころ |
|:---|:---|:---|
| `RETURNED_SQLSTATE` | `23505` | `SQLSTATE` と同じ |
| `COLUMN_NAME` | （空） | 列に紐づくエラーのとき |
| `CONSTRAINT_NAME` | `reviews_product_id_customer_id_key` | **どの制約で落ちたか。制約名で分岐できる** |
| `PG_DATATYPE_NAME` | （空） | 型に紐づくエラーのとき |
| `MESSAGE_TEXT` | `duplicate key value violates...` | `SQLERRM` と同じ |
| `TABLE_NAME` | `reviews` | **どの表か** |
| `SCHEMA_NAME` | `public` | どのスキーマか |
| `PG_EXCEPTION_DETAIL` | `Key (product_id, customer_id)=(1, 1) already exists.` | **どの値で落ちたか** |
| `PG_EXCEPTION_HINT` | （空） | 対処の示唆 |
| `PG_EXCEPTION_CONTEXT` | 実行中の SQL 文＋呼び出し位置 | **これが最重要** |

### 6-2. `PG_EXCEPTION_CONTEXT` が最重要である理由

**`SQLERRM` だけをログに出すと、どこで落ちたかが一切分かりません。** 上の例なら「一意制約違反」までは分かりますが、**その `INSERT` が何十行ある関数のどこにあるのか、どの関数から呼ばれたのか**は分かりません。

`PG_EXCEPTION_CONTEXT` は「実行していた SQL 文の本文」と「PL/pgSQL の呼び出し位置（関数名・行番号・文の種類）」を含みます。**`WHEN OTHERS` で捕まえるなら、`SQLSTATE` / `MESSAGE_TEXT` / `PG_EXCEPTION_CONTEXT` の 3 点をセットで残すのが最低ラインです。**

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §7-1 で「`SQLSTATE` と `SQLERRM` はセットで出す」と書いたのは、`GET STACKED DIAGNOSTICS` を教えていない範囲での最善です。**詳解版としては 3 点セットを推します。**

### 6-3. 実測：`GET CURRENT DIAGNOSTICS` の `PG_CONTEXT`

エラーが起きていないときでも、**今どこを実行しているか**は取れます。

```sql
CREATE OR REPLACE FUNCTION diag_inner() RETURNS void
LANGUAGE plpgsql AS $$
DECLARE v_ctx text;
BEGIN
    GET CURRENT DIAGNOSTICS v_ctx = PG_CONTEXT;
    RAISE NOTICE E'PG_CONTEXT:\n%', v_ctx;
END;
$$;
CREATE OR REPLACE FUNCTION diag_outer() RETURNS void
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM diag_inner();
END;
$$;
SELECT diag_outer();
```

```
NOTICE:  PG_CONTEXT:
PL/pgSQL function diag_inner() line 4 at GET DIAGNOSTICS
SQL statement "SELECT diag_inner()"
PL/pgSQL function diag_outer() line 3 at PERFORM
```

**呼び出しスタックがそのまま取れています。** 「この関数は誰から呼ばれているのか」を調べるとき（トリガーからか、バッチからか、アプリからか）に使えます。

`GET CURRENT DIAGNOSTICS` で取れるのは `ROW_COUNT`（講義版 [[12-2_変数とSQLの実行|12-2]] §8）・`PG_CONTEXT`・`PG_ROUTINE_OID` です。**`GET DIAGNOSTICS` と書くと `CURRENT` の意味になります。**

### 6-4. 実測：ハンドラの外では使えない

```sql
DO $$
DECLARE v_x text;
BEGIN
    GET STACKED DIAGNOSTICS v_x = MESSAGE_TEXT;
END;
$$;
```

```
ERROR:  GET STACKED DIAGNOSTICS cannot be used outside an exception handler
CONTEXT:  PL/pgSQL function inline_code_block line 4 at GET STACKED DIAGNOSTICS
```

`STACKED` は「今ハンドラで扱っている例外の情報」なので、ハンドラの外には存在しません。

## 7. 「エラーログを DB に残したい」問題の整理

### 7-1. 講義版で示した事実

講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §9 で実測したのはこの 2 点です。

| やり方 | 呼び出し元への通知 | DB 内のログ |
|:---|:---|:---|
| 版A（`RAISE;` で再スロー） | **エラーとして伝わる** | 残らない |
| 版B（握りつぶす） | 成功と誤認される | **残る** |

**同じトランザクションの中では両立しません。** 「ログを残す」と「エラーを返す」を同時に満たすには、**ログを別のトランザクションで書く**しかありません。以下、実務での選択肢を短所つきで並べます。

### 7-2. 案① 呼び出し元アプリで catch して、別トランザクションで書く

```
アプリ ── BEGIN ──▶ DB
アプリ ── CALL ───▶ DB   ← ここでエラー
アプリ ── ROLLBACK ─▶ DB  （業務データは巻き戻る）
アプリ ── BEGIN ──▶ DB   （新しいトランザクション）
アプリ ── INSERT INTO error_logs ──▶ DB
アプリ ── COMMIT ──▶ DB
```

| | |
|:---|:---|
| 長所 | **追加の拡張が不要。** どの環境でも動く。ログの内容をアプリ側で整形できる |
| 短所 | **DB 側だけを見ている人（DBA・バッチ運用）からは実装が見えない。** アプリのフレームワークごとに書き方が違う。アプリが落ちるとログも残らない |

**これが第一候補です。** DB 側は `RAISE EXCEPTION` で正しく失敗を伝えることに専念し、記録はアプリの責務にする——**責任の切り方としても素直です。**

### 7-3. 案② `dblink` で自律トランザクションを模す（実測）

PostgreSQL には Oracle の自律トランザクション（`PRAGMA AUTONOMOUS_TRANSACTION`）がありません。**別の接続を張って書けば、それが別トランザクションになります。** `dblink` は自分自身の DB にも接続できます。

```sql
CREATE EXTENSION IF NOT EXISTS dblink;

CREATE TABLE demo_error_logs (
    log_id    serial PRIMARY KEY,
    logged_at timestamptz DEFAULT now(),
    sqlstate  text,
    message   text
);

CREATE OR REPLACE PROCEDURE log_via_dblink()
LANGUAGE plpgsql AS $$
DECLARE
    v_state text;
    v_msg   text;
BEGIN
    UPDATE products SET price = 1 WHERE product_id = 1;
    RAISE EXCEPTION 'わざと失敗させます';
EXCEPTION WHEN OTHERS THEN
    GET STACKED DIAGNOSTICS v_state = RETURNED_SQLSTATE, v_msg = MESSAGE_TEXT;

    -- 別の接続（＝別トランザクション）で書く
    PERFORM dblink_exec(
        format('host=localhost dbname=%s user=postgres password=aevic', current_database()),
        format('INSERT INTO demo_error_logs (sqlstate, message) VALUES (%L, %L)',
               v_state, v_msg));

    RAISE;      -- 呼び出し元にはちゃんとエラーを返す
END;
$$;

CALL log_via_dblink();
SELECT log_id, sqlstate, message FROM demo_error_logs;
SELECT product_id, price FROM products WHERE product_id = 1;
```

```
ERROR:  わざと失敗させます
CONTEXT:  PL/pgSQL function log_via_dblink() line 7 at RAISE

 log_id | sqlstate |      message       
--------+----------+--------------------
      1 | P0001    | わざと失敗させます
(1 row)

 product_id |  price  
------------+---------
          1 | 1200.00
(1 row)
```

**3 つが同時に成立しました。** 呼び出し元にはエラーが返り、ログは残り、業務データ（価格）は巻き戻っています。**講義版 §9 で「両方は取れない」と書いた壁を、別接続で越えています。**

### 7-4. 実測：案②のコスト

**毎回接続を張るので、そのコストは無視できません。**

```sql
DO $$
DECLARE
    v_conn text := format('host=localhost dbname=%s user=postgres password=aevic',
                          current_database());
    v_t0   timestamptz;
    v_dbl  interval;
    v_same interval;
BEGIN
    -- ① dblink（毎回接続を張る）
    v_t0 := clock_timestamp();
    FOR i IN 1..20 LOOP
        PERFORM dblink_exec(v_conn,
            format('INSERT INTO demo_error_logs (sqlstate, message) VALUES (%L, %L)',
                   'P0001', 'dblink'));
    END LOOP;
    v_dbl := clock_timestamp() - v_t0;

    -- ② 同一接続
    v_t0 := clock_timestamp();
    FOR i IN 1..20 LOOP
        INSERT INTO demo_error_logs (sqlstate, message) VALUES ('P0001', 'same');
    END LOOP;
    v_same := clock_timestamp() - v_t0;

    RAISE NOTICE 'dblink で 20 回書き込み: %', v_dbl;
    RAISE NOTICE '同一接続で 20 回書き込み: %', v_same;
END;
$$;
```

実測（2 回実行）：

```
NOTICE:  dblink で 20 回書き込み: 00:00:01.590854
NOTICE:  同一接続で 20 回書き込み: 00:00:00.000609
```

```
NOTICE:  dblink で 20 回書き込み: 00:00:01.452451
NOTICE:  同一接続で 20 回書き込み: 00:00:00.000802
```

**1 回あたり約 73〜80ms 対 約 0.03〜0.04ms。2000 倍前後の差です。**

| | |
|:---|:---|
| 長所 | **DB の中で完結する。** アプリ側の実装に依存しない |
| 短所 | **1 回あたり数十ミリ秒。** 接続文字列にパスワードを書く必要がある（`postgres_fdw` のユーザーマッピングや `.pgpass` で緩和できるが管理対象が増える）。**接続が失敗したらログも残らない。** ループの中で使うと致命的に遅い |

**「めったに起きないエラーの記録」に限って使えます。** `dblink_connect` で接続を張りっぱなしにすれば接続コストは下げられますが、**その接続が持つトランザクションの管理が新たな問題になる**ので、この資料では検証していません＝**未確認**です。

### 7-5. 案③ `RAISE LOG` でサーバログへ（実測）

§5-3 のとおり、**`RAISE LOG` はクライアントに出ずサーバログに残ります。しかもログ出力はトランザクションの巻き戻しの対象ではありません。**

```sql
CREATE OR REPLACE PROCEDURE log_to_serverlog()
LANGUAGE plpgsql AS $$
DECLARE
    v_state text; v_msg text; v_ctx text;
BEGIN
    UPDATE products SET price = 1 WHERE product_id = 1;
    RAISE EXCEPTION 'わざと失敗させます';
EXCEPTION WHEN OTHERS THEN
    GET STACKED DIAGNOSTICS
        v_state = RETURNED_SQLSTATE, v_msg = MESSAGE_TEXT, v_ctx = PG_EXCEPTION_CONTEXT;
    RAISE LOG '[業務エラー] SQLSTATE=% MESSAGE=% CONTEXT=%', v_state, v_msg, v_ctx;
    RAISE;
END;
$$;
```

`RAISE LOG` がサーバログに残ることは §5-3 で実測済みです（`MARK-C LOG` の行）。

| | |
|:---|:---|
| 長所 | **拡張も追加接続も不要。** 巻き戻らない。コストがほぼゼロ |
| 短所 | **SQL で集計できない。** ログの収集・検索の仕組み（ファイル転送・ログ集約）が別に必要。`log_min_messages` の設定に依存する。ログのローテーションで消える |

**「エラーが起きた事実と内容を確実に残す」ことだけが目的なら、これがいちばん安い**です。**「エラーの件数を業務画面に出したい」なら不十分**です。

### 7-6. 案④ `pg_background`（この環境では未導入）

`pg_background` はバックグラウンドワーカーで SQL を実行する拡張で、**それが別トランザクションになる**ので自律トランザクションの代替になります。`dblink` と違い接続を張らないので軽いはずです。

```sql
SELECT name, default_version, installed_version
  FROM pg_available_extensions
 WHERE name IN ('dblink', 'postgres_fdw', 'pg_background');
```

```
     name     | default_version | installed_version 
--------------+-----------------+-------------------
 dblink       | 1.2             | 
 postgres_fdw | 1.1             | 
(2 rows)
```

**`pg_background` はこの環境には存在しません**（標準ディストリビューションに含まれない外部拡張）。したがって動作・性能は**未確認**です。「そういう手もある」以上のことを研修生に言わないでください。

### 7-7. 選択の指針

| 状況 | 推す案 |
|:---|:---|
| アプリから呼ばれる通常の処理 | **案① アプリ側で記録** |
| DB 内のバッチ（`CALL` を直接叩く）で、エラーが稀 | 案② `dblink`（毎回 59ms を許容できるなら） |
| とにかく事実を残したい／性能を落とせない | **案③ `RAISE LOG`** |
| ループの中で 1 件ずつ失敗を記録し、成功分は残したい | **`EXCEPTION` を内側に閉じ込め、外で `COMMIT` する**（[[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §5 のテンプレート）。この形なら**同じ DB のログ表に普通に `INSERT` できます** |

> ⚠️ **最後の行が実は最重要です。**
> 「ログを残しつつエラーも返す」が難しいのは、**処理全体を 1 つのトランザクションで包んでいるから**です。**1 件ずつ `COMMIT` する設計にすれば、失敗した件のログはその後の `COMMIT` で確定します。** 拡張も別接続も要りません。**トランザクションの境界を設計し直すのが、いちばん筋のよい解**です（[[15-2_実践_ロックとMVCC|15-2]] §6）。

## まとめ

- **`EXCEPTION` 句付きブロックは本当に別のトランザクション ID を消費する。** 実測：メイン 19551 に対しブロック内の `INSERT` は 19552。ネスト 3 段で 3 個
- **`BEGIN ... EXCEPTION ... END` と `SAVEPOINT` は同じもの**（64/65 の境目の挙動が完全に一致）
- **subxid のキャッシュは 64 個。** 実測：64 個で `count=64 / overflowed=f`、65 個で `count=64 / overflowed=t`
- **【重要】ループ内の `EXCEPTION` ブロックは「成功すると溜まる」。** 実測：100 回成功 → 溢れる／100 回失敗 → 0／書き込まない → 0。**subxid は書き込み時に割り当てられ、成功したサブトランザクションのものは最上位のコミットまで残る**
- **溢れた後の性能低下は、この環境では再現できず＝未確認。** 「64 で別の仕組みに切り替わる」までが実測で言えること
- **`EXCEPTION` 句を書くだけのコストは 1 回 0.3μs 程度（約 3 倍）。例外が実際に飛ぶと約 170 倍。** `IF` の事前チェックはブロックなしと同等
- **予期できるエラーは `IF` で、競合するエラー（一意制約違反など）は `EXCEPTION` で。** 事前チェックでは競合は防げない
- **【誤解の訂正】`P0001` は `RAISE EXCEPTION` の既定値であり独自コードではない。** 実測：`ERRCODE` を書かない `RAISE EXCEPTION` も同じハンドラに落ちる。`P0001`〜`P0004` は PostgreSQL が使用済み
- **独自コードは実装定義クラス（先頭が 5〜9 または I〜Z）から採る。** `S0001` などが安全
- **クラスコード（サブクラス `000`）で捕まえるとクラス全体を捕まえられる**（`23000` が `23505` を捕まえる）
- **`RAISE` は 5 つの形。`RAISE NOTICE;`（レベルだけ）は書けない。`RAISE;` はハンドラ内限定**
- **`USING` の `COLUMN` / `CONSTRAINT` / `DATATYPE` / `TABLE` / `SCHEMA` は画面に出ない。** `GET STACKED DIAGNOSTICS` で取る
- **`RAISE LOG` はクライアントに出ずサーバログに出る**（`client_min_messages` と `log_min_messages` で重大度の並び順が違うため）。**`RAISE INFO` は `client_min_messages` を無視して常にクライアントへ出る**
- **`WHEN OTHERS` は `assert_failure` と `query_canceled` を捕まえない**
- **`WHEN OTHERS` で捕まえるなら `SQLSTATE` / `MESSAGE_TEXT` / `PG_EXCEPTION_CONTEXT` の 3 点セットを残す**
- **「ログを残しつつエラーも返す」は別トランザクションが必要。** `dblink` で実測できるが 1 回 73〜80ms（同一接続の 2000 倍前後）。**まずはトランザクションの境界を設計し直す（1 件ずつ `COMMIT`）ことを検討する**
- **`pg_background` はこの環境には未導入**
