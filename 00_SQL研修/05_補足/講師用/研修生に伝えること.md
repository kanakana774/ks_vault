## 出口が2つある

**言い方を出口で変える。** 同じ内容でも、誰に何のために語るかが違う。

| 対象 | 出口 | 語る相手 |
|---|---|---|
| **外部研修生** | **配属先での立ち上がり** | 配属先のチーム。派遣元への報告は勤務態度・意欲が中心で、技術評価ではない |
| **内部研修生** | **配属先での立ち上がり ＋ 客先面談** | 常駐先の面談でスキルを問われる場面がある |

どちらも共通して効くのは「**配属直後の1〜2週で信頼を取れるか**」。以下はその形で書いてある。

## 技術スキル：これを学んでおくと強い

- **応用的なSQL構文**: `JOIN`（特に `LEFT JOIN`）・`GROUP BY`・サブクエリは基本として完璧に。**ウィンドウ関数**（`ROW_NUMBER`・`RANK`・`SUM() OVER`）が使えると複雑な集計やランキングが一気に書きやすくなる。**`CASE`式**は実務での使用頻度が非常に高い。**`EXISTS`** は `IN` との使い分けを理解し、性能を意識した選択ができると強い
- **View / Stored Procedure / Function**: 「作成できます」ではなく「**なぜこれらを使うのか**（複雑なSQLの共通化・セキュリティ向上・性能向上）」を自分の言葉で説明できるように
- **実行計画（EXPLAIN）**: 「実行計画を読んでボトルネック（フルテーブルスキャンなど）を分析し、インデックスの追加を検討した経験があります」と具体例で言えると強い
- **自分のSQLを検証する手順**: 「更新する前に同じ `WHERE` で `SELECT` して件数を確認する」「`BEGIN` で囲んで、件数を見てから `COMMIT` する」。**配属直後にこれができる人は少ないので、一番早く信頼が付く**
- **配属先のDBを自分で調べられる**: `information_schema` でテーブル構造や制約を調べられると、初日から自走できる。ツールの `\d` に頼らない
- **方言への構え**: 「Oracle の PL/SQL や SQL Server の T-SQL も、プロジェクトで使われているなら積極的に学習して貢献したい」。**研修で使ったのは PostgreSQL だが、原理は同じで名前が違うだけ**だと分かっていることが大事

## 伝え方：「なぜ」と「どのように」をセットで話す

- ✗「ウィンドウ関数が使えます」
- ○「**部門内売上ランキングのような集計を効率的に行うために**ウィンドウ関数を学習しました。`PARTITION BY` で部門ごとに区切り、`ORDER BY` で売上順に並べることで、1つのクエリでランキングを算出できます」

## 伝え方：思考プロセスを見せる

「A支店の月別売上を出すには？」と聞かれたら、答えだけ言わずに組み立てを口に出す。「まず売上が入っている `sales_orders` と店舗の `stores` を `store_id` で JOIN します。次に `WHERE` でA支店に絞り、`GROUP BY` で月ごとに集計して `SUM` で合計します」

## 伝え方：失敗から学んだ経験を話す

「`JOIN` の条件を間違えて意図しない件数になったことがありました。そこから、必ず件数を確認する、テストデータで複数パターンを試すなど、正確性を担保するチェックを徹底するようになりました」

> **講師メモ**: この「失敗から学んだ」型は、**研修中に実際に踏ませておかないと語れない**。だから追加問題群（行の増殖・NULLで件数が合わない・BETWEENで最終日が漏れる）は「解けたか」ではなく「**踏んだ経験として残ったか**」が成果。振り返りで言語化させると、そのまま配属先で使える。

## 伝え方：分からないことの言い方

配属直後に一番使う。「分かりません」で止めず、**どこまで分かっていて何を確認したいか**を言う。

- ✗「このSQLが分かりません」
- ○「この `LEFT JOIN` が何を取ろうとしているかは読めましたが、`WHERE` に右表の列が入っているので内部結合と同じ動きになっているように見えます。意図的でしょうか」

「**気づいて報告できる**」のは、自分で直せるのと同じくらい評価される。遅いクエリ・ロック待ち・データの不整合は、気づいて上げれば十分。
