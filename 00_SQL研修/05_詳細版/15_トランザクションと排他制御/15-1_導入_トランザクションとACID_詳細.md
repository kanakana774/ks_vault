# トランザクションと排他制御（導入編）
## 〜「全部やる」か「何もしない」かを保証する仕組み〜

ここまで書いてきた `INSERT` / `UPDATE` / `DELETE` は、実行した瞬間にデータベースへ反映されてきました。ですが実務のシステムでは、**「この3つの更新は、3つとも成功するか、1つも実行されないかのどちらかにしてほしい」**という要求が当たり前に出てきます。

それを実現するのが**トランザクション**です。この導入編では、**1つの接続の中で完結する話**——トランザクションの開始と終了、失敗したときの扱い、部分的な取り消し——を扱います。

**「他の人が同時に同じデータを触ったらどうなるか」は、次の [[15-2_実践_ロックとMVCC_詳細|15-2 実践編]] で、2つの窓を並べて実際に目で見ます。**

> **この資料の前提**
> - PostgreSQL 17 で動作確認しています。掲載しているエラーメッセージ・出力は**すべて実測**です。
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] で作成したもの（8章以降と同じ）です。新しく作るものはありません。

### ⚠️ 先に：どこまでが他のDBでも通じる話か

トランザクションの話は、具体的にしようとすると**どうしても特定のDBに寄ります**（この資料では PostgreSQL）。皆さんが現場で使うのが Oracle や MySQL かもしれない以上、**「考え方」と「このDB特有の事情」は分けて持ち帰ってください。**

| | 内容 |
| :--- | :--- |
| **どのDBでも共通**<br>（＝そのまま持っていける） | `BEGIN` / `COMMIT` / `ROLLBACK`、**ACID**、`SAVEPOINT`、自動コミットという考え方、分離レベルという考え方、行ロック・デッドロックという考え方、**トランザクションは短く保つという設計原則** |
| **PostgreSQL 独自**<br>（＝他のDBでは違う可能性） | エラーメッセージの文面、**エラー後にトランザクション全体が中断状態になる挙動**（→ §2-3）、**READ UNCOMMITTED が無い**こと、MVCC の実装方式と `VACUUM`、`pg_stat_activity` などの管理ビュー |

**迷ったら「考え方は共通、確認のしかたと細かい挙動はDB次第」と覚えてください。** 以降、この区別が特に効く場所にだけ 🐘 マークで注記します。

## 1. なぜトランザクションが必要か

### 1-1. 途中で落ちると何が起きるか

Aさんの口座からBさんの口座へ1万円を送金する処理を考えます。必要なSQLは2つです。

```sql
UPDATE accounts SET balance = balance - 10000 WHERE name = 'Alice';  -- ①
UPDATE accounts SET balance = balance + 10000 WHERE name = 'Bob';    -- ②
```

**①が成功して、②の直前でサーバーが落ちたら**どうなるでしょうか。Aさんの1万円は消え、Bさんには届いていません。**お金がこの世から消滅します。**
これは「めったに起きない」話ではありません。サーバーの再起動、ネットワークの切断、アプリのバグによる例外、どれでも同じことが起きます。
トランザクションは、この①と②を**「一つの塊」**として扱わせる仕組みです。塊の途中で何が起きても、**「両方反映される」か「両方なかったことになる」かのどちらか**にしてくれます。

> 💡 **「1つのSQL文なら安全」なのはなぜか。**
> 実は `UPDATE` 1文だけでも、それが100万行を更新するなら「50万行目で落ちる」可能性があります。しかしPostgreSQLは、**明示的に `BEGIN` を書かなくても、SQL 1文は必ず1つのトランザクションとして実行します。** だから1文なら「全部反映」か「1行も反映されない」かのどちらかになります（→ §2）。
> トランザクションを**自分で書く必要があるのは、複数のSQLをまとめたいとき**です。

### 1-2. トランザクションを操作する3つのコマンド

| コマンド | 意味 |
| :--- | :--- |
| `BEGIN` | 「ここから塊が始まります」と宣言する |
| `COMMIT` | 塊の中の変更を**すべて確定**して、塊を終える |
| `ROLLBACK` | 塊の中の変更を**すべて破棄**して、塊を終える |

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 10000 WHERE name = 'Bob';
COMMIT;
```

`COMMIT` に到達する前に接続が切れた場合、PostgreSQL は**自動的に `ROLLBACK` 扱いにします**。つまり「確定を宣言しない限り、確定しない」という設計です。

> `BEGIN` の代わりに `START TRANSACTION` とも書けます（SQL標準の書き方）。動作は同じです。PostgreSQL の世界では `BEGIN` が一般的なので、この資料では `BEGIN` を使います。

> [!question]- 「SQL標準の `START TRANSACTION` に統一したほうがいいのでは？」
> **統一できない、というのが答えです。どちらがデファクトかはDBごとに違います。**
>
> | DB | `BEGIN` | `START TRANSACTION` | その文化での標準 |
> | :--- | :--- | :--- | :--- |
> | **PostgreSQL** | ✅ 公式ドキュメント・psql の慣習 | ✅ 標準として同義と明記 | **`BEGIN`** |
> | **MySQL** | ✅ | ✅ | **`START TRANSACTION`**（公式が推奨。`BEGIN ... END` ブロックと紛らわしいため） |
> | **SQL Server** | `BEGIN TRANSACTION` / `BEGIN TRAN` | ❌ 無い | **`BEGIN TRAN`** |
> | **Oracle** | `BEGIN` は **PL/SQL ブロックの開始**であってトランザクションではない | ❌ 無い | **書かない**（DML 実行時に暗黙開始） |
>
> `START TRANSACTION` に寄せても **SQL Server と Oracle では動きません**。つまり「標準に合わせれば移植できる」という御利益が無い。一方 `BEGIN` は PostgreSQL 公式ドキュメント自身が使っている書き方なので、研修生が現場で読む PostgreSQL 文書と揃います。
>
> **この資料は `BEGIN` を主に、標準は `START TRANSACTION` と一言添える形（＝現状）で行きます。** 実務でトランザクションを生SQLで開始する場面は少なく（フレームワークのトランザクションAPIを使う）、手で打つのは psql での検証時だけ、というのも理由です。
>
> ⚠️ **持ち帰りとして一番効くのは Oracle の行です。Oracle には「トランザクションを開始する文」がありません。** DML を実行した瞬間に始まっていて、`COMMIT` / `ROLLBACK` で終わります。PostgreSQL の癖のまま `BEGIN` と書くと PL/SQL ブロックの開始と解釈されるので、ここは戸惑うポイントです。
### 1-3. 【手を動かす】ROLLBACK を体験する

実際に打ってみましょう。**8章のテーブルをそのまま使います。**

```sql
-- ① 今の値を確認する
SELECT product_id, product_name, price FROM products WHERE product_id = 1;
```

```
 product_id | product_name |  price
------------+--------------+---------
          1 | Laptop       | 1200.00
```

```sql
-- ② トランザクションを開始して、価格を書き換える
BEGIN;
UPDATE products SET price = 99999 WHERE product_id = 1;

-- ③ 同じトランザクションの中から見ると、変更は反映されている
SELECT price FROM products WHERE product_id = 1;
```

```
  price
----------
 99999.00
```

```sql
-- ④ やっぱりやめる
ROLLBACK;

-- ⑤ 元に戻っていることを確認
SELECT price FROM products WHERE product_id = 1;
```

```
  price
---------
 1200.00
```

**③で「変更が見えている」のがポイントです。** トランザクションの中では、自分の変更は自分にだけ見えています。確定していないので、**他の人にはまだ見えていません**（これを実際に2窓で確かめるのが 15-2 です）。

> ⚠️ **`ROLLBACK` は万能ではありません。**
> 取り消せるのは**まだ `COMMIT` していない、今のトランザクションの中の変更だけ**です。一度 `COMMIT` してしまったものは `ROLLBACK` では戻せません。戻すにはバックアップからのリストアが必要になります。

## 2. 自動コミット：実はもう使っている

### 2-1. `BEGIN` を書かないSQLはどうなっているのか

ここまでの14章で、`BEGIN` を書いたことは一度もありませんでした。それでも `UPDATE` はちゃんと反映されていました。

これは PostgreSQL が**自動コミット（autocommit）**で動いているからです。**`BEGIN` を書かずにSQLを実行すると、PostgreSQL はそのSQL 1文を自動的に `BEGIN` と `COMMIT` で包んで実行します。**

```sql
-- あなたが打ったもの
UPDATE products SET price = 1300 WHERE product_id = 1;
```

```sql
-- PostgreSQL が実際に行っていること
BEGIN;
UPDATE products SET price = 1300 WHERE product_id = 1;
COMMIT;
```

つまり**「トランザクションを使っていなかった」のではなく、「1文ずつのトランザクションを使っていた」**わけです。

### 2-2. ツールによって挙動が違うので確認しておく

ここは**実務でハマるポイント**です。使うツールによって、自動コミットの既定が違います。

| ツール                       | 既定                       | 明示的なトランザクションの始め方            |
| :------------------------ | :----------------------- | :-------------------------- |
| `psql`                    | 自動コミット **on**            | `BEGIN;` と打つ                |
| pgAdmin のクエリツール           | 自動コミット **on**            | `BEGIN;` と打つ                |
| Java（JDBC）                | 自動コミット **on**            | `conn.setAutoCommit(false)` |
| Java（Spring）             | **アノテーションを付けなければ JDBC と同じ（on）** | メソッドに `@Transactional` を付ける |

**どれも既定は「自動コミット on」で、off にするのは自分の意思です。** Spring の `@Transactional` も、「そのメソッドにいる間だけ自動コミットを off にし、正常に抜けるときに `commit`、例外が飛び出したら `rollback` してくれる」道具です。裏でやっているのは JDBC の `setAutoCommit(false)` と同じで、**書き忘れを防いでくれるだけ**だと理解しておくと、ほかのツールと同じ枠で考えられます。

> ⚠️ **言語のドライバによっては、既定で自動コミットが off のものもあります**（接続した時点で暗黙に `BEGIN` されている）。
> そういう環境で `COMMIT` を忘れると、**変更が反映されないまま、行のロックだけ握り続ける**という最悪の状態になります（15-2 で実際に見ます）。**「自分が今使っているツールはどちらか」を最初に確認してください。**

### 2-3. 【手を動かす】エラーが起きたトランザクションは「中断状態」になる

これも実務で必ず一度は踏みます。**トランザクションの中で1つでもエラーが出ると、そのトランザクションは中断状態になり、以降のSQLをすべて拒否します。**

```sql
BEGIN;
UPDATE products SET price = 1 WHERE product_id = 1;
SELECT 1/0;                      -- わざとエラーを起こす
SELECT 'この行は実行されるか?';   -- 続けて何か実行してみる
COMMIT;                          -- 確定しようとしてみる
```

実際の出力：

```
BEGIN
UPDATE 1
ERROR:  division by zero
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

読み解くと：

1. `division by zero` でエラーになった
2. その後の `SELECT` は **`current transaction is aborted`（このトランザクションは中断されています）**として拒否された
3. **`COMMIT;` と打ったのに、返ってきたのは `ROLLBACK`** ——中断したトランザクションは確定できず、強制的に巻き戻されます

`UPDATE` の結果も当然残っていません。

```sql
SELECT price FROM products WHERE product_id = 1;
```

```
  price
---------
 1200.00
```

> **`current transaction is aborted` を見たら、原因はそのSQLではなく「もっと前で起きた別のエラー」です。**
> 画面をスクロールして遡り、**最初のエラー**を探してください。これを知らないと、無関係なSQLを何度も直すことになります。
> 復旧するには `ROLLBACK;` を打って、トランザクションを一度終わらせます。**エラーが出た地点までを活かして続けたい**場合は、次の `SAVEPOINT` を使います。

> 🐘 **この「1つエラーが出たらトランザクション全体が中断状態になる」挙動は PostgreSQL 固有です。**
> Oracle や MySQL では、エラーが出た**その文だけ**が失敗し、トランザクションは続行できます。**他のDBから来た人が一番驚くのがここ**なので、逆に「PostgreSQL は厳しい」と覚えておいてください。復旧手段（`SAVEPOINT`）が用意されているのも、この厳しさとセットです。

## 3. ACID：トランザクションが保証する4つのこと

トランザクションが「何を保証してくれるのか」を4つに整理したものが **ACID** です。用語として頻出するので、名前と意味を対応させておきます。

| 特性 | 英語 | ひとことで言うと |
| :--- | :--- | :--- |
| **原子性** | **A**tomicity | 「全部やる」か「何もしない」か |
| **一貫性** | **C**onsistency | ルール（制約）を破った状態で終わらない |
| **分離性** | **I**solation | 同時に動いている他の処理から邪魔されない |
| **永続性** | **D**urability | 確定したものは、電源が落ちても消えない |

**この4つは、この研修のどこで扱うかが決まっています。**

| | どこで扱うか |
| :--- | :--- |
| **A** 原子性 | **この章の主題。** §1・§4（`BEGIN`/`COMMIT`/`ROLLBACK`・`SAVEPOINT`）＋ **§3-1** |
| **C** 一貫性 | **1章（DDL）の制約**で既に扱いました。ここでは「トランザクションとどう関わるか」だけ（→ **§3-2**） |
| **I** 分離性 | **15-2 がまるごとこれです。** 「他の人が同時に触ったらどうなるか」 |
| **D** 永続性 | **§3-3 で軽く。** 開発者が手を入れる余地がほとんどないので、仕組みを知っておく程度でよい |

**つまり、この章で考えるのは A、次の章で考えるのが I です。**

### 3-1. 原子性（A）：どこまでを1つの塊にするか

**ACIDの4つのうち、開発者が毎回判断を迫られるのは A だけです。** DBは「巻き戻す仕組み」を提供してくれますが、**どこからどこまでを1つの塊にするかは決めてくれません。**

```
BEGIN;   ←── ここを、どこに置くか
  ...
COMMIT;  ←── ここを、どこに置くか
```

この「`BEGIN` と `COMMIT` をどこに置くか」を**トランザクション境界**と呼びます。

判断の基準は、いまの時点では**1つだけ**覚えてください。

> **業務として「一緒に無かったことにしたい」範囲を、1つの塊にする。**

送金なら「引く」と「足す」で1つ。注文なら「在庫を引く」「注文を作る」「明細を作る」で1つ。**片方だけ成立した状態があってはいけないもの**が、同じ塊に入ります。

**逆に「塊は大きければ大きいほど安全」ではありません。** 大きすぎるトランザクションには別の害があるのですが、**その害は「他の人が同時に触っている」状況を見ないと実感できません。** そこは次の 15-2 で排他制御を見たあと、[[15-2_実践_ロックとMVCC_詳細|15-2]] §6 でまとめて扱います。

**この章では「小さすぎると壊れる」ほうだけ押さえておいてください。**

### 3-2. 一貫性（C）：制約はいつ検査されるのか

一貫性は「**ルールを破った状態でトランザクションが終わらない**」という保証です。ここでいうルールとは、1章で書いた **PK・FK・UNIQUE・CHECK・NOT NULL** のことです。

**注意すべきは、検査されるタイミングが `COMMIT` 時ではないことです。** 既定では、`INSERT` / `UPDATE` を実行した**その文の直後**に検査され、破っていれば即座にエラーになります（そのままだとトランザクションは中断状態に → §2-3）。「トランザクションが終わるときに辻褄が合っていればいい」わけではありません。

> [!note]- 例外：`COMMIT` まで検査を遅らせる（`DEFERRABLE` 制約）
> FK制約などに `DEFERRABLE INITIALLY DEFERRED` を付けておくと、検査を `COMMIT` の直前まで遅らせられます。
>
> 相互に参照し合うテーブルへ同時に行を挿入するときなど、「一時的に矛盾した状態を経由してから、最後に整合させる」場合に使う仕組みです。**使う場面は限られるので、そういう逃げ道があるとだけ知っておけば十分です。**

**では、どこまでを制約にして、どこからをアプリで守るのか。** これは実務で必ず悩むところです。

たとえば「在庫はマイナスにしない」は `CHECK (stock_quantity >= 0)` で**DB側に書けます**。書けるなら書いたほうがよいか——答えは「**場合による**」です。

| | 利点 | 欠点 |
| :--- | :--- | :--- |
| **制約としてDBに書く** | どの経路から更新されても破れない。バグや手作業のUPDATEも止められる | エラーメッセージが業務用語にならない（「在庫が足りません」ではなく制約違反）。**アプリ側のチェックと二重管理**になり、片方だけ直す事故が起きる |
| **アプリだけで守る** | 業務エラーとして扱いやすい。ルールが1か所にまとまる | **その経路を通らない更新は素通り**する |

**現場でよく取られるのは「アプリで判断し、DBの制約は最後の砦として置く」という形です。** アプリ側が業務エラーを返す役、制約は「万一バグで抜けたときにデータを壊させない」役、と**役割を分けておく**と二重管理の違和感が減ります。

一方で、**複数の行やテーブルにまたがるルール**（「同一顧客の未発送注文は5件まで」など）や、**時刻や外部の状態に依存するルール**は、そもそも制約では表現できません。こちらは素直にアプリの仕事です。

### 3-3. 永続性（D）：WAL

「`COMMIT` が返ってきた＝もう消えない」を成立させているのが **WAL（Write-Ahead Logging、先行書き込みログ）**です。

PostgreSQL は `COMMIT` のとき、**テーブル本体のファイルを書き換えるのを待ちません。** 代わりに「何をどう変えたか」という記録だけを WAL ファイルに書き、それがディスクに届いた時点で `COMMIT` を成功として返します。

テーブル本体への反映は後からまとめて行われ、その前にサーバーが落ちても、**再起動時に WAL を読み直して変更を復元します**。

> 「ログを1本書くだけ」で済むので `COMMIT` が速い、というのがこの仕組みの狙いです。
> WAL はインデックスの話とも繋がっています（インデックスが多いほど WAL の生成量が増えます）。詳しくは [[17-1_導入_物理構造とスキャン方式|17-1]] §8 を参照してください。

> 🐘 **「先にログを書いてから確定する」という考え方はどのDBも同じ**です（Oracle の REDO ログ、MySQL/InnoDB の redo log）。**`WAL` という呼び名とファイルの扱いが PostgreSQL 固有**です。

## 4. SAVEPOINT：一部だけ取り消す

### 4-1. 何のためにあるか

`ROLLBACK` は**トランザクション全体**を巻き戻します。しかし「ここまでの処理は活かして、この1つの処理だけなかったことにしたい」という場面があります。

そこで使うのが **`SAVEPOINT`（セーブポイント）** です。トランザクションの中に**戻れる目印**を置きます。

| コマンド | 意味 |
| :--- | :--- |
| `SAVEPOINT 名前` | ここに目印を置く |
| `ROLLBACK TO SAVEPOINT 名前` | 目印の時点まで戻る（**トランザクションは終わらない**） |
| `RELEASE SAVEPOINT 名前` | 目印を捨てる（そこまでの処理は活きたまま） |

### 4-2. 【手を動かす】

```sql
BEGIN;

UPDATE products SET price = 1500 WHERE product_id = 1;  -- これは活かしたい

SAVEPOINT before_risky;                                  -- ★ 目印を置く

UPDATE products SET price = 0 WHERE product_id = 2;      -- これはやっぱりやめたい

ROLLBACK TO SAVEPOINT before_risky;                      -- ★ 目印まで戻る

-- 確認：product_id=1 の変更は残り、product_id=2 は元のまま
SELECT product_id, price FROM products WHERE product_id IN (1, 2) ORDER BY product_id;

COMMIT;
```

```
 product_id |  price
------------+---------
          1 | 1500.00   ← SAVEPOINT より前なので残る
          2 |  800.00   ← 巻き戻された
```

**`ROLLBACK TO SAVEPOINT` を実行してもトランザクションは終わりません。** そのまま処理を続けて、最後に `COMMIT` できます。

### 4-3. 使いどころと注意

実務での典型は、**「1件失敗しても全体は止めたくないループ処理」**です。

```
1000件を1件ずつ処理する
  各件の前に SAVEPOINT を置く
  失敗したらその件だけ ROLLBACK TO SAVEPOINT してスキップ
  最後にまとめて COMMIT
```

ただし、**セーブポイントは無料ではありません。** 1つ置くごとに PostgreSQL は内部的に「サブトランザクション」を作ります。**1つのトランザクションの中で64個を超えると**、PostgreSQL がメモリ上に持っている管理情報が溢れ、他のセッションまで巻き込んで遅くなることが知られています。

大量ループで1件ごとにセーブポイントを置くのは避け、**こまめに `COMMIT` して1トランザクションを短く保つ設計**を検討してください。

> 💡 **PL/pgSQL の `BEGIN ... EXCEPTION` は、裏でセーブポイントを作っています。**
> ループの中で毎回 `EXCEPTION` ブロックに入る処理も、同じ理由で数が増えると重くなります。詳しくは [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3 補足]] を参照してください。

### 4-4. `SAVEPOINT` は実務でどれくらい使うのか

**結論から言うと、アプリのコードに自分で書くことは、ほとんどありません。** ただし**知らないうちに使っている**ことはよくあります。

| どこで | 自分で書くか | 実際のところ |
| :--- | :--- | :--- |
| **PL/pgSQL の `BEGIN ... EXCEPTION`** | 書かない（暗黙） | **一番よく出会う形。** 例外を捕まえるブロックを書いた時点で、裏でセーブポイントが作られています |
| **Java / JDBC** | 書ける（`conn.setSavepoint()`） | **書けるが、実際に書くことは稀** |
| **Spring の `@Transactional(propagation = NESTED)`** | 書かない（暗黙） | 「ネストしたトランザクション」の正体がセーブポイントです（→ §5） |
| **ORM（JPA / MyBatis など）** | 書かない（暗黙） | フレームワークが内部的に使っていることがあります |

**用途についても、少し整理しておきます。**

`SAVEPOINT` の目的は「**トランザクション境界を細かく刻むこと**」**ではありません。**

| | やること | 他のセッションから見ると |
| :--- | :--- | :--- |
| `COMMIT` を刻む | トランザクションを**終わらせて**、次を始める | **確定が見える。ロックも外れる** |
| `SAVEPOINT` で戻る | トランザクションは**続いたまま**、一部だけ取り消す | **何も見えない。ロックも握ったまま** |

つまり `SAVEPOINT` は「**部分的な失敗を許容する**」ための道具であって、「**トランザクションを短くする**」道具ではありません。**セーブポイントをいくら置いても、トランザクションは1ミリも短くなりません。**

**バッチ処理で「1件失敗しても続行したい」場合、本命は `COMMIT` を刻むほうです。**「1件ずつ `COMMIT` する」設計にすれば、失敗した件をスキップできるうえに、ロックも都度外れます。`SAVEPOINT` が要るのは、**まとめて `COMMIT` したいのに一部だけ捨てたい**という、より限られた場面です。

> [!question]- 「`SAVEPOINT` は PostgreSQL 独自だと思っていた」
> **独自ではありません。SQL標準（SQL:1999）の機能で、主要DBにはすべてあります。** 冒頭の「どのDBでも共通」の欄に入れてあるのはそのためです。
>
> | DB | 作成 | そこへ戻る | 解放 |
> | :--- | :--- | :--- | :--- |
> | **PostgreSQL / MySQL / DB2** | `SAVEPOINT sp1` | `ROLLBACK TO SAVEPOINT sp1` | `RELEASE SAVEPOINT sp1` |
> | **Oracle** | `SAVEPOINT sp1` | `ROLLBACK TO sp1` | **無い**（同名で作り直すと上書き） |
> | **SQL Server** | **`SAVE TRANSACTION sp1`** | **`ROLLBACK TRANSACTION sp1`** | **無い** |
>
> **構文が方言なのは SQL Server だけ**です。そして肝心なのは、**「トランザクションは終わらない／ロックも解放されない」という性質がどのDBでも同じ**だということ。つまりこの §4 の結論——**`SAVEPOINT` は部分的な失敗を許容する道具であって、トランザクションを短くする道具ではない**——は、そのままどのDBにも持っていけます。

## 5. `BEGIN` の入れ子はできない

**PostgreSQL では、トランザクションの中でさらに `BEGIN` することはできません。** 2回目の `BEGIN` は `WARNING`（`ERROR` ではない）を出すだけで**黙って無視**され、トランザクションは最初の `BEGIN` から続く1つのままです。区切りを入れたいときは `BEGIN` ではなく `SAVEPOINT`（→ §4）を使ってください。これが SAVEPOINT が存在する理由です。

> アプリケーション側のフレームワーク（Spring の `@Transactional(propagation = REQUIRES_NEW)` など）が「ネストしたトランザクション」を提供している場合、**その正体はセーブポイント**か、**別のコネクションを取り直しているか**のどちらかです。DBそのものに入れ子の機能があるわけではない、と理解しておいてください。

> [!example]- 手を動かして確かめる（警告と、実際に壊れる例）
> 「トランザクションの中でさらにトランザクションを始める」と、何が起きるかを実際に見ます。
>
> ```sql
> BEGIN;
> BEGIN;   -- もう一度 BEGIN してみる
> ```
>
> ```
> BEGIN
> WARNING:  there is already a transaction in progress
> BEGIN
> ```
>
> 入れ子になっていると思い込んで書くと、こうなります。
>
> ```sql
> BEGIN;                    -- 外側のつもり
>   UPDATE ... ;            -- 残したい処理
>
>   BEGIN;                  -- 内側のつもり（実際は無視される）
>     UPDATE ... ;          -- 失敗しうる処理
>   ROLLBACK;               -- 内側だけ戻すつもり
>                           -- → 実際には【全部】巻き戻る！
>
> COMMIT;
> ```
>
> `ROLLBACK` は**最初の `BEGIN` まで**戻します。「残したい処理」も消えます。

> [!question]- 「ネストの挙動もDBごとに違うのでは？」
> **その通りで、しかもここは PostgreSQL と MySQL で結果が正反対になります。** 上の「全部巻き戻る」は PostgreSQL の話です。
>
> | DB | トランザクション中に再度 `BEGIN` すると |
> | :--- | :--- |
> | **PostgreSQL** | `WARNING` を出して**黙って無視**。1つのトランザクションのまま → `ROLLBACK` で**全部戻る** |
> | **MySQL** | ⚠️ **暗黙コミットが走る**（`BEGIN` / `START TRANSACTION` は implicit commit を起こす文）。**そこまでの変更が確定してしまい**、後から `ROLLBACK` しても戻らない |
> | **SQL Server** | ネストでき `@@TRANCOUNT` が増える。内側の `COMMIT` はカウントを1減らすだけで確定しない。ただし**名前無しの `ROLLBACK TRANSACTION` は一発で全部戻す** |
> | **Oracle** | `BEGIN` がそもそもトランザクション制御ではない。本当に独立させたいなら `PRAGMA AUTONOMOUS_TRANSACTION` |
>
> **「入れ子のつもりで書くと事故る」という結論はどのDBでも共通ですが、事故り方が逆です。**
>
> - PostgreSQL … **消したくないものまで消える**
> - MySQL … **消したいものが残る**
>
> どちらも怖い。なのでこの節は「PostgreSQL ではこうなる」で終わらせず、**「入れ子は使わない。区切りたいなら `SAVEPOINT`」を DB 非依存の作法として持ち帰ってもらう**のが正解です。

## この章のまとめ

- **複数のSQLをセットで扱いたいときにトランザクションを書く。** 1文だけなら自動コミットが面倒を見てくれている
- **`COMMIT` するまで確定しない。** 接続が切れたら自動で `ROLLBACK`
- **ACID のうち、開発者が毎回判断するのは A（どこを1つの塊にするか）だけ。** 基準は「業務として一緒に無かったことにしたい範囲」
