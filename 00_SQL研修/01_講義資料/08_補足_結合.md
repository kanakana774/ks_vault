# SQL結合・実践補足資料：結合を正しく制御する

本資料では、基本的な結合を理解した後に陥りやすい「罠」と、実務で求められる「結合の思考プロセス」について解説します。

## 1. ON句の正体：それは単なる「評価式」である

`ON` 句には通常 `t1.id = t2.id` と書きますが、本質的には **「その行を結合して良いか？」を判定し、真（TRUE）を返すかどうか** だけを見ています。

### ON TRUE（全行結合）
```sql
SELECT c.name, m.rank_name
FROM customers c
LEFT JOIN memberships m ON TRUE;
```
- **結果**: `customers` の各行に対して、`memberships` の**全行**が紐付きます（デカルト積）。
- **解説**: `ON` 句が常に `TRUE` を返すため、条件なしで結合されます。`ON` 句はあくまで「式」であることを意識しましょう。

### ON 句に NULL 条件を指定した場合の挙動
以下の違いを理解することは非常に重要です。

| クエリ | 挙動と結果 |
| :--- | :--- |
| **LEFT JOIN** で `ON ... AND o.order_id IS NULL` | **左側のテーブルの行はすべて残ります。** 右側の列は条件を満たさないため、すべて `NULL` で埋められます。 |
| **INNER JOIN** で `ON ... AND o.order_id IS NULL` | 結合条件が `FALSE`（またはUNKNOWN）になるため、**1行も返されません。** |


## 2. 非等価結合：IDの一致だけが結合ではない

実務では、外部キー（ID）がなくても「意味的な繋がり」で結合することがあります。これを**非等価結合**と呼びます。

### シナリオ：勤務日時点での時給を特定する

従業員の「勤怠実績」と、時期によって変動する「時給マスタ」の2つのテーブルがあるとします。  
ある日の給与を計算するには、その従業員のその勤務日時点での正しい時給を適用しなければなりません。

- **テーブル①: `attendance_logs` (勤怠実績)**
    - 誰が (`employee_id`)、いつ (`work_date`)、何時間働いたか (`hours_worked`) を記録します。
- **テーブル②: `historical_rates` (時給マスタ)**
    - 従業員ごとの時給の履歴を管理します。従業員IDは `staff_code` という異なる列名で管理されています。
    - 同じ従業員でも、昇給などにより適用期間 (`start_date` から `end_date` まで) ごとに異なる時給 (`rate`) が設定されています。

この2つのテーブル間には外部キー制約はなく、IDの列名も異なります。単純にIDだけで結合すると、一人の従業員に対して複数の時給レコードが紐づいてしまい、正しい給与計算ができません。

**「勤務日 (`work_date`) が、時給の適用期間内 (`start_date` と `end_date` の間) にある」という条件** を加えることで、初めてその日の勤務に対する正しい時給を1つに特定できます。

**SQLクエリ:**  
`LEFT JOIN` を使用し、勤怠記録を主軸に、該当する時給レコードを結合します。

```sql
WITH
  -- 勤怠実績テーブルを定義
  attendance_logs AS (
    SELECT 101 AS employee_id, '2025-10-25' AS work_date, 8 AS hours_worked UNION ALL
    SELECT 101 AS employee_id, '2025-11-10' AS work_date, 8 AS hours_worked UNION ALL -- 昇給後の勤務
    SELECT 202 AS employee_id, '2025-11-15' AS work_date, 7 AS hours_worked
  ),
  -- 期間ごとに変動する時給マスタテーブルを定義
  historical_rates AS (
    SELECT 101 AS staff_code, 1000 AS rate, '2025-04-01' AS start_date, '2025-10-31' AS end_date UNION ALL -- 従業員101の旧時給
    SELECT 101 AS staff_code, 1100 AS rate, '2025-11-01' AS start_date, '2026-03-31' AS end_date UNION ALL -- 従業員101の新時給（昇給）
    SELECT 202 AS staff_code, 1200 AS rate, '2025-04-01' AS start_date, '2026-03-31' AS end_date     -- 従業員202の時給
  )

-- 複数の条件（IDの一致と期間内判定）を使ってテーブルを結合
SELECT
  a.employee_id,
  a.work_date,
  a.hours_worked,
  r.rate,
  -- その日の給与を計算
  (a.hours_worked * r.rate) AS daily_wage
FROM
  attendance_logs AS a
LEFT JOIN
  historical_rates AS r ON a.employee_id = r.staff_code -- 条件1: IDが一致する⇒外部キー制約もなければ、列名も異なる
                        AND a.work_date BETWEEN r.start_date AND r.end_date; -- 条件2: 勤務日が時給の適用期間内である⇒直接的に関係がない列同士
```

**実行結果のイメージ:**

|employee_id|work_date|hours_worked|rate|daily_wage|
|:--|:--|:--|:--|:--|
|101|2025-10-25|8|1000|8000|
|101|2025-11-10|8|1100|8800|
|202|2025-11-15|7|1200|8400|

**解説:**  
このクエリの `ON` 句がポイントです。

1. `a.employee_id = r.staff_code`:  
    まず、`employee_id` と `staff_code` という**名前の異なる列**で従業員を紐付けます。
2. `AND a.work_date BETWEEN r.start_date AND r.end_date`:  
    次に、単純なIDの一致に加えて、**「勤怠日」が「時給の適用期間」に含まれているか**という範囲条件で絞り込みます。

この2つの条件を組み合わせることで、従業員ID `101` の勤務記録に対して、複数の時給レコードの中から**その日時点での正しい時給**をピンポイントで結合できます。

- `2025-10-25` の勤務は、適用期間 `2025-04-01`～`2025-10-31` の時給 `1000` 円のレコードに結合されます。
- `2025-11-10` の勤務は、適用期間 `2025-11-01`～`2026-03-31` の時給 `1100` 円のレコードに結合されます。

このように、複数のテーブルが持つ情報（この例ではIDと時間）を組み合わせた複雑な条件を `ON` 句に記述することで、短絡的な結合では得られない、ビジネス上意味のあるデータを導き出すことができます。これは「非等価結合（Non-Equi Join）」と呼ばれるテクニックの一例です。

## 3. SQLの思考プロセス：宣言的視点でルートを探す

![[00_SQL研修/01_講義資料/_attachments/sql_lesson2_ERD.png]]


SQLを書くとき、頭の中では「実行順序」とは逆のステップで考えるのがコツです。

### ステップ1：欲しい項目（SELECT）を宣言する
まず、最終結果に必要な列を書き出します。
「顧客名(`c.name`) と、その人が購入した商品名(`p.product_name`) が欲しい」

### ステップ2：ER図から「経路」を見つける
次に、それらの列を持つテーブルをどう繋ぐか、ER図でルートを探します。
- 始点：`CUSTOMERS`
- 終点：`PRODUCTS`
- **ルート**: `CUSTOMERS` → `ORDERS` → `ORDERITEMS` → `PRODUCTS`

### ステップ3：正しい「意味」のルートを選ぶ（重要！）
例えば、「顧客が買った商品」を知りたい場合、以下の2つのルートが考えられますが、意味が全く異なります。

1.  **正解：購入ルート** (`CUSTOMERS` → `ORDERS` → `ORDERITEMS` → `PRODUCTS`)
    - 実際に「お金を払って注文した」事実に基づきます。
2.  **不正解：レビュールート** (`CUSTOMERS` → `REVIEWS` → `PRODUCTS`)
    - これだと「レビューを書いた商品」しか出てきません。一度もレビューを書いていない顧客は消えてしまいます。

**「どのテーブルを経由するか」で、結果のビジネス的な意味が変わる**ことに注意してください。

## 4. 結合の順序：LEFT JOIN を殺す INNER JOIN の罠

複数のテーブルを結合する場合、結合の順番と種類に注意しないと、意図せずデータが消えます。

### 失敗例：左外部結合が内部結合に上書きされる
「すべての顧客を表示し、注文があればその商品名も出す」という意図で書かれた以下のSQLを見てください。

```sql
SELECT
    c.name,
    p.product_name
FROM
    customers c
    LEFT JOIN orders o ON c.customer_id = o.customer_id
    INNER JOIN orderitems oi ON o.order_id = oi.order_id -- ← ここが罠！
    INNER JOIN products p ON oi.product_id = p.product_id;
```

**何が起きるか？**
1. `customers` LEFT JOIN `orders` により、注文のない顧客（`o.order_id` が NULL）もこの時点では残っています。
2. しかし、次の `INNER JOIN orderitems` の評価時、`o.order_id` が NULL の行は `oi.order_id = o.order_id` という条件を満たせません。
3. その結果、**注文のない顧客がすべて結果から消滅します。**

### 解決策：一貫して LEFT JOIN を使う
一度 `LEFT JOIN` を始めたら、それ以降の従属するテーブル（枝葉のデータ）も `LEFT JOIN` で繋ぐのがいいでしょう。

```sql
SELECT
    c.name,
    p.product_name
FROM
    customers c
    LEFT JOIN orders o ON c.customer_id = o.customer_id
    LEFT JOIN orderitems oi ON o.order_id = oi.order_id -- LEFTにする
    LEFT JOIN products p ON oi.product_id = p.product_id; -- LEFTにする
```


## 5. 業務におけるテーブル分割の意義

なぜこんなに複雑な結合が必要なのでしょうか？

### 例：PAYMENTS（支払い）テーブル
`ORDERS` テーブルに `amount` や `method` を含めず、わざわざ `PAYMENTS` を分けているのはなぜでしょうか。
- **理由1：分割払いに対応するため**
  - 1つの注文（1行）に対して、複数回の支払い（多行）が発生する可能性があるからです。
- **理由2：状態の管理**
  - 「注文はされたが、まだ支払われていない」という状態を、`PAYMENTS` にレコードがあるかないかで表現できます。

このように、**「1（注文）対 多（支払い）」の関係がある場所では必ずテーブルが分かれます。** 結合は、その分かれた関係を元のビジネスの形に再構築する作業なのです。

### まとめ
1.  **ON句はフィルター**：結合前に「どの行をくっつけるか」を判定する。
2.  **経路が命**：ER図を見て、ビジネスルールに合った正しいテーブルを辿る。
3.  **LEFTの後は慎重に**：`LEFT JOIN` の後に `INNER JOIN` を書くと、それまでの `LEFT` の効果が消えることがある。
4.  **1対多を意識する**：なぜ分かれているかを知れば、結合の必要性がわかる。

## 6. 行の増殖に注意：1対多を複数結合する際の罠

1つのテーブルに対して、複数の「1対多」の関係にあるテーブルを同時に結合すると、結果セットの行数が予想を超えて膨れ上がり、数値計算（合計など）が合わなくなることがあります。

### シナリオ：倉庫ごとに「在庫」と「スタッフ」を一覧表示したい
`WAREHOUSES` テーブルを中心に、以下の2つを結合しようとした場合を考えます。
- 1つの倉庫には、複数の **在庫 (`INVENTORY`)** がある（1対多）
- 1つの倉庫には、複数の **スタッフ (`STAFF`)** がいる（1対多）

#### 実行してしまうと危険なSQL
```sql
SELECT
    w.warehouse_name,
    i.product_id,
    s.name AS staff_name
FROM
    warehouses w
    INNER JOIN inventory i ON w.warehouse_id = i.warehouse_id
    INNER JOIN staff s ON w.warehouse_id = s.warehouse_id;
```

#### なぜ行数が膨れ上がるのか？
例えば、ある倉庫（A倉庫）に **「在庫が100種類」** あり、**「スタッフが10人」** いたとします。
このとき、期待する結果は 100 + 10 = 110行 くらいに思えるかもしれませんが、実際には **100 × 10 = 1,000行** が出力されます。

SQLの結合は、条件に合うものをすべて組み合わせようとするため、**「すべての在庫」と「すべてのスタッフ」の全パターン（総当たり）** が生成されてしまうのです。

| 倉庫名 | 商品ID | スタッフ名 |
| :--- | :--- | :--- |
| A倉庫 | 商品001 | スタッフA |
| A倉庫 | **商品001** | **スタッフB** |
| A倉庫 | **商品002** | **スタッフA** |
| A倉庫 | 商品002 | スタッフB |
| ... | (100種類) | (10人) |

### この現象が引き起こす深刻な問題：集計値の不整合
もしこのSQLで「在庫の合計」を計算しようとすると、結果はとんでもない数値になります。

```sql
-- 危険な集計：在庫数がスタッフの人数分だけ重複して足されてしまう
SELECT
    w.warehouse_name,
    SUM(i.stock_quantity) -- 本来の在庫数 × スタッフの人数 という異常な値になる
FROM
    warehouses w
    INNER JOIN inventory i ON w.warehouse_id = i.warehouse_id
    INNER JOIN staff s ON w.warehouse_id = s.warehouse_id
GROUP BY
    w.warehouse_name;
```

### 解決策：先に集計するか、クエリを分ける
このような「独立した複数の1対多」を扱いたい場合は、結合する前にそれぞれを独立して処理する必要があります。

**方法1：サブクエリやCTEで先に集計を済ませる**
```sql
WITH warehouse_stock AS (
    -- 先に倉庫ごとの在庫合計を出しておく
    SELECT warehouse_id, SUM(stock_quantity) as total_stock
    FROM inventory GROUP BY warehouse_id
)
SELECT
    w.warehouse_name,
    ws.total_stock,
    s.name AS staff_name
FROM
    warehouses w
    LEFT JOIN warehouse_stock ws ON w.warehouse_id = ws.warehouse_id
    LEFT JOIN staff s ON w.warehouse_id = s.warehouse_id;
-- これなら在庫数は重複せず、行数はスタッフの数だけで済む
```

**方法2：全く別のクエリとして実行する**
「在庫一覧」と「スタッフ一覧」は、ビジネス的な意味が異なるデータです。一つの表に無理やりまとめようとせず、アプリケーション側で別々に取得して表示するのも正しい設計です。

> **ポイント**: 
> 結合の結果、行数が「親テーブルの行数」や「子テーブルの行数」よりも異常に多くなっている場合は、**独立した1対多の関係を同時に結合していないか**を確認してください。
