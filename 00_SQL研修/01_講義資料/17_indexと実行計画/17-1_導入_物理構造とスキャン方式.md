**この章の範囲**：なぜインデックスが速いのかを物理構造から見る。作り方と `EXPLAIN` の読み方は [[17-2_実践_EXPLAINの読み方|17-2]]。

> - PostgreSQL 17。掲載している**実行計画・ページ数・実行時間はすべて実測**
> - テーブルは [[17_indexと実行計画で使用するテーブル|17_indexと実行計画で使用するテーブル]] で作成（`customers` 10万件 / `orders` 100万件）

## 1. 物理層の現実：DBの敵は「ディスクI/O」である

### 1-1. CPUはストレージのデータを直接は読めない

![[17-1_PCの中のメモリとストレージ.excalidraw]]

| | メモリ | ストレージ |
| :--- | :--- | :--- |
| 速さ | **速い**（ナノ秒） | 遅い（SSD：マイクロ秒＝**約1,000倍**／HDD：ミリ秒＝**約10万倍**） |
| 容量 | 小さい | **大きい** |
| 電源を切ると | 消える | **残る** |
| CPUから | **直接読み書きできる** | **直接は読み書きできない** |

**最後の行が決定的です。** DBのファイルはストレージにありますが、CPUはそこを直接触れません。必ず一度メモリへコピーしてから読み書きします。つまり `SELECT` を1回投げるたびに「**ストレージ → メモリ**」の引っ越しが起きていて、**それが圧倒的に遅い。**

**チューニングとは、極論すれば「いかに遅いディスクI/Oを減らし、速いメモリ上のデータだけで処理を完結させるか」という戦いです。**

> **用語の整理**：本来の総称は「ストレージ」ですが、`EXPLAIN` の出力自体が `Sort Method: external merge  Disk: 8080kB` と表示するので、この資料では**「ディスク」**で通します。

### 1-2. データの最小単位「ページ（ブロック）」

**PostgreSQLは、データを1行ずつ読み書きしません。8KB（正確には8KiB）の箱にまとめて読み書きします。** この箱を「ページ」（またはブロック）と呼びます。

![[17-1_全体像_データの通り道.excalidraw]]

**データの通り道**

1. **接続ごとにサーバープロセスが1つ**立ち、SQLはそのプロセスが処理する。
2. 必要なページが**共有バッファ**にあるか探す。**共有バッファは全プロセスで共有する1つのメモリ領域**なので、誰かが読んだページは他の接続からもそのまま使える。
3. 無ければ、その下の**OSのページキャッシュ**（PostgreSQLの管理外）を探す。
4. それにも無ければ、**実際のディスクを読む**。テーブルもインデックスも、それぞれ別のファイル。
5. 読んだページは**コピーされて上へ上がり**、共有バッファに載る。**元のページはディスクに残ったまま。**

**遅いのは一番下との往復だけです。** だからチューニングの目標は「**ディスクを読む回数（ページ数）を減らすこと**」の一点に集約されます。

> 💡 **`EXPLAIN (ANALYZE, BUFFERS)` の `shared hit` と `read` は、この図の「どこで見つかったか」を表しています。** `hit` は共有バッファで見つかった数、`read` は下まで取りに行った数です。17-2 でずっとこの数字を見ます。

| | 個数の関係 |
| :--- | :--- |
| 1テーブル | → **1個以上**のファイル（**1ファイル1GBが上限**で、超えると自動分割される） |
| 1ファイル | → **最大131,072ページ**（1GB ÷ 8KB） |
| 1ページ | → **複数のタプル**（行） |

> **用語の整理**：**「ページ」と「ブロック」は同じもの**です。公式ドキュメントでも `EXPLAIN` の出力でも両方が出てきます（`relpages` / `block_size` / `Heap Blocks`）。**同じものだと思って読んでください。** この資料では原則「ページ」で通します。

### 1-3. ページの中身

**テーブルもインデックスも、ディスク上では「8KBページがぎっしり並んだ1つのファイル」で、両者は別々のファイルになります。**

![[17-1_ページの内部構造.excalidraw]]

- 先頭に**ページヘッダ**、続いて**アイテムポインタ（実データへの住所）**が前から積まれる。
- 実際の**行データは後ろから詰められ**、真ん中に空き領域が残る。
- **ポインタの並び順と行の並び順は一致しません。** だからページ内で行を並べ替えても、実データを動かさずポインタだけ書き換えれば済む。
- 空き領域が尽きたら、新しいページが使われる。

*   **ページ（ブロック）:** ディスクとメモリ間を移動する最小単位。
*   **タプル（アイテム）:** ページの中に格納された個々の行データ。

**ここが本質です。** たとえ1行だけ読みたくても、その行が含まれる**8KBのページを丸ごと**メモリにロードします。だから性能の話は最終的に「**何ページ読んだか**」に還元されます。

### 1-4. 基準になる2つの数字

**この2つを覚えてください。以降ずっと基準として使います。**

|  | ページ数 | 1ページあたり |
| :--- | ---: | ---: |
| `customers`（10万件） | **1,235ページ** | 81行 |
| `orders`（100万件） | **7,255ページ** | 138行 |

「1行だけ欲しくても81行分（8KB）を丸ごと読む」という無駄が、数字として現れています。そして──**実行計画の `Buffers` がこの数と一致していたら、全ページ読んだ＝全件走査**、という判断ができます。この読み方を17-2でずっと使います。

> [!example]- 手を動かして確かめる（ページ数と、テーブル／インデックスが別ファイルであること）
> ページ数は `pg_class` というシステムカタログに記録されています。
>
> ```sql
> SELECT relname,
>        relpages                        AS ページ数,
>        reltuples::bigint               AS 行数,
>        round(reltuples / relpages)     AS 1ページあたり行数,
>        pg_size_pretty(pg_relation_size(oid)) AS サイズ
> FROM pg_class
> WHERE relname IN ('customers', 'orders')
> ORDER BY relname;
> ```
>
> ```text
>   relname  | ページ数 |  行数   | 1ページあたり行数 |  サイズ
> -----------+----------+---------+-------------------+---------
>  customers |     1235 |  100000 |                81 | 9880 kB
>  orders    |     7255 | 1000000 |               138 | 57 MB
> ```
>
> `relpages` / `reltuples` は**統計情報**なので、大量に更新した直後などは実際とずれます。正確な値が要るときは `ANALYZE` してから見てください。
>
> 実ファイルのパスも見られます。**`orders` と `orders_pkey` が別ファイル**になっているのが確認できます。
>
> ```sql
> SELECT 'orders' AS obj, pg_relation_filepath('orders') AS path
> UNION ALL SELECT 'orders_pkey', pg_relation_filepath('orders_pkey');
> ```
>
> ```text
>      obj     |       path
> -------------+------------------
>  orders      | base/60822/60828
>  orders_pkey | base/60822/60831     ← テーブルとは別のファイル！
> ```

## 2. インデックスとは何か

### 2-1. 定義

インデックスとは、**「特定の列の値」と「その値を持つ行の物理的な居場所」をセットにして、<font color="#ff0000">検索しやすい順序で並べ替えた別表</font>（索引）**のことです。

*   **現実世界の例:** 本の巻末の「索引」。単語（値）とページ番号（住所）が五十音順に並んでいるので、本編を1ページ目からめくらずに済みます。
*   **物理的な実態:** テーブル本体とは別の**独立したファイル**。インデックス自体もディスク上にページ単位で保存されます。

### 2-2. ポインタとしての「CTID」

索引に書かれている「ページ番号」に相当するのが **CTID** です。

*   **中身:** `(ブロック番号, オフセット番号)` — 例 `(550, 2)` は「550番目のページの2番目のデータ」。
*   **役割:** これがあれば「〇番目のページの〇行目」へ直接アクセス（ランダムアクセス）できます。

つまりインデックスの中身は、**「値 → CTID」のペアが値の順番に並んでいるだけ**のものです。

### 2-3. CTIDは隠し列として見られる

CTIDは**どのテーブルにも最初から存在する隠し列**で、`SELECT ctid, ...` と書けばそのまま見られます。**これから何度も出てくる「住所」の正体です。**

> [!example]- 手を動かして確かめる（ページの切り替わりを目で見る）
> ```sql
> SELECT ctid, customer_id, city FROM customers ORDER BY customer_id LIMIT 5;
> ```
>
> ```text
>  ctid  | customer_id |  city
> -------+-------------+--------
>  (0,1) |           1 | City_1
>  (0,2) |           2 | City_2
>  (0,3) |           3 | City_3
>  (0,4) |           4 | City_4
>  (0,5) |           5 | City_5
> ```
>
> `(0,1)` は「**0番ページの1行目**」です。連番で挿入したので、先頭5件が同じ0番ページに固まっています。
>
> ```sql
> SELECT ctid, customer_id FROM customers WHERE customer_id BETWEEN 81 AND 84 ORDER BY customer_id;
> ```
>
> ```text
>   ctid  | customer_id
> --------+-------------
>  (0,81) |          81
>  (0,82) |          82
>  (1,1)  |          83      ← ここでページが変わった
>  (1,2)  |          84
> ```
>
> **0番ページには82行入り、83行目から1番ページに移った**ことが目で見えます。これが「8KBの箱に詰めていく」ということです。

## 3. インデックスがないとどうなるか（Seq Scan）

インデックスがない状態で、10万件の顧客から特定の都市の顧客（200件）を探します。PostgreSQLは**シーケンシャルスキャン（Seq Scan、全件走査）**を選びます。全ページを先頭から順に読み、ページ内の全タプルをチェックして条件に合わないものを捨てます。

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE city = 'City_123';
```

```text
 Seq Scan on customers  (cost=0.00..2485.00 rows=200 width=69)
                        (actual time=0.016..10.227 rows=200 loops=1)
   Filter: (city = 'City_123'::text)
   Rows Removed by Filter: 99800
   Buffers: shared hit=1235
 Execution Time: 10.247 ms
```

*   **`Buffers: shared hit=1235`** — §1-4 の `customers` の総ページ数と**完全に一致**。全ページ読んだ証拠です。
*   **`Rows Removed by Filter: 99800`** — 200件を得るために99,800件を読んで捨てています。

目的以外のデータが共有バッファを占有し、他のキャッシュを追い出すという副作用もあります。

## 4. インデックスがあるとどうなるか

同じテーブルから、主キーで1件だけ取り出します。

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE customer_id = 50000;
```

```text
 Index Scan using customers_pkey on customers  (cost=0.29..8.31 rows=1 width=69)
                                               (actual time=0.005..0.006 rows=1 loops=1)
   Index Cond: (customer_id = 50000)
   Buffers: shared hit=3
 Execution Time: 0.011 ms
```

**`Buffers: shared hit=3`。たった3ページ、0.011ms。** 全件走査の1,235ページに対し**約1/400**、実行時間は約930倍の差です。

なぜ「3ページ」で済むのか。その答えがB-Treeの構造にあります。

## 5. B-Treeインデックスの構造

**実務で使うのはほぼB-Tree（バランス木）です。** `CREATE INDEX` で何も指定しなければB-Treeが作られます。

### 5-1. 構造と辿り方

*   **ルート / インターナル ノード:** 検索範囲の案内板（「この値以上なら、次はこのページ」）。
*   **リーフ ノード:** キー値と **TID（行の位置）**のペアが、**ソートされた状態で**並ぶ。

![[17-1_インデックスのイメージ.excalidraw]]

**辿り方は単純です。** 上から「探している値がどの範囲に入るか」を見て担当の子へ降りる。それをリーフに着くまで繰り返すだけです。**ルートは必ずここから始まる入口**で、木の頂点は常に1つです。

**そしてポイントはリーフです。** リーフには「値」だけでなく **`(p2, 3行目)` という行の住所**が書いてあります。§2-3 の `ctid` そのものです。**インデックスは、この住所録を値の順に並べたもの**でしかありません。最後にその住所を頼りに、テーブル本体の**そのページだけ**を読みます。読んだのは**色が付いた箱＝4ページ**で、他の3ページには一度も触っていません。

#### 実際の木はもっと「平たい」

いまの図は**深さを見せるためにわざと3段**にしました。`customers`（10万件）の実物はこうです。

![[17-1_Btreeを1件引き当てる.excalidraw]]

- **左がインデックス（木）、右がテーブル本体（ページの列）。** この2つは**別のファイル**です。
- **どの箱も1枚で1ページ（8KB）。** 木のノード1つも、本体のマス1つも同じ8KBの箱です。
- **だから「読んだページ数」＝「色が付いた箱の数」**として数えられます。

**8個のデータで3段だったのに、10万件で2段。** インターナルが無く、ルートから直接リーフへ降りています。**リーフ1ページには実測で367件**入っていたので、実際の木は件数のわりに驚くほど平たくなるのです。

### 5-2. 読むページ数は「木の深さ ＋ 本体1枚」

`WHERE customer_id = 50000` の動きをページ単位で追うと、**`customers` の木は2段**なのでこうなります。

1.  **ルートページ（1枚目）:** 値 `50000` がどの範囲に入るか比較し、次に読むリーフページを特定。
2.  **リーフページ（2枚目）:** ここに対応する **CTID** が入っている。
3.  **テーブル本体（3枚目）:** そのCTIDを元に、ヒープのページをピンポイントで読む。

| インデックス | 行数 | 木の深さ | 読むページ数 |
| :--- | ---: | :--- | :--- |
| `customers_pkey` | 10万 | **2段**（ルート＋リーフ） | 2（索引）＋ 1（本体）＝ **3** |
| `orders_pkey` | 100万 | **3段**（ルート＋中間＋リーフ） | 3（索引）＋ 1（本体）＝ **4** |

`customers` の「3」は §4 の `Buffers: shared hit=3` と一致します。`orders` は実測でも `shared hit=4` です。

**行数が10倍になっても、増えたのは1ページだけ。** これがB-Treeの強さで、$O(\log N)$ の意味です。木は常にバランスを保つよう自動調整されるため、1億件あっても深さは通常4〜5層に収まります。段数はデータ量で決まり、リーフの振り分け情報がルート1ページ（8KB）に収まらなくなると、間にもう1段（インターナル）が生えます。

> [!example]- 手を動かして確かめる（木の深さを見る）
> `pageinspect` 拡張の `bt_metap()` がインデックスのメタ情報を見せてくれます。
>
> ```sql
> CREATE EXTENSION IF NOT EXISTS pageinspect;   -- ※作成には管理者権限が必要
>
> SELECT 'customers_pkey' AS idx, level FROM bt_metap('customers_pkey')
> UNION ALL
> SELECT 'orders_pkey',           level FROM bt_metap('orders_pkey');
> ```
>
> ```text
>       idx       | level
> ----------------+-------
>  customers_pkey |     1
>  orders_pkey    |     2
> ```
>
> `level` はルートノードの階層で、**リーフが0段目**です。つまり実際の深さは `level + 1` 段になります。権限がなくて `CREATE EXTENSION` できない場合は、この出力を見るだけで構いません。

### 5-3. リーフも「ページ」で区切られている

ここまで「リーフ」と一言で呼んできましたが、**リーフも8KBのページの集まり**です。

![[17-1_Btreeインデックスの構造.excalidraw]]

**「リーフが繋がっている」というのは比喩ではありません。** 各リーフページのヘッダに、**左右の隣のページ番号が実際に書き込まれています**。1枚読み終えたら、そこに書いてある番号を見てそのまま次へ進めます。**ルートまで戻り直す必要がありません。**

そしてリーフ1ページには**数百件**が入ります。だから、

- **1ページに収まる範囲検索** → リーフは**1枚読むだけ**で済む
- はみ出したぶんだけ、隣のページを1枚ずつ足して読む

`BETWEEN` や不等号が速いのは、この2つが噛み合っているからです。

### 5-4. B-Treeが得意なこと・苦手なこと

リーフノードが**ソート済み**であることが、得意分野をそのまま決めています。

> **前提：以下はすべて「インデックスを張った列を、そのまま条件に使う場合」の話です。**
> **別の列**を条件にしても、**同じ列でも加工してしまう**と（`WHERE DATE(order_date) = ...` など）使われません。**「列はそのまま、加工は右辺へ」が鉄則**で、効かなくなるパターンは 17-2 §5 でまとめて扱います。

| 用途                     | 使える？ | 理由                                   |
| :--------------------- | :--: | :----------------------------------- |
| 等価検索 `= `              |  ⭕   | 木を辿って一点に到達できる                        |
| 範囲検索 `<` `>` `BETWEEN` |  ⭕   | ソート済みなので、始点を見つけたら横に読み進めるだけ           |
| ソート `ORDER BY`         |  ⭕   | インデックス順に読めば、それがソート結果になる              |
| 最大・最小 `MAX` `MIN`      |  ⭕   | 木の左端／右端を見るだけ（100万行でも**実測4ページ**）      |
| `IS NULL`              |  ⭕   | PostgreSQLはNULLもインデックスに格納する（**他のDBは注意**） |
| 前方一致 `LIKE 'ABC%'`     |  △   | 条件付きで使える（→ 17-2 §5-③）               |
| 部分一致 `LIKE '%ABC%'`    |  ❌   | 「〜で終わる」は辞書を引けないのと同じ                  |

**`MAX` / `MIN` が速いのは、木の端を1つ見れば答えが出るから**です。実行計画には `Limit` が付き、**1件見つけた時点で打ち切って**います。`MAX` はインデックスを逆から辿るので **`Index Only Scan Backward`** になります。

## 6. 4つのスキャン方式

同じ「インデックスを使う」でも、PostgreSQLは**該当行の数と散らばり方**に応じて読み方を変えます。実行計画に出てくる名前は、この読み方の名前です。

| 方式 | ひとことで言うと | 本体（ヒープ）を読む？ |
| :--- | :--- | :---: |
| **Seq Scan** | 索引を使わず先頭から全部読む | 全ページ読む |
| **Index Scan** | 索引で住所を引いて、1件ずつ本体を取りに行く | 1件ごとに読む |
| **Bitmap Index Scan**<br>＋ Bitmap Heap Scan | 住所を全部集めて地図を作り、ページ順にまとめて読む | 必要なページを1回ずつ |
| **Index Only Scan** | 索引の中に答えが全部あるので本体を見ない | **読まない** |

### 6-1. Seq Scan（全件走査）

先頭のページから最後のページまで、順番に全部読みます。

*   **遅いとは限りません。** 順番に読むためディスクの先読み（read-ahead）が効き、1ページあたりのコストはランダムアクセスの**4分の1**として計算されます。該当行が多いなら、これが最速です。
*   **危険信号は `Rows Removed by Filter`。** 読んだ大半を捨てているなら、インデックスの出番です。

### 6-2. Index Scan（1件ずつ狙い撃ち）

インデックスからCTIDを1件取り出し、そのページを読み、また次のCTIDを取り出す──を繰り返します。該当行が**少ない**ときに最速です（主キー1件で3ページ → §5-2）。

**弱点は該当行が増えたとき**で、2つあります。どちらも「**インデックスは値の順、テーブルは物理の順**」というズレから生まれます。

1.  **飛び回るので1ページが高くつく。** ランダムアクセスは順番に読むより4倍高いものとして計算されます（`random_page_cost`）。
2.  **同じページを何度も読んでしまう。** 1件ずつ取りに行くので、同一ページに該当行が3つあれば、そのページに3回アクセスしにいきます。

**この2つはデータが散らばっているほど悪化します。** それを解決するのが次のBitmapです。

### 6-3. Bitmap Index Scan ＋ Bitmap Heap Scan（地図を作ってまとめ読み）

**該当行が「多くて、しかも散らばっている」ときの折衷案です。** 実行計画では必ず2つのノードがペアで現れます。考え方は**「1件ずつ取りに行くのをやめて、先に買い物リストを作る」**です。

![[17-1_BitmapScanの2フェーズ.excalidraw]]

**フェーズ1：Bitmap Index Scan（地図を作る）**
インデックスを走査して条件に合う行のCTIDを**すべて**集め、メモリ上に「**どのページの、何行目が必要か**」を示すビットマップ（地図）を作ります。この段階では**テーブル本体をまだ1ページも読んでいません。**

**フェーズ2：Bitmap Heap Scan（地図に従って回収する）**
地図を**ページ番号順**に見ていき、必要なページだけを順番に読みます。

この「ページ番号順」がキモです。バラバラの場所を行ったり来たりせず、ディスクの端から一筆書きで読み進められ、さらに**各ページを最大1回しか読みません**。

> **`Index Scan` の値段は、データの散らばり具合（`correlation`）に左右される。**
> **`Bitmap Heap Scan` の値段は、散らばり具合に左右されない。**

だからプランナの判断はこうなります。

| 状況 | 選ばれる方式 |
| :--- | :--- |
| 該当が少ない、または並びが揃っている | `Index Scan` が最安 |
| **散らばっているので Index Scan は高くつきそう。<br>でも全件読むほどではない** | **→ 次善の策として `Bitmap Heap Scan`** |
| 該当が大部分 | `Seq Scan` が最安 |

**実測です。** `city = 'City_123'`（該当200件、物理的に散在）の場合：

| 方式 | 読んだページ数 | 実行時間 |
| :--- | ---: | ---: |
| Seq Scan（インデックスなし） | 1,235 | 10.2 ms |
| **Bitmap Heap Scan** | **202** | **0.20 ms** |

> ⚠️ **`Recheck Cond` は Bitmap Heap Scan なら必ず表示される行で、これ自体は異常のサインではありません。**
> 見るべきは `Heap Blocks:` に **`lossy=N`** が出ていないか（該当が多すぎて地図が `work_mem` に収まらず、行単位からページ単位まで精度を落とした状態）と、**`Rows Removed by Index Recheck`** が出ていないか。**どちらも出ていれば `work_mem` 不足のサイン**です（設定変更は管理者の仕事なので、「そう出ていた」と報告できれば十分）。

### 6-4.「散らばっている」とはどういうことか

なぜ Index Scan ではなく Bitmap が選ばれたのか。**同じ200件でも、それが何ページに散っているかがまるで違う**からです。

| 条件 | 該当行数 | それが載っているページ数 |
| :--- | ---: | ---: |
| `WHERE city = 'City_123'` | 200 | **200**（1行につき1ページ！） |
| `WHERE customer_id BETWEEN 1 AND 200` | 200 | **3** |

**同じ200件なのに、200ページ対3ページ。** これが「データの散らばり方（`correlation`）」の正体です。`city` は値が循環するよう挿入したので全ページに散り、`customer_id` は連番なので固まっています。

**取得する行数が同じでも、散らばっていれば読むページ数は激増する。** だからPostgreSQLは、散らばっているときは Bitmap でページ順に整えてから読むのです。

> [!example]- 手を動かして確かめる（`ctid` で散らばりを見る）
> ```sql
> SELECT ctid, customer_id FROM customers WHERE city = 'City_123' ORDER BY ctid LIMIT 6;
> ```
>
> ```text
>   ctid   | customer_id
> ---------+-------------
>  (1,41)  |         123
>  (7,55)  |         623
>  (13,69) |        1123
>  (20,2)  |        1623
>  (26,16) |        2123
>  (32,30) |        2623
> ```
>
> ページ番号が 1 → 7 → 13 → 20 → 26 → 32 と、**6ページ前後ずつ飛んでいます**。1件読むたびに別のページへ移動しなければなりません。
>
> ```sql
> -- 該当行数と、それが使っているページ数を数える
> SELECT COUNT(*)                                        AS 該当行数,
>        COUNT(DISTINCT (ctid::text::point)[0]::int)     AS 使用ページ数
> FROM customers WHERE city = 'City_123';
>
> -- 比較：連番の主キー範囲で同じ200件を取ると？
> SELECT COUNT(*)                                        AS 該当行数,
>        COUNT(DISTINCT (ctid::text::point)[0]::int)     AS 使用ページ数
> FROM customers WHERE customer_id BETWEEN 1 AND 200;
> ```

![[17-1_同じページを何度も読む.excalidraw]]

**リーフは値の順に並んでいますが、その先の「行の住所」は本体のあちこちを指しています。** だから値の順に1件ずつ辿ると、本体の読みは前後に飛び回り、**同じページに何度も戻ってくる**ことになります。Bitmap は「必要なページの集合」を先に作るので、**各ページを1回ずつ読んで終わり**です。

実測すると、`orders` から1,380行（実際は**20ページ**に収まっている）を取る場合でこうなります。

| 方式 | 読んだページ数（`Buffers`） | 実際に存在するページ数 |
| :--- | ---: | ---: |
| `Index Scan`（強制） | **1,384** | 20 |
| `Bitmap Heap Scan` | **24** | 20（`Heap Blocks: exact=20`） |

**1,384 対 24。** Index Scan は1ページを平均69回も読み直しています。

※ この実測は全部 `shared hit`（メモリ）だったため、実行時間の差は2倍程度でした。**この往復が実際のディスク読みに変わる本番環境で、はじめて数十倍の差として現れます。**

### 6-5. Index Only Scan（本体を見ない）

**インデックスの中に必要な列が全部含まれている場合、テーブル本体を一切読みません。**

ただし条件があります。インデックスには「その行が今のトランザクションから見えるか」という**可視性の情報がありません**。そこでPostgreSQLは **Visibility Map（VM）** という小さなファイルで「このページの全行は誰から見ても可視」かを確認します。

*   VMで確認できたページ → 本体を読まない
*   確認できなかったページ → 本体を読んで確認する ＝ これが **`Heap Fetches`**

**`VACUUM` を実行するとVMが更新されます。** 逆に更新が多くVACUUMが追いついていないテーブルでは `Heap Fetches` が増え、Index Only Scan の旨みが消えます。

### 6-6. 使い分けの早見表

| 該当行の割合 | 選ばれやすい方式 | 決め手 |
| :--- | :--- | :--- |
| ごく少数（〜1%） | Index Scan / Index Only Scan | ランダムアクセスが少数で収まる |
| 中程度 | Bitmap Heap Scan | ページを1回ずつ、順番に読める |
| 大部分 | Seq Scan | どうせ全ページ読むなら余計な手間が無駄 |

「中程度」と「大部分」の境目は §7-2 で見ます。

## 7. 実行計画：プランナはどう判断しているか

**インデックスを作っても、PostgreSQLが必ず使うとは限りません。** ここで「**プランナ（オプティマイザ）**」が登場します。

![[17-1_SQLが実行されるまでの4段階.excalidraw]]

| 段階 | やること |
| :--- | :--- |
| ① パーサー | SQL文の構文を解析する |
| ② リライター | ビューの展開など、内部的な書き換えを行う |
| ③ **プランナー** | **統計情報**を見てコストを計算し、**実行計画**を1つ選ぶ |
| ④ エグゼキューター | 選ばれた実行計画のとおりに実行する |

**注目すべきは「プランナーが見ているのは統計情報だけで、実データではない」ことです。** だから**統計情報が古いと、プランナは平気で間違えます**。大量に `INSERT` / `UPDATE` した直後は `ANALYZE テーブル名;` を打ってください（→ 17-2 §5-⑦）。

そして `EXPLAIN` は**③で作られた計画を見せるコマンド**、`EXPLAIN ANALYZE` は**④まで実際に走らせて実測値も出すコマンド**です。

```sql
-- 予測だけを見る（クエリは実行されない）
EXPLAIN SELECT * FROM customers WHERE city = 'City_123';

-- 実際に実行して、実測値も見る
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE city = 'City_123';
```

### 7-1. コストベースの意思決定

PostgreSQLは統計情報（テーブルのサイズ、値のバラつきなど）から複数の実行パターンのコストを計算し、**最も安いものを選びます**。

*   **インデックスを使う判断:** 「インデックスページを数枚読み、必要なデータページだけを飛んで読むコスト」が「全ページを順番に読むコスト」より安いとき。
*   **あえて使わない判断（Seq Scan）:** テーブルが極端に小さいとき、または `WHERE` 条件に合致するデータが全体の大部分を占めるとき。

### 7-2. 「大部分」とは何割なのか

**結論から言うと、「何％」という固定の目安はありません。** `orders`（100万件）で該当行の割合を少しずつ増やして測ると、Seq Scan に切り替わる境界はこれだけ動きました。

| 条件 | Seq Scan に切り替わる境界 |
| :--- | :--- |
| 素の `Index Scan` ／ 物理配置がバラバラ | **約1%** |
| `Bitmap Heap Scan` が使える ／ 物理配置がバラバラ | **約45〜50%** |
| `Index Scan` ／ 物理配置がインデックス順と一致 | **約55%** |

**同じテーブル・同じ件数なのに、境界が50倍違います。** 決め手は**「インデックスの順番と、テーブルの物理的な格納順がどれだけ一致しているか」**── §6-4 で見た散らばり具合（`correlation`）です。

実際に境界を跨いだときの中身を見ると、**Bitmap の 18,505 が Seq Scan の 19,755 を超えた瞬間に乗り換えた**だけでした。**プランナは常にこの比較をしているに過ぎません。**

世間でよく言われる「5〜10%が境界」という目安は、表の1行目（素の `Index Scan`）を想定したものです。**数字を覚えることに意味はありません。`EXPLAIN` で実際に確かめる習慣のほうが大事です。**

```sql
-- 散らばり具合そのものは pg_stats で見られる（1.0 に近いほどインデックス順に読める）
SELECT tablename, attname, correlation FROM pg_stats WHERE tablename = 'orders';
```

## 8. トレードオフ：インデックスの代償

インデックスは「読むのを速くする」代わりに、「書くのを遅く」します。**張れば張るだけ速くなるわけではありません。**

### 8-1. 書き込みが遅くなる

`INSERT` / `UPDATE` / `DELETE` のたびに、**テーブル本体だけでなく、関連するすべてのインデックスファイルも更新**しなければなりません。**インデックスが3本あれば、1回の `INSERT` で4つのファイルに書き込む**ことになります。

さらに更新内容は必ず **WAL（先行書き込みログ）**にも記録されます（→ [[15-1_導入_トランザクションとACID|15-1 トランザクションとACID]] §3-2 の Durability）。インデックスが多いほどWALの生成量が増え、チェックポイントの負荷も上がります。

### 8-2. ディスク容量を食う

インデックスも物理的なファイルです。列の組み合わせを増やすと、**インデックスの合計がテーブル本体を追い越すことも珍しくありません。**

とくに問題なのが、**作ったまま一度も使われていないインデックス**です。検索を1ミリ秒も速くしていないのに、書き込み負荷と容量だけを食い続けます。**実務では `pg_stat_user_indexes.idx_scan` を見て定期的に棚卸しします**（演習の締めで実際にやります）。

### 8-3. メンテナンスが要る

*   更新を繰り返すとインデックス内に隙間ができ（断片化）、検索効率が落ちます。`VACUUM` や `REINDEX` の検討が必要です。
*   §6-5 の `Index Only Scan` を効かせるにも `VACUUM` が必要です。
*   **稼働中のサービスでインデックスを作る／消すこと自体にも作法があります**（→ [[17-2_実践_EXPLAINの読み方|17-2]] §1-3）。

## まとめ

1.  **すべては「何ページ読んだか」に還元される。** メモリとディスクの速度差が1,000〜10万倍だから、ページ数を減らすことがそのまま速さになる。
2.  **インデックスは「値 → CTID」を並べ替えた別表**であり、テーブルとは別の物理ファイル。
3.  **読み方は4種類**（Seq / Index / Bitmap / Index Only）。該当行の数と散らばり方で使い分けられる。
4.  **プランナはコストで選ぶ**ので、インデックスを作っても使われないことがある。境界を決めるのは選択率と `correlation`。
5.  **代償は書き込み負荷と容量。** 張れば速くなる魔法の杖ではない。

> 💡 **15章との繋がり。** 「読むページ数」が増える原因は、インデックスの張り方だけではありません。**MVCC で溜まった古いバージョンの行を `VACUUM` が回収できていない**と、同じ行数でもページ数が増えて全体が遅くなります（→ [[15-2_実践_ロックとMVCC|15-2]] §2-3）。§6-5 の `Index Only Scan` が効かなくなるのも同じ理由です。

次の [[17-2_実践_EXPLAINの読み方|17-2]] では、実際にインデックスを作り、`EXPLAIN` を読んで検証する手順に進みます。
