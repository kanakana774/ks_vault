### PL/pgSQL内のトランザクション基本ルール

PostgreSQLのPL/pgSQLには、大きく分けて2つの「コンテキスト（実行環境）」があります。

#### ① 関数 (FUNCTION) の中：【常にアトミック】
関数は、呼び出し元のSQLの一部として実行されます。
*   **ルール**: 内部で `COMMIT` や `ROLLBACK` は**一切使えません。**
*   **理由**: 関数は「一つの大きなトランザクションの一部」として動くことが保証されているため、勝手に一部だけ確定させることは許されません。

#### ② プロシージャ (PROCEDURE) または DOブロック：【非アトミック】
これらは独立して呼び出すことができます。
*   **ルール**: 内部で `COMMIT` や `ROLLBACK` を**使えます。**
*   **例外**: ただし、他のトランザクション（例：`BEGIN;` と打った後）の中で `CALL` された場合は、`COMMIT` は使えません。

### 「勝手に作られるトランザクション」の正体

PL/pgSQL内で意識すべき「隠れたトランザクション制御」は以下の2つです。

#### A. 暗黙のメイン・トランザクション
プロシージャや `DO` ブロックを開始すると、自動的に一つのトランザクションが始まっています。`COMMIT` を書くと、その時点までの処理を確定し、**直後に新しいトランザクションを自動で開始**します。

#### B. EXCEPTIONによる「サブトランザクション」
PL/pgSQLで `BEGIN ... EXCEPTION` という構文を書くと、PostgreSQLは内部的に **SAVEPOINT（セーブポイント）** を作成します。

1.  `BEGIN`（EXCEPTION付き）に入る → **SAVEPOINT を自動作成**
2.  内部のSQL実行
3.  エラーが発生 → **SAVEPOINT まで自動ロールバック**し、`EXCEPTION` ブロックへ
4.  正常に終了 → **SAVEPOINT を自動解除（RELEASE）**

**【ここが重要！】**
PostgreSQLの仕様で、**「セーブポイントが生きている間は、親のトランザクションを COMMIT/ROLLBACK できない」**という制約があります。
`EXCEPTION` ブロックの中にいる間は、まだ「エラーが起きたらここまで戻る」というセーブポイントが有効な状態なので、`COMMIT` しようとすると「サブトランザクションがアクティブです」と怒られるのです。

### 実務的な使い分けのまとめ

もし「バッチ処理」を書きたいなら、以下の構造をテンプレートにするのが正解です。例外処理をするブロックを内側のブロックで作ります。

```sql
DO $$
DECLARE
    r RECORD;
BEGIN
    FOR r IN SELECT id FROM my_table LOOP
        -- 1. ここで「例外処理」の境界を作る
        BEGIN 
            -- 何か処理
            UPDATE my_table SET processed = true WHERE id = r.id;
            
            -- ここでエラーが起きても、このBEGINブロックの開始までしか戻らない
        EXCEPTION WHEN OTHERS THEN
            -- エラーログ記録など
            RAISE WARNING 'ID % でエラー', r.id;
        END;

        -- 2. 例外処理ブロックの「外」でCOMMIT
        -- これで、今回のループ分（成功 or エラーログ）が確定する
        COMMIT; 
    END LOOP;
END $$;
```

**結論：**
PL/pgSQLは「エラーハンドリング（EXCEPTION）」を始めると、その区間を**「ひとまとまりの安全圏（サブトランザクション）」**として扱います。その安全圏の中にいるうちは、DB全体の確定（COMMIT）はさせてもらえない、と覚えると分かりやすいです。
