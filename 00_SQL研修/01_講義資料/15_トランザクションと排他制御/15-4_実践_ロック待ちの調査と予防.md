# ロック待ちの調査と予防
## 〜固まったときに、何をどの順で見るか〜

[[15-2_実践_ロックとMVCC|15-2]] では「なぜ待つのか」を見ました。この資料は、**実際に処理が固まったときに何をどの順で調べるか**という手順書です。

> **この資料の使い方**
> - **これは講義では通しません。詰まったときに開いてください。** 演習問題6の参照先でもあります。
> - PostgreSQL 17 で動作確認しています。掲載している出力・設定値は**すべて実測**です。
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] のものです。
> - 2窓のシナリオは [[15-2_実践_ロックとMVCC|15-2]] §0 の準備がそのまま使えます。

## 1. 固まったときの手順

### 1-1. 調べる順番

「画面が返ってこない」「バッチが進まない」と言われたら、この順に見ます。

```
固まった
  │
  ├─ ① 待っているのは誰か        pg_blocking_pids()      → 15-2 §1-3
  │
  ├─ ② 待たせているのは誰か      state / xact_start      → §2-1
  │
  ├─ ③ 犯人は何をしているか
  │      state = active               … 重い処理の実行中。終わるのを待つ
  │      state = idle in transaction  … COMMIT 漏れ。人を探す  → §2
  │
  ├─ ④ 止めるか、待つか          pg_cancel / pg_terminate → §2-4
  │
  └─ ⑤ 再発させない              タイムアウトを入れる      → §4
```

**①と②は同じクエリで分かります。**まずは 15-2 §1-3 のクエリを打ってください。そこから先が、この資料の内容です。

### 1-2. どこまでが「正常な待ち」か

**「固まった」と言われたら、まず何秒なのかを聞いてください。**

PostgreSQL はロック待ちが `deadlock_timeout`（既定 **1秒**）を超えて初めてデッドロックの検査を始めます（→ 15-2 §5-2）。つまり**1〜2秒の待ちは、混んでいれば普通に起きる正常な動作**です。

調べる価値があるのは、**数十秒〜数分単位で止まっている**ときです。

## 2. `idle in transaction` を見つける

犯人の `state` が `idle in transaction` だったら、それは**性能問題ではなく `COMMIT` 漏れ**です。ここを見分けられるかどうかで、調査の方向がまったく変わります。

### 2-1. 【手を動かす】犯人の状態を見る

**窓A**で更新して、`COMMIT` せずに放置します。

```sql
-- 窓A
BEGIN;
UPDATE products SET price = price + 100 WHERE product_id = 1;
```

**窓B**で同じ行を更新します（返ってこなくなります）。

```sql
-- 窓B
UPDATE products SET price = price + 50 WHERE product_id = 1;
```

**窓C**から、このデータベースに繋いでいる接続の状態を一覧します。

```sql
-- 窓C
SELECT pid,
       state,
       now() - xact_start AS xact_age,
       wait_event_type,
       left(query, 45)    AS last_query
FROM pg_stat_activity
WHERE datname = current_database()
  AND state IS NOT NULL
  AND pid <> pg_backend_pid()
ORDER BY xact_start;
```

実測：

```
  pid  |        state        |    xact_age     | wait_event_type |                  last_query
-------+---------------------+-----------------+-----------------+-----------------------------------------------
 15560 | idle in transaction | 00:00:05.414847 | Client          | UPDATE products SET price = price + 100 WHERE
 13116 | active              | 00:00:03.271732 | Lock            | UPDATE products SET price = price + 50 WHERE
```

読み解きます。

| 列 | 犯人（15560） | 被害者（13116） |
| :--- | :--- | :--- |
| `state` | **`idle in transaction`**（トランザクションを開いたまま何もしていない） | `active`（実行中） |
| `xact_age` | **5秒**トランザクションを握っている | 3秒待っている |
| `wait_event_type` | `Client`（**次の命令が来るのを待っている**） | `Lock`（**ロックが空くのを待っている**） |

**`state = idle in transaction` かつ `wait_event_type = Client` は、「人間かアプリが `COMMIT` を打ってくれるのを待っている」状態です。**放っておいても永遠に終わりません。

> 💡 **`xact_age` は「どれだけ長くトランザクションを握っているか」です。**
> これが数分〜数時間になっている接続を見つけたら、それだけで問題です（→ §2-3）。監視するなら、この値です。

### 2-2. `query` 列は「今実行中のSQL」ではない

ここは必ず一度は誤診します。

**`pg_stat_activity.query` は、その接続が「最後に実行した」SQLです。** 今それを実行しているとは限りません。

上の実測で、犯人（15560）の `query` には `UPDATE products SET price = price + 100 ...` と出ています。これを見て「重い UPDATE が走りっぱなしだ」と判断すると、**まったく的外れな調査**が始まります。実際にはその `UPDATE` はとっくに終わっていて、`COMMIT` が来ないだけです。

> ⚠️ **`query` は必ず `state` とセットで読んでください。**
> - `state = active` → `query` は**今実行中**のSQL
> - `state = idle in transaction` → `query` は**最後に実行した**SQL。今は何もしていない
> - `state = idle` → `query` は最後に実行したSQL。トランザクションも開いていない（無害）

### 2-3. 1本放置されるだけで何が起きるか

`idle in transaction` が1本あるだけで、次の2つが同時に起きます。

1. **その接続が触った行のロックが外れません。**（→ 15-2 §1-1）その行を更新したい人が全員止まります。
2. **`VACUUM` が古いバージョンの行を回収できなくなります。**（→ 15-2 §2-3）「まだこのトランザクションから見えるかもしれない」ものは消せないので、**そのトランザクションが開いている間に他のセッションが作った古い行も、まとめて回収不能になります。**放置が長いほどテーブルが膨らみ、**関係のないテーブルまで遅くなります。**

**2つ目のほうが厄介です。**ロックは「その行を触る人」しか困りませんが、VACUUM の停滞は**データベース全体に効いてきます。**

典型的な原因は3つです。

| 原因 | ありがちな状況 |
| :--- | :--- |
| 人間が `BEGIN;` したまま席を立った | pgAdmin や psql で調査中にそのまま昼休みへ |
| アプリが `COMMIT` / `ROLLBACK` を忘れた | 例外が飛んだ経路で `close()` されていない |
| 自動コミットが off のツールを使っている | 本人は「ただ `SELECT` しただけ」のつもり（→ [[15-1_導入_トランザクションとACID\|15-1]] §2-2） |

### 2-4. `pg_cancel_backend` が効かない場合がある

> [!example]- 手を動かして確かめる（`t` が返っても止まっていない）
> §2-1 の状態のまま、犯人をキャンセルしてみます。
>
> ```sql
> -- 窓C
> SELECT pg_cancel_backend(pid) AS cancel_result, state
> FROM pg_stat_activity
> WHERE datname = current_database() AND state = 'idle in transaction';
> ```
>
> ```
>  cancel_result |        state
> ---------------+---------------------
>  t             | idle in transaction
> ```
>
> **`t`（成功）が返ってきました。**ところがもう一度見ると：
>
> ```sql
> SELECT pid, state FROM pg_stat_activity
> WHERE datname = current_database() AND state = 'idle in transaction';
> ```
>
> ```
>   pid  |        state
> -------+---------------------
>  15560 | idle in transaction
> ```
>
> **まだ生きています。**
>
> `pg_cancel_backend` は「**実行中のクエリ**をキャンセルする」コマンドです。`idle in transaction` の接続は**何も実行していない**ので、キャンセルする対象がありません。それでも戻り値は「シグナルを送れた」という意味の `t` になります。
>
> **この場合に効くのは `pg_terminate_backend`（接続ごと切断）だけです。**

```sql
SELECT pg_terminate_backend(15560);   -- 接続を切る。トランザクションはロールバックされる
```

> ⚠️ **`pg_terminate_backend` は他人の処理を強制終了させるコマンドです。**
> 本番で実行する前に、必ず次を確認してください。
> 1. その接続が何をしているか（`query` と `state`。→ §2-2）
> 2. どれだけ長く握っているか（`xact_age`）
> 3. **持ち主に連絡がつくか**（切ればその人の作業は巻き戻ります）
> 4. 切った後に**同じことが起きない手当て**があるか（→ §4）

## 3. `pg_locks` は何を教えて、何を教えてくれないか

### 3-1. 【2窓】待っている最中の `pg_locks` を見る

> [!example]- 手を動かして確かめる
> §2-1 と同じ状態（窓Aが握り、窓Bが待っている）で、窓Cから実行します。
>
> ```sql
> -- 窓C
> SELECT pid, locktype, relation::regclass AS relation,
>        page, tuple, transactionid, mode, granted
> FROM pg_locks
> WHERE relation = 'products'::regclass OR locktype IN ('transactionid','tuple')
> ORDER BY pid, locktype;
> ```
>
> 実測（15560 = 窓A、13116 = 窓B）：
>
> ```
>   pid  |   locktype    | relation | page | tuple | transactionid |       mode       | granted
> -------+---------------+----------+------+-------+---------------+------------------+---------
>  13116 | relation      | products |      |       |               | RowExclusiveLock | t
>  13116 | transactionid |          |      |       |         18727 | ShareLock        | f
>  13116 | transactionid |          |      |       |         18728 | ExclusiveLock    | t
>  13116 | tuple         | products |    0 |    22 |               | ExclusiveLock    | t
>  15560 | relation      | products |      |       |               | RowExclusiveLock | t
>  15560 | transactionid |          |      |       |         18727 | ExclusiveLock    | t
> ```

**`granted = f`（取れていない）の行が1つだけあります。**これが「待っている」ことの正体です。

```
 13116 | transactionid | ... | 18727 | ShareLock | f
```

**「PID 13116 は、トランザクションID 18727 が終わるのを待っている」**と読みます。そして最終行を見ると、**18727 を持っているのは PID 15560**です。これで犯人が特定できます。

つまり PostgreSQL の行ロック待ちは、**「行を待つ」のではなく「相手のトランザクションが終わるのを待つ」**という形で表現されています。だから `granted = f` の行には、テーブル名も行番号も出てきません。

### 3-2. 行ロックのモードは `pg_locks` に出てこない

**ここが一番の誤解ポイントです。**

15-2 §4-8 で見た4つの行ロックモード（`FOR UPDATE` / `FOR NO KEY UPDATE` / `FOR SHARE` / `FOR KEY SHARE`）を `pg_locks` の中に探しても、**一つも見つかりません。**上の実測にも出ていません。

**理由は、行ロックがロックマネージャに登録されていないからです。**

PostgreSQL は行ロックを、**行そのもの（各行が持っているシステム列）に書き込んで**表現します。「この行は、このトランザクションが、この強さで押さえている」という情報は、メモリ上のロック管理表ではなく**テーブルの中**にあります。

| | どこにあるか | `pg_locks` に出るか |
| :--- | :--- | :--- |
| テーブルロック（`RowExclusiveLock` など） | ロックマネージャ | **出る** |
| トランザクションID の待ち（`ShareLock` / `granted=f`） | ロックマネージャ | **出る** |
| 行ロックのモード（`FOR UPDATE` など） | **行そのもの** | **出ない** |

> 💡 **これが、PostgreSQL が「何億行ロックしても平気」な理由です。**
> 行ロックはロック管理表を消費しません。行に書くだけなので、100万行を `FOR UPDATE` してもメモリは増えません。他のDBで「行ロックが多すぎるとテーブルロックに格上げされる（ロックエスカレーション）」という現象がありますが、**PostgreSQL にはこれがありません。**

**実務では `pg_blocking_pids()`（15-2 §1-3）1本で足ります。**「誰が誰を待っているか」はそれで分かり、「どのモードで待っているか」は `pg_locks` を見ても分からないからです。

### 3-3. `pg_locks` を読む価値があるのはテーブルロックのとき

では `pg_locks` はいつ使うのか。**テーブル全体が止まっているとき**です。

`ALTER TABLE` / `CREATE INDEX`（`CONCURRENTLY` なし）/ `VACUUM FULL` / 明示的な `LOCK TABLE` は、**テーブル全体に強いロック**を取ります。これらは `pg_locks` の `locktype = 'relation'` にはっきり出ます。

```sql
-- テーブル全体を止めている犯人を探す
SELECT pid, relation::regclass AS relation, mode, granted
FROM pg_locks
WHERE locktype = 'relation'
  AND mode IN ('AccessExclusiveLock', 'ShareLock', 'ExclusiveLock')
ORDER BY relation, granted;
```

**`AccessExclusiveLock` が1つ取られていると、そのテーブルは `SELECT` すらできなくなります。**「特定のテーブルだけ全部止まった」ときは、まずこれを疑ってください。

> 💡 **`max_locks_per_transaction`（実測 `64`）は、この「テーブル単位のロック」の上限です。**
> 行ロックは §3-2 のとおり管理表を使わないので、この値とは無関係です。パーティションを大量に触るバッチなどで足りなくなることがあります。

## 4. 予防：4つのタイムアウト

調べ方が分かっても、**毎回人間が調べに行くのでは運用になりません。**「一定時間で自動的に諦めさせる」設定を知っておきます。

### 4-1. 【手を動かす】いまの設定値を見る

```sql
SHOW lock_timeout;
SHOW statement_timeout;
SHOW idle_in_transaction_session_timeout;
SHOW deadlock_timeout;
SHOW log_lock_waits;
```

実測（PostgreSQL 17 の初期状態）：

```
 lock_timeout                        | 0
 statement_timeout                   | 0
 idle_in_transaction_session_timeout | 0
 deadlock_timeout                    | 1s
 log_lock_waits                      | off
```

**`0` は「無効」という意味です。**つまり**素の PostgreSQL は、ロックが空くのを永久に待ちます。**§1 で見た「固まった」状態は、放っておけば本当に永久に続きます。

### 4-2. 4つの違い

| パラメータ | 何を打ち切るか | 既定 | 誰が決めるか |
| :--- | :--- | :--- | :--- |
| `lock_timeout` | **ロック待ちだけ** | `0`（無効） | アプリ（`SET LOCAL`） |
| `statement_timeout` | SQL 1文の**実行時間全体**（ロック待ちも重い処理も含む） | `0`（無効） | アプリ／DB単位 |
| `idle_in_transaction_session_timeout` | **`BEGIN` したまま放置している接続**（→ §2） | `0`（無効） | DB管理者 |
| `deadlock_timeout` | デッドロックの**検査を始めるまでの待ち時間**（打ち切りではない） | `1s` | 触らない |

**`deadlock_timeout` だけは性格が違います。**これは「何秒待ったら諦めるか」ではなく「何秒待ったらデッドロックかどうか調べ始めるか」です（→ 15-2 §5-2）。値を小さくすると検査が頻繁に走って重くなるだけなので、通常は触りません。

### 4-3. 【2窓】`lock_timeout` を効かせてみる

**窓A**で更新して止めておきます。

```sql
-- 窓A
BEGIN;
UPDATE inventory SET stock_quantity = stock_quantity WHERE product_id=1 AND warehouse_id=1;
```

**窓B**で、3秒だけ待つように指定してから同じ行を更新します。

```sql
-- 窓B
SET lock_timeout = '3s';
UPDATE inventory SET stock_quantity = stock_quantity WHERE product_id=1 AND warehouse_id=1;
```

実測：

```
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (0,16) in relation "inventory"
時間: 3033.293 ミリ秒
```

**3秒で諦めてエラーになりました。**永久に待つのではなく、アプリ側でエラーとして受け取れます。

`statement_timeout` でも似たことは起きますが、**メッセージが違うので区別できます。**

```
ERROR:  canceling statement due to statement timeout
```

**この違いは重要です。**`lock_timeout` で落ちたなら「誰かとぶつかっている」、`statement_timeout` で落ちたなら「その SQL 自体が重い」——原因の方向がまったく違います。

> 💡 **使いどころ。**
> - **画面から呼ぶ処理** … 10秒固まって待たせるより、**3秒で諦めて「混み合っています。もう一度お試しください」と返す**ほうが親切です
> - **夜間バッチ** … 逆に、待ってでも完遂させたい
>
> **だから全体設定ではなく、処理ごとに `SET LOCAL lock_timeout = '3s';` と書きます。**`SET LOCAL` は**そのトランザクションの中だけ**有効で、`COMMIT` すると元に戻ります。

> **`NOWAIT`（15-2 §4-5）との違いは「0秒で諦めるか、N秒だけ待つか」だけです。**
> `NOWAIT` は取れなければ即エラー、`lock_timeout` は指定秒数だけ粘ってからエラーになります。

### 4-4. `log_lock_waits`：後から調べられるようにしておく

`log_lock_waits` を `on` にすると、`deadlock_timeout`（1秒）を超えたロック待ちが**サーバーログに残ります。**次のような行です（※これは形式を示すための例で、実測ではありません。この設定はサーバー側なので手元では試せません）。

```
LOG:  process 13116 still waiting for ShareLock on transaction 18727 after 1000.123 ms
```

既定は `off` です（実測で確認済み）。つまり**何も設定していないシステムでは、「昨夜のあの時間に何が詰まっていたか」を後から知る方法がありません。**

**これは事前に on にしておかないと意味がない設定です。**障害が起きてから on にしても、そのときの記録は残っていません。

### 4-5. どこまでがアプリ開発者の裁量か

| やること | 誰が | どうやって |
| :--- | :--- | :--- |
| `lock_timeout` / `statement_timeout` を処理ごとに設定する | **アプリ開発者** | コードに `SET LOCAL` を書く |
| `idle_in_transaction_session_timeout` を入れる | DB管理者 | サーバー設定（`postgresql.conf`） |
| `log_lock_waits` を on にする | DB管理者 | サーバー設定 |
| そもそも長いトランザクションを作らない | **アプリ開発者** | → 15-2 §6 |

**設定値を決めるのは1年目の仕事ではありません。**サーバー設定を変える権限は、まず与えられません。

**それでも「こういう設定があるので入れてもらえませんか」と言えることは、1年目の仕事です。**「原因は分かりませんが固まりました」と「`idle in transaction` が30分放置されていました。`idle_in_transaction_session_timeout` の設定をご検討いただけますか」では、まったく違う報告になります。

## この章のまとめ

| | 覚えること |
| :--- | :--- |
| **調べる順番** | 待っている人 → 待たせている人 → **その `state`** → 止めるか待つか → 再発防止 |
| **`idle in transaction`** | 性能問題ではなく **`COMMIT` 漏れ**。ロックも VACUUM も止める |
| **`query` 列** | 「今実行中」ではなく「**最後に実行した**」SQL。`state` とセットで読む |
| **`pg_cancel_backend`** | `idle in transaction` には**効かない**（`t` が返っても止まらない）。`pg_terminate_backend` を使う |
| **`pg_locks`** | **行ロックのモードは出てこない**。出るのは「どのトランザクションの終了を待っているか」とテーブルロック |
| **タイムアウト** | 既定はすべて `0`＝**無効＝永久に待つ**。`SET LOCAL lock_timeout` はアプリ側で書ける |
| **`log_lock_waits`** | 既定 `off`。**事前に on にしていないと、後から調べられない** |
