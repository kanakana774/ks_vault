## 1. トランザクションとは

**複数のSQLを「全部やる」か「何もしない」かにまとめる仕組み。**

```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE name = 'Alice';
UPDATE accounts SET balance = balance + 10000 WHERE name = 'Bob';
COMMIT;
```

①だけ成功して②の前に落ちたら、お金が消えます。`BEGIN`〜`COMMIT` で囲めば、**両方反映されるか、両方なかったことになるか**のどちらかになります。

| コマンド | 意味 |
| :--- | :--- |
| `BEGIN` | ここから塊が始まる |
| `COMMIT` | 塊の変更を**すべて確定**して終える |
| `ROLLBACK` | 塊の変更を**すべて破棄**して終える |

- `COMMIT` 前に接続が切れたら**自動で `ROLLBACK`**。「宣言しない限り確定しない」
- **`ROLLBACK` で戻せるのは、まだ `COMMIT` していない変更だけ**
- `BEGIN` と `START TRANSACTION` は同じ

### 【手を動かす】ROLLBACK

```sql
SELECT price FROM products WHERE product_id = 1;   -- 1200.00

BEGIN;
UPDATE products SET price = 99999 WHERE product_id = 1;
SELECT price FROM products WHERE product_id = 1;   -- 99999.00（自分には見えている）
ROLLBACK;

SELECT price FROM products WHERE product_id = 1;   -- 1200.00（戻った）
```

**トランザクションの中では、自分の変更は自分にだけ見えます。** 他の人にはまだ見えていません（15-2 で2窓で確認します）。

## 2. 自動コミット

**`BEGIN` を書かないSQLは、1文が自動的に `BEGIN`〜`COMMIT` で包まれています。** 14章まで `BEGIN` を書かずに動いていたのはこのためです。

**自分でトランザクションを書く必要があるのは、複数のSQLをまとめたいときだけ**です。

| ツール／環境 | 何も指定しないときの既定 | 明示的に始めるには |
| :--- | :--- | :--- |
| `psql` / pgAdmin | 自動コミット **on** | `BEGIN;` |
| Java（JDBC） | 自動コミット **on** | `conn.setAutoCommit(false)` |
| Java（Spring） | **アノテーションを付けなければ on** | メソッドに `@Transactional` |

**どれも既定は on で、off にするのは自分の意思です。** ドライバによっては既定 off のものもあり、その場合 `COMMIT` を忘れると**変更が反映されないまま行のロックだけ握り続けます**（15-2 で見ます）。

### 【手を動かす】エラーが出たトランザクションは中断状態になる

```sql
BEGIN;
UPDATE products SET price = 1 WHERE product_id = 1;
SELECT 1/0;                      -- わざとエラー
SELECT 'この行は実行されるか?';
COMMIT;
```

```
BEGIN
UPDATE 1
ERROR:  division by zero
ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

1. エラー以降のSQLは**すべて拒否**される
2. **`COMMIT` と打っても `ROLLBACK` が返る**
3. `UPDATE` も残らない

> **`current transaction is aborted` を見たら、原因は「もっと前で起きた最初のエラー」です。** 遡って探してください。
> 復旧は `ROLLBACK;`。**途中まで活かしたいなら `SAVEPOINT`（→ §4）。**

> 🐘 **この挙動は PostgreSQL 固有です。** Oracle や MySQL では、エラーが出た**その文だけ**が失敗し、トランザクションは続行できます。

## 3. ACID

| 特性 | ひとことで | どこで扱うか |
| :--- | :--- | :--- |
| **A** 原子性 | 「全部やる」か「何もしない」か | **§3-1・§1・§4（この章の主題）** |
| **C** 一貫性 | 制約を破った状態で終わらない | §3-2（1章の制約の続き） |
| **I** 分離性 | 同時に動く他の処理に邪魔されない | **15-2 がまるごとこれ** |
| **D** 永続性 | 確定したものは電源が落ちても消えない | §3-3（軽く） |

**この章で考えるのは A、次の章で考えるのが I です。**

### 3-1. 原子性（A）：どこまでを1つの塊にするか

**4つのうち、開発者が毎回判断するのは A だけ**です。DBは巻き戻す仕組みを提供しますが、**どこで区切るかは決めてくれません。**

この区切りを**トランザクション境界**と呼びます。基準はいまの時点では1つだけ：

> **業務として「一緒に無かったことにしたい」範囲を、1つの塊にする。**

送金なら「引く」と「足す」で1つ。注文なら「在庫を引く／注文を作る／明細を作る」で1つ。

**大きすぎても困るのですが、その理由はロックを見ないと分かりません** → 15-2 §6。この章では「小さすぎると壊れる」だけ押さえてください。

### 3-2. 一貫性（C）：制約はいつ検査されるか

**`COMMIT` 時ではなく、その文の直後**に検査されます（破ればその場でエラー → 中断状態）。

> [!note]- 例外：`DEFERRABLE` 制約
> `DEFERRABLE INITIALLY DEFERRED` を付けると `COMMIT` 直前まで検査を遅らせられます。相互参照するテーブルへ同時に挿入する場合などに使います。**そういう逃げ道があるとだけ知っておけば十分です。**

**どこまで制約にして、どこからアプリで守るか。**「在庫はマイナスにしない」は `CHECK (stock_quantity >= 0)` で書けます。

| | 利点 | 欠点 |
| :--- | :--- | :--- |
| **制約で守る** | どの経路からでも破れない | エラーが業務用語にならない。**アプリと二重管理**になる |
| **アプリで守る** | 業務エラーとして扱える | **その経路を通らない更新は素通り** |

**よく取られるのは「アプリで判断し、制約は最後の砦として置く」**という役割分担です。
ただし**複数の行やテーブルにまたがるルール**（「未発送注文は5件まで」等）は制約では書けません。これはアプリの仕事です。

### 3-3. 永続性（D）：WAL

`COMMIT` のとき PostgreSQL は**テーブル本体の書き換えを待たず**、変更内容の記録（**WAL**）だけディスクに書いて成功を返します。落ちても再起動時に WAL から復元されます。**ログ1本で済むので `COMMIT` が速い**、というのが狙いです。

> 🐘 「先にログを書く」という考え方はどのDBも同じ（Oracle の REDO、MySQL の redo log）。**`WAL` という呼び名が PostgreSQL 固有**です。
> インデックスとの関係は [[17-1_導入_物理構造とスキャン方式|17-1]] §8。

## 4. SAVEPOINT：一部だけ取り消す

`ROLLBACK` は全体を巻き戻します。**「ここまでは活かして、この処理だけ取り消したい」**ときに使います。

| コマンド | 意味 |
| :--- | :--- |
| `SAVEPOINT 名前` | 目印を置く |
| `ROLLBACK TO SAVEPOINT 名前` | 目印まで戻る（**トランザクションは終わらない**） |
| `RELEASE SAVEPOINT 名前` | 目印を捨てる（処理は活きたまま） |

```sql
BEGIN;
UPDATE products SET price = 1500 WHERE product_id = 1;  -- 活かしたい
SAVEPOINT before_risky;
UPDATE products SET price = 0 WHERE product_id = 2;     -- やめたい
ROLLBACK TO SAVEPOINT before_risky;
COMMIT;
```

```
 product_id |  price
------------+---------
          1 | 1500.00   ← 残る
          2 |  800.00   ← 巻き戻った
```

### 注意と、実務での立ち位置

- **1トランザクション内で64個を超えると性能が落ちます。** ループで1件ごとに置かないこと
- **PL/pgSQL の `BEGIN ... EXCEPTION` は裏でセーブポイントを作っています**（→ [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]]）

**自分でコードに書くことは、ほとんどありません。** 一番よく出会うのは上の PL/pgSQL の暗黙のものです。

**そして用途を誤解しやすいので1点だけ：**

| | やること | 他のセッションから見ると |
| :--- | :--- | :--- |
| `COMMIT` を刻む | トランザクションを**終わらせて**次を始める | **確定が見える。ロックも外れる** |
| `SAVEPOINT` で戻る | トランザクションは**続いたまま**一部だけ取消 | **何も見えない。ロックも握ったまま** |

**`SAVEPOINT` はトランザクションを短くしません。** 「部分的な失敗を許容する」道具です。バッチで「1件失敗しても続行」なら、本命は `COMMIT` を刻むほうです。

## 5. `BEGIN` の入れ子はできない

2回目の `BEGIN` は `WARNING` を出すだけで**黙って無視**されます（`ERROR` ではないので気づきにくい）。

```
BEGIN
WARNING:  there is already a transaction in progress
BEGIN
```

**入れ子のつもりで書くと、内側の `ROLLBACK` が最初の `BEGIN` まで全部巻き戻します。** 区切りたいときは `SAVEPOINT` を使ってください。これが `SAVEPOINT` が存在する理由です。

> フレームワークの「ネストしたトランザクション」（Spring の `REQUIRES_NEW` など）の正体は、**セーブポイント**か**別コネクション**のどちらかです。DBに入れ子の機能があるわけではありません。

---

## まとめ

- **複数のSQLをセットで扱いたいときに書く。** 1文なら自動コミットが面倒を見ている
- **`COMMIT` するまで確定しない。** 切断されたら自動 `ROLLBACK`
- **ACID のうち開発者が毎回判断するのは A だけ。** 基準は「業務として一緒に取り消したい範囲」
- **一部だけ戻すなら `SAVEPOINT`。ただしトランザクションは短くならない。`BEGIN` の入れ子は不可**
- 🐘 **PostgreSQL 固有はこれ**：**エラーが出るとトランザクション全体が中断状態になる**
