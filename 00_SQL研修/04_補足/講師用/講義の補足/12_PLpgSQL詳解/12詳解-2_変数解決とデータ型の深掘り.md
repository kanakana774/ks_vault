# 変数解決とデータ型の深掘り

## 〜名前はいつ「変数」になり、値はいつ型を変えるのか〜

講義版 [[12-1_PLpgSQLの基礎とDOブロック|12-1]] §5 では「変数名と列名が衝突すると `ambiguous` で止まる。だから `v_` / `p_` を付ける」という結論だけを出しました。**なぜ PostgreSQL がそう振る舞うのか、規約以外にどんな解き方があるのか、そしてその解き方をなぜ採らなかったのか**を、この資料で埋めます。

後半は代入の型変換です。**PL/pgSQL の代入は `::` のキャストと同じではありません。** ここは「`CAST` なら通るのに代入だと落ちる」という形で顕在化するので、実測で示します。あわせて、講義版では扱っていない `RECORD` / `CREATE TYPE` / 配列 / JSONB を、**なぜ講義から外したか**を添えて整理します。

> **この資料の前提**
> - PostgreSQL 17.5 で動作確認しています。掲載しているエラーメッセージ・出力は**すべて実測**です。
> - **これは講師用の資料です。研修生には配りません。**
> - 対応する講義版: [[12-1_PLpgSQLの基礎とDOブロック|12-1]] §4・§5・§6 ／ [[12-2_変数とSQLの実行|12-2]] §6・§7
> - 使用するテーブルは [[00_SQL研修/02_問題/08_結合から使用するテーブル|08_結合から使用するテーブル]] のものです。一部の実験だけ使い捨ての表と型を作ります。

## 1. 変数と列名の解決規則

### 1-1. 誰が解決しているのか

PL/pgSQL は本体の SQL 文をサーバに渡すとき、**その中に現れる識別子のうち「自分が知っている変数名」をパラメータ（`$1`, `$2`, …）に置き換えます。** 置き換えの候補になるのは、その位置から見えているすべての変数・引数です。

`WHERE customer_id = customer_id` と書いたとき、両辺が置き換え候補になり得ます。だから PostgreSQL には次の 3 通りの読み方があります。

1. 列 `=` 変数（書いた人の意図）
2. 変数 `=` 変数（常に真）
3. 列 `=` 列（NULL でなければ常に真）

**どれを選ぶかを決める設定が `#variable_conflict` です。既定は `error`（決めずにエラーにする）。**

### 1-2. 実測：3 値の違いを見分ける

「両辺が同じ名前」の形では `use_variable` と `use_column` の違いが見えにくいので、**ぶつかっている名前を `SELECT` の出力側に書く**形で測ります。変数 `customer_id` の値は 1、`WHERE` で選ぶ行の列の値は 5 です。

**① `use_variable`（変数を優先）**

```sql
DO $$
#variable_conflict use_variable
DECLARE
    customer_id integer := 1;
    v_got       integer;
BEGIN
    SELECT customer_id INTO v_got FROM customers WHERE customers.customer_id = 5;
    RAISE NOTICE 'SELECT customer_id が返した値 = %', v_got;
END;
$$;
```

```
NOTICE:  SELECT customer_id が返した値 = 1
DO
```

**② `use_column`（列を優先）** — 指示子の行だけ差し替えます。

```sql
DO $$
#variable_conflict use_column
DECLARE
    customer_id integer := 1;
    v_got       integer;
BEGIN
    SELECT customer_id INTO v_got FROM customers WHERE customers.customer_id = 5;
    RAISE NOTICE 'SELECT customer_id が返した値 = %', v_got;
END;
$$;
```

```
NOTICE:  SELECT customer_id が返した値 = 5
DO
```

**③ 既定（指示子の行を書かない）**

```sql
DO $$
DECLARE
    customer_id integer := 1;
    v_got       integer;
BEGIN
    SELECT customer_id INTO v_got FROM customers WHERE customers.customer_id = 5;
    RAISE NOTICE 'SELECT customer_id が返した値 = %', v_got;
END;
$$;
```

```
ERROR:  column reference "customer_id" is ambiguous
DETAIL:  It could refer to either a PL/pgSQL variable or a table column.
QUERY:  SELECT customer_id            FROM customers WHERE customers.customer_id = 5
CONTEXT:  PL/pgSQL function inline_code_block line 7 at SQL statement
```

**同じ 1 行の SQL が、指示子だけで 1 を返すか 5 を返すかが変わります。**

| 指示子 | 衝突したとき |
|:---|:---|
| `#variable_conflict error` | エラーにする（**既定**） |
| `#variable_conflict use_variable` | PL/pgSQL の変数を優先 |
| `#variable_conflict use_column` | テーブルの列を優先 |

### 1-3. なぜ講義版でこれを教えないのか

実測が示すとおり、**指示子 1 行の有無で SQL の意味が変わります。** そのコードを読む人が指示子を見落とすと、意味を取り違えます。しかも指示子は**関数の先頭**にあり、問題の SQL は何十行も下にあります。

- `use_variable` を選ぶと、うっかり列と同名の変数を作った瞬間に、その列を参照するすべての SQL が黙って壊れます（エラーにならない）。
- `use_column` はさらに危険で、変数の値を渡したつもりの `WHERE` が「列 = 列」になり、**全行が対象になります**。`UPDATE` でこれをやると全行更新です。

**「名前をぶつけない」という規約は、読む人に何も要求しません。** 講義版が `v_` / `p_` を採用したのはこの理由です（[[12-1_PLpgSQLの基礎とDOブロック|12-1]] §5-2 の 💡 に書いた「設定でごまかすと読む人が設定を知らないと意味を取り違える」の中身がこれです）。

研修生に `#variable_conflict` の存在を聞かれたら、**「既存のコードを読むときに必要な知識であって、新しく書くときに使う道具ではない」**と答えてください。

### 1-4. 実測：指示子を書ける場所は決まっている

```sql
DO $$
DECLARE
    customer_id integer := 1;
#variable_conflict use_variable
BEGIN
    RAISE NOTICE 'ok';
END;
$$;
```

```
ERROR:  syntax error at or near "#"
LINE 4: #variable_conflict use_variable
        ^
```

**`DECLARE` の途中には書けません。** 関数（またはブロック）の本文の**先頭**、`DECLARE` の前に置きます。

### 1-5. 実測：綴りを間違えると `CREATE` 時に落ちる

```sql
DO $$
#variable_conflict use_varaible
BEGIN
    RAISE NOTICE 'ok';
END;
$$;
```

```
ERROR:  syntax error at or near "use_varaible"
LINE 2: #variable_conflict use_varaible
                           ^
```

指示子は文法の一部なので、綴り間違いは黙って無視されず構文エラーになります。**これは救いです**（黙って `error` のまま動くと、指示子を書いたつもりの人が混乱します）。

## 2. 引数名と列名の衝突

### 2-1. 実測：引数も同じ規則で衝突する

```sql
CREATE OR REPLACE FUNCTION t_conf(customer_id integer) RETURNS text
LANGUAGE plpgsql AS $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO v_name FROM customers WHERE customer_id = customer_id;
    RETURN v_name;
END;
$$;
SELECT t_conf(1);
```

```
CREATE FUNCTION
ERROR:  column reference "customer_id" is ambiguous
LINE 1: SELECT name             FROM customers WHERE customer_id = c...
                                                     ^
DETAIL:  It could refer to either a PL/pgSQL variable or a table column.
QUERY:  SELECT name             FROM customers WHERE customer_id = customer_id
CONTEXT:  PL/pgSQL function t_conf(integer) line 5 at SQL statement
```

**`CREATE` は通り、実行時に落ちます**（[[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §1 のとおり）。

### 2-2. 【よくある誤解】実測：`$1` に書き換えても直らない

「引数は `$1` で参照すれば衝突しない」という説明を見かけますが、**それだけでは直りません。**

```sql
CREATE OR REPLACE FUNCTION t_conf2(customer_id integer) RETURNS text
LANGUAGE plpgsql AS $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO v_name FROM customers WHERE customer_id = $1;
    RETURN v_name;
END;
$$;
SELECT t_conf2(1);
```

```
ERROR:  column reference "customer_id" is ambiguous
LINE 1: SELECT name             FROM customers WHERE customer_id = $...
                                                     ^
DETAIL:  It could refer to either a PL/pgSQL variable or a table column.
QUERY:  SELECT name             FROM customers WHERE customer_id = $1
CONTEXT:  PL/pgSQL function t_conf2(integer) line 5 at SQL statement
```

**エラーメッセージが指しているのは右辺ではなく左辺です。** `$1` にしたのは「引数を指す側」だけで、`WHERE` の左に書いた `customer_id`（列を指すつもり）は依然として「変数か列か」が決まりません。**衝突は名前が 1 か所でも残っていれば起きます。**

### 2-3. 実測：直し方は 3 つ

```sql
-- ① 列を修飾する（+ $1）
CREATE OR REPLACE FUNCTION t_conf4(customer_id integer) RETURNS text
LANGUAGE plpgsql AS $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO v_name FROM customers WHERE customers.customer_id = $1;
    RETURN v_name;
END;
$$;
SELECT t_conf4(1) AS "列を修飾 + $1";

-- ② 引数を関数名で修飾する
CREATE OR REPLACE FUNCTION t_conf3(customer_id integer) RETURNS text
LANGUAGE plpgsql AS $$
DECLARE
    v_name text;
BEGIN
    SELECT name INTO v_name FROM customers WHERE customers.customer_id = t_conf3.customer_id;
    RETURN v_name;
END;
$$;
SELECT t_conf3(1);
```

```
 列を修飾 + $1 
---------------
 Alice
(1 row)

 t_conf3 
---------
 Alice
(1 row)
```

**②の `t_conf3.customer_id` は「関数名をラベルとして使う」書き方です。** ブロックラベルと同じ仕組みで、PL/pgSQL は関数本体の最外ブロックに関数名のラベルを暗黙に付けています。

③ **そもそも `p_customer_id` にする。** これが講義版の答えで、①②のどちらも読み手に「なぜこう書いてあるか」の説明を要求します。

> ⚠️ **既存コードの修理では①②が必要になります。**
> 「引数名を変えたいが、呼び出し側が名前付き引数（`t_conf(customer_id => 1)`）で呼んでいるので変えられない」という状況は実務であります。そのときは①で列を修飾するのがいちばん安全です。

## 3. 代入は「キャスト」ではない

### 3-1. 規則（公式ドキュメント）

PostgreSQL 17 のドキュメント（`plpgsql-statements`）は代入の型変換をこう定義しています。

> If the expression's result data type doesn't match the variable's data type, the value will be coerced as though by an **assignment cast**. If no assignment cast is known for the pair of data types involved, the PL/pgSQL interpreter will attempt to convert the result value **textually, that is by applying the result type's output function followed by the variable type's input function**. Note that this could result in run-time errors generated by the input function, if the string form of the result value is not acceptable to the input function.

つまり順番は 2 段です。

1. **代入キャスト（assignment cast）があればそれを使う**
2. なければ**「出力関数でテキストにして、入力関数で読み直す」**（I/O 変換）

**明示キャスト（`CAST(x AS t)` / `x::t`）は 1 の候補に入りません。** ここが分かれ目です。

### 3-2. 実測：`CAST` は通るのに代入は落ちる

`boolean` → `integer` は PostgreSQL に**明示キャストとしては存在します**が、代入キャストではありません。

```sql
SELECT CAST(true AS integer) AS "CAST(true AS integer)";

DO $$
DECLARE
    v_n integer;
BEGIN
    v_n := true;
    RAISE NOTICE 'v_n = %', v_n;
END;
$$;
```

```
 CAST(true AS integer) 
-----------------------
                     1
(1 row)

ERROR:  invalid input syntax for type integer: "t"
CONTEXT:  PL/pgSQL assignment "v_n := true"
PL/pgSQL function inline_code_block line 5 at assignment
```

**`CAST` は 1 を返すのに、代入は落ちます。しかもエラーメッセージが `"t"` です。**

これが §3-1 の 2 段目の証拠です。代入キャストが見つからなかったので、`true` を `boolean` の出力関数でテキストにして `'t'` を得て、それを `integer` の入力関数に渡した——だから「`t` は integer として読めない」というエラーになりました。**もしキャストが使われていたら 1 になっていたはずです。**

### 3-3. 実測：数値は丸められる（切り捨てではない）

`numeric` → `integer` には代入キャストがあります。

```sql
DO $$
DECLARE
    v_a integer;
    v_b integer;
BEGIN
    v_a := 3.7;
    v_b := 2.5;
    RAISE NOTICE '3.7 -> %  /  2.5 -> %', v_a, v_b;
END;
$$;
```

```
NOTICE:  3.7 -> 4  /  2.5 -> 3
```

**四捨五入されます。切り捨てではありません。** 「金額を integer 変数で受けたら 1 円多かった」の原因はこれです。切り捨てたいなら `trunc()` / `floor()` を明示します。

### 3-4. 実測：文字列は入力関数を通る

```sql
DO $$
DECLARE
    v_n integer;
BEGIN
    v_n := '  42  ';
    RAISE NOTICE 'v_n = %', v_n;
END;
$$;
```

```
NOTICE:  v_n = 42
```

```sql
DO $$
DECLARE
    v_n integer;
BEGIN
    v_n := '42abc';
END;
$$;
```

```
ERROR:  invalid input syntax for type integer: "42abc"
LINE 1: v_n := '42abc'
               ^
QUERY:  v_n := '42abc'
CONTEXT:  PL/pgSQL function inline_code_block line 5 at assignment
```

```sql
DO $$
DECLARE
    v_d date;
BEGIN
    v_d := 'きょう';
END;
$$;
```

```
ERROR:  invalid input syntax for type date: "きょう"
LINE 1: v_d := 'きょう'
               ^
QUERY:  v_d := 'きょう'
CONTEXT:  PL/pgSQL function inline_code_block line 5 at assignment
```

**前後の空白は `integer` の入力関数が許すので通ります。** 「アプリから来た文字列を変数に代入したら、値によって落ちる」という不安定なバグはここから出ます。**外部由来の文字列を代入するときは、代入に任せず自分で検証するか、明示的に `::type` を書いて意図を残してください。**

### 3-5. `CONTEXT` の読み方

上の実測で `CONTEXT` が `at assignment` になっている点に注目してください。SQL 文の中で起きたエラーは `at SQL statement`、代入で起きたエラーは `at assignment` です。**`CONTEXT` の末尾を見れば「PL/pgSQL のどの種類の文で落ちたか」が分かります。** デバッグのときは行番号より先にここを見ると早いです。

## 4. `CONSTANT` / `NOT NULL` / `DEFAULT`

### 4-1. 実測：4 つの挙動

```sql
-- ① CONSTANT に代入する
DO $$
DECLARE
    v_rate CONSTANT numeric := 0.10;
BEGIN
    v_rate := 0.15;
END;
$$;

-- ② NOT NULL に NULL を代入する
DO $$
DECLARE
    v_id integer NOT NULL := 100;
BEGIN
    v_id := NULL;
END;
$$;

-- ③ NOT NULL に既定値を書かない
DO $$
DECLARE
    v_id integer NOT NULL;
BEGIN
    RAISE NOTICE '%', v_id;
END;
$$;

-- ④ NOT NULL 変数に、NULL を返すクエリを INTO する
--    customers.customer_id = 3（Charlie）は membership_id が NULL
DO $$
DECLARE
    v_id integer NOT NULL := 0;
BEGIN
    SELECT membership_id INTO v_id FROM customers WHERE customer_id = 3;
    RAISE NOTICE '%', v_id;
END;
$$;
```

```
ERROR:  variable "v_rate" is declared CONSTANT
LINE 5:     v_rate := 0.15;
            ^
ERROR:  null value cannot be assigned to variable "v_id" declared NOT NULL
CONTEXT:  PL/pgSQL function inline_code_block line 5 at assignment
ERROR:  variable "v_id" must have a default value, since it's declared NOT NULL
LINE 3:     v_id integer NOT NULL;
                         ^
ERROR:  null value cannot be assigned to variable "v_id" declared NOT NULL
CONTEXT:  PL/pgSQL function inline_code_block line 5 at SQL statement
```

読み取れること。

- **①③は `CREATE`（コンパイル）時に落ちます。** 行番号が `LINE` として出ています。
- **②④は実行時**です。`CONTEXT` が付いています。
- **④が実務で効きます。** 講義版 [[12-2_変数とSQLの実行|12-2]] §2-1 で「0 件だと NULL が入って、遠くで症状が出る」と説明した問題を、**`NOT NULL` 宣言だけでその場で止められます。** `STRICT` は「1 件でなければエラー」ですが、`NOT NULL` は「NULL が入ったらエラー」なので、`LEFT JOIN` の結果が NULL だった場合も捕まえられます。

### 4-2. 実測：`DEFAULT` はブロックに入るたびに評価される

```sql
DO $$
DECLARE
    i integer;
BEGIN
    FOR i IN 1..3 LOOP
        DECLARE
            v_t timestamptz := clock_timestamp();
        BEGIN
            RAISE NOTICE '% 回目: %', i, v_t;
        END;
        PERFORM pg_sleep(0.01);
    END LOOP;
END;
$$;
```

```
NOTICE:  1 回目: 2026-08-12 15:08:43.899456+09
NOTICE:  2 回目: 2026-08-12 15:08:43.914839+09
NOTICE:  3 回目: 2026-08-12 15:08:43.930835+09
```

**値が毎回変わっています。** 初期値式は「関数が最初に呼ばれたとき 1 回」ではなく「そのブロックに入るたび」に評価されます。ドキュメントも明記しています。

> A variable's default value is evaluated and assigned to the variable **each time the block is entered** (not just once per function call).

### 4-3. 【検証】代入に `=` は使えるか。「9.4 以降で許容」は正しいか

旧版の教材には「値の代入には `:=` を使用します（PostgreSQL 9.4 以降は `=` も許容されています）」という記述があります。**このバージョン条件は裏付けがありません。** 検証結果を順に示します。

**(a) `=` が動くことは実測できました。**

```sql
DO $$
DECLARE
    v_n integer := 0;
BEGIN
    v_n = 5;                 -- 代入
    RAISE NOTICE 'v_n = %', v_n;
    IF v_n = 5 THEN          -- こちらは比較
        RAISE NOTICE '比較の = も同じ綴り';
    END IF;
END;
$$;
```

```
NOTICE:  v_n = 5
NOTICE:  比較の = も同じ綴り
```

宣言部でも 3 通りすべてが通ります。

```sql
DO $$
DECLARE
    v_a text DEFAULT 'D';
    v_b text := 'C';
    v_c text = 'E';
BEGIN
    RAISE NOTICE 'DEFAULT=% := =% = =%', v_a, v_b, v_c;
END;
$$;
```

```
NOTICE:  DEFAULT=D := =C = =E
```

**(b) PostgreSQL 17 のドキュメントは、バージョン条件を付けずに両方を併記しています。**

> _variable_ { := | = } _expression_;
> Equal (`=`) can be used instead of PL/SQL-compliant `:=`.

**(c) 「9.4 以降」という条件の出どころは、機能追加ではなく文書化のタイミングです。**

- PostgreSQL 9.3 のドキュメントは代入構文を `variable := expression;` としか書いておらず、`=` に言及していません。
- PostgreSQL 9.4 のドキュメントには `variable { := | = } expression;` と上記の一文があります。
- しかし **PostgreSQL 9.4 のリリースノートに「`=` を代入に使えるようにした」という項目はありません**（9.4 の PL/pgSQL 項目は `GET DIAGNOSTICS` のコールスタック取得、`print_strict_params`、`plpgsql.extra_warnings` / `extra_errors` の 3 つ）。
- 2012〜2013 年のメーリングリストには、9.3 以前でも `=` が動くことを前提にした「どこに文書化されているのか」という質問が残っています。

**結論：`=` は 9.4 より前から動いており、9.4 で「文書化された」だけです。したがって「9.4 以降で許容」という書き方は誤りです。** 詳解版でも「公式ドキュメントは `:=` と `=` を併記している」に留め、バージョン条件は書かないでください。（何番目のバージョンで受理されるようになったかは特定できていません＝**未確認**。）

**そのうえで、`=` は使わないでください。** 理由は上の (a) の実測がそのまま示しています。**同じ 1 つのブロックの中に、代入の `=` と比較の `=` が同じ綴りで並びます。** `:=` にしておけば、どちらであるかが見た瞬間に分かります。講義版が `:=` だけを教えるのはこの理由です。

## 5. `RECORD` / `%ROWTYPE` / `CREATE TYPE`

講義版 [[12-2_変数とSQLの実行|12-2]] §7 では「`RECORD` は代入されるまで構造が決まらない」と書きました。**その「決まらない」が具体的に何を意味するか**を実測します。

### 5-1. 実測：`RECORD` は代入前は触れない／代入ごとに構造が変わる

```sql
DO $$
DECLARE
    r_x RECORD;
BEGIN
    RAISE NOTICE '%', r_x.anything;
END;
$$;
```

```
ERROR:  record "r_x" is not assigned yet
DETAIL:  The tuple structure of a not-yet-assigned record is indeterminate.
CONTEXT:  SQL expression "r_x.anything"
PL/pgSQL function inline_code_block line 5 at RAISE
```

```sql
DO $$
DECLARE
    r_x RECORD;
BEGIN
    SELECT 1 AS a, 'x' AS b INTO r_x;
    RAISE NOTICE '1回目: a=% b=%', r_x.a, r_x.b;

    SELECT 2 AS c INTO r_x;
    RAISE NOTICE '2回目: c=%', r_x.c;
    RAISE NOTICE 'では a は? %', r_x.a;
END;
$$;
```

```
NOTICE:  1回目: a=1 b=x
NOTICE:  2回目: c=2
ERROR:  record "r_x" has no field "a"
CONTEXT:  SQL expression "r_x.a"
PL/pgSQL function inline_code_block line 10 at RAISE
```

**同じ変数が、代入のたびにフィールドの集合を丸ごと入れ替えています。** これが「実行時に構造が決まる」の中身です。つまり `r_x.a` というコードが正しいかどうかは、**そこに至るまでに何が代入されたかに依存します**——静的には決められません。

### 5-2. 実測：`%ROWTYPE` は宣言した時点で構造を持つ

```sql
DO $$
DECLARE
    r_p products%ROWTYPE;
BEGIN
    RAISE NOTICE 'product_id = % / NULL か = %', r_p.product_id, (r_p.product_id IS NULL);
    RAISE NOTICE '%', r_p.no_such_column;
END;
$$;
```

```
NOTICE:  product_id = <NULL> / NULL か = t
ERROR:  record "r_p" has no field "no_such_column"
CONTEXT:  SQL expression "r_p.no_such_column"
PL/pgSQL function inline_code_block line 7 at RAISE
```

**代入していなくても `r_p.product_id` は触れて NULL を返します。** これが `RECORD` との実質的な違いです。ただし**存在しない列を書いても `CREATE` 時には検出されません**（[[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §3）。「構造を持っている」ことと「静的に検査される」ことは別です。

### 5-3. 実測：複合型変数の `IS NULL` は罠

```sql
DO $$
DECLARE
    r_p products%ROWTYPE;
    r_r RECORD;
BEGIN
    RAISE NOTICE 'r_p IS NULL = %', (r_p IS NULL);
    SELECT * INTO r_p FROM products WHERE product_id = 999;
    RAISE NOTICE '0件を INTO した後: r_p IS NULL = %', (r_p IS NULL);
    SELECT * INTO r_r FROM products WHERE product_id = 999;
    RAISE NOTICE '0件を INTO した RECORD: r_r IS NULL = %', (r_r IS NULL);
END;
$$;
```

```
NOTICE:  r_p IS NULL = t
NOTICE:  0件を INTO した後: r_p IS NULL = t
NOTICE:  0件を INTO した RECORD: r_r IS NULL = t
```

**「宣言直後」と「0 件を `INTO` した後」が区別できません。** 行構成型の `IS NULL` は「すべてのフィールドが NULL なら真」なので、この 2 つは同じ結果になります。**「取れたかどうか」を `IS NULL` で判定してはいけません。** `FOUND` を使ってください（[[12-2_変数とSQLの実行|12-2]] §3）。

### 5-4. 実測：`CREATE TYPE` の複合型

```sql
CREATE TYPE product_summary AS (
    label      text,
    is_premium boolean
);

DO $$
DECLARE
    v_s product_summary;
BEGIN
    v_s := ROW('Laptop', true);
    RAISE NOTICE 'label=% is_premium=%', v_s.label, v_s.is_premium;
    v_s.label := 'Laptop（改）';
    RAISE NOTICE 'フィールド単位の代入: %', v_s.label;
    v_s := ROW('a', 'b', 'c');
END;
$$;

SELECT (ROW('Laptop', true)::product_summary).label;
```

```
NOTICE:  label=Laptop is_premium=t
NOTICE:  フィールド単位の代入: Laptop（改）
ERROR:  invalid input syntax for type boolean: "b"
CONTEXT:  PL/pgSQL function inline_code_block line 10 at assignment

 label  
--------
 Laptop
(1 row)
```

`ROW('a','b','c')` は 3 番目の要素が余りますが、**フィールド数の不一致はエラーになりません。** 落ちたのは 2 番目の `'b'` を `boolean` に変換できなかったためです（§3 の I/O 変換）。実測で確認しました。

```sql
DO $$
DECLARE
    v_s product_summary;
BEGIN
    v_s := ROW('a', true, 'c');     -- 多い
    RAISE NOTICE 'label=% is_premium=%', v_s.label, v_s.is_premium;
END;
$$;
DO $$
DECLARE
    v_s product_summary;
BEGIN
    v_s := ROW('a');                -- 少ない
    RAISE NOTICE 'label=% is_premium=%', v_s.label, v_s.is_premium;
END;
$$;
```

```
NOTICE:  label=a is_premium=t
NOTICE:  label=a is_premium=<NULL>
```

**多い分は捨てられ、足りない分は NULL になります。どちらも警告なしです。** `CREATE TYPE` の複合型に `ROW(...)` で値を詰めるのは、この点で危険です。

### 5-5. 使い分け

| | 構造が決まるとき | 触れる列 | 使う場面 |
|:---|:---|:---|:---|
| `%ROWTYPE` | 宣言時（表の定義から） | 表の全列 | 1 つの表の行をそのまま扱う |
| `RECORD` | 代入時（毎回変わる） | 直前に代入したクエリの列 | JOIN 結果・必要な列だけの結果・ループ変数 |
| `CREATE TYPE` の複合型 | 型の定義時 | 型に書いた列 | 複数の関数で共有する戻り値の形 |

**`CREATE TYPE` を講義版から外した理由**は 2 つです。(1) `RETURNS TABLE` があれば「表を返す」用途は満たせる（講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §1-3）。(2) **型は DB オブジェクトなので、作ったら片付けの対象が増えます。** 研修の 1 回の講義で作って消すものを増やしたくありませんでした。

## 6. 表構造を変えたときの `%ROWTYPE`

### 6-1. 実測：`SELECT *` なら追従する／列を明示すると追従しない

```sql
CREATE TABLE demo_alt (id integer, a text);
INSERT INTO demo_alt VALUES (1, 'A');

CREATE OR REPLACE FUNCTION f_alt() RETURNS text
LANGUAGE plpgsql AS $$
DECLARE
    r_row demo_alt%ROWTYPE;
BEGIN
    SELECT * INTO r_row FROM demo_alt WHERE id = 1;
    RETURN format('列数の内訳: id=%s a=%s', r_row.id, r_row.a);
END;
$$;
SELECT f_alt();
ALTER TABLE demo_alt ADD COLUMN b text DEFAULT 'B';
SELECT f_alt();                     -- 同じセッションで

-- 列を明示している版
CREATE OR REPLACE FUNCTION f_alt2() RETURNS text
LANGUAGE plpgsql AS $$
DECLARE
    r_row demo_alt%ROWTYPE;
BEGIN
    SELECT id, a INTO r_row FROM demo_alt WHERE id = 1;
    RETURN format('id=%s a=%s b=%s', r_row.id, r_row.a, r_row.b);
END;
$$;
SELECT f_alt2();
```

```
        f_alt         
----------------------
 列数の内訳: id=1 a=A
(1 row)

ALTER TABLE
--- 列を足した後、同じセッションで ---
        f_alt         
----------------------
 列数の内訳: id=1 a=A
(1 row)

   f_alt2    
-------------
 id=1 a=A b=
(1 row)
```

- **`SELECT *` 版**：列が 2 → 3 に増えても落ちません。`%ROWTYPE` の構造も `SELECT *` の列も同時に 3 列になったので整合しています。
- **列を明示した版**：`SELECT id, a INTO r_row` は 2 列しか埋めないのに、`r_row` は 3 フィールドあります。**`b` は NULL のまま**で、エラーにも警告にもなりません（`plpgsql.extra_warnings = 'strict_multi_assignment'` を入れれば警告できます → [[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §6-3）。

### 6-2. 実務での含意

- **`%ROWTYPE` 変数には `SELECT *` で入れるのが原則。** 列を数えて書くと、列が増えたときに黙って NULL のフィールドができます。
- ただし **`SELECT *` を関数の中で使うと、列が増えた分だけ無駄に読みます。** 必要な列だけ欲しいなら `%ROWTYPE` ではなく `RECORD` を使い、`SELECT id, a INTO r_row` と書くのが整合的です。**「`%ROWTYPE` + `SELECT *`」か「`RECORD` + 列の明示」の 2 択で、混ぜないこと。**
- 講義版 [[12-2_変数とSQLの実行|12-2]] §7-1 で「どちらでも書けるなら `%ROWTYPE`」と書いたのは、`SELECT *` で 1 行を丸ごと受ける前提の話です。研修生が「必要な列だけ取りたいのに `%ROWTYPE` を使う」方向に走ったら、この 2 択を示してください。

## 7. 配列

講義版には一切登場しません。**「1 文の SQL で書けるものを配列とループに置き換えると遅くなる」（[[12-3_制御構造|12-3]] §7）という原則と真正面からぶつかる**ため、配列を教えると誤用が増えると判断しました。ここでは講師が聞かれたときのために整理します。

### 7-1. 実測：添字は 1 から始まり、範囲外は NULL

```sql
DO $$
DECLARE
    v_ids integer[] := ARRAY[10, 20, 30];
BEGIN
    RAISE NOTICE 'v_ids     = %', v_ids;
    RAISE NOTICE 'v_ids[0]  = % （範囲外は NULL）', v_ids[0];
    RAISE NOTICE 'v_ids[1]  = %', v_ids[1];
    RAISE NOTICE 'v_ids[99] = % （範囲外は NULL）', v_ids[99];
    RAISE NOTICE 'array_length(v_ids, 1) = %', array_length(v_ids, 1);
    RAISE NOTICE 'cardinality(v_ids)     = %', cardinality(v_ids);
END;
$$;
```

```
NOTICE:  v_ids     = {10,20,30}
NOTICE:  v_ids[0]  = <NULL> （範囲外は NULL）
NOTICE:  v_ids[1]  = 10
NOTICE:  v_ids[99] = <NULL> （範囲外は NULL）
NOTICE:  array_length(v_ids, 1) = 3
NOTICE:  cardinality(v_ids)     = 3
```

**範囲外は例外ではなく NULL です。** 他の言語から来た人がいちばん驚くところで、**添字のずれが例外にならないので気づけません。**

### 7-2. 実測：NULL 配列と「穴」

```sql
DO $$
DECLARE
    v_a integer[];
BEGIN
    RAISE NOTICE '宣言直後: % / IS NULL = %', v_a, (v_a IS NULL);
    v_a[3] := 99;
    RAISE NOTICE '[3] に代入した後: % / length = %', v_a, array_length(v_a, 1);
    RAISE NOTICE '[1] は % （穴が空く）', v_a[1];
END;
$$;
```

```
NOTICE:  宣言直後: <NULL> / IS NULL = t
NOTICE:  [3] に代入した後: [3:3]={99} / length = 1
NOTICE:  [1] は <NULL> （穴が空く）
```

**`[3:3]={99}` という表示に注目してください。** PostgreSQL の配列は添字の下限を任意に持てるので、「3 番目だけがある長さ 1 の配列」になりました。`array_length` は 1 です。**「i 番目に代入したから長さは i」ではありません。** 空の配列から積み上げるなら `v_a := v_a || 値;`（連結）か `ARRAY[]::integer[]` からの `array_append` を使ってください。

### 7-3. 実測：`array_agg` で集めて `FOREACH` で回す

```sql
DO $$
DECLARE
    v_ids   integer[];
    v_id    integer;
    v_total numeric := 0;
BEGIN
    SELECT array_agg(product_id ORDER BY product_id) INTO v_ids
      FROM products WHERE category_id = 1;
    RAISE NOTICE 'Electronics の product_id = % （% 個）', v_ids, cardinality(v_ids);

    FOREACH v_id IN ARRAY v_ids LOOP
        v_total := v_total + (SELECT price FROM products WHERE product_id = v_id);
    END LOOP;
    RAISE NOTICE '価格合計 = %', v_total;
END;
$$;
```

```
NOTICE:  Electronics の product_id = {1,2,6,13} （4 個）
NOTICE:  価格合計 = 2450.00
```

### 7-4. 実測：`unnest` を使えばループが要らない

まったく同じ答えを、ループなしで出せます。

```sql
DO $$
DECLARE
    v_ids   integer[];
    v_total numeric;
BEGIN
    SELECT array_agg(product_id ORDER BY product_id) INTO v_ids
      FROM products WHERE category_id = 1;

    SELECT sum(p.price) INTO v_total
      FROM unnest(v_ids) AS t(id)
      JOIN products p ON p.product_id = t.id;

    RAISE NOTICE 'unnest 版の合計 = %', v_total;
END;
$$;
```

```
NOTICE:  unnest 版の合計 = 2450.00
```

`WHERE` に使うだけなら `= ANY` で済みます。

```sql
DO $$
DECLARE
    v_ids integer[] := ARRAY[1, 2, 3];
    v_n   bigint;
BEGIN
    SELECT count(*) INTO v_n FROM products WHERE product_id = ANY(v_ids);
    RAISE NOTICE '= ANY(配列) で % 件', v_n;
END;
$$;
```

```
NOTICE:  = ANY(配列) で 3 件
```

**§7-3 の `FOREACH` 版は、講義版 [[12-3_制御構造|12-3]] §7 で「やるな」と教えた N+1 そのものです。** 4 件だから目立ちませんが、1 万件なら 1 万回のクエリになります。**配列を使うなら `unnest` / `= ANY` で「集合として」渡すのが正しい使い方で、`FOREACH` で回すのは最後の手段です。**

### 7-5. 実測：多次元配列と `array_length`

```sql
DO $$
DECLARE
    v_m integer[][] := ARRAY[[1,2,3],[4,5,6]];
BEGIN
    RAISE NOTICE '% / 1次元=% 2次元=% / cardinality=%',
        v_m, array_length(v_m,1), array_length(v_m,2), cardinality(v_m);
END;
$$;
```

```
NOTICE:  {{1,2,3},{4,5,6}} / 1次元=2 2次元=3 / cardinality=6
```

**`array_length` は次元を指定する必要があり、`cardinality` は全要素数を返します。** 1 次元配列では両者が一致するので違いが見えませんが、多次元では別物です。

## 8. JSONB

### 8-1. なぜ講義から外したか

**JSONB は「12章の話ではない」からです。** 12章の目的は「SQL では書けない手順を PL/pgSQL で書けるようになること」で、JSONB は**データ型と関数の話**です。教えるなら 01章（データ型）の延長に置くべきで、PL/pgSQL の文法を学んでいる最中に差し込むと、`->` と `->>` の区別という別種の混乱を持ち込みます。

加えて実務上の懸念があります。**JSONB は「とりあえず何でも入る」ので、正規化を学ぶ前の研修生に渡すと設計を壊す道具になります。** 「列を増やすのが面倒だから JSONB に入れる」という選択を、6〜11章で正規化と制約を学んだ直後に覚えさせたくありません。

したがって研修生に聞かれたら「12章では扱わない。使う必要が出たときに調べれば足りる」と答えるのが方針です。以下は講師用の最低限の整理です。

### 8-2. 実測：組み立てる

```sql
DO $$
DECLARE
    v_doc jsonb;
BEGIN
    SELECT jsonb_build_object(
               'product_id',   p.product_id,
               'product_name', p.product_name,
               'price',        p.price,
               'stocks',       (SELECT jsonb_agg(jsonb_build_object(
                                          'warehouse_id', i.warehouse_id,
                                          'qty',          i.stock_quantity)
                                       ORDER BY i.warehouse_id)
                                  FROM inventory i
                                 WHERE i.product_id = p.product_id))
      INTO v_doc
      FROM products p
     WHERE p.product_id = 1;

    RAISE NOTICE E'\n%', jsonb_pretty(v_doc);
END;
$$;
```

```
NOTICE:  
{
    "price": 1200.00,
    "stocks": [
        {
            "qty": 50,
            "warehouse_id": 1
        },
        {
            "qty": 10,
            "warehouse_id": 2
        }
    ],
    "product_id": 1,
    "product_name": "Laptop"
}
```

> ⚠️ **キーの順番が書いた順と違うことに注目してください。**
> `jsonb` はキーを内部形式で保持するので、**入力の順序を保存しません**（`json` 型は保存します）。「JSON の文字列を比較してテストする」ようなことをすると壊れます。

### 8-3. 実測：取り出す

```sql
DO $$
DECLARE
    v_doc jsonb := '{"a": {"b": 10}, "list": [1,2,3]}';
BEGIN
    RAISE NOTICE '-> は jsonb を返す:  % （型は jsonb）', v_doc -> 'a';
    RAISE NOTICE '->> は text を返す:  %', v_doc -> 'a' ->> 'b';
    RAISE NOTICE '配列の添字は 0 から: %', v_doc -> 'list' -> 0;
    RAISE NOTICE 'キーの存在 ?:        % / %', (v_doc ? 'a'), (v_doc ? 'zzz');
    RAISE NOTICE '#>> でパス指定:      %', v_doc #>> ARRAY['a','b'];
END;
$$;
```

```
NOTICE:  -> は jsonb を返す:  {"b": 10} （型は jsonb）
NOTICE:  ->> は text を返す:  10
NOTICE:  配列の添字は 0 から: 1
NOTICE:  キーの存在 ?:        t / f
NOTICE:  #>> でパス指定:      10
```

**JSON の配列は添字が 0 から始まります。§7-1 で見た PostgreSQL の配列は 1 から始まります。** 同じ関数の中で両方を扱うと必ず間違えるので、講師としてここは強調しておいてください。

| 演算子 | 返る型 | 意味 |
|:---|:---|:---|
| `->` | `jsonb` | キー／添字で 1 段取り出す（連結できる） |
| `->>` | `text` | キー／添字で取り出してテキストにする（終端） |
| `#>` / `#>>` | `jsonb` / `text` | パス（配列）で一気に取り出す |
| `?` | `boolean` | キーが存在するか |

### 8-4. 実測：`->>` の結果は `text` なので比較に注意

```sql
DO $$
DECLARE
    v_doc jsonb := '{"price": 100}';
BEGIN
    IF (v_doc ->> 'price')::numeric > 50 THEN
        RAISE NOTICE 'キャストすれば数値比較できる';
    END IF;
    RAISE NOTICE 'text のまま比較すると辞書順: % ', ((v_doc ->> 'price') > '50');
END;
$$;
```

```
NOTICE:  キャストすれば数値比較できる
NOTICE:  text のまま比較すると辞書順: f 
```

**`'100' > '50'` が偽になっています。** 辞書順では `'1' < '5'` なので当然ですが、エラーは出ません。**`->>` を数値として使うなら必ず明示キャストを書く**——これは実務で本当に踏まれるバグです。

### 8-5. 実測：`jsonb_populate_record` でレコード変数に流し込む

```sql
DO $$
DECLARE
    r_p  products%ROWTYPE;
    v_in jsonb := '{"product_id": 99, "product_name": "Test", "category_id": 1, "price": 12.34}';
BEGIN
    r_p := jsonb_populate_record(NULL::products, v_in);
    RAISE NOTICE 'id=% name=% price=%', r_p.product_id, r_p.product_name, r_p.price;

    RAISE NOTICE '--- 知らないキーが混ざっていたら ---';
    r_p := jsonb_populate_record(NULL::products, v_in || '{"unknown_key": 1}'::jsonb);
    RAISE NOTICE 'エラーにはならない: id=%', r_p.product_id;

    RAISE NOTICE '--- 型が合わないキーがあったら ---';
    r_p := jsonb_populate_record(NULL::products, '{"product_id": "abc"}'::jsonb);
END;
$$;
```

```
NOTICE:  id=99 name=Test price=12.34
NOTICE:  --- 知らないキーが混ざっていたら ---
NOTICE:  エラーにはならない: id=99
NOTICE:  --- 型が合わないキーがあったら ---
ERROR:  invalid input syntax for type integer: "abc"
CONTEXT:  PL/pgSQL function inline_code_block line 14 at assignment
```

- **第 1 引数は「型のひな型」です。** `NULL::products` と書くことで「`products` の行構成型で受けたい」と伝えています。
- **知らないキーは黙って無視されます。** 「キー名を打ち間違えたのに動いた（けれど値が入っていない）」が起きます。
- **型が合わないキーはエラーになります。** ここは §3 と同じ I/O 変換のエラーです。

### 8-6. 実測：逆向き

```sql
DO $$
DECLARE
    r_p products%ROWTYPE;
BEGIN
    SELECT * INTO r_p FROM products WHERE product_id = 1;
    RAISE NOTICE '%', to_jsonb(r_p);
END;
$$;
```

```
NOTICE:  {"price": 1200.00, "product_id": 1, "category_id": 1, "product_name": "Laptop"}
```

**`to_jsonb(行構成型)` で 1 行を丸ごと JSONB にできます。** 「関数の戻り値を JSONB 1 個にまとめる」用途にはこれが最短です。ただし**列名がそのまま外部インタフェースになる**ので、表の列名を変えた瞬間に API が変わることに注意してください。

## まとめ

- **名前の衝突は PL/pgSQL が SQL に変数を埋め込む段階で起きる。** `#variable_conflict` の 3 値で解決規則を変えられるが、**指示子 1 行で SQL の意味が変わる**ので新規コードでは使わない
- **`use_column` は特に危険。** 変数を渡したつもりの `WHERE` が「列 = 列」になり、全行が対象になる
- **【誤解の訂正】`$1` に書き換えても衝突は直らない。** 直っていないのは列を指す側。列を修飾する／引数を関数名で修飾する／`p_` を付ける、の 3 択
- **代入は明示キャストではない。** 代入キャストがなければ「出力関数 → 入力関数」の I/O 変換になる。実測：`CAST(true AS integer)` は 1 なのに `v_n := true` は `invalid input syntax for type integer: "t"`
- **`numeric` → `integer` の代入は四捨五入**（`2.5` → `3`）。切り捨てではない
- **`NOT NULL` 変数は「NULL が入った瞬間」に止められる。** `LEFT JOIN` の NULL 混入対策として `STRICT` より広く効く
- **`DEFAULT` の初期値はブロックに入るたび評価される**
- **【検証結果】代入の `=` は動く。「9.4 以降で許容」は誤り。** 9.4 の変更は文書化であって機能追加ではない（リリースノートに該当項目なし）。**バージョン条件は書かず、`:=` だけを教える**（同じブロックに代入と比較が同じ綴りで並ぶのを避けるため）
- **`RECORD` は代入のたびにフィールドの集合が入れ替わる。** 直前に何を代入したかでコードの正しさが決まる
- **`%ROWTYPE` は宣言時に構造を持つが、`CREATE` 時の列名検査はされない**（→ [[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §3）
- **複合型変数の `IS NULL` では「未代入」と「0 件を `INTO` した」を区別できない。** 判定は `FOUND` で
- **`%ROWTYPE` には `SELECT *`、必要な列だけなら `RECORD`。** 混ぜると黙って NULL のフィールドができる
- **配列の添字は 1 から、JSON 配列の添字は 0 から。** 配列の範囲外は例外ではなく NULL
- **配列を `FOREACH` で回すのは N+1。`unnest` / `= ANY` で集合として渡す**
- **`->>` は `text`。数値比較には明示キャストが必要**（`'100' > '50'` は偽）
- **JSONB を講義から外したのは「12章の主題ではない」ため。** 正規化を学んだ直後の研修生に「何でも入る箱」を渡さない
