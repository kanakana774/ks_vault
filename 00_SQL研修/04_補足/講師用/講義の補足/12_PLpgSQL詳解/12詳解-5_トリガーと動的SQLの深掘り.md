# トリガーと動的 SQL の深掘り
## 〜発火順序・遷移テーブル・再帰、そして識別子と値の境界〜

講義版 [[12-5_トリガーと動的SQL|12-5]] では、トリガーは「`BEFORE` で検証・補正、`AFTER` で記録」、動的 SQL は「識別子は `%I`、値は `USING`」まで教えています。

この資料は、そこから先——**複数のトリガーが同時に付いているとき何が起きるか、大量更新にどう耐えるか、再帰をどう止めるか**、そして**動的 SQL で `USING` が使えない場面**を扱います。

> **この資料の前提**
> - **これは講師用です。研修生には配りません。**
> - PostgreSQL 17 で動作確認しています。掲載している出力は**すべて実測**です。
> - 対応する講義版: [[12-5_トリガーと動的SQL|12-5]]

---

## 1. 発火順序は「トリガー名のアルファベット順」

### 1-1. 【実測】

同じテーブル・同じタイミングに 3 つのトリガーを、**わざと作成順とアルファベット順がずれるように**登録します。

```sql
CREATE TABLE dx_trg (id integer);

CREATE OR REPLACE FUNCTION dx_say() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN RAISE NOTICE '発火: %', TG_NAME; RETURN NEW; END; $$;

CREATE TRIGGER zzz_last   BEFORE INSERT ON dx_trg FOR EACH ROW EXECUTE FUNCTION dx_say();
CREATE TRIGGER aaa_first  BEFORE INSERT ON dx_trg FOR EACH ROW EXECUTE FUNCTION dx_say();
CREATE TRIGGER mmm_middle BEFORE INSERT ON dx_trg FOR EACH ROW EXECUTE FUNCTION dx_say();

INSERT INTO dx_trg VALUES (1);
```

```
NOTICE:  発火: aaa_first
NOTICE:  発火: mmm_middle
NOTICE:  発火: zzz_last
INSERT 0 1
```

**作成順（zzz → aaa → mmm）ではなく、名前順（aaa → mmm → zzz）に発火しました。**

### 1-2. 実務での意味

これは**設計上の落とし穴**です。

- `BEFORE` トリガーが 2 つあり、片方が `NEW` を書き換え、もう片方がその値を検証する場合、**順序が結果を変えます**。
- その順序が「名前のアルファベット順」という、業務的に無意味な基準で決まっています。
- 後から `check_...` という名前のトリガーを足したら、既存の `normalize_...` より先に走ってしまった——という事故が起きます。

**順序に依存する処理を複数のトリガーに分けないでください。** どうしても分けるなら、`10_normalize` `20_validate` のように**名前に順序を埋め込む**のが実務の慣習です。

`TG_NAME` にはトリガー名が入ります。デバッグのとき、どのトリガーが動いているかを出すのに使えます。

## 2. `BEFORE` で `RETURN NULL` すると行が消える

講義版では「`RETURN NEW` で書き込む」とだけ教えています。`RETURN NULL` にすると**その行の処理そのものが取り消されます**。

### 2-1. 【実測】

```sql
CREATE OR REPLACE FUNCTION dx_skip() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF NEW.id % 2 = 0 THEN
        RAISE NOTICE 'id=% は偶数なので握りつぶす', NEW.id;
        RETURN NULL;
    END IF;
    RETURN NEW;
END; $$;

CREATE TRIGGER dx_skip_trg BEFORE INSERT ON dx_trg FOR EACH ROW EXECUTE FUNCTION dx_skip();

DELETE FROM dx_trg;
INSERT INTO dx_trg VALUES (1), (2), (3), (4);
SELECT * FROM dx_trg ORDER BY id;
```

```
NOTICE:  id=2 は偶数なので握りつぶす
NOTICE:  id=4 は偶数なので握りつぶす
INSERT 0 2
 id 
----
  1
  3
(2 rows)
```

**4 行 `INSERT` したのに `INSERT 0 2`。** エラーも警告も出ずに 2 行が消えています。

### 2-2. なぜ危険か

**アプリケーションから見ると「`INSERT` は成功した」ように見えます。** 戻ってくる件数を確認していなければ、データが入っていないことに気づけません。

「不正な行は黙って捨てる」という設計は、**ほぼ常に間違い**です。捨てるなら `RAISE EXCEPTION` で明示的に拒否してください（[[12-5_トリガーと動的SQL|12-5]] §2 で教えているのはこちらの形です）。

`RETURN NULL` が正当なのは、**「アーカイブ済みテーブルへの書き込みを、パーティション側へ振り替えた」**ような、行を別の場所に確実に書いたうえで元を止める場合に限られます。

## 3. 行トリガーと文トリガー

### 3-1. 【実測】文トリガーは 0 行でも発火する

```sql
CREATE OR REPLACE FUNCTION dx_stmt() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN RAISE NOTICE '文トリガー発火 (TG_OP=%, TG_LEVEL=%)', TG_OP, TG_LEVEL; RETURN NULL; END; $$;

CREATE TRIGGER dx_stmt_trg AFTER UPDATE ON dx_trg FOR EACH STATEMENT EXECUTE FUNCTION dx_stmt();

-- 1行も該当しない UPDATE
UPDATE dx_trg SET id = id WHERE id = 99999;
```

```
NOTICE:  文トリガー発火 (TG_OP=UPDATE, TG_LEVEL=STATEMENT)
UPDATE 0
```

**`UPDATE 0` なのに発火しています。**

| | `FOR EACH ROW` | `FOR EACH STATEMENT` |
|:---|:---|:---|
| 呼ばれる回数 | 対象行の数だけ | SQL 文 1 つにつき 1 回 |
| 0 行のとき | 呼ばれない | **呼ばれる** |
| `NEW` / `OLD` | 使える | **使えない（NULL）** |

`TG_LEVEL` で自分がどちらとして呼ばれたかが分かります。

### 3-2. 使い分け

- **行ごとの値が必要** → 行トリガー
- **「この表が更新された」という事実だけ必要**（キャッシュの無効化、集計テーブルの再計算フラグを立てる等） → 文トリガー

文トリガーは 10 万行の更新でも 1 回しか呼ばれないので、**大量更新に強い**のが最大の利点です。

---

## 4. 遷移テーブル：行トリガーを大量に回さずに済ませる

講義版 [[12-5_トリガーと動的SQL|12-5]] §5 で「`FOR EACH ROW` は 10 万行なら 10 万回呼ばれる」と警告しました。**PostgreSQL 10 以降には、その回避策があります。**

`REFERENCING NEW TABLE AS ... / OLD TABLE AS ...` を書くと、**その文で変更された行の集合を、1 つの仮想的な表として文トリガーから参照できます**。

### 4-1. 【実測】

```sql
CREATE OR REPLACE FUNCTION dx_transition() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE v_cnt integer; v_sum bigint;
BEGIN
    SELECT count(*), sum(id) INTO v_cnt, v_sum FROM new_rows;
    RAISE NOTICE '遷移テーブル: % 行、id合計 %', v_cnt, v_sum;
    RETURN NULL;
END; $$;

CREATE TRIGGER dx_trans_trg
    AFTER INSERT ON dx_trg
    REFERENCING NEW TABLE AS new_rows
    FOR EACH STATEMENT EXECUTE FUNCTION dx_transition();

INSERT INTO dx_trg VALUES (11), (13), (15);
```

```
NOTICE:  遷移テーブル: 3 行、id合計 39
INSERT 0 3
```

**3 行の `INSERT` に対してトリガー関数は 1 回だけ呼ばれ、その中で 3 行すべてを集合として扱えています。**

### 4-2. なぜ重要か

監査ログのような「全行を記録する」処理は、行トリガーで書くと 1 行 1 回の `INSERT` になります。遷移テーブルなら **`INSERT INTO audit SELECT * FROM new_rows;` の 1 文**で済みます。

**10 万行の更新に対して、10 万回の関数呼び出し＋10 万回の `INSERT` が、1 回の関数呼び出し＋1 文の `INSERT` になります。** 講義版では扱いませんが、実務で監査ログを設計するなら第一候補です。

制約: 遷移テーブルは **`AFTER` トリガーでのみ**使えます（`BEFORE` では変更がまだ確定していないため）。

## 5. 再帰トリガーと `pg_trigger_depth()`

トリガーの中で同じテーブルを更新すると、そのトリガーがまた動きます。止めないと無限に続きます。

### 5-1. 【実測】

```sql
CREATE TABLE dx_rec (id integer, n integer);

CREATE OR REPLACE FUNCTION dx_recur() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    RAISE NOTICE 'depth=%', pg_trigger_depth();
    IF pg_trigger_depth() < 3 THEN
        UPDATE dx_rec SET n = n + 1 WHERE id = NEW.id;
    END IF;
    RETURN NULL;
END; $$;

INSERT INTO dx_rec VALUES (1, 0);
CREATE TRIGGER dx_rec_trg AFTER UPDATE ON dx_rec FOR EACH ROW EXECUTE FUNCTION dx_recur();

UPDATE dx_rec SET n = n + 1 WHERE id = 1;
SELECT * FROM dx_rec;
```

```
NOTICE:  depth=1
NOTICE:  depth=2
NOTICE:  depth=3
UPDATE 1
 id | n 
----+---
  1 | 3
(1 row)
```

**`pg_trigger_depth()` は「今、何段目のトリガーの中にいるか」を返します。** ユーザーが直接実行した文の中では 0、トリガーから呼ばれると 1、そのトリガーが起こした更新のトリガーでは 2、と増えます。

### 5-2. 使い方

再帰を止める定番は 2 つです。

```sql
-- ① 関数の中で判定する
IF pg_trigger_depth() > 1 THEN RETURN NULL; END IF;

-- ② トリガーの WHEN 句で判定する（関数呼び出しすら起きない）
CREATE TRIGGER ... WHEN (pg_trigger_depth() = 1) EXECUTE FUNCTION ...;
```

**②の方が安いです**（[[12-5_トリガーと動的SQL|12-5]] §4 の `WHEN` 句と同じ理由）。

なお、上の実測で `n` が 3 になっているように、**止めるまでの更新は実際に行われています**。「深さで止める」は無限ループを防ぐ手段であって、意図しない更新をなかったことにする手段ではありません。

## 6. `INSTEAD OF` トリガー：JOIN したビューを更新可能にする

### 6-1. 【実測】そのままでは更新できない

```sql
CREATE VIEW v_product_category AS
SELECT p.product_id, p.product_name, p.price, c.category_name
  FROM products p JOIN categories c ON p.category_id = c.category_id;

UPDATE v_product_category SET price = 1234 WHERE product_id = 1;
```

```
ERROR:  cannot update view "v_product_category"
DETAIL:  Views that do not select from a single table or view are not automatically updatable.
HINT:  To enable updating the view, provide an INSTEAD OF UPDATE trigger or an unconditional ON UPDATE DO INSTEAD rule.
```

**`HINT` が答えを言っています。** 単一テーブルから作ったビューは自動的に更新可能ですが、JOIN があると PostgreSQL はどのテーブルを更新すべきか決められません。

### 6-2. 【実測】`INSTEAD OF` で振り分ける

```sql
CREATE OR REPLACE FUNCTION v_pc_update() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    UPDATE products SET price = NEW.price WHERE product_id = OLD.product_id;
    RETURN NEW;
END; $$;

CREATE TRIGGER v_pc_upd INSTEAD OF UPDATE ON v_product_category
    FOR EACH ROW EXECUTE FUNCTION v_pc_update();

BEGIN;
UPDATE v_product_category SET price = 1234 WHERE product_id = 1;
SELECT product_id, product_name, price FROM products WHERE product_id = 1;
ROLLBACK;
```

```
UPDATE 1
 product_id | product_name |  price  
------------+--------------+---------
          1 | Laptop       | 1234.00
(1 row)
```

**ビューに対する `UPDATE` が、背後の `products` に届きました。**

`INSTEAD OF` は行トリガー専用で、ビューにしか付けられません。**「複雑なテーブル構成を隠して、アプリには単純な表として見せる」**という設計に使えますが、**隠した分だけ実際に何が更新されるかが読めなくなる**ことも忘れないでください。

## 7. トリガーを調べる・止める

### 7-1. 存在を調べる

| 方法 | 内容 |
|:---|:---|
| `\d テーブル名` | psql。そのテーブルのトリガー一覧が表示される |
| `SELECT * FROM pg_trigger WHERE tgrelid = 'テーブル名'::regclass;` | システムカタログを直接見る |
| `information_schema.triggers` | 標準的なビュー。他 DBMS と同じ書き方で調べたいとき |

`pg_trigger` には内部的な制約トリガー（外部キー用）も含まれるので、`AND NOT tgisinternal` を付けると自分で作ったものだけ見られます。

### 7-2. 止める（危険）

```sql
ALTER TABLE 表名 DISABLE TRIGGER トリガー名;   -- 個別に止める
ALTER TABLE 表名 DISABLE TRIGGER ALL;          -- 全部止める（外部キーも含む）
SET session_replication_role = 'replica';       -- そのセッションのユーザートリガーを止める
```

**データ移行のときによく使われますが、極めて危険です。**

- `DISABLE TRIGGER ALL` は**外部キー制約のトリガーまで止めます**。整合性のない行が入り、後で気づいたときには原因が分からなくなります。
- `session_replication_role` はセッション単位なので、**止め忘れたまま別の処理を流す**事故が起きます。

止めるなら「何のために」「いつ戻すか」をセットで決めてください。研修生には**「こういう手段があるが、まず使わない」**と伝える程度で十分です。

## 8. 動的 SQL：`USING` で渡せないもの

講義版 [[12-5_トリガーと動的SQL|12-5]] §7-3 で「識別子は `%I`、値は `USING`」と教えました。その境界を正確に押さえます。

**`USING` が渡すのは SQL のパラメータ（`$1`）です。SQL のパラメータは「値が来る場所」にしか置けません。**

| 置ける | 置けない |
|:---|:---|
| `WHERE col = $1` | `FROM $1`（テーブル名） |
| `VALUES ($1, $2)` | `SELECT $1 FROM t`（列名として） |
| `LIMIT $1` | `ORDER BY $1`（列の指定として) |

`ORDER BY $1` は**構文としては通りますが、「1 という定数で並べ替える」**という意味になり、列名としては働きません。ここは研修生がよく誤解します。

### 8-1. 【実測】`format` の各指定子と NULL の扱い

```sql
SELECT format('%L', 'abc')    AS lit_text,
       format('%L', NULL)     AS lit_null,
       format('%I', 'my col') AS ident_with_space,
       quote_literal('abc')   AS q_literal,
       quote_nullable(NULL)   AS q_nullable;
```

```
 lit_text | lit_null | ident_with_space | q_literal | q_nullable 
----------+----------+------------------+-----------+------------
 'abc'    | NULL     | "my col"         | 'abc'     | NULL
(1 row)
```

押さえどころが 3 つあります。

1. **`%L` は NULL を `'NULL'`（文字列）ではなく `NULL`（SQL のキーワード）にします。** これが正しい挙動です。`quote_literal(NULL)` は NULL そのものを返すので、文字列連結すると**式全体が NULL になり、SQL が消えます**。NULL を含みうる値には `quote_nullable` か `%L` を使ってください。
2. **`%I` は空白を含む識別子を `"my col"` と引用符で囲みます。** これが `||` による連結では絶対に得られない安全性です。
3. `%s` は何も加工しません。**SQL の組み立てに `%s` を使うのは、`||` で連結するのと同じ危険**です。メッセージ文字列を作るときだけに使ってください。

### 8-2. `EXECUTE` はプランをキャッシュしない

`EXECUTE` に渡した文字列は、**毎回パースと計画作成が行われます**。実測は [[12詳解-6_性能とアンチパターン|12詳解-6]] §3 にありますが、**約 6 倍の差**が出ました。

これは欠点であると同時に利点でもあります。[[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §3-4 の「generic plan のせいで特定の引数だけ遅い」問題は、動的 SQL にすれば起きません。**「毎回計画を作り直したい」が正当な要求になる場面がある**ということです。

## まとめ

- **同じタイミングのトリガーは「名前のアルファベット順」に発火する**（実測）。順序に依存する処理を複数トリガーに分けない
- **`BEFORE` の `RETURN NULL` は行を黙って消す。** `INSERT 4` が `INSERT 0 2` になっても呼び出し元にはエラーが出ない
- **文トリガーは 0 行でも発火し、`NEW`/`OLD` は使えない**（実測）
- **遷移テーブル（`REFERENCING NEW TABLE`）を使えば、大量更新でも関数呼び出しは 1 回**。監査ログの第一候補
- **`pg_trigger_depth()` で再帰を止める。** `WHEN` 句で判定する方が安い
- **JOIN したビューは `INSTEAD OF` トリガーで更新可能にできる**
- **`DISABLE TRIGGER ALL` は外部キーまで止める。** 使うなら戻す手順とセットで
- **`USING` は「値の位置」にしか渡せない。** テーブル名・列名は `%I`
- **`%L` は NULL を SQL の `NULL` にする。** `quote_literal(NULL)` は NULL を返して式全体を壊す
- **`EXECUTE` はプランをキャッシュしない。** 欠点にも利点にもなる
