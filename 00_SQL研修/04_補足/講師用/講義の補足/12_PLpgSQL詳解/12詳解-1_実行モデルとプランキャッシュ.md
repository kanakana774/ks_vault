# PL/pgSQL の実行モデルとプランキャッシュ
## 〜「いつ解析され、いつ計画が作られるのか」〜

研修生からよく出る質問に「関数を作ったときに文法チェックしてくれないんですか」があります。答えは「**本体の SQL はチェックされません**」で、その理由は PL/pgSQL の実行モデルにあります。

この資料では、`CREATE FUNCTION` から実際にクエリが走るまでに何が起きているかを実測で追います。

> **この資料の前提**
> - **これは講師用です。研修生には配りません。**
> - PostgreSQL 17 で動作確認しています。掲載している出力は**すべて実測**です。
> - 対応する講義版: [[12-1_PLpgSQLの基礎とDOブロック|12-1]]、[[12-2_変数とSQLの実行|12-2]]、[[12-4_関数とプロシージャと例外処理|12-4]]

---

## 1. `CREATE FUNCTION` は何をチェックしているか

### 1-1. 【実測】存在しない列を参照する関数は、作れてしまう

```sql
CREATE OR REPLACE FUNCTION broken_func()
RETURNS text LANGUAGE plpgsql AS $$
DECLARE v_x text;
BEGIN
    SELECT no_such_column INTO v_x FROM customers WHERE customer_id = 1;
    RETURN v_x;
END;
$$;
```

```
CREATE FUNCTION
```

**エラーになりません。** 呼ぶと初めて落ちます。

```sql
SELECT broken_func();
```

```
ERROR:  column "no_such_column" does not exist
QUERY:  SELECT no_such_column          FROM customers WHERE customer_id = 1
CONTEXT:  PL/pgSQL function broken_func() line 4 at SQL statement
```

`CREATE FUNCTION` がやっているのは、**PL/pgSQL としての構文解析だけ**です。「`BEGIN` と `END` が対応しているか」「`IF` に `THEN` があるか」は見ますが、**本体に埋め込まれた SQL 文の中身は文字列として保持するだけ**で、テーブルや列の存在は確認しません。

### 1-2. これが講義版のどこに効くか

[[12-2_変数とSQLの実行|12-2]] §6 で `%ROWTYPE` を「テーブル定義に追従する」と説明しています。旧版の教材はこれを一歩進めて **「`%ROWTYPE` はコンパイル時に列名の存在チェックが走るから `RECORD` より安全」** と書いていましたが、**これは誤りです。**

- PL/pgSQL に「コンパイル時」と呼べる段階はありますが、それは **`CREATE` 時ではなく、そのセッションで初めて呼ばれたとき**です。
- そのときも、チェックされるのは「実行しようとした SQL」であって、DDL 変更を静的に検出する仕組みはありません。

**`%ROWTYPE` を使う理由は「型を書き写さなくてよい」「意図が読み手に伝わる」であって、静的チェックではありません。** 研修生に説明するときは、ここを混同しないでください。

### 1-3. 【実測】一度成功した関数も、列を消せば次の呼び出しで落ちる

「初回実行時にコンパイルされてキャッシュされる」なら、その後に列を消したらどうなるか。

```sql
CREATE TABLE dx_t (id integer, val text);
INSERT INTO dx_t VALUES (1, 'a');

CREATE OR REPLACE FUNCTION dx_f() RETURNS text LANGUAGE plpgsql AS $$
DECLARE v text;
BEGIN
    SELECT val INTO v FROM dx_t WHERE id = 1;
    RETURN v;
END;
$$;

SELECT dx_f() AS first_call;
ALTER TABLE dx_t DROP COLUMN val;
SELECT dx_f() AS after_drop;
```

```
 first_call 
------------
 a
(1 row)

ALTER TABLE
ERROR:  column "val" does not exist
QUERY:  SELECT val        FROM dx_t WHERE id = 1
CONTEXT:  PL/pgSQL function dx_f() line 4 at SQL statement
```

**同一セッションでキャッシュされていても、古い計画が使い回されて壊れたデータを返す、ということは起きません。** PostgreSQL は DDL の変更を検知してキャッシュを無効化し、作り直そうとして失敗しています。

> **講師用の答え方**: 「関数はいつチェックされるの?」→ **「作るときは構文だけ。テーブルや列は、実際にその行を通ったときに初めて確認される」**。だから **`IF` の片方の枝しか通っていない関数は、通っていない枝のエラーに気づけない**、という話まで繋げると納得されます。

## 2. `DO` ブロックはキャッシュされない

関数・プロシージャは、初回呼び出し時に解析した結果を**セッションが続く限り保持**します。一方 `DO` ブロックは名前を持たないので、**実行のたびに解析からやり直します**。

研修中に `DO` ブロックを何度も流しても体感差は出ませんが、**「本番のバッチを `DO` で書いて何万回も呼ぶ」設計はこの点で不利**です。繰り返し呼ぶものは関数・プロシージャにする理由の 1 つがこれです。

## 3. プランキャッシュ：custom plan と generic plan

### 3-1. 何が問題になるのか

PL/pgSQL の中の SQL は、内部的に**プリペアド文（パラメータ付きの文）**として保持されます。パラメータ付きの文には、実行計画の作り方が 2 通りあります。

| 種類 | 内容 |
|:---|:---|
| **custom plan**（個別計画） | 実際の引数の値を見て、毎回計画を作り直す。計画作成のコストがかかるが、値に合った計画になる |
| **generic plan**（汎用計画） | 引数を `$1` のまま扱い、1 つの計画を使い回す。計画作成のコストが消える代わりに、値の偏りを無視する |

PostgreSQL は **最初の 5 回は custom plan で実行し、そのコストの平均と generic plan のコストを比べて、generic が悪くなければ以降は generic に切り替えます**。

### 3-2. 【実測】5 回を境に計画表示が変わる

PL/pgSQL の中を直接覗くのは難しいので、同じ仕組みを使う `PREPARE` / `EXECUTE` で観察します。

```sql
PREPARE p1(integer) AS SELECT count(*) FROM dx_big WHERE id = $1;

EXPLAIN (COSTS OFF) EXECUTE p1(500);
```

```
                    QUERY PLAN                     
 Aggregate
   ->  Index Only Scan using dx_big_pkey on dx_big
         Index Cond: (id = 500)
(3 rows)
```

**`id = 500` と、実際の値が計画に埋まっています**（custom plan）。ここから 4 回実行して、6 回目を見ます。

```sql
EXECUTE p1(500); EXECUTE p1(500); EXECUTE p1(500); EXECUTE p1(500);
EXPLAIN (COSTS OFF) EXECUTE p1(500);
```

```
                    QUERY PLAN                     
 Aggregate
   ->  Index Only Scan using dx_big_pkey on dx_big
         Index Cond: (id = $1)
(3 rows)
```

**`id = $1` に変わりました。** generic plan に切り替わっています。

### 3-3. 【実測】`plan_cache_mode` で強制できる

```sql
SET plan_cache_mode = force_generic_plan;
PREPARE p2(integer) AS SELECT count(*) FROM dx_big WHERE id = $1;
EXPLAIN (COSTS OFF) EXECUTE p2(500);
```

```
                    QUERY PLAN                     
 Aggregate
   ->  Index Only Scan using dx_big_pkey on dx_big
         Index Cond: (id = $1)
(3 rows)
```

1 回目から generic plan です。設定値は `auto`（既定）/ `force_custom_plan` / `force_generic_plan` の 3 つです。

### 3-4. これが問題になる典型例

**データの偏りが大きい列**を引数で絞り込む関数です。

`status` 列に `'Pending'` が 100 件、`'Completed'` が 100 万件あるとします。

- `'Pending'` を渡したときの最適な計画はインデックススキャン
- `'Completed'` を渡したときの最適な計画はシーケンシャルスキャン

generic plan は「引数が何であっても同じ計画」なので、**どちらか一方で必ず損をします**。「同じ関数なのに、ある引数のときだけ急に遅くなる」「サーバを再起動した直後は速いのに、しばらくすると遅くなる」という症状が出たら、まずこれを疑ってください。

対処は `SET plan_cache_mode = force_custom_plan;` を関数に付ける（`ALTER FUNCTION ... SET plan_cache_mode = ...`）か、動的 SQL（`EXECUTE`）にして毎回計画を作らせるかです。**動的 SQL がプランをキャッシュしないという性質は、ここでは利点になります**（→ [[12詳解-6_性能とアンチパターン|12詳解-6]] §3）。

## 4. 開発時にだけ効かせる静的チェック：`plpgsql.extra_warnings`

PL/pgSQL には、既定では黙って通る危険な書き方を**警告にする**設定があります。

| 値 | 何を検出するか |
|:---|:---|
| `shadowed_variables` | 外側の変数・引数を隠す宣言 |
| `strict_multi_assignment` | `SELECT INTO` の変数の数と列の数が合わない |
| `too_many_rows` | `SELECT INTO` が複数行を返した |
| `all` | 上記すべて |

### 4-1. 【実測】`too_many_rows` が講義版 §2-2 の問題を捕まえる

[[12-2_変数とSQLの実行|12-2]] §2-2 で「複数件でも黙って先頭 1 行が入る」を実測しました。これを警告にできます。

```sql
SET plpgsql.extra_warnings = 'all';

DO $$
DECLARE v_name text;
BEGIN
    SELECT name INTO v_name FROM customers;
    RAISE NOTICE 'v_name = %', v_name;
END;
$$;
```

```
WARNING:  query returned more than one row
HINT:  Make sure the query returns a single row, or use LIMIT 1.
NOTICE:  v_name = Alice
```

**警告は出ますが、処理は止まりません。** 止めたいなら `plpgsql.extra_errors` に同じ値を設定します。

### 4-2. 【実測】`shadowed_variables` は「引数を隠す宣言」を捕まえる

```sql
SET plpgsql.extra_warnings = 'shadowed_variables';

CREATE OR REPLACE FUNCTION dx_shadow(p_id integer)
RETURNS integer LANGUAGE plpgsql AS $$
DECLARE p_id integer := 99;
BEGIN
    RETURN p_id;
END;
$$;
```

```
WARNING:  variable "p_id" shadows a previously defined variable
LINE 3: DECLARE p_id integer := 99;
                ^
CREATE FUNCTION
```

一方、**入れ子ブロックで外側の変数と同名を宣言した場合は、この設定でも警告が出ませんでした**（実測）。

```sql
SET plpgsql.extra_warnings = 'shadowed_variables';
DO $$
DECLARE v_x integer := 1;
BEGIN
    DECLARE v_x integer := 2;
    BEGIN
        RAISE NOTICE 'inner = %', v_x;
    END;
END;
$$;
```

```
NOTICE:  inner = 2
```

警告なしで通ります。**[[12-1_PLpgSQLの基礎とDOブロック|12-1]] §6 で教えているスコープの入れ子は、この設定では守ってもらえない**ということです。研修生に「設定を入れておけば安全」と言わないでください。

### 4-3. 実務での置き方

セッション単位の `SET` は開発時にしか効きません。恒久的にかけるなら次のどちらかです。

- `postgresql.conf` に `plpgsql.extra_warnings = 'all'`（開発環境のみ）
- `ALTER DATABASE dev_db SET plpgsql.extra_warnings = 'all';`

**本番で `extra_errors` を有効にするのは危険**です。既存の動いているコードが突然エラーになります。

## 5. `plpgsql_check` 拡張

より本格的な静的解析には `plpgsql_check` という外部拡張があります。関数本体の SQL を実際に実行せずに検査し、存在しない列・型の不一致・到達しないコードなどを報告します。

**この環境には導入されていません**（`pg_available_extensions` に存在しないことを確認済み）。研修環境に入れるには追加インストールが必要なので、**研修では扱いません**。質問されたら「そういう拡張はあるが、標準では入っていない」と答えてください。

---

## まとめ

- **`CREATE FUNCTION` は PL/pgSQL の構文しか見ない。** 本体の SQL の妥当性は、実際にその行を通ったときに初めて確認される
- **旧版の「`%ROWTYPE` はコンパイル時に列名チェックされる」は誤り。** `%ROWTYPE` の価値は静的チェックではなく、型の追従と可読性
- **DDL を変えるとキャッシュは無効化される。** 古い計画で壊れた結果を返すことはない
- **`DO` ブロックはキャッシュされない。** 繰り返し呼ぶものは関数・プロシージャにする
- **プリペアド文は 5 回を境に generic plan に切り替わる**（実測で `id = 500` → `id = $1`）。データの偏りが大きい列では、これが「特定の引数のときだけ遅い」の原因になる
- **`plpgsql.extra_warnings` は開発環境で有効にする価値がある。** ただし入れ子ブロックの変数隠蔽は検出されない
- **`plpgsql_check` はこの環境に未導入**
