# SQLの現場で求められる人材像 — 研修の設計基準

> 更新: 2026-08-12 / 位置づけ: **講師用の設計基準**（研修生に配る文書ではない。研修生向けの言い方は §5）
> 目的: 「現場が求めるもの」を、**研修のどこで担保するか／担保しないと決めるか**まで落とす
> 現場の姿そのもの（案件の型・使う技術・タスク例）は [[★常駐先の想定業務★]] が正本。この文書は**そこから人物像と研修要件を導く**役
> 個別トピックの網羅は [[トピック網羅チェックリスト]]

---

## 0. 一言でいうと

求められているのは「**単にSQLが書ける人**」ではなく、「**SQLという道具を使って、ビジネス上の課題を正確かつ効率的に解決してくれる人**」。

研修の言葉に翻訳すると:

> **構文を教え切ることがゴールではない。「データの意味を考える」「自分が出した結果を疑う」「遅い理由を説明できる」の3つの癖をつけて送り出す。**

構文の網羅は手段であって目的ではない、というのがこの文書の唯一の主張。

## 1. 求められる5つの資質 → 研修での担保

| # | 資質 | 現場での現れ方 | 研修での担保 | 状態 |
|---|---|---|---|---|
| 1 | **データの意味を考えられる** | 仕様書どおりに書くだけでなく、業務背景を理解しようとする。だから**仕様の矛盾に気づける** | 実務想定問題の「思考プロセス」節／マスタとトラン／ER図からの経路選択 | ◎ |
| 2 | **正確性と品質を担保できる** | 販売管理・会計では1円の誤差も許されない。**自分のSQLを疑ってテストする慎重さ**とレビューを受け入れる素直さ | 罠ベースの追加問題群（01〜07章）／実務想定問題の事前検証ステップ | ○ **←検証の作法が講義に無い（§3-1）** |
| 3 | **パフォーマンスを意識できる** | 開発環境の少量データでは通るクエリが本番の数百万件で死ぬ。`EXPLAIN` を読み、インデックスの重要性を理解している | 17章（物理構造・EXPLAIN実測・効かない落とし穴・結合アルゴリズム） | ◎ |
| 4 | **周辺技術に柔軟に対応できる** | Shell / Python / Java からSQLが呼ばれ、BIツールと繋がる。SQL以外にも抵抗がない | **担保しない**（§2で割り切り）。地図だけ渡す | × 意図的 |
| 5 | **粘り強く原因を追究できる** | 障害調査＝探偵仕事。ログを読み、SQLでデータを追い、絡んだ事象から原因を突き止める | 実務想定問題「障害調査」／ロック調査／アンチジョインでの突合 | △ **←道具立てが未整備（[[トピック網羅チェックリスト]] A-3・A-6）** |

状態: ◎=講義＋演習で担保 ／ ○=担保しているが穴あり ／ △=部分的 ／ ×=担保しない（意図的）

### 1-1. データの意味を考えられる人

ただ仕様書通りにクエリを書くだけでなく、「**このデータは何を表しているのか**」「**なぜこの集計が必要なのか**」といった業務背景を理解しようと努める人材は重宝される。データの意味を理解することで、**仕様の矛盾に気づいたり**、より良い集計方法を提案したりできるから。

**研修での担保（既にできている）**

- [[01_RDBMSとDDL]] のコラム「マスタとトラン」＝テーブルを見て役割を判断する語彙
- [[00_なぜテーブルを分けるのか]]・[[00_補足_正規化の詳細]] ＝なぜこの形なのかを説明できる
- [[08_補足_結合]] §3「宣言的視点でルートを探す」＝ER図から**意味の正しい経路**を選ぶ。同じ結果に見えて意味が違う結合を区別させる、この教材の要
- 実務想定問題の各問に付いている **「【システム上の目的】」と「思考プロセス」** ＝「何のための集計か」を先に読ませる形式になっている

**この資質は現行教材の設計思想そのもの**なので、追加は不要。むしろ**削らないよう守る**対象。

### 1-2. 正確性と品質を担保できる人

業務システム、特に販売管理や会計システムでは1円の誤差も許されない。自分が書いたSQLが本当に正しい結果を返すか、**あらゆるケースを想定してテストできる慎重さ**や、他者のレビューを真摯に受け入れる素直さが求められる。

**研修での担保（強い）** — 01〜07章の追加問題は、ほぼ全部この資質のための教材になっている。

- 「〜ではない」で絞ったら件数が合わない（NULL）／`||` と `CONCAT` のNULL差／目に見えない空白／`COUNT(*)` と `COUNT(列)`／整数除算／`WHEN` の書き順／`TIMESTAMP` への `BETWEEN`／`LIMIT`・`OFFSET` の重複と欠落／年跨ぎで壊れる月次集計
- `WHERE` は「対象を選ぶ」だけでなく「**対象外を守る**」ために書く（03_UPDATE 問題11）

**穴**: → §3-1（**書いたSQLを自分で検証する手順**が講義に無い）

### 1-3. パフォーマンスを意識できる人

開発環境の少量データでは問題なく動いたクエリが、本番環境の数百万件のデータでは非常に遅くなる、というのはよくある話。`EXPLAIN`（実行計画）で非効率な処理を見つけたり、インデックスの重要性を理解している人材は高く評価される。

**研修での担保（この研修の強み）** — 17章はここに正面から答えている。

- [[17-1_導入_物理構造とスキャン方式]] ＝なぜ速いのかを物理層（ページ・I/O・B-Tree）から説明できる
- [[17-2_実践_EXPLAINの読み方]] ＝`Index Cond` と `Filter` の違い、**同じインデックスでも値によって計画が変わる**、効かない落とし穴7種。**すべて実測**
- [[17-3_補足_結合アルゴリズム]] ＝Nested Loop / Hash / Merge を実測で比較

「開発環境では出ない」という人材想定の核心そのものが、**ケース4（値によって計画が変わる）**として教材化できている。ここは面接で語れる形になっている。

### 1-4. 周辺技術にも柔軟に対応できる人

SQLはあくまでシステムの一部。Shellスクリプトや Python からSQLが実行されたり、BIツールと連携したりすることが多いため、SQL以外の技術にも抵抗なく学んでいける姿勢が重要。

**判断: 研修では担保しない。** → §2

### 1-5. 粘り強く原因を追究できる人

「障害調査・原因分析」はまさに探偵の仕事。ログを読み、SQLでデータを一つひとつ追いかけ、複雑に絡み合った事象の中から原因を突き止めるには、論理的思考力と粘り強さが不可欠。

**研修での担保（部分的）**

- 実務想定問題「問題2：障害調査 - 顧客からの問い合わせ対応」＝この資質のための唯一の演習
- [[15-2_実践_ロックとMVCC]] §1-3「誰が誰を待っているのかを調べる」＝止まっている原因を突き止める
- [[シーケンスが飛ぶ現象]]（`04_補足/過去にあった質問/`）＝「なぜそうなるか」を追う型の資料。この蓄積を増やすこと自体がこの資質の教材になる

**穴**: 調査の**道具**が揃っていない。孤児レコード検出・件数突合（アンチジョイン、[[トピック網羅チェックリスト]] A-3）と、既存テーブル構造をSQLで調べる手段（同 A-6）。さらに「既存の長いSQLを読む」演習が無い（同 B-1）。**この3つは全部この資質に紐づく**ので、優先度を上げる根拠になる。

## 2. 研修で担保しないと決めるもの（割り切り）

設計基準として大事なのは「やること」より「**やらないと決めたこと**」。求められているのは事実だが、SQL研修（PostgreSQL・実質数日〜数週）では扱わない。

| 求められているが扱わない | 理由 | 代わりに渡すもの |
|---|---|---|
| Shell / Python / Java からのSQL実行 | 言語研修の領域。2か月目のAPI研修が MyBatis で担保する | 「SQLは呼ばれる側」という位置づけの説明だけ |
| BIツール（Tableau / Power BI） | 案件で入ってから覚えれば足りる。汎用性が低い | — |
| DWH系（BigQuery / Snowflake / dbt / Airflow） | [[★常駐先の想定業務★]] の②だが、①業務システム系が主戦場 | [[バックエンドDBカオスマップ_2025末]] で**地図だけ**見せる |
| 論理設計を自分でやる演習 | 正規化は読み物どまり。設計は経験年数の領域 | [[00_なぜテーブルを分けるのか]]・[[08_補足_テーブル構造について考えてみる]] で読解まで |
| 要件定義 | 3か月目でも「要件は与えられる」（`MyWork/03_研修カリキュラム.md` §6） | — |
| クラウド・コンテナ・CI/CD | 研修全体で未経験（同 §6） | — |

**この表の意味**: 「求められている＝研修に入れる」ではない。入れない判断をここに書いておかないと、毎回同じ検討をやり直すことになる。

## 3. この整理で見つかった抜け（人材想定から導かれるのに教材が無いもの）

[[トピック網羅チェックリスト]] は「構文」の網羅を見た。こちらは「資質」から見た抜けで、**構文の一覧には出てこない**種類のもの。

### 3-1. 書いたSQLを自分で検証する作法が、講義にも通常演習にも無い【最重要】

資質#2（正確性）の核心。「あらゆるケースを想定してテストできる慎重さ」を**具体的な手順**として教えている場所が無い。

現状ある場所は**実務想定問題の解説の中だけ**:

> 「`UPDATE` を実行する前に、必ず『どのような値に更新されるのか』を `SELECT` で確認するのが鉄則です。この**『事前検証』プロセスを研修で徹底させます**」
> （[[00_SQL研修/03_解答/問題集_実務想定/業務システムを意識した問題_回答付]] 問題3の講師向け解説）
> 「件数確認をしてからコミットする流れは『分かっているエンジニア』の動き」（[[電子カルテの業務想定]]）

**自分で「研修で徹底させます」と書いているのに、それを教える教材が無い。** 実務想定問題は最後にやる発展問題なので、そこまで到達しない研修生には一度も伝わらない。

教える中身（1ページで足りる）:

1. **更新の前に同じ `WHERE` で `SELECT`** して、対象と件数を目で見る
2. **影響行数を先に見積もる** → `UPDATE` の結果件数と一致するか照合する
3. **`BEGIN` で囲み、件数を確認してから `COMMIT`**（違ったら `ROLLBACK`）→ [[15-1_導入_トランザクションとACID]] と直結
4. **消す・変える前に退避**（`CREATE TABLE 退避 AS SELECT ...`）→ チェックリスト A-1 と直結
5. **境界を疑う**: NULL・0件・重複・日付の端。既存の追加問題群が全部この確認項目になっている

→ 置き場案: `01_講義資料/00_SQLを検証する.md`（[[00_SQLを書く時の注意]] の隣。**書き方の作法**と**検証の作法**の対）。あるいは §3-3 と合わせて1本。

### 3-2. 業務担当者との連携が人材想定に入っていない

[[★常駐先の想定業務★]] の「SES案件としての特徴」には**書いてある**:

> 「業務担当者との連携が多い（仕様確認・抽出条件相談など）」

しかしこの文書の5資質には入っていない。実際には**現場で最も評価が分かれる部分**（「言われたものを作る人」と「条件の曖昧さを潰してから作る人」の差）。資質#1（データの意味）の裏返しでもある。

研修で担保できる範囲は限られるが、**問題文の曖昧さを意図的に残して「何を確認しますか？」と問う**形なら演習にできる。

> なお [[改善案]] には受講生の声として「問題文がわかりにくい ⇒ 実務で必要ない日本語能力が求められるのは無駄」がある。**曖昧さは減らすべきだが、「業務仕様として本質的に曖昧なもの」は別**。前者は直し、後者は演習の材料にする、という切り分けをしておくと両方立つ。

### 3-3. 本番データを触る怖さ・作業手順が体系化されていない

「1円の誤差も許されない」の実務的な意味は、**事故らない手順を持っていること**。

- `WHERE` 無し `UPDATE` / `DELETE` の事故 → 03_UPDATE 問題11・問題13 が部分的にカバー
- 自動コミットのツール差 → [[15-1_導入_トランザクションとACID]] §2-2 でカバー済み（良い）
- 長時間ロック・大量更新の分割 → [[15-2_実践_ロックとMVCC]] と PL/pgSQL 章に散在
- 作業前の退避・戻し方 → **無い**

散在している上記を「本番作業の作法」として1枚に集約する価値がある（§3-1 と同じノートでよい）。

## 5. 研修生に伝えるメッセージ（配布・口頭用）

ここから下は**研修生向けの言い方**。上の設計基準とは読者が違うので分けてある。研修の最後や個別面談で使う。

### 技術スキル：これを学んでおくと強い

- **応用的なSQL構文**: `JOIN`（特に `LEFT JOIN`）・`GROUP BY`・サブクエリは基本として完璧に。**ウィンドウ関数**（`ROW_NUMBER`・`RANK`・`SUM() OVER`）が使えると複雑な集計やランキングが一気に書きやすくなる。**`CASE`式**は実務での使用頻度が非常に高い。**`EXISTS`** は `IN` との使い分けを理解し、性能を意識した選択ができると強い
- **View / Stored Procedure / Function**: 「作成できます」ではなく「**なぜこれらを使うのか**（複雑なSQLの共通化・セキュリティ向上・性能向上）」を自分の言葉で説明できるように
- **実行計画（EXPLAIN）**: 「実行計画を読んでボトルネック（フルテーブルスキャンなど）を分析し、インデックスの追加を検討した経験があります」と具体例で言えると評価が高い
- **方言への学習意欲**: 「Oracle の PL/SQL や SQL Server の T-SQL も、プロジェクトで使われているなら積極的に学習して貢献したい」

### 伝え方：「なぜ」と「どのように」をセットで話す

- ✗「ウィンドウ関数が使えます」
- ○「**部門内売上ランキングのような集計を効率的に行うために**ウィンドウ関数を学習しました。`PARTITION BY` で部門ごとに区切り、`ORDER BY` で売上順に並べることで、1つのクエリでランキングを算出できます」

### 伝え方：思考プロセスを見せる

「A支店の月別売上を出すには？」と聞かれたら、答えだけ言わずに組み立てを口に出す。「まず売上が入っている `sales_orders` と店舗の `stores` を `store_id` で JOIN します。次に `WHERE` でA支店に絞り、`GROUP BY` で月ごとに集計して `SUM` で合計します」

### 伝え方：失敗から学んだ経験を話す

「`JOIN` の条件を間違えて意図しない件数になったことがありました。そこから、必ず件数を確認する、テストデータで複数パターンを試すなど、正確性を担保するチェックを徹底するようになりました」

> **講師メモ**: この「失敗から学んだ」型は、**研修中に実際に踏ませておかないと語れない**。だから追加問題群（行の増殖・NULLで件数が合わない・BETWEENで最終日が漏れる）は「解けたか」ではなく「**踏んだ経験として残ったか**」が成果。振り返りで言語化させると、そのまま面接の材料になる。
