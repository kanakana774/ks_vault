講義中に手元に置く用。**資料と同じ順番**に並べているので、上から下に進めれば流れは崩れません。

各節の書き方：

- **落とす一言** … その節で受講生の頭に残せば勝ちの1文

# 15-1 導入編

## 1. なぜトランザクションが必要か

### 1-1. 途中で落ちると何が起きるか ◎ 4分
**落とす一言**：**2つ以上の更新をセットで扱う処理は、放っておけば必ずいつか壊れる。**
- 送金の例で「①だけ成功して②の直前で落ちる」→ **お金が消滅する**
- 「めったに起きない」で流さない。再起動・切断・アプリの例外、どれでも同じ
- △ 「1文なら安全」の理由（暗黙のトランザクション）は §2 で回収するので、ここでは触れる程度

### 1-2. BEGIN / COMMIT / ROLLBACK ◎ 3分
**落とす一言**：**`COMMIT` するまで確定しない。接続が切れたら自動で `ROLLBACK`。**
- 「確定を宣言しない限り確定しない」という設計思想として言う
- △ `START TRANSACTION` は「同じもの」で流す

### 1-3.【手を動かす】ROLLBACK を体験 ◎🔬 5分
**必ず画面で。受講生にも打たせる。**
**落とす一言**：**本番のデータを触る前に `BEGIN` と打つ。これは自分を守るための習慣。**
- ③の「トランザクションの中では自分の変更が見えている」を強調 → **15-2 §2 の伏線**
- 「`ROLLBACK` は Ctrl+Z ではない。`COMMIT` 済みは戻せない」を必ず言う

## 2. 自動コミット

### 2-1. BEGIN を書かないSQLはどうなっているか ◎ 3分
**落とす一言**：**トランザクションを使っていなかったのではなく、1文ずつのトランザクションを使っていた。**
- 14章まで `BEGIN` を書かなかったのに動いていた理由、として入る

### 2-2. ツールによる違い ○ 3分
**落とす一言**：**どれも既定は自動コミット on。off にするのは自分の意思。**
- **表の修正済み**：以前 Spring の行を「既定でメソッド全体が1トランザクション」と書いていたが誤り。**`@Transactional` を付けなければ JDBC と同じ（on）**
- 「`@Transactional` は、そのメソッドにいる間だけ自動コミットを off にしてくれる道具」と言うと、他ツールと同じ枠で理解できる
- 「既定 off のドライバもある。そこで `COMMIT` 忘れ＝ロックを握り続ける」→ **15-2 §1-1 に繋ぐ**

### 2-3.【手を動かす】中断状態 ◎🔬 6分
**この章で最も「あとで助かる」節。必ず画面で出す。**
**落とす一言**：**`current transaction is aborted` を見たら、原因はそのSQLではない。もっと前のエラーを探せ。**
- **`COMMIT;` と打ったのに `ROLLBACK` が返る**——ここで一度止めて画面を指す
- 「新人が半日溶かす典型」と言ってよい
- 復帰方法は §4 の SAVEPOINT で回収する（演習問題2）
- 🐘 **ここで初めて 🐘 マークが出ます。** 15-1 冒頭の「どこまでが他のDBでも通じるか」の表を一度指してください
  「**Oracle や MySQL はエラーが出た文だけ失敗する。トランザクション全体は続けられる**」と添えると、あの表の意味が伝わります。**他DB経験者がいる回では特に効きます**（一番驚かれるポイント）

## 3. ACID

### ACID の表 → 「この章のどこで扱うか」の対応表 ◎ 3分
**落とす一言**：**この章で本気で考えるのは A、次の章で本気で考えるのが I。**
- ACID の4文字暗記は求めない。**「A は §3-1・§1・§4、C は §3-2、I は 15-2 まるごと、D は §3-3」**という地図だけ渡す
- △ 一貫性の検査タイミング（文の直後／`DEFERRABLE`）は**折りたたみに格下げ済み**。飛ばしてよい

### 3-1. 原子性（A）：どこまでを1つの塊にするか ◎ 4分
**落とす一言**：**業務として「一緒に無かったことにしたい」範囲を、1つの塊にする。**
- **この章の時点では「小さすぎると壊れる」だけを扱う。**「大きすぎると困る」理由は**まだ言わない**（ロックを見ていないので実感できない）→ 15-2 §6 で回収
- ⚠️ 旧版はここで「大きすぎるとロックを長く握る」と書いていたが、**この時点では伏線として成立しないので削除済み**

### 3-2. 一貫性（C）：制約はいつ検査されるか ○ 4分
**落とす一言**：**検査は `COMMIT` 時ではなく、その文の直後。**
- **後半の「どこまで制約にして、どこからアプリで守るか」が本題**。制約とアプリの二重管理は実務で必ず悩むところ
- 落とす一言その2：**「アプリで業務エラーを返し、制約は最後の砦として置く」と役割を分ける**
- ⚠️ **旧版の「在庫はマイナスにしない＝DBが知らないルール」は誤りだったので修正済み**（`CHECK` で書ける）。いま書いてあるのは「複数行・複数テーブルにまたがるルールは制約では書けない」

### 3-3. 永続性（D）：WAL △ 3分
**落とす一言**：**`COMMIT` が速いのは、テーブル本体ではなくログを1本書いているだけだから。**
- 🐘 「**先にログを書く**という考え方はどのDBも同じ。`WAL` という呼び名が PostgreSQL 固有」
- **飛ばす／繋ぎ**：「WALはindexの章とも繋がるので、17-1 §8 を見ておいてください」

## 4. SAVEPOINT

### 4-1〜4-2.【手を動かす】部分的に戻す ○🔬 6分
**落とす一言**：**`ROLLBACK TO SAVEPOINT` してもトランザクションは終わらない。**
- 出力の `product_id=1 は 1500 のまま / 2 は 800 に戻る` を画面で見せる
- **§2-3 の中断状態から復帰できることは、ここでは言わない。** 演習問題2で自分で気づかせる

### 4-3. 使いどころと注意 △ 2分
**出す数字**：**1トランザクション内で64個を超えると性能が落ちる**
- 「ループで1件ごとに置くな」だけ言えばよい

### 4-4. `SAVEPOINT` は実務でどれくらい使うか − 読み物
**質問されたとき用**（「これ実際に使うんですか？」は必ず聞かれます）。
- **アプリのコードに自分で書くことはほぼ無い。**ただし **PL/pgSQL の `BEGIN ... EXCEPTION` は裏で作っている**（12〜13章と演習7・8に直結）
- Java からも書けるが（`conn.setSavepoint()`）稀。Spring の `NESTED` の正体もこれ
- **一番効く一言**：**`SAVEPOINT` はトランザクションを短くしない。**「部分的な失敗を許容する」道具であって、境界を刻むのは `COMMIT` の仕事
  → バッチで「1件失敗しても続行」なら、本命は **`COMMIT` を刻むほう**（演習問題8）

## 5. BEGIN の入れ子はできない △ 3分
**落とす一言**：**`ERROR` ではなく `WARNING` なのが厄介。黙って無視される。**
- 5-2 の「内側のつもりの `ROLLBACK` が全部巻き戻す」を1回読む
- **飛ばす／繋ぎ**：「区切りたいなら `SAVEPOINT`。それが §4 がある理由です」

## 1. 書き込み同士はぶつかる

### 1-1.【2窓】UPDATE は待たされる ◎👥 8分
**この章の入口。ここが決まると後が全部楽になる。**
**落とす一言**：**行ロックは、トランザクションが終わるまで絶対に外れない。**
**出す数字**：窓Bの `UPDATE` は **5,958ms** 待たされた（＝窓Aが握っていた時間そのもの）
- 窓Bが返ってこない状態で**一度手を止めて全員に確認させる**
- 窓Aの `COMMIT` で窓Bが動く瞬間を見せる。ここが一番効く
- 「昼休みに `BEGIN` して放置＝障害」を言う（→ 演習問題6で回収）

### 1-2. 待たされた側はどの値を読み直すか ◎ 5分
**落とす一言**：**待たされた `UPDATE` は、ロックが外れてから行を読み直す。だから 1350。**
- 1250 じゃないの？ という顔をしたら勝ち。**READ COMMITTED の肝**
- **⚠️の「DB側で計算しているから正しい」を必ず言う** → §4-1 の伏線。ここを張らないとロストアップデートが刺さらない

### 1-3. 誰が誰を待っているか ○🔬 4分
**落とす一言**：**固まったら、外から「誰が誰を待っているか」を確認できる。**
- `pg_blocking_pids()` を画面で実行して見せる
- ⚠️ **旧版の「実務で最も使う1本なので書き写して」は削除済み。** 研修生が実務で PostgreSQL を使うとは限らないので、**クエリの暗記ではなく「そういう窓口がある」ことを持ち帰らせる**

### 1-4. 犯人の状態を見て、必要なら止める ○🔬 6分
**ここが「確認とキル」の本体。演習問題6で全部使います。**
**落とす一言**：**`query` 列は「今実行中のSQL」ではなく「最後に実行したSQL」。`state` とセットで読む。**
- `state` の3分類（`active` / **`idle in transaction`** / `idle`）を板書。**`idle in transaction` ＝ `COMMIT` 漏れ**
- 「昼休みに `BEGIN` して放置＝障害」はここで言う
- `pg_cancel_backend`（穏当）と `pg_terminate_backend`（接続ごと切る）の違い
- **落とす一言その2**：**`idle in transaction` に `pg_cancel_backend` は効かない。`t` が返っても止まっていない**（演習問題6の問い4がここ）
- 🐘 「名前は PostgreSQL 固有。Oracle なら `V$SESSION` と `ALTER SYSTEM KILL SESSION`、MySQL なら `SHOW PROCESSLIST` と `KILL`」
- **これ以上（`pg_locks` / タイムアウト設定）は [[15-4_補足_ロック待ちの調査と予防|15-4（講師用）]] に隔離済み。受講生には配りません**

## 2. 読み取りは待たされない：MVCC

### 2-1.【2窓】SELECT は即座に返る ◎👥 6分
**落とす一言**：**読み取りと書き込みは互いにブロックしない。これが PostgreSQL の同時実行性能の土台。**
**出す数字**：**0.917ms** で返る。値は**古い 1200**
- §1-1 と対比させる。「さっきは待った、今度は待たない。何が違う？」と問う

### 2-2. なぜ古い値が読めるのか ◎ 5分
**落とす一言**：**PostgreSQL は `UPDATE` で元の行を上書きしない。新しい行を別に足している。**
- 表（読み×読み／読み×書き／書き×書き）を板書推奨
- **この「便利さ」が §4-1 で牙を剥く**、と予告しておくと効く

### 2-3. MVCC の代償 △ 2分
**飛ばす／繋ぎ**：「溜まった古い行を回収するのが `VACUUM`。普段は autovacuum が裏で走っています」（資料 §2-3 に説明あり。**深追いしない**）

## 3. 分離レベル

> **節番号に注意。**資料の §3 は **3-1〜3-4 の4節**です（以前このカンペは 3-1〜3-6 と書いていましたが、資料と合っていませんでした）。
> 3つの現象・標準／実際の対比表・「覚えるべき2点」・READ UNCOMMITTED の実演は、**すべて §3-1 の中**に入っています。

### 3-1. 分離レベルの一覧：標準とPostgreSQLの実際 ◎🔬 9分
この1節に4つ詰まっているので、この順で話します。

1. **3つの現象**（ダーティ／ノンリピータブル／ファントム）… 表を上から。**名前だけ通せばよい** ○ 4分
2. **標準 vs PostgreSQL の対比表** … 「他のDBの教科書の表をそのまま覚えるな」の実例として使う
3. **落とす一言**：**覚えるのは2つだけ。「ダーティリードは起きない」「Repeatable Read はファントムも防ぐ」。** ◎ 3分
4. **折りたたみの実演**（READ UNCOMMITTED は効かない） 🔬 2分
   - `SHOW transaction_isolation` が `read uncommitted` と返るのに、**見えるのは 1200**——この食い違いを画面で見せる
   - **3分で強い驚きを作れるので、押していても残す価値があります**

### 3-2. READ COMMITTED と REPEATABLE READ の挙動差 ○ 4分
**出す数字**：READ COMMITTED は **1200 → 1300 / 件数5**、REPEATABLE READ は **1200 → 1200 / 件数4**
- 再現手順は資料の折りたたみの中。**時間が押していたら実演せず表だけ見せる**（ここは削れる）

### 3-3. REPEATABLE READ 以上は「失敗する」ことがある △ 3分
**落とす一言**：**待つのではなく、エラーで落ちる。だからリトライ処理が必須。**
- `could not serialize access due to concurrent update` を読み上げる
- **飛ばす／繋ぎ**：「上げるならリトライとセット、とだけ覚えて」

### 3-4. どれを使えばいいか ◎ 2分
**落とす一言**：**既定の READ COMMITTED のままでよい。**
- 「特定の行を触らせたくないだけなら、分離レベルより行ロック」→ **§4 へ繋ぐ**

## 4. 明示的な行ロック

### 4-1.【2窓】ロストアップデート ◎👥 12分
### **この章の山場。何を削ってもここは削らない。**
**落とす一言**：**「読んで、計算して、書き戻す」は壊れる。テストでは絶対に発覚しない。**
**出す数字**：両方が **50** を読み、最終在庫 **47**（正解は 42）。**窓Aの5個が完全に消える**
- 手順の前に「正解はいくつ？」と聞いて **42** と言わせてから始める
- **§2 の MVCC が裏目に出ている**と明示的に繋ぐ。「さっき褒めた性質が、ここでは敵」
- 「本番の繁忙時にだけ起きる」＝一番厄介なバグ、と締める

### 4-2. 悲観ロック：FOR UPDATE で先に押さえる ◎🔬 8分
**落とす一言**：**待つ位置が `UPDATE` から `SELECT` に前倒しされる。だから古い値を掴めなくなる。**
**出す数字**：窓Bの `SELECT ... FOR UPDATE` が **3,229ms** 待ち、読む値は **45** → 42 になる
- 💡の「1文で書けば `FOR UPDATE` は要らない」を必ず言う。**要るのは「読んで判断してから書き戻す」時だけ**
- 在庫チェック（足りなければ断る）がまさにそれ → 演習問題7に直結
- **「悲観ロック」という用語をここで出す。** §4-3 の「楽観ロック」と対になるので、名前で覚えさせる
- NOWAIT / SKIP LOCKED は**折りたたみに格下げ済み**。「待ちたくない時の逃げ道が2つある」で通過（`SKIP LOCKED` はジョブキューの定番、とだけ）

### 4-3.【2窓】楽観ロック − 読み物（演習問題4で回収）
**落とす一言**（触れるなら1文だけ）：**楽観ロックの失敗は、エラーではなく `UPDATE 0` として返ってくる。**
**出す数字**：窓Bは **2,901ms 待たされたのち `UPDATE 0`**（行は `stock_quantity=45 / version=2` になっている）
- **§0 で足した `version` 列をここで使います。**「更新したら version を1増やす／読んだときの version のままなら更新する」の2点だけ
- 質問されたら：**なぜ `stock_quantity` そのものを条件にしないのか → 「50→45→50」と戻された場合を見逃すから。version は増える一方**
- **講義では扱いません。**「もう一つの直し方が資料にあります。演習問題4の後半でやります」で通す
- **触れるなら §1-2 との接続だけ**：待たされた `UPDATE` が行を読み直す（＝1350になった理由）→ だから `WHERE` の条件も最新の行で評価されて0件になる。**同じ仕組みが検知装置として働いている**
- 質問されたら：**専用の `version` 列を使うのが定番。フレームワークが自動化していることもある**（Spring Data JPA の `@Version` など）。**中で組み立てている SQL はいま手で書いたものと同じ**、と言えば十分
  ※ **外部研修生は SQL のみ受講**なので、Java の資料へのリンクは資料本体には貼っていません（折りたたみに一般論として残してあります）

### 4-4. 書き戻しパターンの3分類 − 読み物（余裕があれば3分）
**落とす一言**：**まず①1文で書けないか疑う。無理なら、人が挟まるなら③楽観、挟まらず競合が頻繁なら②悲観。**
- **この表だけは板書する価値があります。**演習問題4の問い8がこれを問います
- **判断軸は2つ**に整理してあります：**①読んでから書くまでに何が挟まるか ②どれくらいの頻度でぶつかるか**
  - 人が挟まるのに②悲観を選ぶ＝**画面を開いている5分間ずっとロック**（これが一番効く）
  - 競合が頻繁なのに③楽観を選ぶ＝**リトライ地獄**
- 「①と③はどちらも**更新0件を見て判断する**。エラーが出ないから成功、と書くコードは両方で壊れる」
- 折りたたみに**4つめ（そもそも競合させない設計：キュー化／履歴を追記して合算）**を入れてあります。聞かれたときだけ

### 4-5. ロックの種類と強さ ○ 5分
**構成を変えました。モード表を先頭に置き、`FOR SHARE` をこの節に吸収しています。**
**落とす一言**：**自分で書くのは実質 `FOR UPDATE` だけ。残りは PostgreSQL が必要最小限の強さで勝手に取っている。**
- 4段階の表 → 「下に行くほど邪魔しない」だけ押さえる。**暗記不要**
- `FOR SHARE` の実測：同士は **1.864ms**（通る）／vs `UPDATE` は **5,880ms**（待つ）
- ⚠️ **以前このカンペと資料に「`pg_locks` を見たときに読めるように」と書いてありましたが、誤りでした。**
  **この4つのモードは `pg_locks` には出てきません**（行ロックはロック管理表ではなく行そのものに書かれるため）。訂正済み。詳細は 15-4（講師用）§3-2

### 4-6.【2窓】FKは黙ってロックを取っている ○👥 7分
**落とす一言**：**自分で `LOCK` を書いていないのに待たされることがある。FK が裏で取っている。**
**出す数字**：親の非キー列 `UPDATE` は **2.512ms**（通る）／親の `DELETE` は **6,861ms**（待つ）
- 「注文を登録しただけなのに顧客マスタの更新が固まった」という実務あるあるとして話す
- **逆に「FKのために自分で `FOR SHARE` を書く必要はない」**と明言する（よくある誤解）
- 締めに §4-5 の表へ戻る：**「住所の UPDATE が通ったのは、`city` がキー列じゃないから」**——表の並びがそのまま結果になっている

## 5. デッドロック

### 5-1.【2窓】起こしてみる ◎👥 8分
**落とす一言**：**ロックを取る順番が逆なだけで起きる。**
- **どちらが殺されるかは選べない**を強調
- エラーメッセージの `Process X waits ... blocked by process Y` の2行を指して読む

### 5-2. 検知の仕組み ○ 3分
**出す数字**：`deadlock_timeout` = **1s**
**落とす一言**：**毎回調べているわけではない。検査自体が高いから。だから1秒くらい待つのは正常。**

### 5-3. 対策 ◎ 5分
**落とす一言**：**全員が同じ順番でロックを取れば起きない。**

## 6. トランザクションの境界 − 読み物（余裕があれば8分）

**講義では扱いません。演習問題9（紙の問題）で回収します。**

触れるなら、**6-2 の表だけ**を口頭で。ここが一番効きます。

**落とす一言**：**トランザクションの中で外部APIを呼ばない。送ったメールは `ROLLBACK` できない。**

  ※ **外部研修生は SQL のみ受講**なので、本文は「多くのフレームワークでは関数・メソッドの入口と出口が境界」という一般論で書いてあります。**弊社の研修生には折りたたみを開いて Spring の表を見せてください**
- 締めの一文を板書推奨：**「トランザクションは短く。ただし、業務として一緒に取り消したい範囲より小さくしてはいけない。」**

## 15-3（補足）の扱い

**15-3 は講義では扱いません。** 演習問題7・8 を解くときの参照先として渡します。

> 「プロシージャの中で `COMMIT` が書けるかどうかは、書く場所で変わります。問題7と8でそこを踏むので、詰まったら 15-3 を見てください。」

**質問された時に出せるポイント**：

- 関数（`FUNCTION`）は**常に**トランザクション制御不可。プロシージャ（`PROCEDURE`）は**条件付きで**可
- 外側で `BEGIN;` されていると `invalid transaction termination`
- `EXCEPTION` 句を持つブロックの**本体**での `COMMIT` は `cannot commit while a subtransaction is active`
- **`EXCEPTION` ハンドラの中は通ってしまう**（が、不要かつ危険なので書かない）
