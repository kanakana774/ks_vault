# 15章 講義カンペ（トランザクションと排他制御）

講義中に手元に置く用。**資料と同じ順番**に並べているので、上から下に進めれば流れは崩れません。

各節の書き方：

- **落とす一言** … その節で受講生の頭に残せば勝ちの1文
- **出す数字** … 口に出す実測値
- **飛ばす／繋ぎ** … 話さない部分と、その場合の一言

扱いの記号：

| 記号 | 意味 |
| :---: | :--- |
| ◎ | 必ず話す（外すと後が繋がらない） |
| ○ | 話す |
| △ | 一言で流す |
| − | 読み物。「資料にあるので読んでおいて」で済ます |
| 🔬 | 画面で実行して見せる |
| 👥 | **2窓で見せる**（この章の主役） |

---

## この章の設計思想

**15-1 は「1つの窓で完結する話」、15-2 は「2つの窓がないと分からない話」で割っています。**

同時実行は口で説明しても伝わりません。**15-2 は全部画面で見せてください。** 資料は「講義後に自分で再現するための手順書」として書いてあります。

**この章で一番残したいのは 15-2 §4-1（ロストアップデート）です。** ここだけは絶対に削らないでください。「読んで、計算して、書き戻す」が壊れることを体験させるのが、この章の存在理由です。

> **2026-08 追記：資料に §4-3（楽観ロック）／§4-4（書き戻し3分類）／§6（トランザクションの境界）と、15-4（ロック待ちの調査と予防）を足しました。**
> **講義時間は増やしていません。**これらは全部「−（読み物）」扱いで、**演習問題4・6・9で回収します。**講義では表を指差して「詳しくは資料」で通してください。

# 15-1 導入編

## 1. なぜトランザクションが必要か

### 1-1. 途中で落ちると何が起きるか ◎ 4分
**落とす一言**：**2つ以上の更新をセットで扱う処理は、放っておけば必ずいつか壊れる。**
- 送金の例で「①だけ成功して②の直前で落ちる」→ **お金が消滅する**
- 「めったに起きない」で流さない。再起動・切断・アプリの例外、どれでも同じ
- △ 「1文なら安全」の理由（暗黙のトランザクション）は §2 で回収するので、ここでは触れる程度

### 1-2. BEGIN / COMMIT / ROLLBACK ◎ 3分
**落とす一言**：**`COMMIT` するまで確定しない。接続が切れたら自動で `ROLLBACK`。**
- 「確定を宣言しない限り確定しない」という設計思想として言う
- △ `START TRANSACTION` は「同じもの」で流す

### 1-3.【手を動かす】ROLLBACK を体験 ◎🔬 5分
**必ず画面で。受講生にも打たせる。**
**落とす一言**：**本番のデータを触る前に `BEGIN` と打つ。これは自分を守るための習慣。**
- ③の「トランザクションの中では自分の変更が見えている」を強調 → **15-2 §2 の伏線**
- 「`ROLLBACK` は Ctrl+Z ではない。`COMMIT` 済みは戻せない」を必ず言う

## 2. 自動コミット

### 2-1. BEGIN を書かないSQLはどうなっているか ◎ 3分
**落とす一言**：**トランザクションを使っていなかったのではなく、1文ずつのトランザクションを使っていた。**
- 14章まで `BEGIN` を書かなかったのに動いていた理由、として入る

### 2-2. ツールによる違い ○ 3分
**落とす一言**：**自分が今使っているツールがどちらか、最初に確認する。**
- 表を上から。**Python（psycopg）だけ既定 off** なのを指差す
- 「off のツールで `COMMIT` 忘れ＝ロックを握り続ける」→ **15-2 §1-1 に繋ぐ**

### 2-3.【手を動かす】中断状態 ◎🔬 6分
**この章で最も「あとで助かる」節。必ず画面で出す。**
**落とす一言**：**`current transaction is aborted` を見たら、原因はそのSQLではない。もっと前のエラーを探せ。**
- **`COMMIT;` と打ったのに `ROLLBACK` が返る**——ここで一度止めて画面を指す
- 「新人が半日溶かす典型」と言ってよい
- 復帰方法は §4 の SAVEPOINT で回収する（演習問題2）

## 3. ACID

### 3-1. 4つの特性とDB／開発者の分担 ○ 6分
**落とす一言**：**ACIDはDBに任せれば守られるものではない。A（どこを1つの塊にするか）は開発者の仕事。**
- 表を上から。**「開発者がやること」の列を読む**のが本題
- 塊が小さすぎ＝整合性が壊れる／大きすぎ＝ロックを長く握る（→ 15-2 §1-1、演習問題8）
- △ ACIDの4文字暗記は求めない。「Iだけ次の章まるごと使う」と言って繋ぐ

### 3-2. Durability と WAL △ 3分
**落とす一言**：**`COMMIT` が速いのは、テーブル本体ではなくログを1本書いているだけだから。**
- **飛ばす／繋ぎ**：「WALはindexの章とも繋がるので、17-1 §8 を見ておいてください」

## 4. SAVEPOINT

### 4-1〜4-2.【手を動かす】部分的に戻す ○🔬 6分
**落とす一言**：**`ROLLBACK TO SAVEPOINT` してもトランザクションは終わらない。**
- 出力の `product_id=1 は 1500 のまま / 2 は 800 に戻る` を画面で見せる
- **§2-3 の中断状態から復帰できることは、ここでは言わない。** 演習問題2で自分で気づかせる

### 4-3. 使いどころと注意 △ 2分
**出す数字**：**1トランザクション内で64個を超えると性能が落ちる**
- 「ループで1件ごとに置くな」だけ言えばよい。詳細は演習問題8で回収

## 5. BEGIN の入れ子はできない △ 3分
**落とす一言**：**`ERROR` ではなく `WARNING` なのが厄介。黙って無視される。**
- 5-2 の「内側のつもりの `ROLLBACK` が全部巻き戻す」を1回読む
- **飛ばす／繋ぎ**：「区切りたいなら `SAVEPOINT`。それが §4 がある理由です」

## 2. 読み取りは待たされない：MVCC

### 2-1.【2窓】SELECT は即座に返る ◎👥 6分
**落とす一言**：**読み取りと書き込みは互いにブロックしない。これが PostgreSQL の同時実行性能の土台。**
**出す数字**：**0.917ms** で返る。値は**古い 1200**

### 2-2. なぜ古い値が読めるのか ◎ 5分
**落とす一言**：**PostgreSQL は `UPDATE` で元の行を上書きしない。新しい行を別に足している。**
- 表（読み×読み／読み×書き／書き×書き）を板書推奨

### 2-3. MVCC の代償 △ 2分

## 3. 分離レベル

## 4. 明示的な行ロック

### 4-1.【2窓】ロストアップデート ◎👥 12分
### **この章の山場。何を削ってもここは削らない。**
**落とす一言**：**「読んで、計算して、書き戻す」は壊れる。テストでは絶対に発覚しない。**
**出す数字**：両方が **50** を読み、最終在庫 **47**（正解は 42）。**窓Aの5個が完全に消える**

- 「本番の繁忙時にだけ起きる」＝一番厄介なバグ、と締める

### 4-2. FOR UPDATE で防ぐ ◎🔬 8分
**落とす一言**：**待つ位置が `UPDATE` から `SELECT` に前倒しされる。だから古い値を掴めなくなる。**
**出す数字**：窓Bの `SELECT ... FOR UPDATE` が **3,229ms** 待ち、読む値は **45** → 42 になる
- 💡の「1文で書けば `FOR UPDATE` は要らない」を必ず言う。**要るのは「読んで判断してから書き戻す」時だけ**
- 在庫チェック（足りなければ断る）がまさにそれ → 演習問題7に直結

### 4-3.【2窓】楽観ロック − 読み物（演習問題4で回収）
**落とす一言**（触れるなら1文だけ）：**楽観ロックの失敗は、エラーではなく `UPDATE 0` として返ってくる。**
**出す数字**：窓Bは **2,629ms 待たされたのち `UPDATE 0`**
- **講義では扱いません。**「もう一つの直し方が資料にあります。演習問題4の後半でやります」で通す

### 4-4. 書き戻しパターンの3分類 − 読み物（余裕があれば3分）

### 4-5. NOWAIT / SKIP LOCKED △ 4分
**落とす一言**：**`SKIP LOCKED` はジョブキューの定番。**
- 実測（1,2がロック中なら3が返る）を見せると早い
- **飛ばす／繋ぎ**：「待ちたくない時の逃げ道が2つある、とだけ」（N秒だけ待つ `lock_timeout` は 15-4 §4-3）

### 4-6. FOR SHARE ○ 4分

## 6. トランザクションの境界 − 読み物（余裕があれば8分）

**講義では扱いません。演習問題9（紙の問題）で回収します。**

触れるなら、**6-2 の表だけ**を口頭で。ここが一番効きます。

**落とす一言**：**トランザクションの中で外部APIを呼ばない。送ったメールは `ROLLBACK` できない。**

- 理由は2つセットで言う：**(1) `ROLLBACK` で取り消せない副作用**／**(2) 相手の応答時間ぶん行ロックを握り続ける**（→ §1-1 の 5,958ms）
- 「決済APIが30秒詰まったら、その商品を買おうとした人が全員30秒止まる。**テストでは絶対に発覚しない**」
- 6-3 の `@Transactional` は**2か月目のAPI研修への予告**として1文だけ：「境界を変えるとは、メソッドを分けること」
- 締めの一文を板書推奨：**「トランザクションは短く。ただし、業務として一緒に取り消したい範囲より小さくしてはいけない。」**
  片方だけ覚えると壊れる（前半だけ＝§4-1 の壊れ方／後半だけ＝外部APIを抱えたまま長時間ロック）

# 15-4 ロック待ちの調査と予防 − 全部読み物

**講義では通しません。** ただし **15-3 と違って、これは受講生に配ります。**

> 「処理が固まったときに何をどの順で見るか、手順書にしてあります。演習問題6で使うので、そこで開いてください。」

**演習問題6で受講生が触る範囲**：

- §2 `idle in transaction` … **`state` を見ないと誤診する**（`query` は「最後に実行したSQL」）
- §2-4 `pg_cancel_backend` が効かない … **`t` が返っても止まっていない**
- §3-2 `pg_locks` に行ロックのモードは出てこない … **ここが問題6の問い6**
- §4 4つのタイムアウト … **既定は全部 `0`＝無効＝永久に待つ**

**質問されたら出せるポイント**：

- `lock_timeout` と `statement_timeout` は**エラーメッセージで区別できる**（`due to lock timeout` / `due to statement timeout`）→ 原因の方向が違う
- `SET LOCAL lock_timeout` は**アプリのコードに書ける**。`idle_in_transaction_session_timeout` と `log_lock_waits` は**サーバー設定なので管理者に依頼する**
- `log_lock_waits` は既定 `off`。**事前に on にしていないと、後から「あのとき何が詰まっていたか」は分からない**
- 締めに使える一言：**「設定値を決めるのは1年目の仕事ではないが、依頼できることを知っているのは1年目の仕事」**

## 15-3（補足）の扱い

**15-3 は講義では扱いません。** 演習問題7・8 を解くときの参照先として渡します。

> 「プロシージャの中で `COMMIT` が書けるかどうかは、書く場所で変わります。問題7と8でそこを踏むので、詰まったら 15-3 を見てください。」

**質問された時に出せるポイント**：

- 関数（`FUNCTION`）は**常に**トランザクション制御不可。プロシージャ（`PROCEDURE`）は**条件付きで**可
- 外側で `BEGIN;` されていると `invalid transaction termination`
- `EXCEPTION` 句を持つブロックの**本体**での `COMMIT` は `cannot commit while a subtransaction is active`
- **`EXCEPTION` ハンドラの中は通ってしまう**（が、不要かつ危険なので書かない）
