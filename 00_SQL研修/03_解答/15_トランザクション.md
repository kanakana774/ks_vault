### 問題1：行ロックと待機（クエリツール2窓での操作）
この問題では、PostgreSQLがどのように行を保護し、他のトランザクションを待機させるかを体験します。

**【手順】**
1. `窓A`：クエリツールを開き、以下のSQLを実行してください（まだCOMMITしません）。
   ```sql
   BEGIN;
   -- 商品ID: 1 (Laptop) の価格を更新
   UPDATE Products SET price = price + 100 WHERE product_id = 1;
   ```
2. `窓B`： 別のクエリツールを開き、以下のSQLを実行してください。
   ```sql
   -- 同じ商品ID: 1 の価格をさらに更新しようとする
   UPDATE Products SET price = price + 50 WHERE product_id = 1;
   ```
3. 窓Bの実行ボタンが「実行中...（停止ボタンが光っている状態）」になり、処理が終わらないことを確認してください。
4. 窓Aで `COMMIT;` を実行してください。
5. 窓Bの処理が即座に完了することを確認してください。

窓Bで `COMMIT;` を行った後、商品ID: 1 の最終的な価格はいくらになりますか？また、なぜ窓Bは待機させられたのか、講義資料の言葉（ロックの種類）を使って説明してください。
#### 解答
このプロシージャが同時に複数のセッション（顧客）から実行された場合を考えてみましょう。
*   **排他制御がない場合（Race Condition）**:
    1.  ユーザーAが在庫10を確認。
    2.  ユーザーBが在庫10を確認（ほぼ同時）。
    3.  ユーザーAが5個注文し、在庫を5に更新。
    4.  ユーザーBが8個注文しようとするが、さっき確認した「10」を基準に計算してしまうと、実際の在庫が足りないのに注文が通ってしまう（または在庫がマイナスになる）リスクがあります。
*   **SELECT FOR UPDATE の効果**:
    ユーザーAが `SELECT ... FOR UPDATE` を実行した瞬間、その行にロックがかかります。ユーザーBが同じ行を `SELECT ... FOR UPDATE` しようとすると、ユーザーAのトランザクションが終了（COMMIT/ROLLBACK）するまで待機状態になります。これにより、正確な在庫数に基づいた処理が保証されます。

### 問題2：在庫引き当てを伴う注文処理の自動化
顧客から商品の注文を受けた際、在庫をチェックして注文を確定させるストアドプロシージャ `proc_create_order` を作成してください。このプロシージャは以下の仕様を満たす必要があります。

1.  **引数**: `p_customer_id` (顧客ID), `p_product_id` (商品ID), `p_warehouse_id` (倉庫ID), `p_quantity` (注文数)
2.  **排他制御**:
    *   在庫確認から更新までの間、他のセッションが同じ商品の在庫を書き換えないよう、`INVENTORY` テーブルの該当行に対して **行ロック（SELECT FOR UPDATE）** を取得してください。
3.  **在庫チェック**:
    *   指定された倉庫に十分な在庫があるか確認してください。
    *   在庫が不足している場合は、独自エラー（EXCEPTION）を発生させ、処理を中断してください。
      ※難しければ、`RAISE NOTICE`でログを出力するだけでいいです。
4.  **注文処理（トランザクション内で行うこと）**:
    *   `ORDERS` テーブルに新規レコードを挿入する（STATUSは 'Pending' 固定）。
    *   `ORDERITEMS` テーブルに明細レコードを挿入する。
    *   `INVENTORY` テーブルの在庫数（STOCK_QUANTITY）を注文数分減算する。
5.  **一貫性の保持**:
    *   いずれかの処理でエラーが発生した場合は、全ての変更を無効（ROLLBACK）にし、全ての処理が成功した場合のみ確定（COMMIT）させてください。
#### 解答
```sql
CREATE OR REPLACE PROCEDURE proc_create_order(
    p_customer_id INT,
    p_product_id INT,
    p_warehouse_id INT,
    p_quantity INT
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_order_id INT;
    v_current_stock INT;
BEGIN
    -- 1. 排他制御：対象の在庫レコードを行ロックする
    -- (SELECT FOR UPDATE により、他トランザクションからの更新を待機させる)
    SELECT stock_quantity INTO v_current_stock
    FROM inventory
    WHERE product_id = p_product_id AND warehouse_id = p_warehouse_id
    FOR UPDATE;

    -- 2. 在庫チェック
    IF v_current_stock IS NULL THEN
        RAISE EXCEPTION '指定された商品または倉庫が存在しません。';
    ELSIF v_current_stock < p_quantity THEN
        RAISE EXCEPTION '在庫不足です。現在の在庫: %, 注文数: %', v_current_stock, p_quantity;
    END IF;

    -- 3. ORDERSテーブルへ挿入 (IDは本来シリアルだが、今回は簡易的にMAX+1とする)
    SELECT COALESCE(MAX(order_id), 0) + 1 INTO v_order_id FROM orders;
    
    INSERT INTO orders (order_id, customer_id, order_date, status)
    VALUES (v_order_id, p_customer_id, CURRENT_DATE, 'Pending');

    -- 4. ORDERITEMSテーブルへ挿入
    INSERT INTO orderitems (order_item_id, order_id, product_id, quantity)
    VALUES ((SELECT COALESCE(MAX(order_item_id), 0) + 1 FROM orderitems), v_order_id, p_product_id, p_quantity);

    -- 5. 在庫数の減算更新
    UPDATE inventory
    SET stock_quantity = stock_quantity - p_quantity
    WHERE product_id = p_product_id AND warehouse_id = p_warehouse_id;

    -- 成功メッセージ
    RAISE NOTICE '注文完了: ORDER_ID %, 商品ID %, 数量 %', v_order_id, p_product_id, p_quantity;

EXCEPTION
    WHEN OTHERS THEN
        -- エラーが発生した場合はロールバック（プロシージャ内の例外は自動的にROLLBACK対象となるが明示的に意識する）
        RAISE INFO 'エラーが発生したため、処理をロールバックします。エラー内容: %', SQLERRM;
        ROLLBACK;
        RETURN;
END;
$$;
```
#### テスト実行例

**正常系：**
```sql
CALL proc_create_order(1, 1, 1, 5);
-- 実行後、ORDERS, ORDERITEMSが増え、INVENTORYの在庫が50→45に減っていることを確認
```

**異常系（在庫不足）：**
```sql
CALL proc_create_order(1, 9, 1, 10);
-- 商品ID:9 (Luxury Sofa) は在庫2しかないため、エラーメッセージが表示され、テーブルは更新されない
```

### 問題3：未発送注文の一括発送バッチ（分割コミット実装）
現在、システム内には「支払い済み（Processing）」の注文が複数あります。これらを一括で「出荷済み（Shipped）」に更新するバッチ処理 `proc_batch_shipping` を作成してください。

**仕様：**
1.  **対象抽出**: `ORDERS` テーブルから `STATUS = 'Processing'` の注文をすべて抽出する。
2.  **ループ処理**: 抽出した注文を1件ずつループで処理する。
3.  **更新内容**: 
    *   `SHIPMENTS` テーブルに新規レコードを作成（Status: 'In Transit', Shipped_Date: 当日）。
    *   `ORDERS` テーブルの `STATUS` を 'Shipped' に更新。
4.  **分割コミット**: **1件処理が終わるたびに `COMMIT` を実行**してください。

**下記は時間があれば試してみてください。**
5.  **擬似エラーの混入**: 
    *   学習のため、特定の条件（例：`order_id = 13`）の時に、あえてエラー（例外）を発生させる仕組みを入れ、**「エラーが起きても、それより前にコミットされたデータは消えない（手戻りがない）」**ことを確認してください。

#### 解答
```sql
CREATE OR REPLACE PROCEDURE proc_batch_shipping()
LANGUAGE plpgsql
AS $$
DECLARE
    v_order_record RECORD;
    v_shipment_id INT;
BEGIN
    -- 1. Statusが 'Processing' の注文をループで回す
    FOR v_order_record IN 
        SELECT order_id FROM orders WHERE status = 'Processing' ORDER BY order_id
    LOOP
        BEGIN
            -- 2. 擬似エラーの発生 (学習用：IDが13の時にエラーを起こす)
            IF v_order_record.order_id = 13 THEN
                RAISE EXCEPTION 'ID:13で予期せぬエラーが発生しました！';
            END IF;

            -- 3. SHIPMENTSの登録 (IDはMAX+1で簡易的に取得)
            SELECT COALESCE(MAX(shipment_id), 0) + 1 INTO v_shipment_id FROM shipments;
            
            INSERT INTO shipments (shipment_id, order_id, shipped_date, status)
            VALUES (v_shipment_id, v_order_record.order_id, CURRENT_DATE, 'In Transit');

            -- 4. ORDERSのステータス更新
            UPDATE orders 
            SET status = 'Shipped' 
            WHERE order_id = v_order_record.order_id;

            RAISE NOTICE '注文ID: % の発送処理に成功しました。', v_order_record.order_id;

            -- 5. ★ここで確定（COMMIT）★
            -- プロシージャ内でのCOMMITにより、この1件はDBに永続化される
            COMMIT;

        EXCEPTION
            WHEN OTHERS THEN
                -- エラーが起きた場合はこの1件だけロールバック
                RAISE WARNING '注文ID: % でエラーが発生しました。この件をスキップします。エラー: %', 
                              v_order_record.order_id, SQLERRM;
                -- プロシージャ内ではEXCEPTIONブロックに入ると自動でサブトランザクションがロールバックされる
        END;
    END LOOP;
END;
$$;
```

#### 体験の手順

このプロシージャを実行して、挙動を確認しましょう。
##### 1. 事前データの確認
現在、`STATUS = 'Processing'` の注文は ID 7 と ID 13 です。
```sql
SELECT order_id, status FROM orders WHERE status = 'Processing';
-- 結果： 7, 13
```
##### 2. プロシージャの実行
```sql
CALL proc_batch_shipping();
```

**実行時の出力ログ（イメージ）：**
> NOTICE: 注文ID: 7 の発送処理に成功しました。
> WARNING: 注文ID: 13 でエラーが発生しました。この件をスキップします。エラー: ID:13で予期せぬエラーが発生しました！

##### 3. 結果の確認
ここが**「手戻りがない」ことを確認する重要ポイント**です。

```sql
SELECT order_id, status FROM orders WHERE order_id IN (7, 13);
```

| order_id | status | 備考 |
| :--- | :--- | :--- |
| 7 | **Shipped** | **成功！COMMITされたので変更が残っている** |
| 13 | **Processing** | **失敗。この件だけ元の状態に戻っている** |

#### 解説：なぜこの処理が重要なのか

1.  **長時間ロックの回避**:
    100万件のデータを一つの `BEGIN...COMMIT` で処理すると、その間ずっとテーブルにロックがかかり、他のユーザーが操作できなくなります。1件ずつ、あるいは1,000件ずつ COMMIT することで、ロックをこまめに解放できます。

2.  **リスタート（再送）の効率化**:
    もし1,000件中900件目でサーバーがダウンした場合、一括コミットだと1件目からやり直しになります。分割コミットしていれば、**「すでに Shipped になったものは飛ばして、900件目から再開する」**という運用が可能です。

3.  **注意点：プロシージャの呼び出し方**:
    `COMMIT` を含むプロシージャを呼び出すときは、**「呼び出し側でトランザクションを開始していないこと」**が条件です。
    （例：`BEGIN; CALL ...; COMMIT;` の中では実行できず、単独で `CALL` する必要があります）
