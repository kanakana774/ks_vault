# 性能とアンチパターン
## 〜どこで遅くなるのかを数字で押さえ、講義で「教えなかった理由」を言えるようにする〜

講義版 [[12-3_制御構造|12-3]] §7 で「ループ内でクエリを投げると約 90 倍遅い」を実測しました。この資料では、**PL/pgSQL のどの書き方にどれだけコストがかかるのか**を一通り測り直し、講師が数字で答えられる状態にします。

後半は、**講義版であえて教えなかった項目とその理由**の一覧です。研修生に「なぜ教えないのか」と聞かれたときの答えになります。

> **この資料の前提**
> - **これは講師用です。研修生には配りません。**
> - PostgreSQL 17 で動作確認しています。掲載している実行時間は**すべて実測**です（同一ホスト・ローカル接続）。
> - 実行時間は環境に依存します。**絶対値ではなく比率**を見てください。
> - 対応する講義版: [[12-1_PLpgSQLの基礎とDOブロック|12-1]] §1-2、[[12-3_制御構造|12-3]] §7

---

## 1. ループと集合演算：差の大きさは「ループの中で何をするか」で決まる

講義版では 2 種類のケースを測っています。**同じ「ループは遅い」でも、桁が違います。**

### 1-1. ケースA：ループの中でクエリを投げる（N+1）

顧客ごとの合計を求める処理を、①顧客をループして毎回集計する ②`GROUP BY` 1 文、で比較しました（10 万行・顧客 500 人）。

```
① ループ版   : 3475.203 ms / 3941.810 ms
② 1文版      :   37.821 ms /   43.985 ms
```

**約 90 倍。** ループ版は同じテーブルを 500 回スキャンしています。

### 1-2. ケースB：ループの中で主キー指定の `UPDATE` をするだけ

10 万行を ①1 行ずつ主キー指定で `UPDATE` ②1 文の `UPDATE`、で比較しました。

```
① ループ版   : 2645.252 ms / 3306.217 ms
② 1文版      : 2225.162 ms / 1732.973 ms
```

**1.2〜1.9 倍**にとどまります。

### 1-3. なぜ差が違うのか

ケースBでは、**どちらの方法でも「10 万行を書き換える」というコスト（WAL 書き込み・ページ更新）が支配的**です。ループのオーバーヘッドはその上に乗るだけなので、比率は小さくなります。

ケースAでは、**ループ版だけが「500 回のテーブルスキャン」という余分な仕事をしています**。1 文版は 1 回のスキャンで済むので、差が仕事量そのものの差になります。

> **講師用の注意**: 「ループは 10 倍遅い」のような一律の数字を言わないでください。**「ループの中でクエリを投げているか」を見る**のが正しい判断基準です。研修生には「N+1」という言葉と一緒に教えると、アプリ側（ORM の N+1）の知識と繋がります。

## 2. `EXCEPTION` ブロックのコスト

`BEGIN ... EXCEPTION` は内部的にセーブポイント（サブトランザクション）を作ります（→ [[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]] §4-2、[[12詳解-3_例外とサブトランザクション|12詳解-3]]）。**エラーが起きなくてもコストがかかります。**

20 万回のループで、内側に `EXCEPTION` ブロックを置く／置かないを比較しました。

```sql
-- ① EXCEPTION なし
DO $$
DECLARE v_x integer;
BEGIN
    FOR i IN 1..200000 LOOP
        v_x := i * 2;
    END LOOP;
END; $$;

-- ② 毎回 EXCEPTION ブロックを通る
DO $$
DECLARE v_x integer;
BEGIN
    FOR i IN 1..200000 LOOP
        BEGIN
            v_x := i * 2;
        EXCEPTION WHEN OTHERS THEN
            NULL;
        END;
    END LOOP;
END; $$;
```

```
① EXCEPTION なし : 11.363 ms
② EXCEPTION あり : 78.019 ms
```

**約 6.9 倍。** 1 回も例外が起きていないのにこの差です。

**「念のため全部 `EXCEPTION` で囲む」がなぜアンチパターンなのか**の根拠がこれです。講義版 [[12-4_関数とプロシージャと例外処理|12-4]] §7-3 で「`EXCEPTION` を書く範囲は狭くする」と教えていますが、理由は可読性だけでなく性能にもあります。

**事前に `IF` でチェックできるなら、そちらの方が速い**というのが結論です。

## 3. 動的 SQL（`EXECUTE`）の再パースコスト

`EXECUTE` は文字列を毎回パースして計画を作り直します（→ [[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §3）。

2 万回のループで、通常の SQL と `EXECUTE` を比較しました。

```sql
-- ① 通常の SQL（プランがキャッシュされる）
DO $$ DECLARE v integer; BEGIN
  FOR i IN 1..20000 LOOP SELECT count(*) INTO v FROM dx_big WHERE id = i; END LOOP;
END; $$;

-- ② EXECUTE（毎回パース）
DO $$ DECLARE v integer; BEGIN
  FOR i IN 1..20000 LOOP EXECUTE 'SELECT count(*) FROM dx_big WHERE id = $1' INTO v USING i; END LOOP;
END; $$;
```

```
① 通常の SQL : 94.672 ms
② EXECUTE    : 553.722 ms
```

**約 5.8 倍。**

**動的 SQL は「必要なときだけ」使ってください。** テーブル名や列名が実行時に決まる場合に限る、というのが講義版 [[12-5_トリガーと動的SQL|12-5]] §6 の立場です。

ただし [[12詳解-1_実行モデルとプランキャッシュ|12詳解-1]] §3-4 のとおり、**「毎回計画を作り直す」ことが利点になる場面もあります**。値の偏りが大きい列で generic plan に固定されて遅くなっているなら、動的 SQL の方が速いこともあります。

## 4. `RAISE NOTICE` のコスト

デバッグ用の `RAISE NOTICE` を消し忘れたまま本番に出す事故はよくあります。2 万回のループで測りました。

```
① RAISE なし                          :   1.285 ms
② RAISE NOTICE あり・client_min_messages = warning（抑止） :   2.605 ms
③ RAISE NOTICE あり・そのまま出力      : 599.567 ms
```

**抑止していれば 2 倍程度ですが、実際にクライアントへ送ると約 470 倍です。**

読み取れることは 2 つです。

1. **コストの大半は「メッセージを組み立ててクライアントに送る」部分**にある。
2. **`client_min_messages` を上げれば、コードから消さなくてもほぼ無害にできる。**

ただし②でも 2 倍になっているとおり、**完全に無料ではありません**。ループの内側に置いた `RAISE NOTICE` は、消すかレベルを `DEBUG` に落とすのが本筋です。

> **講師用**: 研修生の演習コードは `RAISE NOTICE` だらけになります。それでよいのですが、**「本番のバッチでこれをやると、ログの量とコストで死ぬ」**という一言は添えてください。

## 5. `pg_stat_statements` から見ると PL/pgSQL の中はどう見えるか

**この環境には導入されていません**（実測）。

```sql
SELECT name, setting FROM pg_settings WHERE name = 'shared_preload_libraries';
SELECT count(*) AS available FROM pg_available_extensions WHERE name = 'pg_stat_statements';
SELECT count(*) AS installed FROM pg_extension WHERE extname = 'pg_stat_statements';
```

```
           name           | setting 
--------------------------+---------
 shared_preload_libraries | 
(1 row)

 available 
-----------
         1
(1 row)

 installed 
-----------
         0
(1 row)
```

**拡張ファイル自体は用意されていますが、`shared_preload_libraries` が空なので有効化されていません。** 有効にするにはサーバの再起動が必要です。

以下は導入した場合の話（**この環境では未検証**）です。

- 既定の `pg_stat_statements.track = 'top'` では、**アプリから見えるのは `CALL my_proc()` の 1 行だけ**です。中で何百回クエリが走っていても、内訳は見えません。
- `pg_stat_statements.track = 'all'` にすると、**関数・プロシージャの中で実行されたクエリも個別に記録されます**。N+1 を見つけたいならこの設定が必要です。

**「PL/pgSQL に処理を押し込むと、外から性能が見えにくくなる」**というのは、設計上の実在するデメリットです。講義では触れませんが、講師は知っておいてください。

## 6. 「PL/pgSQL に移せば速くなる」という誤解

講義版 [[12-1_PLpgSQLの基礎とDOブロック|12-1]] §1-1 では、PL/pgSQL の利点を**「アプリと DB の往復が減ること」**だと説明しています。ここを正確に押さえてください。

- **往復が減る効果は、ネットワークの遅延に比例します。** アプリと DB が別サーバ（別 AZ、別データセンター）なら 1 往復に数ミリ秒かかるので、100 往復が 1 往復になれば数百ミリ秒の改善になります。
- **同一ホストのローカル接続では、往復のコストはほぼ無視できます。** この研修環境（psql とサーバが同一 PC）では、往復削減の効果を体感できません。
- **DB サーバの CPU は、アプリサーバより増やしにくい**のが普通です。ロジックを DB に寄せると、いちばんスケールさせにくい場所に負荷を集めることになります。

つまり **PL/pgSQL は「速くする道具」ではなく「往復を減らす道具」であり、その効果は環境次第**です。講義版で「PL/pgSQL で書いた方が速い、ではありません」と釘を刺しているのはこのためです。

## 7. 実務での判断基準

**PL/pgSQL を選んでよい場面**

| 場面 | 理由 |
|:---|:---|
| 1 行ごとに前の結果を見て処理を変える必要がある | SQL 1 文では書けない（例: 在庫の順次引き当て） |
| データの整合性を、アプリを経由しない更新に対しても守りたい | トリガー・制約は DB 側にしか置けない |
| 複数の更新を 1 つの塊として、往復 1 回で実行したい | ネットワーク越しの場合に効く |
| 複雑な集計ロジックを、引数付きのビューのように再利用したい | `RETURNS TABLE` |

**選ぶべきでない場面**

| 場面 | 代わりに |
|:---|:---|
| 1 文の SQL で書ける | その 1 文で書く |
| 業務ロジックが今後よく変わる | アプリ側。DB のコードはデプロイもテストもレビューもしにくい |
| チームに PL/pgSQL を読める人が少ない | アプリ側 |
| 外部システムと連携する | アプリ側。DB からの外部呼び出しはトランザクションを長く持つ |

## 8. 講義版で「あえて教えなかったこと」と理由

研修生や他の講師に「なぜこれを教えないのか」と聞かれたときの答えです。

| 外した項目 | 理由 |
|:---|:---|
| **配列 / `FOREACH`** | 演習で一切使わない。SQL の集合演算（`unnest`・`IN`）で書けるものを、わざわざ手続き的に書く癖がつく |
| **JSONB** | 研修全体で JSON を扱っていない。12章だけで出すと前提が飛ぶ。API 研修（2か月目）で扱う方が筋が良い |
| **`CREATE TYPE`** | 型を 1 つ増やすと管理対象が増える。研修の規模では `RECORD` と `%ROWTYPE` で足りる |
| **`VARIADIC`** | 使う場面が研修の題材に無い |
| **`ASSERT`** | `plpgsql.check_asserts` の設定が前提になり、「設定次第で動かないコード」を教えることになる |
| **ブロックラベル `<<name>>`** | 変数の隠蔽を解決する用途は、命名規約（`v_`/`p_`）で不要になる。多重ループの脱出も演習に無い |
| **`GET STACKED DIAGNOSTICS`** | `SQLERRM` と `SQLSTATE` で研修の範囲は足りる。詳細診断は運用の話 |
| **`ON CONFLICT`（UPSERT）** | SQL 側の機能。SQL の章で扱っていないのに PL/pgSQL の章で初出するのは筋が悪い |
| **明示カーソル（`OPEN`/`FETCH`/`CLOSE`）** | `FOR ... IN SELECT` が内部でやってくれる。明示的に書く必要があるのは `WHERE CURRENT OF` と `REFCURSOR` を返す場合だけで、どちらも研修の範囲外 |
| **変動性（`VOLATILE`/`STABLE`/`IMMUTABLE`）** | 実行計画の話が前提になる。17章（index と実行計画）を終えた人向けの話題 |
| **`SECURITY DEFINER`** | 権限設計の話。研修では全員が同じユーザーで作業するので実感できない |
| **プロシージャ内の分割 `COMMIT`** | 条件が 2 つあり、`EXCEPTION` 句との関係も絡む。15章（[[15-3_補足_PLpgSQLの中のトランザクション制御|15-3]]）で扱うのが正しい順序 |
| **文トリガー・遷移テーブル** | トリガー自体が 12-5 で初出。行トリガーを理解する前に選択肢を増やさない |

**共通する方針は 2 つです。**

1. **演習で使わないものは講義に置かない。** 使わない知識は定着せず、資料が長くなるだけです。
2. **他の章で扱う方が筋が良いものは、そちらに送る。** 12章を「PL/pgSQL の全部」にしないことで、章の役割がはっきりします。

## まとめ

- **ループが遅いかどうかは「ループの中でクエリを投げているか」で決まる。** N+1 なら約 90 倍、単純な行ごと更新なら 1.2〜1.9 倍（実測）
- **`EXCEPTION` ブロックは、例外が起きなくても約 6.9 倍のコスト**（20 万回ループ・実測）
- **`EXECUTE` は約 5.8 倍**（2 万回ループ・実測）
- **`RAISE NOTICE` は実際に出力すると約 470 倍。** 抑止すれば約 2 倍で済む
- **`pg_stat_statements` はこの環境に未導入。** 導入しても `track = 'all'` にしないと PL/pgSQL 内部は見えない
- **PL/pgSQL は速くする道具ではなく、往復を減らす道具。** 同一ホストでは効果が出ない
- **講義から外した項目には、それぞれ理由がある**（§8 の表）
