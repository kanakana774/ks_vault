# 詳解：トランザクションIDと行の可視性

**[[15-2_実践_ロックとMVCC_詳細|15-2]] の §2（MVCC）と §3（分離レベル）の裏側です。**
**講師の把握用に書いてあります。**研修生への配布・投影は想定していません（用語も内部名のまま出します）。

> **実測環境**
> - PostgreSQL 17.5 / ローカル。使い捨てDB `tmp_visibility` で計測し、計測後に `DROP DATABASE` 済み
> - テーブルは3行だけ。**`price` にはインデックスを張っていません**（HOT更新の観察用）
>   ```sql
>   CREATE TABLE items (id INT PRIMARY KEY, name TEXT, price NUMERIC);
>   INSERT INTO items VALUES (1,'apple',1200), (2,'banana',800), (3,'cherry',500);
>   ```
> - **載せている数字はすべて実測**です。xid の値はマシンと実行順で変わりますが、**大小関係と挙動は変わりません**

---

## 1. 登場する数字は4種類だけ

| 名前 | 何を指すか | どこで見えるか |
| :--- | :--- | :--- |
| **xid**（トランザクションID） | 「書いた」トランザクションに付く連番 | `txid_current_if_assigned()`／`pg_stat_activity.backend_xid` |
| **`xmin` / `xmax`**（行が持つ） | その行の版が**いつから／いつまで**有効か | 行のシステム列 `SELECT xmin, xmax FROM items` |
| **スナップショット** | 「自分にはどの xid の結果が見えるか」の判定基準 | `pg_current_snapshot()` → `xmin:xmax:実行中リスト` |
| **`ctid`** | その版が物理的にどこ（ページ番号, 行番号）に居るか | 行のシステム列 `SELECT ctid FROM items` |

**`xmin`/`xmax` は「行が持つ数字」、スナップショットは「トランザクションが持つ判定基準」。** この2つの掛け合わせで可視性が決まります。名前が似ているので、ここを混ぜないことが全部の入口です。

---

## 2. xid は「書いたとき」にだけ作られる

読むだけのトランザクションには**xid が付きません。** 実測：

```sql
BEGIN;
SELECT txid_current_if_assigned();                    -- (空) ← まだ無い
SELECT price FROM items WHERE id = 1;                 -- 1200
SELECT txid_current_if_assigned(), pg_current_snapshot();
--   (空)   |  23754:23754:                           ← 読んでも付かない
UPDATE items SET price = 1250 WHERE id = 1;
SELECT txid_current_if_assigned();                    -- 23754  ← 書いた瞬間に付いた
ROLLBACK;
```

| いつ | 自分の xid | 何が起きたか |
| :--- | :--- | :--- |
| `BEGIN` 直後 | **無い** | 仮想IDだけ持っている |
| `SELECT` 後 | **無い** | 読むだけなら要らない |
| `UPDATE` 後 | **23754** | 行に自分の印を書く必要が出たので割り当てられた |

**なぜ分けるのか。** xid は有限（32bit）で、消費すると周回対策（→ §8）のコストがかかります。**読むだけのトランザクションに配らないのは、xid を節約するため**です。実務では圧倒的多数が読み取りなので、これが効きます。

> [!question]- `txid_current()` と `txid_current_if_assigned()` の違い
> **`txid_current()` は「無ければ割り当てて」返します。** つまり**観測しただけで xid を消費します。**
> 状態を覗く目的では必ず **`txid_current_if_assigned()`**（無ければ `NULL`）を使ってください。
> 監視スクリプトで `txid_current()` を回すと、読み取り専用のはずのセッションが xid を持ち始め、**§6 のホライズンを止める側に回ります。**

## 3. 行は「xmin と xmax」で有効期間を持つ

**`UPDATE` は上書きではありません。**「古い版に終了印（`xmax`）を書き、新しい版を別の場所に足す」——これだけです。

```
UPDATE items SET price = 1300 WHERE id = 1;   （窓A、xid 23760）

  ページ0
  ┌──────────────────────────────────────────────┐
  │ (0,9)   xmin=23759  xmax=23760   price=1205  │ ← 古い版。「23760 が消した」と印が付く
  │ (0,10)  xmin=23760  xmax=0       price=1300  │ ← 新しい版。「23760 が作った」
  └──────────────────────────────────────────────┘
                                    ↑ xmax=0 は「まだ誰も消していない」
```

**同じ瞬間に、2つの窓は違う版を見ます。** 実測（窓Aは `COMMIT` していない）：

| 見る人 | `ctid` | `xmin` | `xmax` | `price` |
| :--- | ---: | ---: | ---: | ---: |
| **窓A**（自分が更新した） | (0,10) | 23760 | 0 | **1300** |
| **窓B**（別接続） | (0,9) | 23759 | **23760** | **1205** |

窓Aが `COMMIT` した後に窓Bから読むと、(0,10) / 1300 に切り替わります。**行は書き換わっていません。窓Bの判定結果が変わっただけです。**

| 操作 | 古い版 | 新しい版 |
| :--- | :--- | :--- |
| `INSERT` | — | `xmin` = 自分の xid |
| `UPDATE` | `xmax` = 自分の xid | `xmin` = 自分の xid |
| `DELETE` | `xmax` = 自分の xid | **作らない** |

---

## 4. ロールバックしても `xmax` は消えない

§2 の実測は `ROLLBACK` で終わっています。その直後の行：

```
 id | xmin  | xmax  | ctid  | price
----+-------+-------+-------+-------
  1 | 23753 | 23754 | (0,1) |  1200      ← xmax に、失敗した 23754 が残っている
```

**`xmax` が入っていても「消えている」ことにはなりません。** PostgreSQL は `xmax` の数字を見たあと、**その xid がコミットされたか／ロールバックされたか**を別の場所（**clog**、コミットログ）に問い合わせて判断します。

> **これが 15-2 §4-6 の「行ロックは `pg_locks` に出ない。行そのものに書かれる」の実体です。**
> `SELECT ... FOR UPDATE` も、やっていることは「まだ消していないが `xmax` に自分の印を置く」。だからロック情報はロック管理表ではなく行の中にあり、**トランザクションが終われば clog を見た時点で自動的に無効**になります。ロックを1つずつ解放して回る処理は要りません。
>
> 副作用として、**ロールバックした更新も「死んだ版」をディスクに残します。** 失敗した処理も `VACUUM` の仕事を増やす、ということです。

---

## 5. スナップショットは3つの部品

`pg_current_snapshot()` の出力は **`xmin:xmax:実行中リスト`** です。実測では `23760:23760:` でした。

| 部品 | 意味 | 判定 |
| :--- | :--- | :--- |
| **`xmin`** | まだ実行中のうち、いちばん小さい xid | **これより小さい xid は、コミット済みかどうかを clog で見るだけ** |
| **`xmax`** | まだ割り当てられていない次の xid | **これ以上の xid は、無条件に見えない**（自分より後に始まった） |
| **実行中リスト** | `xmin` 以上 `xmax` 未満で実行中の xid | **載っていれば見えない** |

**`23760:23760:` は「23760 以降は見えない。実行中リストは空」と読みます。** 窓Aの xid 23760 は実行中なのにリストに載っていませんが、**`xmax` と一致する xid は「これ以上」に含まれるのでリストに載せる必要がない**——という省略です。リストが空だから誰も動いていない、ではありません。

**ある版が自分に見えるかの判定：**

```
  xmin（行）が … 自分から見てコミット済み？ ──No──→ 見えない（まだ作られていない）
                        │Yes
                        ▼
  xmax（行）が … 0 か、自分から見て未コミット／不可視？ ──Yes──→ 見える
                        │No（＝自分から見てコミット済みの誰かが消した）
                        ▼
                     見えない
```

**READ COMMITTED はこの判定基準を文ごとに作り直し、REPEATABLE READ はトランザクションの最初の1回だけ作ります。** 15-2 §3-2 の差は、この一行の違いから出ています。

## 6. `VACUUM` のホライズンは xid ではなく `backend_xmin`

**15-2 完成品 §2-3 は「いま生きているトランザクションのうち最小の xid」と書いていますが、これは近似です。** 正確には**読むだけのトランザクション（xid を持たない）も回収を止めます。**

実測。窓Aで**読むだけの** REPEATABLE READ を開いたまま放置し、別のセッションから更新して `VACUUM` をかけました。

```
  pid  | backend_xid | backend_xmin |        state
-------+-------------+--------------+---------------------
 20300 |             |        23767 | idle in transaction   ← 窓A。xid は無いのに xmin を持つ
```

```
VACUUM (VERBOSE) items;
  tuples: 14 removed, 5 remain, 2 are dead but not yet removable
  removable cutoff: 23767, which was 1 XIDs old when operation ended
```

**窓Aは1行も書いていないのに、cutoff がその `backend_xmin` に固定されています。** 窓Aを終わらせて再実行すると：

```
  tuples: 2 removed, 3 remain, 0 are dead but not yet removable
  removable cutoff: 23768
```

**残っていた2件が消えました。**

| 見る場所 | 何が分かるか | 読むだけの tx を捉えられるか |
| :--- | :--- | :---: |
| `pg_snapshot_xmin(pg_current_snapshot())` | **書いた**（xid を持つ）tx のうち最小 | **✕** |
| `pg_stat_activity.backend_xid` | そのセッションが書いたときの xid | **✕** |
| **`pg_stat_activity.backend_xmin`** | **そのセッションのスナップショットが必要としている最古の xid** | **○** |
| `VACUUM (VERBOSE)` の `removable cutoff` | `VACUUM` が実際に使った値 | **○**（結果として） |

**犯人探しに使うのはこれです。**

```sql
SELECT pid, state, backend_xid, backend_xmin,
       now() - xact_start AS 経過時間, left(query, 40) AS 最後のSQL
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL OR backend_xid IS NOT NULL
ORDER BY coalesce(backend_xmin, backend_xid);
```

> **講義でどう話すか。** 完成品（§2-3）は `pg_snapshot_xmin` の一本で通しています。**扱っている題材が「`COMMIT` 忘れで `idle in transaction` 放置」＝必ず書いているケースなので、近似で結論が変わらない**ためです。
> **「長い `SELECT` でも `VACUUM` は止まる」**まで踏み込むなら、この節を見せてください。レプリカで長い分析クエリを流してマスタが膨らむ、という実務事故はこちら側の話です。

## 7. 更新の物理：HOT更新

**インデックスを張っていない列だけを更新すると、インデックスを触りません。** これを **HOT更新**（Heap-Only Tuple）と呼びます。

実測。`price`（インデックスなし）を12回更新：

| | 結果 |
| :--- | :--- |
| `n_tup_upd` / `n_tup_hot_upd` | **12 / 12**（全部 HOT） |
| `ctid` の変化 | (0,9) → (0,15) … **ページ0の中だけを移動** |
| `pg_relation_size('items')` | **8192 → 8192**（1ページのまま。増えていない） |
| `pg_relation_size('items_pkey')` | 16384（変化なし） |

続けて **`id`（主キー）を更新**すると：

| | 結果 |
| :--- | :--- |
| `n_tup_upd` / `n_tup_hot_upd` | **14 / 12** … 増えた2件は **HOT にならなかった** |

**HOT になる条件は2つ。**

1. **インデックスが張られている列を1つも変えない**
2. **同じページに新しい版を置く空きがある**（無ければ別ページ＝非HOT）

**効き方が2段階あります。**

- **インデックスを更新しない** … 書き込み量が減る。インデックスが5本あるテーブルなら差は大きい
- **`VACUUM` を待たずに掃除できる**（HOT pruning）… 同じページ内で連鎖している死んだ版は、次にそのページを読んだ拍子に片付けられます。だから更新を繰り返してもページが増えませんでした

> **17章との接続。** 「更新が多いテーブルで、更新される列にインデックスを張ると急に遅くなる」——原因はこれです。**インデックスを1本増やす判断は、`SELECT` を速くするコストとして HOT を諦めることを含みます。**

> [!question]- `fillfactor` を下げるのはこのため
> HOT の条件2（同じページに空きがある）を満たしやすくするために、**あらかじめページに空きを残しておく**設定が `fillfactor` です（既定100）。
> 更新が激しいテーブルで `ALTER TABLE ... SET (fillfactor = 80)` とするのは、「20%を将来の版のために取っておく」という意味です。
> ただし**空きを作るぶんテーブルは大きくなり、全件スキャンは遅くなります。** 更新の多さと引き換えです。

## 8. freeze と wraparound

**xid は32bit（約42億）で、使い切ると0に戻ります。** 周回するので、**「23760 は 100 より新しい」という絶対的な判定ができません。** 比較は常に「自分から見て前か後か」という相対判定です。

そこで、**十分に古くなった版には「もう誰から見てもコミット済み」という印を付けて、xid の比較そのものから外します。** これが **freeze（凍結）**です。

実測：

| | `relfrozenxid` | `age(relfrozenxid)` |
| :--- | ---: | ---: |
| `VACUUM FREEZE` 前 | 23753 | 20 |
| `VACUUM FREEZE` 後 | **23773** | **0** |

> ⚠️ **凍結は `xmin` 列では見えません。** 上の実測でも、凍結後の `SELECT xmin FROM items` は 23767 / 23770 / 23771 のまま変わりませんでした（`relfrozenxid` がそれらより進んでいるので、凍結済みなのは確実）。
> **`xmin` 列は生の値を返す**ので、凍結の有無は **`relfrozenxid` と `age()`** で見ます。行単位で確かめたければ `pageinspect` の `t_infomask` が必要です。

| 設定（既定値） | 意味 |
| :--- | :--- |
| `vacuum_freeze_min_age` = 5000万 | これより古い版を、通常の `VACUUM` のついでに凍結する |
| `autovacuum_freeze_max_age` = 2億 | `age` がこれを超えたら、**設定に関係なく強制的に** autovacuum が走る |

**長時間トランザクションを放置すると、ここでも詰みます。** §6 のとおりホライズンが止まると凍結も進まず、`age` が上がり続けます。限界に近づくと警告が出て、最後は**新しいトランザクションを受け付けなくなります**（読み取り専用状態）。

> **「トランザクションを長く開けたままにしない」の理由は3段構えです。**
> ① その行を触る人が待つ（15-2 §1-1）→ ② 死んだ版が回収されずテーブルが膨らむ（§6）→ ③ **凍結が進まず、最悪クラスタが停止する**（ここ）
> ①はその行だけ、②はDB全体、③はインスタンス全体。**害の広がり方が段違い**です。

## 9. 分離レベルの内側

### 9-1. REPEATABLE READ が落とす瞬間の判定

**判定材料は `xmax` です。** 更新しようとした行の `xmax` に「自分のスナップショットより後にコミットされた xid」が入っていたら、その版の上には積めません。§5 の判定で「自分には最新版が見えない」のに、`UPDATE` は最新版の上にしか積めない——この矛盾で落ちます（詳細は [[15-2_実践_ロックとMVCC_詳細|15-2]] §3-3）。

### 9-2. multixact：複数人がロックすると `xmax` が別物になる

**`xmax` に入るのは xid だけではありません。** 同じ行を複数のトランザクションが同時にロックすると、`xmax` は **MultiXactId**（別カウンタの番号）に切り替わります。実測：

| 状況 | `xmax` |
| :--- | ---: |
| 1つのセッションが `FOR SHARE` | **23768** … そのセッションの xid |
| 2つのセッションが `FOR SHARE` | **13** … 急に小さい数字＝**MultiXactId** |

**xid が23768まで進んでいるのに13が出るので、xid として読むと完全に誤読します。** どちらの意味かは行の infomask のビットで区別されていて、**システム列 `xmax` からは区別できません。**

> **実務での意味。** MultiXactId も**別カウンタなので独自に枯渇・周回します。** 外部キーの多いスキーマで親行が多数の子から参照されると `FOR KEY SHARE` が積み重なり、`multixact members` 用の領域が膨らんで autovacuum が走ります。
> 「`pg_multixact` が大きい」「multixact の wraparound 警告」はこの経路です。**`xmax` の数字が飛び飛びに見えたら multixact を疑う**、とだけ覚えておけば追いかけられます。

### 9-3. SERIALIZABLE（SSI）：書き込みが衝突していないのに落ちる

**SERIALIZABLE は「どの範囲を読んだか」まで追跡します。** 実測（`items` の id=2:800、id=3:500）：

| 順 | 窓A | 窓B |
| :--- | :--- | :--- |
| ① | `BEGIN ISOLATION LEVEL SERIALIZABLE;`<br>`SELECT sum(price) FROM items WHERE id IN (2,3);` → **1300** | 同じく → **1300** |
| ② | `UPDATE items SET price = price + 1 WHERE id = 2;` → `UPDATE 1` | |
| ③ | `COMMIT;` → 成功 | |
| ④ | | `UPDATE items SET price = price + 1 WHERE id = 3;` → **エラー** |

```
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during write.
HINT:  The transaction might succeed if retried.
```

**2つの窓は1行も同じ行を更新していません**（Aは id=2、Bは id=3）。それでも落ちます。**「相手が読んだ範囲を自分が書き換えた」関係が両方向にできた**からです。

**注目すべきは落ちた場所です。** `COMMIT` ではなく **④の `UPDATE` の時点**——`DETAIL` の *during write* がそれで、危険な関係の中心（pivot）だと判定された瞬間に殺されています。**`COMMIT` で落ちる場合も別にあり、どちらもエラーコードは `40001` です。**

| | 検知するもの | エラー文 |
| :--- | :--- | :--- |
| **REPEATABLE READ** | 同じ**行**への更新の衝突 | `could not serialize access due to concurrent update` |
| **SERIALIZABLE** | 上＋**読んだ範囲と書いた範囲の依存関係** | `could not serialize access due to read/write dependencies among transactions` |

**どちらも `40001` なので、リトライ処理は SQLSTATE で拾えます。** 逆に言えば、**エラーメッセージの文字列で分岐を書いてはいけません。**

## 10. 観測に使うSQL（まとめ）

| 見たいもの | SQL |
| :--- | :--- |
| 行の版の状態 | `SELECT xmin, xmax, ctid, * FROM items;` |
| 自分の xid（割り当てずに） | `SELECT txid_current_if_assigned();` |
| 自分のスナップショット | `SELECT pg_current_snapshot();` |
| **回収を止めている犯人** | `SELECT pid, state, backend_xid, backend_xmin FROM pg_stat_activity;` |
| `VACUUM` が実際に使った基準 | `VACUUM (VERBOSE) <表>;` の `removable cutoff` |
| 凍結の進み具合 | `SELECT relfrozenxid, age(relfrozenxid) FROM pg_class WHERE relname='<表>';` |
| HOT が効いているか | `SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname='<表>';` |

> ⚠️ **`txid_current()` は観測に使わないこと**（§2）。無ければ割り当ててしまうので、覗くだけのつもりで xid を消費し、自分がホライズンを止める側に回ります。
