# 【講師用】運用とチューニング

> **これは講師側だけで持つ資料です。受講生には配りません。**
>
> **配らない理由**：ここで扱う `work_mem` や `random_page_cost` は**サーバー設定を変える話**で、
> 1年目に権限が与えられることはまずありません。それでいて、読んだ受講生が本番で試すと事故ります。
> **「設定値を決める」話はジュニアに求められる範囲を超えている**、という判断です。
>
> **受講生側に残してあるもの**（この資料を読まなくても講義が成立するように配置済み）
> - `CONCURRENTLY` の作法 → **17-2 §1-3** の折りたたみ
> - VACUUM が何をするものか → **15-2 §2-3** と **17-1 §6-5**
> - 統計情報が古いと何が起きるか → **17-2 §5-⑦**
> - indexの棚卸し（`idx_scan = 0` を見る） → **演習の締め**
>
> **この資料の用途**：受講生に質問されたときの裏取りと、講師自身が現場で使うため。

現場でのチューニングは、だいたいこの順に進みます。

```text
① 遅いクエリを見つける      ← ここが分からないと何も始まらない
② 実行計画を読む            ← 17-2 でやった
③ インデックスを直す        ← 17-2 でやった
④ 余計なものを片付ける      ← 貼りっぱなしのindexを棚卸しする
⑤ 統計情報とVACUUMを保つ    ← 放置すると③の努力が無効化される
⑥ メモリの限界を知る        ← ここまで来て初めて設定の話になる
⑦ コストモデルを実機に合わせる ← SSDなら random_page_cost
```

この資料は **①、④、⑤、⑥、⑦** を扱います。

## 1. どのクエリが遅いのかを見つける

「システムが遅い」と言われたとき、いきなり `EXPLAIN` を打つ相手がいません。**まず犯人を特定する**必要があります。手段は3つあり、**上から順に導入が簡単**です。

### 1-1. 今まさに動いているものを見る（`pg_stat_activity`）

**導入コスト：ゼロ。** 標準で使えるビューです。「今、重い処理が動いている」という状況で最初に見ます。

```sql
SELECT pid,
       now() - query_start AS 経過時間,
       state,
       wait_event_type,
       wait_event,
       left(query, 60) AS クエリ
FROM pg_stat_activity
WHERE state <> 'idle'
  AND pid <> pg_backend_pid()
ORDER BY query_start;
```

見るべきポイントは3つです。

| 列 | 何が分かるか |
| :--- | :--- |
| `経過時間` | 長時間居座っているクエリ。まずこれを疑う |
| `state` | `active`＝実行中／`idle in transaction`＝**トランザクションを開いたまま放置**（後述） |
| `wait_event_type` | `Lock` なら他の処理を待っている＝ロック競合。`IO` ならディスク待ち |

> ⚠️ **`idle in transaction` が長時間居座っているのは危険信号です。**
> `BEGIN` したまま `COMMIT` していない接続で、**その間 VACUUM が古い行を回収できません**（→ §3）。アプリのトランザクション管理漏れが原因のことが多く、放っておくとテーブルが膨れ続けます。

止めたい場合の手順は [[00_SQL研修/01_講義資料/99_実行中のPIDを見てみよう|99_実行中のPIDを見てみよう]] を参照してください。

### 1-2. 遅いクエリをログに残す（`log_min_duration_statement`）

**導入コスト：ゼロ。再起動も不要です。** 「指定ミリ秒を超えたクエリを全部ログに書く」という設定で、**犯人探しの本命**です。

```sql
-- 200ms を超えたクエリをログに記録する（セッション限定）
SET log_min_duration_statement = 200;

-- データベース全体に適用したい場合（次の接続から有効）
ALTER DATABASE sql_lesson_execution_plan SET log_min_duration_statement = 200;

-- 元に戻す
RESET log_min_duration_statement;
```

ログの出力先はこれで確認できます。

```sql
SHOW logging_collector;   -- on ならファイルに出ている
SHOW log_directory;
SHOW log_filename;
SHOW data_directory;      -- log_directory が相対パスならこの下
```

**閾値の決め方**は、いきなり `0`（全部記録）にしないことです。ログが爆発してディスクを圧迫します。まず `1000`（1秒）で始めて、犯人が出てこなければ `500`、`200` と下げていくのが安全です。

### 1-3. 実務の定番：`pg_stat_statements`（導入に再起動が必要）

**導入コスト：中。** 「どのクエリが**累計で**一番時間を使っているか」を集計してくれる拡張です。実務では事実上の標準ですが、**サーバの再起動が必要**なので、勝手に入れられない環境もあります。

```text
postgresql.conf に追記
    shared_preload_libraries = 'pg_stat_statements'
    ↓
    PostgreSQL を再起動
    ↓
    CREATE EXTENSION pg_stat_statements;
```

導入できたら、こう使います。

```sql
-- 累計実行時間が長い順に10件
SELECT calls        AS 実行回数,
       round(total_exec_time)      AS 合計ms,
       round(mean_exec_time, 2)    AS 平均ms,
       left(query, 60)             AS クエリ
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

**`log_min_duration_statement` との使い分け**が重要です。

| | 得意なこと | 見落とすもの |
| :--- | :--- | :--- |
| `log_min_duration_statement` | **1回が重い**クエリ（3秒かかるバッチなど） | 1回10msだが1日100万回呼ばれるクエリ |
| `pg_stat_statements` | **累計で重い**クエリ（塵も積もれば型） | — |

実際のシステムでボトルネックになるのは、**後者であることが少なくありません。** 1回10msのクエリが1画面表示で200回呼ばれていた（いわゆるN+1問題）、というのが典型です。`pg_stat_statements` はこれを `calls` の多さで一発で見つけます。

導入できない環境では、`log_min_duration_statement` を低めに設定して、出力されたログを集計するツール（`pgBadger` など）で代用します。

## 2. インデックスの棚卸し

17-1 §8 で見た通り、インデックスには**書き込みが遅くなる・容量を食う**という代償があります。にもかかわらず、現場のDBには**誰も使っていないインデックス**が高い確率で残っています。「念のため」「昔の機能で使っていた」といった理由です。

**導入コスト：ゼロ。** これも標準のビューだけで調べられます。

### 2-1. 使われていないインデックスを探す

```sql
SELECT s.relname                                  AS テーブル,
       s.indexrelname                             AS インデックス,
       s.idx_scan                                 AS 使用回数,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS サイズ
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE NOT i.indisprimary        -- 主キーは除外
  AND NOT i.indisunique         -- UNIQUE制約も除外（消せないので）
ORDER BY s.idx_scan, pg_relation_size(s.indexrelid) DESC;
```

この研修環境で実行すると、こうなりました。

```text
 テーブル  |       インデックス       | 使用回数 | サイズ
-----------+--------------------------+----------+---------
 orders    | idx_orders_status        |        0 | 6896 kB   ← 一度も使われていない
 customers | idx_customers_membership |        1 | 696 kB
 orders    | idx_orders_order_date    |        2 | 21 MB
 customers | idx_customers_name       |        3 | 3104 kB
 customers | idx_customers_city       |       10 | 688 kB
 orders    | idx_orders_customer_id   |     1019 | 9256 kB   ← よく使われている
```

**`idx_scan = 0` は「作ってから一度も使われていない」という意味です。** これらは検索を1ミリ秒も速くしていないのに、INSERT/UPDATEのたびに更新され、容量を食い続けています。

### 2-2. 消す前に必ず確認すること

`idx_scan = 0` を見つけても、**すぐに消してはいけません。** 3つ確認します。

1.  **統計はいつからのものか。** `idx_scan` は統計をリセットしてからの累計です。「先週リセットしたばかり」なら判断材料になりません。
    ```sql
    SELECT stats_reset FROM pg_stat_database WHERE datname = current_database();
    ```
2.  **月次・年次バッチで使っていないか。** 月末にしか動かない処理のためのインデックスは、平常時は `idx_scan = 0` に見えます。**最低でも1ヶ月**、できれば繁忙期を跨いで観察します。
3.  **制約を支えていないか。** 主キーとUNIQUE制約のインデックスは消せません（上のクエリで除外済み）。

### 2-3. 安全な消し方

いきなり `DROP` せず、**まず無効化して様子を見る**方法があります。

```sql
-- ① インデックスを「プランナから見えなく」する（データは残る）
UPDATE pg_index SET indisvalid = false
WHERE indexrelid = 'idx_orders_status'::regclass;
```

```sql
-- ② しばらく運用して問題が出なければ、本当に削除する（この行だけを単独で実行）
DROP INDEX CONCURRENTLY idx_orders_status;
```

> ⚠️ `pg_index` を直接更新するのは**システムカタログの書き換え**です。本番で行う場合は必ず手順を確認し、戻し方（`indisvalid = true`）を用意しておいてください。抵抗がある場合は、素直にメンテナンス時間に `DROP INDEX` して、必要なら作り直す方が安全です。
>
> 削除に付けている `CONCURRENTLY` については §2-5 で説明します。

### 2-4. 逆に「足りない」を探す

使われていないものだけでなく、**Seq Scan が多発しているテーブル**も分かります。

```sql
SELECT relname                       AS テーブル,
       seq_scan                      AS 全件走査の回数,
       seq_tup_read                  AS 全件走査で読んだ行数,
       idx_scan                      AS index使用回数
FROM pg_stat_user_tables
WHERE seq_scan > 0
ORDER BY seq_tup_read DESC;
```

**`seq_tup_read`（全件走査で読んだ行数の累計）が突出しているテーブル**は、インデックスが足りていない候補です。ただし17-2 ケース4で見た通り、**小さいテーブルや大部分を取るクエリでは Seq Scan が正解**なので、この数字だけで判断せず、実際のクエリを `EXPLAIN` して確かめてください。

### 2-5. `CONCURRENTLY` の作法と後始末

**この節の内容は 17-2 §1-3 の折りたたみへ移しました。**（受講生に渡す側に置いた方が使われるため）

要点だけ再掲：

- 作成・削除・再作成の3つに付けられる（`REINDEX CONCURRENTLY` は PG12 以降）
- **3つともトランザクションブロック内では実行できない**（`VACUUM` と同じ制約）
- **無関係なテーブルの長トランザクションでも待たされる** → 実行前に `pg_stat_activity` を確認
- 失敗すると `INVALID` なインデックスが残る → `SELECT ... FROM pg_index WHERE NOT indisvalid;` で確認し、`REINDEX CONCURRENTLY` か `DROP INDEX CONCURRENTLY`

## 3. 統計情報とVACUUMを保つ

ここは**放置すると、せっかく張ったインデックスが効かなくなる**という話です。地味ですが、実務では最も多いトラブル源のひとつです。

### 3-1. 統計情報が古いと計画を間違える

17-2 §5-⑦ で実測した通り、統計情報が実態とズレると、プランナは**誤った計画を選びます**（推定66,667行に対し実際149,585行で、`Bitmap Heap Scan` → `Seq Scan` に判断が変わりました）。

通常は **autovacuum** が自動で `ANALYZE` してくれますが、追いつかない場面があります。

*   **大量データを一括投入した直後**（バッチ処理、データ移行）
*   **autovacuum の閾値に届かない**大きなテーブル（既定では「全体の10%が変化したら」なので、1億行のテーブルでは1,000万行変わるまで動きません）

```sql
-- いつANALYZEされたかを確認する
SELECT relname     AS テーブル,
       n_live_tup  AS 有効行数,
       n_dead_tup  AS 不要行数,
       last_analyze,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY relname;
```

**大量投入の直後は、待たずに手で打つのが確実です。**

```sql
ANALYZE テーブル名;
```

### 3-2. `VACUUM` は何をしているのか

PostgreSQL は `UPDATE` や `DELETE` をしても、**古い行をその場では消しません**。「もう誰からも見えない」と印を付けて残します。これが `n_dead_tup`（不要行）です。

`VACUUM` はこの不要行を回収し、**そのページを再利用可能にします**。回収されないとどうなるか。

*   テーブルが**膨れ続ける**（bloat）。行数は同じなのにページ数だけ増え、全件走査が遅くなります。
*   17-1 で見た通り、性能は「何ページ読んだか」で決まります。**不要行で膨れたテーブルは、それだけで遅くなります。**

```sql
-- 不要行が溜まっていないか
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS 不要行率
FROM pg_stat_user_tables
WHERE n_dead_tup > 0
ORDER BY n_dead_tup DESC;
```

**不要行率が常時20%を超えているようなら**、autovacuum が追いついていません。そのテーブルだけ設定を強くできます。

```sql
-- このテーブルは「2%変化したら」autovacuumを動かす（既定は20%）
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02);
```

> §1-1 で触れた **`idle in transaction` の放置は、ここに効いてきます。** 古いトランザクションが1つでも開いていると、「まだ誰かが見ているかもしれない」ため VACUUM は行を回収できません。**接続を1つ放置しただけでテーブルが膨れ続ける**、という事故が実際に起こります。

### 3-3. `Index Only Scan` は VACUUM 依存

17-1 §6-5 で説明した通り、`Index Only Scan` は **Visibility Map** に頼っています。そして**VMを更新するのは `VACUUM` です。**

つまり **VACUUM が追いついていないと、`Index Only Scan` の `Heap Fetches` が増え、せっかくのカバリングインデックスが効かなくなります。**

```sql
-- Heap Fetches が増えていないか確認する
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, order_date FROM orders WHERE customer_id = 500;
```

`Heap Fetches: 0` なら理想、大きな数字が出ていたら `VACUUM テーブル名;` を検討してください。

### 3-4. HOT update：インデックスを減らすと更新も速くなる

**インデックスが更新性能に効く仕組み**には、もう一段の話があります。

PostgreSQL には **HOT（Heap Only Tuple）update** という最適化があります。

> **更新した列にインデックスが張られておらず、かつ同じページに空きがあれば、インデックスを一切更新せずに済ませる。**

逆に言えば、**インデックスの張られた列を更新すると、この最適化が効きません。**

**実測してみます。** 同じ `INT` 型の列を2つ用意し、片方にだけインデックスを張って、同じ5,000行を更新します。

```sql
CREATE TABLE hot_test (id INT PRIMARY KEY, a INT, b INT, filler TEXT)
  WITH (fillfactor = 70);          -- ページに空きを作っておく
INSERT INTO hot_test SELECT gs, gs, gs, repeat('x',60) FROM generate_series(1,100000) gs;
CREATE INDEX idx_hot_a ON hot_test (a);      -- a にだけindexを張る
```

```sql
VACUUM ANALYZE hot_test;    -- ★この行だけを単独で実行すること
```

```sql
-- ① indexの無い列 b を更新
UPDATE hot_test SET b = b + 1 WHERE id <= 5000;

-- ② indexの有る列 a を更新
UPDATE hot_test SET a = a + 1 WHERE id <= 5000;
```

> ⚠️ `VACUUM` を他のSQLとまとめて流すと `ERROR: VACUUM cannot run inside a transaction block` になります。単独で実行してください。

結果です。

| 更新した列 | 更新行数 | うちHOT更新 | HOT率 | 読んだページ | WALレコード | 実行時間 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| **`b`（indexなし）** | 5,000 | **2,216** | **44.3%** | 27,154 | 13,464 | **21.3 ms** |
| **`a`（indexあり）** | 5,000 | **0** | **0%** | 44,643 | 16,796 | **26.8 ms** |

**インデックスの張られた列を更新した瞬間、HOT率が 0% になりました。** 結果として、読んだページが1.6倍、WALが1.25倍、実行時間が1.26倍に増えています。

*   HOT率が44.3%と中途半端なのは、**同じページに空きがある行しかHOTにできない**ためです。`fillfactor` を下げる（＝ページにあらかじめ空きを作る）と改善します。更新が多いテーブルでは `fillfactor = 70〜90` を検討する価値があります。
*   **実務上の教訓**：頻繁に更新される列には、**できるだけインデックスを張らない**。更新頻度の高い列へのインデックスは、検索を速くする以上に更新を重くしている可能性があります。

```sql
-- HOT率を確認する（高いほど良い）
SELECT relname, n_tup_upd AS 更新行数, n_tup_hot_upd AS HOT更新,
       round(100.0 * n_tup_hot_upd / NULLIF(n_tup_upd,0), 1) AS HOT率
FROM pg_stat_user_tables WHERE n_tup_upd > 0 ORDER BY 4;
```

## 4. メモリの限界を知る（`work_mem`）

ここまでは「ディスクをどう読むか」の話でした。最後は **「メモリに収まらなかったら何が起きるか」** です。

インデックスをどれだけ整えても、**ソートや結合がメモリから溢れると、そこで一気に遅くなります。**

### 4-1. `temp` が出たら黄信号

17-2 §3-5 で触れた `Buffers` の項目のうち、**`temp` が付いたものは一時ファイル＝ディスク**です。

| 項目 | 意味 | 出るタイミング |
| :--- | :--- | :--- |
| `shared hit` | 共有バッファ（メモリ）から読んだ | 常に |
| `shared read` | ディスクから読んだ | キャッシュに無かったとき |
| `shared dirtied` | 共有バッファ上のページを**変更した**（まだディスクには書いていない） | `INSERT`/`UPDATE`/`DELETE` |
| `shared written` | クエリ実行中に、バッファが足りず**ディスクへ押し出した** | 同上。**多いなら `shared_buffers` 不足** |
| **`temp read` / `temp written`** | **`work_mem` に収まらず、一時ファイルに書き出して読み戻した** | **ソート・ハッシュが溢れたとき** |

`dirtied` と `written` は更新系クエリで現れます（17-1 §8 のINSERT実測でも `dirtied=469 written=471` が出ていました）。変更したページは通常あとでチェックポイントがまとめて書き出すので、**`written` がクエリ実行中に多発しているなら、共有バッファが足りていない**サインです。

**`temp` はチューニングで最も分かりやすい改善余地です。** 見つけたら `work_mem` を疑ってください。

`work_mem` は「**ソートやハッシュ1つあたりに使ってよいメモリ量**」で、既定は 4MB です。

```sql
SHOW work_mem;
```

### 4-2. Sort の3つの方式

`Sort` ノードには `Sort Method` が表示され、**どれが出ているかで状況が分かります。**

`customers`（10万件）を、**インデックスの無い `phone` 列**でソートします。`work_mem` を変えながら観察してください。

```sql
SET work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers ORDER BY phone OFFSET 99999;
RESET work_mem;
```

```text
Limit  (actual time=... rows=1 loops=1)
  Buffers: shared hit=1238, temp read=3019 written=3233     ← 一時ファイルを使っている
  ->  Sort  (actual time=... rows=100000 loops=1)
        Sort Key: phone
        Sort Method: external merge  Disk: 8080kB           ← メモリに収まらなかった
        ->  Seq Scan on customers  (rows=100000 loops=1)
```

`work_mem` を変えて測ると、こうなりました（実行時間は3回測った代表値）。

| `work_mem` | `Sort Method` | 一時ファイル | 実行時間 |
| :--- | :--- | :--- | ---: |
| 64kB | `external merge  Disk: 8080kB` | `temp read=3019 written=3233` | 約 75 ms |
| **4MB（既定）** | `external merge  Disk: 8032kB` | `temp read=1004 written=1006` | 約 57 ms |
| **32MB** | **`quicksort  Memory: 11666kB`** | **なし** | **約 30 ms** |

**既定の4MBでも溢れていた**点に注目してください。10万行 × 約80バイト ＝ 約8MB のソートに、4MBでは足りなかったのです。32MBを与えて初めて `quicksort`（メモリ内完結）になり、**約2倍**速くなりました。

> **「たった2倍か」と思うかもしれません。** それは**この研修環境が小さいから**です。一時ファイルは書いた直後なのでOSのキャッシュに残っており、「ディスクを使った」と言っても実際にはメモリから読み戻せています。
> 本番規模で、**一時ファイルが実際にディスクへ書かれる**状況では、この差は桁で効いてきます。**注目すべきは実行時間の差ではなく、`external merge` と `temp` が出ているという事実そのもの**です。

さらに速い3つ目の方式があります。`LIMIT` を付けた場合です。

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers ORDER BY phone LIMIT 10;
```

```text
Limit  (cost=4395.96..4395.99 rows=10 width=69) (actual time=... rows=10 loops=1)
  Buffers: shared hit=1235
  ->  Sort  (actual time=... rows=10 loops=1)
        Sort Key: phone
        Sort Method: top-N heapsort  Memory: 26kB           ← わずか26kB
        ->  Seq Scan on customers  (rows=100000 loops=1)
```

**`top-N heapsort` は「上位N件だけ保持する」方式**です。全件を並べ替えず、常に10件分の入れ物だけを維持しながら流していきます。だから**メモリが26kBで済み、`work_mem` を1バイトも増やさずに約10ms**（`quicksort` の約30msよりさらに速い）。`quicksort` が使った11,666kB と比べると、**約450分の1のメモリ**です。

| `Sort Method` | 意味 | 評価 |
| :--- | :--- | :---: |
| `top-N heapsort` | `ORDER BY 〜 LIMIT N`。上位N件だけ保持 | 🌟 |
| `quicksort` | 全データがメモリに収まった | ✅ |
| `external merge` | **メモリに収まらずディスクを使った** | ⚠️ |

> **`ORDER BY` に `LIMIT` を付けられないか**を考える価値があります。「全部ソートしてから先頭10件」ではなく「先頭10件だけ選ぶ」に変えられれば、メモリ消費が桁で変わります。

### 4-3. Hash の `Batches`

`Hash Join` も同じです（→ [[17-3_補足_結合アルゴリズム_詳細|17-3_補足_結合アルゴリズム_詳細]]）。ハッシュテーブルが `work_mem` に収まらないと、**分割してディスクに退避**します。

```sql
SET work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
```

| `work_mem` | `Batches` | 一時ファイル | 実行時間 |
| :--- | ---: | :--- | ---: |
| 64kB | **64** | `temp read=3231 written=3231` | **734.8 ms** |
| 4MB（既定） | **1** | なし | **359.7 ms** |

**見るべきは `Batches` が1かどうか、それだけです。**

```text
Buckets: 131072  Batches: 1  Memory Usage: 4540kB     ← 理想
Buckets: 4096    Batches: 64 Memory Usage: 89kB       ← 64分割してディスクへ退避
```

> **`Memory Usage` の数字に惑わされないでください。** 溢れている方が `89kB` と小さく表示されます。分割したうちの「一番大きかったバッチ」のピーク値なので、**細かく分割するほど小さく見える**のです。判断材料は `Batches` です。

### 4-4. `work_mem` をどう決めるか

**必要量は実測から逆算できます。**

```text
Sort Method: external merge  Disk: 8080kB
                                   ↑ 約8MB あれば収まる
```

`Disk:` の値が「ディスクに書き出した量」なので、**それを超える `work_mem` を与えれば `quicksort` になります**。上の例では 8080kB なので、16MB あたりを設定すれば十分です。

ただし **`work_mem` を安易に上げるのは危険です。**

> **`work_mem` は「1接続あたり」ではなく「1つのソート/ハッシュ操作あたり」の上限です。**
> 1つのクエリに `Sort` が2つ、`Hash Join` が1つあれば、そのクエリだけで **`work_mem` × 3** を使います。それが同時接続100本で走れば、単純計算で **`work_mem` × 300**。
> `work_mem = 256MB` などと全体設定にすると、**サーバのメモリを簡単に食い潰します。**

**安全な進め方**はこうです。

```sql
-- ① まず、そのクエリだけで試す（セッション限定）
SET work_mem = '32MB';
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
RESET work_mem;

-- ② 特定の処理にだけ適用したいなら、トランザクション内で
BEGIN;
SET LOCAL work_mem = '256MB';   -- このトランザクションを抜けたら自動で戻る
SELECT ... ;                    -- 重い集計バッチなど
COMMIT;
```

**全体の `work_mem` は控えめに保ち、重いバッチ処理だけ `SET LOCAL` で個別に上げる**、というのが実務での定石です。

## 5. プランナのコストモデルが現実とズレるとき（`random_page_cost`）

ここまでは「プランナは正しく判断する」前提で進めてきました。**最後に、その前提が崩れるケースを1つだけ扱います。**

「インデックスがあるのに `Seq Scan` が選ばれる」と悩んだとき、SQLでもインデックスでもなく、**この設定1つが原因**であることは珍しくありません。

### 5-1. `random_page_cost` はHDD時代の値のまま

プランナは「ページを1枚読むコスト」を次の想定で計算しています。

| パラメータ | 既定値 | 意味 |
| :--- | :--- | :--- |
| `seq_page_cost` | 1.0 | ページを**順番に**1枚読む |
| `random_page_cost` | **4.0** | ページを**ランダムに**1枚読む |

**`random_page_cost = 4.0` は「ランダムアクセスは順次読みの4倍高い」という想定**です。これは**磁気ヘッドが物理的に移動していたHDD時代の値**です。

SSDにはヘッドの移動がありません。さらに、よく使うデータは共有バッファ（メモリ）に載っているので、**ランダムアクセスの罰則はほぼゼロ**です。それでもプランナは「4倍高い」と信じたまま計算します。

結果として、**インデックスを使う計画が実際より高く見積もられ、`Seq Scan` が選ばれてしまう**ことがあります。

| 環境 | 推奨値 |
| :--- | :--- |
| HDD | **4.0**（既定のまま） |
| SSD / NVMe | **1.1 〜 2.0** |
| データがほぼメモリに載っている | **1.1** に近い値 |

```sql
-- セッション限定で試す（安全）
SET random_page_cost = 1.1;
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
RESET random_page_cost;
```

**まずセッション限定で試して、計画と実測が改善することを確認してから**、`postgresql.conf` に反映してください。

### 5-2. 実例：7倍速い計画が選ばれなかった

> [!example]- 実測（`city` 5件分・顧客1,000人を結合）
> ```sql
> EXPLAIN (ANALYZE, BUFFERS)
> SELECT c.name, o.order_date
> FROM customers c JOIN orders o ON c.customer_id = o.customer_id
> WHERE c.city IN ('City_1','City_2','City_3','City_4','City_5');
> ```
>
> **プランナが選んだ計画（`random_page_cost = 4`：既定値）**
>
> ```text
> Hash Join  (cost=1282.80..21162.91 rows=9960 width=22)
>            (actual time=21.038..312.043 rows=10000 loops=1)
>   Hash Cond: (o.customer_id = c.customer_id)
>   Buffers: shared hit=7468 read=6
>   ->  Seq Scan on orders o  (actual time=0.029..190.397 rows=1000000 loops=1)  ← indexがあるのに使わない
>         Buffers: shared hit=7255
>   ->  Hash  (actual time=20.981..20.983 rows=1000 loops=1)
>         Buckets: 1024  Batches: 1  Memory Usage: 59kB
>         ->  Bitmap Heap Scan on customers c  (actual time=2.229..20.702 rows=1000 loops=1)
> Execution Time: 312.427 ms
> ```
>
> **`random_page_cost` をSSD相当に下げると**
>
> ```sql
> SET random_page_cost = 1.1;
> ```
>
> ```text
> Nested Loop  (cost=15.10..8662.60 rows=9960 width=22)
>              (actual time=0.070..43.174 rows=10000 loops=1)
>   Buffers: shared hit=13005 read=214
>   ->  Bitmap Heap Scan on customers c  (actual time=0.064..0.438 rows=1000 loops=1)
>         Buffers: shared hit=219
>   ->  Index Scan using idx_orders_customer_id on orders o
>             (actual time=0.037..0.042 rows=10 loops=1000)
>         Index Cond: (customer_id = c.customer_id)
>         Buffers: shared hit=12786 read=214
> Execution Time: 43.436 ms
> ```
>
> **312.4ms → 43.4ms。約7倍速い計画が、既定設定では選ばれませんでした。**

### 5-3. 「読んだページ数が少ない方が速い」とは限らない

上の実例には、この章のここまでの説明とぶつかる観察が含まれています。

**速い方（Nested Loop）の方が、読んだページ数は多いのです。** 13,219ページ 対 7,474ページ。

なぜ速いのか。

*   `Hash Join` は `orders` の**100万行すべてを実行器に通して**ハッシュ照合しています（`Seq Scan` だけで190ms）。**行数がそのままCPUの仕事量**になっています。
*   `Nested Loop` が触った13,000ページは**ほぼ全て `shared hit`**、つまりメモリ上の同じインデックス領域を繰り返し叩いているだけです。1回あたりが極めて安い。

**「読んだページ数」は、本番でディスクを読むときの目安**です。**全部キャッシュに乗っている環境では、「何行処理したか」の方が効いてきます。**

目安は目安として、**最後は実測（`actual time`）で判断してください。**

### 5-4. プランナに別の計画を作らせて比べる

「なぜこっちを選んだの？」を調べる道具があります。特定の方式を一時的に禁止して、もう一方のコストを見るのです。

```sql
SET enable_seqscan = off;    -- Seq Scan を禁止
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
RESET enable_seqscan;        -- 必ず戻す

-- 他にもこんなスイッチがあります
-- enable_indexscan / enable_bitmapscan / enable_hashjoin / enable_nestloop
```

セッション限定なので安全です。**両方のコストと実測を並べて見る**と、プランナの判断根拠が見えてきます。

> ⚠️ これは**調査用の道具**です。「`Seq Scan` を禁止したら速くなったから」と本番で `enable_seqscan = off` を設定するのは間違いです。**原因（統計情報が古い／`random_page_cost` が実態と合っていない）を直してください。**

> [!note]- 参考：cost はどう作られているのか
> `cost` は魔法の数字ではなく、**ページ数と行数からの単純な足し算**です。`customers` の全件走査 `cost=0.00..2485.00` は次のように分解できます。
>
> ```text
> seq_page_cost      1.0    × 1,235ページ  = 1,235
> cpu_tuple_cost     0.01   × 100,000行    = 1,000
> cpu_operator_cost  0.0025 × 100,000行    =   250
>                                    合計  = 2,485   ← 表示と一致
> ```
>
> 「機械的に計算しているだけ」と分かれば、2つの計画のコストを見比べる作業に納得がいくはずです。各パラメータは `SHOW cpu_tuple_cost;` などで確認できます。

## まとめ：詰まったときの手順

上から順に実行してください。

1.  **犯人を特定する。**
    *   今動いているなら `pg_stat_activity`
    *   過去のものなら `log_min_duration_statement` でログに出す
    *   累計で重いものを探すなら `pg_stat_statements`（要導入）
2.  **`EXPLAIN (ANALYZE, BUFFERS)` を取る。** 憶測で直さない（→ 17-2）。
3.  **読んだページ数（`Buffers`）が多いノードを探す。** `pg_class.relpages` と一致していたら全件走査。
4.  **`temp` が出ていないか確認する。** 出ていたら `work_mem` 不足（→ §4）。
5.  **推定 `rows` と実測 `rows` がズレていないか確認する。** ズレていたら `ANALYZE`（→ §3-1）。
6.  **インデックスを直す**（→ 17-2）。
7.  **落ち着いたら棚卸しする。** `idx_scan = 0` のインデックスを消す（→ §2）。
8.  **状態を保つ。** VACUUM が追いついているか、不要行が溜まっていないかを定期的に見る（→ §3）。

**最後に、この章で一番覚えて帰ってほしいこと。**

> **チューニングは「速くする」作業であると同時に、「速い状態を保つ」作業です。**
> インデックスを1本張って終わりではありません。使われなくなったインデックスは書き込みを重くし、VACUUM が止まればテーブルは膨れ、統計情報が古くなればプランナは誤った計画を選びます。**定期的に見る仕組みを作ることが、単発のチューニングより効きます。**
