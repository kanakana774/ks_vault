# 補足：結合アルゴリズム（Nested Loop / Hash Join / Merge Join）

`JOIN` は1つの書き方しかありませんが、**PostgreSQLの内部では3つの全く違うアルゴリズム**のどれかで実行されます。実行計画に出てくる `Nested Loop` / `Hash Join` / `Merge Join` がそれです。

同じ結合でも、方式が違えばコストは3倍以上変わります。まず実測を見てください。

```sql
SELECT COUNT(*) FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
```

| 方式 | 推定コスト | 実測時間 | 読んだページ数 |
| :--- | ---: | ---: | ---: |
| **Hash Join**（プランナが選んだ） | **23,365** | 273 ms | 8,490 |
| Merge Join（強制） | 34,825 | 293 ms | 1,429 |
| Nested Loop（強制） | 76,863 | — | — |

> **前提**：[[17_indexと実行計画で使用するテーブル|17章のテーブル]]（`customers` 10万件=1,235ページ / `orders` 100万件=7,255ページ）。PostgreSQL 17 での実測値です。

---

## 1. 素朴にやると何が起きるか

結合とは「**片方の行に対して、条件に合う相手の行を見つける**」作業です。何も工夫しないと、こうなります。

```text
for a in A の全行:              -- 10万行
    for b in B の全行:          -- 100万行
        if a.key == b.key:      -- 比較
            出力
```

比較回数は **10万 × 100万 = 1,000億回**。これが「$O(n \times m)$」です。現実的な時間では終わりません。

3つのアルゴリズムは、**この総当たりをどう回避するか**の3つの答えです。

| 方式 | 総当たりの回避方法 |
| :--- | :--- |
| Nested Loop | 内側を**インデックスで引く**（総当たりの内側ループを潰す） |
| Hash Join | 内側を**ハッシュテーブルにする**（探すのをやめて計算する） |
| Merge Join | 双方を**ソートして並走する**（一度通り過ぎたら戻らない） |

---

## 2. Nested Loop（二重ループ型）

### 仕組み

素朴な二重ループそのままですが、**内側をインデックスで引く**ことで実用的になります。

```text
for a in 外側テーブル:                        -- ここは全件読む
    for b in インデックスで引いた該当行:       -- ここが O(log N) になる
        出力
```

### 実測：コストの内訳が手で追える

`Nested Loop` を強制すると、こうなります。

```text
Nested Loop  (cost=0.42..76863.00 rows=1000000 width=0)
  ->  Seq Scan on customers c  (cost=0.00..2235.00 rows=100000 width=4)
  ->  Index Only Scan using idx_orders_customer_id on orders o
            (cost=0.42..0.65 rows=10 width=4)
```

内側の `cost=...0.65` は **1ループあたり**のコストです。だから総コストはこう計算できます。

```text
外側（customers 全件）        2,235
内側 0.65 × 100,000ループ  ≒ 65,000
                     合計  ≒ 76,863   ← 表示と一致
```

**`loops` が多いノードのコストは掛け算で膨らむ**（17-2 §3-4）という話が、そのまま数字で見えます。

### 得意な場面：外側が十分に絞れているとき

逆に、外側が10行しかなければ最強です。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, o.order_date FROM customers c JOIN orders o
  ON c.customer_id = o.customer_id WHERE c.customer_id BETWEEN 1 AND 10;
```

```text
Nested Loop  (cost=4.79..488.26 rows=110 width=22) (actual time=0.025..0.109 rows=100 loops=1)
  Buffers: shared hit=133
  ->  Index Scan using customers_pkey on customers c  (rows=10 loops=1)
        Buffers: shared hit=3
  ->  Bitmap Heap Scan on orders o  (rows=10 loops=10)      ← 10回だけ
        Buffers: shared hit=130
Execution Time: 0.137 ms
```

**133ページ、0.137ms。** Hash Join の8,490ページとは比べものになりません。

*   **強い条件**：外側が少数（数百〜数千）＋**内側の結合キーにインデックスがある**
*   **弱点**：外側が大量だと `loops` が爆発する
*   **`LIMIT` と相性が良い**：先頭から必要な分だけ作れるので、途中で打ち切れる

## 3. Hash Join（ハッシュテーブル型）

ここが一番「なぜ速いのか」が分かりにくいところなので、詳しく見ます。

### 3-1. なぜ「ハッシュ化」すると安くなるのか

**核心は「探すのをやめて、計算する」ことです。**

総当たりが遅いのは、相手を見つけるために**探している**からです。100万行の中から `customer_id = 5` の行を探すには、100万回比較するしかありません。

ハッシュテーブルは、これを**計算**に置き換えます。

```text
【探す】          key=5 の行はどこ？ → 先頭から1つずつ比較 → 最悪100万回
【計算する】      hash(5) = 41 → 「41番目の箱」→ そこを1回見るだけ
```

なぜ1回で済むのか。**ハッシュテーブルの実体は「連続したメモリ上の配列」**で、ハッシュ値がそのまま**配列の添字**になるからです。

```text
バケット配列（連続メモリ）
 ┌──────┬──────┬──────┬─────┬──────┬──────┐
 │  0   │  1   │ ...  │ 41  │ ...  │131071│
 └──────┴──────┴──────┴─────┴──────┴──────┘
                          ↑
      hash(5) = 41 → 添字41 へ直接ジャンプ（比較ゼロ）
```

配列の添字アクセスは「先頭アドレス ＋ 添字 × 要素サイズ」という**足し算1回**です。探索ループが存在しません。これが $O(1)$ の意味です。

### 3-2. だから「掛け算」が「足し算」になる

この性質のおかげで、計算量が根本的に変わります。

| | 必要な操作回数 |
| :--- | :--- |
| 総当たり | 10万 × 100万 = **1,000億回**の比較 |
| Hash Join | 10万回（作る）＋ 100万回（引く）＝ **110万回**のハッシュ計算 |

**約9万分の1です。** $O(n \times m)$ が $O(n + m)$ になった、というのはこの差を指しています。

### 3-3. 2つのフェーズ

```text
【フェーズ1：Build】小さい方のテーブルを読んで、ハッシュテーブルを作る
for c in customers:                 -- 10万行、1回だけ読む
    i = hash(c.customer_id) % バケット数
    バケット[i] に c を入れる

【フェーズ2：Probe】大きい方を1行ずつ流し込む
for o in orders:                    -- 100万行、1回だけ読む
    i = hash(o.customer_id) % バケット数
    for c in バケット[i]:            -- ほぼ1〜2件しか入っていない
        if c.customer_id == o.customer_id:
            出力
```

**ここが重要です。プローブ側（`orders`）はメモリに残しません。** 1行読んでハッシュを計算し、該当バケットを見て、出力したら捨てる。**流しっぱなし**です。

だから**メモリが必要なのはビルド側だけ**であり、プランナは**小さいテーブルをビルド側に選びます**。

### 3-4. 実測：各テーブルを「1回だけ」読んだ証拠

```text
Hash Join  (cost=3485.00..23365.11 rows=1000000 width=0)
           (actual time=43.750..239.674 rows=1000000 loops=1)
  Hash Cond: (o.customer_id = c.customer_id)
  Buffers: shared hit=8490
  ->  Seq Scan on orders o  (rows=1000000 loops=1)          ← プローブ側
        Buffers: shared hit=7255
  ->  Hash  (rows=100000 loops=1)                           ← ビルド側
        Buckets: 131072  Batches: 1  Memory Usage: 4540kB
        Buffers: shared hit=1235
        ->  Seq Scan on customers c  (rows=100000 loops=1)
              Buffers: shared hit=1235
Execution Time: 273.291 ms
```

**`Buffers: shared hit=8490` に注目してください。**

```text
orders    7,255ページ
customers 1,235ページ
          ─────────
   合計   8,490ページ   ← 完全に一致
```

**「積」ではなく「和」になっています。** 各テーブルをそれぞれ1回ずつ読んだだけ、という証拠です。総当たりなら `orders` を10万回読み直すことになっていました。

また `loops=1` であることも確認してください。Nested Loop と違い、**内側が何度も呼ばれていません**。

### 3-5. `Buckets` の意味

> `Buckets: 131072  Batches: 1  Memory Usage: 4540kB`

*   **`Buckets: 131072`** … バケット配列の要素数。10万行に対して2の冪（$2^{17}$）で確保されています。行数より多めに取ることで、1バケットに入る件数を1〜2件に抑えています。
*   **`Batches: 1`** … ハッシュテーブル全体が `work_mem` に収まった、という意味。**ここが2以上だとディスクに溢れています**（→ 演習 問題8）。
*   **`Memory Usage: 4540kB`** … 実際に使ったメモリ量。

### 3-6. 衝突しても速い理由

異なる値が同じバケットに入ること（**衝突**）はあります。その場合はバケット内を順に比較するので、厳密には $O(1)$ ではありません。

ただし上記の通り**バケット数を行数より多く確保している**ので、1バケットの中身は平均1〜2件です。「100万件から探す」が「1〜2件から探す」に変わっているので、実質的に $O(1)$ として扱えます。

### 3-7. 弱点

**① 等価結合（`=`）専用**

**ハッシュ化は大小関係を壊します。** `hash(5)` と `hash(6)` の間には何の関係もありません。だから「`>` の相手を探す」ことが原理的にできません。

実際に非等価結合を書くと、Hash Join は候補にすら上がりません。

```sql
EXPLAIN SELECT COUNT(*) FROM orders o JOIN customers c
  ON o.customer_id > c.customer_id AND c.customer_id < 3;
```

```text
Nested Loop  (cost=0.72..20654.49 rows=666667 width=0)      ← Hash Join ではない
  ->  Index Only Scan using customers_pkey on customers c
  ->  Index Only Scan using idx_orders_customer_id on orders o
```

**② メモリを消費する**

ビルド側が `work_mem` に収まらないと、`Batches` が増えてディスクに溢れます。

**③ 起動コストが高い**

ビルドが完了するまで1行も返せません。だから `LIMIT` との相性が悪く、Nested Loop に負けることがあります。

## 4. Merge Join（ソート＆マージ型）

### 仕組み

**双方が結合キーでソート済みであること**を前提に、2つのポインタを同時に進めます。

```text
orders   の customer_id : 1, 1, 2, 3, 5, 5, 8 ...
customers の customer_id: 1, 2, 3, 4, 5, 6, 8 ...
                          ↑両方の先頭を比較し、小さい方を進める
```

一度通り過ぎた行には戻りません。だから**それぞれ1回ずつ読むだけ**で終わります。

### 実測

```text
Merge Join  (cost=0.83..34825.89 rows=1000000 width=0)
            (actual time=0.030..255.006 rows=1000000 loops=1)
  Merge Cond: (o.customer_id = c.customer_id)
  Buffers: shared hit=281 read=1148
  ->  Index Only Scan using idx_orders_customer_id on orders o  (rows=1000000 loops=1)
  ->  Index Only Scan using customers_pkey on customers c       (rows=100000 loops=1)
Execution Time: 293.687 ms
```

**読んだページ数は1,429で、Hash Join の8,490より少ない**点が面白いところです。両側が `Index Only Scan` になっており、インデックスがソート済みなのでソート処理も不要、テーブル本体も読んでいません。

それでもプランナが Hash Join を選んだのは、コスト見積もりが 34,825 対 23,365 で Hash Join の方が安かったからです（実測時間はほぼ互角でした）。

*   **強い条件**：両側が**すでにソート済み**（インデックス順に読める）
*   **非等価結合にも使える**（`<` `>` など、順序が意味を持つため）
*   ソートが必要な場合は `Sort` ノードが挿入され、その分高くなります

## 5. 3方式の比較

| 観点 | Nested Loop | Hash Join | Merge Join |
| :--- | :--- | :--- | :--- |
| 計算量の考え方 | 外側 × 内側の索引探索 | $O(n + m)$ | $O(n + m)$（ソート済み前提） |
| 外側が少数 | ◎ | △ | △ |
| 大量同士 | ✕ | ◎ | ◎ |
| 内側にインデックス | **必須級** | 不要 | ソート順に読めると強い |
| 等価結合（`=`） | ⭕ | ⭕ | ⭕ |
| 非等価（`<` `>`） | ⭕ | **✕** | ⭕ |
| メモリ消費 | 小 | **大**（ビルド側） | 小 |
| 起動コスト | 低（すぐ1行返る） | 高（ビルド完了まで待つ） | 中 |
| `LIMIT` との相性 | ◎ | △ | △ |
| ディスク溢れ | なし | `Batches > 1` | `Sort` で発生 |

**実測コスト（同じ結合）**：Hash Join 23,365 ＜ Merge Join 34,825 ＜ Nested Loop 76,863

## 6.【手を動かす】方式を切り替えて比べる

プランナに別の方式を選ばせて、コストを比較できます。セッション限定なので安全です。

```sql
-- Nested Loop を強制（Hash と Merge を禁止）
SET enable_hashjoin = off;
SET enable_mergejoin = off;
EXPLAIN SELECT COUNT(*) FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
RESET enable_hashjoin; RESET enable_mergejoin;

-- Merge Join を強制（Hash と Nested Loop を禁止）
SET enable_hashjoin = off;
SET enable_nestloop = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT COUNT(*) FROM orders o JOIN customers c ON o.customer_id = c.customer_id;
RESET enable_hashjoin; RESET enable_nestloop;
```

> ⚠️ `EXPLAIN` に `ANALYZE` を付けずに実行すると**見積もりだけ**が出ます。Nested Loop を強制した場合は実行が非常に長くなる可能性があるので、まず `ANALYZE` なしでコストを確認してください。

**やってみる価値があるのは「プランナが選ばなかった方の理由が分かる」ことです。** 遅いと感じたとき、他の方式のコストと見比べれば、プランナの判断が妥当だったのか、それとも統計情報や設定が原因なのかを切り分けられます。

## まとめ

1.  **3方式はすべて「総当たり（$n \times m$）をどう避けるか」の答え。**
2.  **Hash Join が速いのは「探すのをやめて計算する」から。** ハッシュ値が配列の添字になるので、探索ループが消えて $O(n+m)$ になる。
3.  **プローブ側はメモリに残さず流すだけ。** だからメモリが要るのはビルド側（小さい方）のみ。
4.  **`Buffers` が両テーブルのページ数の「和」**になっていれば、それぞれ1回だけ読めている証拠。
5.  **ハッシュは順序を壊すので等価結合専用。** 非等価なら Nested Loop か Merge Join。
6.  **外側が絞れているなら Nested Loop が圧勝**（実測133ページ / 0.137ms）。方式に優劣はなく、状況で決まる。
