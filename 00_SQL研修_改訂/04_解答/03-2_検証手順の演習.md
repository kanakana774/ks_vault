## 問題 1: 実行する前に、変わる範囲を見る
- **目的**: `UPDATE` の `WHERE` をそのまま `SELECT` に付けて、対象と件数を確認できるようになる

### 問題:

「大阪の顧客のランクを Silver（`membership_id = 2`）にそろえたい」という依頼が来ました。
書きたい `UPDATE` はこれです。

```sql
UPDATE customers SET membership_id = 2 WHERE city = 'Osaka';
```

**【問1】** この `UPDATE` を実行する前に、**変わる行を確認するSQL**を書いてください。

**【問2】** 何件が対象になりますか。また、その中で**すでに Silver の顧客**は誰ですか。

### 解答:

**【問1】**

```sql
SELECT customer_id, name, city, membership_id
FROM customers
WHERE city = 'Osaka'
ORDER BY customer_id;
```

`SET` は写さず、**`WHERE` だけを同じにする**のがポイントです。

**【問2】** **3件**。すでに Silver なのは **`customer_id = 11`（Leo）**。

### 期待結果:

```
 customer_id | name | city  | membership_id
-------------+------+-------+---------------
           2 | Bob  | Osaka |             1
           8 | Ivy  | Osaka |             1
          11 | Leo  | Osaka |             2
(3 rows)
```

### 解説:

顔ぶれを見ておくと「Leo はもう Silver だから、実際に変わるのは2件だ」と分かります。
**件数だけでなく中身も見る**のは、このためです。

## 問題 2: 0件を見逃さない
- **目的**: `UPDATE 0` がエラーではなく「1件も変わっていない」という意味だと理解する

### 問題:

問題1の `UPDATE` を、うっかり都市名を小文字で書いてしまいました。

```sql
BEGIN;
UPDATE customers SET membership_id = 2 WHERE city = 'osaka';
```

**【問1】** 何と返りますか。

**【問2】** エラーは出ますか。

**【問3】** この間違いは、問題1の手順を踏んでいれば気づけました。どこで気づけますか。

### 解答:

**【問1】** `UPDATE 0`

**【問2】** **出ません。**

**【問3】** 実行前の `SELECT` が **0件**になるので、その時点で気づけます。

### 期待結果:

```
BEGIN
UPDATE 0
```

### 解説:

文字列の比較は**大文字と小文字を区別します**（`'osaka'` と `'Osaka'` は別の値）。

`UPDATE 0` は「正常に実行できたが、条件に当てはまる行が無かった」という意味です。
**エラーが出ないので「成功した」と思ってしまうのが、この間違いの怖いところ**です。

> **件数を見ないコードは、検証していないのと同じです。**

確認が終わったら `ROLLBACK;` してください。

## 問題 3: `BEGIN` で囲んで、実行してから決める
- **目的**: `BEGIN` → 確認 → `ROLLBACK` を自分の手で打ち、更新を戻せることを体感する

### 問題:

「東京の顧客のランクを1つ上げる」作業を、**戻せる形で**実行します。

```sql
UPDATE customers SET membership_id = membership_id + 1 WHERE city = 'Tokyo';
```

**【問1】** この `UPDATE` を `BEGIN` で囲み、**更新後の結果を確認してから戻す**までの一連のSQLを書いてください。

**【問2】** `UPDATE` は何件と返りますか。

**【問3】** `ROLLBACK` した後、`membership_id` はどうなっていますか。

### 解答:

**【問1】**

```sql
BEGIN;

UPDATE customers SET membership_id = membership_id + 1 WHERE city = 'Tokyo';

SELECT customer_id, name, membership_id
FROM customers WHERE city = 'Tokyo' ORDER BY customer_id;

ROLLBACK;

-- 戻ったことを確認
SELECT customer_id, name, membership_id
FROM customers WHERE city = 'Tokyo' ORDER BY customer_id;
```

**【問2】** `UPDATE 5`

**【問3】** **元の値に戻っています。**

### 期待結果:

```
BEGIN
UPDATE 5
 customer_id | name  | membership_id      ← 更新後（1つ増えている）
-------------+-------+---------------
           1 | Alice |             3
           4 | Diana |             4
           5 | Ellen |             3
           7 | Hank  |             2
          10 | Kevin |             4
(5 rows)

ROLLBACK
 customer_id | name  | membership_id      ← 元に戻っている
-------------+-------+---------------
           1 | Alice |             2
           4 | Diana |             3
           5 | Ellen |             2
           7 | Hank  |             1
          10 | Kevin |             3
(5 rows)
```

### 解説:

**これが一番強い検証です。** 実際に更新した結果を見てから、確定するかどうかを決められます。

`COMMIT` に変えれば確定します。`BEGIN` と打ったら**必ず `COMMIT` か `ROLLBACK` で閉じてください**。
開いたまま放置すると、その行を更新したい人が待たされます。

## 問題 4: 退避を取って、戻す
- **目的**: `CREATE TABLE ... AS SELECT` で退避を作り、そこから元の値を戻せるようになる

### 問題:

`COMMIT` してしまった後でも戻せるように、作業前に退避を取ります。

**【問1】** `customers` の全行を `customers_bk_20220421` という名前のテーブルに退避するSQLを書いてください。

**【問2】** 退避を取ったあと、間違って**全員を Bronze（`membership_id = 1`）にしてしまいました**。

```sql
UPDATE customers SET membership_id = 1;
```

退避テーブルを使って、**`customer_id = 1`（Alice）だけ**元の値に戻してください。
（まとめて戻す書き方は次の章で扱います。ここは1件だけでよいです）

**【問3】** 最後にリセットSQLを流して、全員を初期状態に戻してください。

### 解答:

**【問1】**

```sql
CREATE TABLE customers_bk_20220421 AS SELECT * FROM customers;
```

**【問2】**

```sql
-- 退避から元の値を読む
SELECT customer_id, membership_id FROM customers_bk_20220421 WHERE customer_id = 1;
--  → 2

-- 見えた値で戻す
UPDATE customers SET membership_id = 2 WHERE customer_id = 1;
```

**【問3】** 準備セクションのリセットSQLを流す。最後に `DROP TABLE customers_bk_20220421;` も実行する。

### 期待結果:

```
SELECT 11          ← 退避（11行コピーされた）
UPDATE 11          ← 全員 Bronze にしてしまった

 customer_id | membership_id
-------------+---------------
           1 |             2     ← 退避には元の値が残っている
```

### 解説:

`CREATE TABLE ... AS SELECT` は、**`SELECT` の結果をそのまま新しいテーブルにする**書き方です。
「消す前に退避」「バッチの中間結果を置く」の定番で、実務で最もよく使う保険です。

**名前に日付を入れておく**と、いつの退避か分かります。作業が終わったら消してください。

> **退避は `BEGIN` の前に作ります。** 理由は問題7で確かめます。

## 問題 5: NULL は「〜ではない」に入らない
- **目的**: `<>` が NULL の行を落とすことを確認し、`IS NULL` で補えるようになる

### 問題:

「Silver（`membership_id = 2`）ではない顧客」を数えたいので、こう書きました。

```sql
SELECT count(*) FROM customers WHERE membership_id <> 2;
```

**【問1】** 何件返りますか。

**【問2】** `membership_id = 2` の件数と、テーブルの全件数も数えてください。3つの数を足し引きして、**おかしいところ**を指摘してください。

**【問3】** 「Silver ではない顧客（ランク未設定の人も含む）」を正しく数えるSQLを書いてください。

### 解答:

**【問1】** **6件**

**【問2】** 全件は **11件**、`= 2` は **4件**。
`11 - 4 = 7` のはずなのに、`<> 2` は **6件**しか返りません。**1件足りません。**
消えているのは `membership_id` が NULL の `customer_id = 3`（Charlie）です。

**【問3】**

```sql
SELECT count(*) FROM customers
WHERE membership_id <> 2 OR membership_id IS NULL;
```

→ **7件**

### 期待結果:

```
 eq2
-----
   4

 ne2
-----
   6

 ne2_null
----------
        7
```

### 解説:

`NULL <> 2` の答えは「真」ではなく **「わからない」** です。
`WHERE` は「真」の行だけを通すので、**「わからない」行は落ちます。**

これが `UPDATE` の `WHERE` で起きると、**更新されるべき行が黙って残ります。** エラーは出ません。

`= NULL` も同じ理由で常に0件です。

```sql
SELECT count(*) FROM customers WHERE membership_id = NULL;   -- → 0
SELECT count(*) FROM customers WHERE membership_id IS NULL;  -- → 1
```

**NULL の判定は `IS NULL` / `IS NOT NULL` を使います**（→ [[02_演算子|02 演算子]]）。

## 問題 6: 件数が合っていても、変わっていないことがある
- **目的**: 件数の照合だけでは足りず、中身の確認が要ることを体感する

### 問題:

「名古屋の顧客のランクを1つ上げる」作業をします。

```sql
BEGIN;
UPDATE customers SET membership_id = membership_id + 1 WHERE city = 'Nagoya';
```

**【問1】** 実行前の `SELECT` で、対象は何件ですか。

**【問2】** `UPDATE` は何件と返りますか。

**【問3】** 更新後の値を確認してください。**件数は合っているのに、狙いどおりになっていない行**があります。どの行で、なぜですか。

### 解答:

**【問1】** **2件**（`customer_id = 3` Charlie と `customer_id = 9` Jack）

**【問2】** `UPDATE 2`

**【問3】** **`customer_id = 3`（Charlie）が NULL のまま変わっていません。**
`membership_id` が NULL なので、`NULL + 1` の答えも **NULL** になるためです。

### 期待結果:

```
 customer_id |  name   |  city  | membership_id     ← 実行前
-------------+---------+--------+---------------
           3 | Charlie | Nagoya |
           9 | Jack    | Nagoya |             2
(2 rows)

BEGIN
UPDATE 2

 customer_id |  name   | membership_id                ← 実行後
-------------+---------+---------------
           3 | Charlie |                   ← NULL のまま
           9 | Jack    |             3
(2 rows)
```

### 解説:

**`UPDATE 2` は「2行に触った」という意味で、「2行が狙いどおりに変わった」という意味ではありません。**

NULL を含む計算の答えは、すべて NULL になります（`NULL + 1`、`NULL * 2`、`NULL || 'abc'` も同じ）。
「1つ上げる」つもりが、Charlie については**何も起きていない**わけです。

だから手順は「件数を照合する」で終わりではなく、**`SELECT` で中身も見る**まで含めます。

未設定の人にも値を入れたいなら、意図を明示して分けて書きます。

```sql
UPDATE customers SET membership_id = membership_id + 1
WHERE city = 'Nagoya' AND membership_id IS NOT NULL;

UPDATE customers SET membership_id = 1
WHERE city = 'Nagoya' AND membership_id IS NULL;
```

## 問題 7: 退避を `BEGIN` の中で作ってはいけない
- **目的**: PostgreSQL では `CREATE TABLE` もトランザクションに含まれることを確認する

### 問題:

退避を `BEGIN` の後に作ってしまいました。

```sql
BEGIN;
CREATE TABLE customers_bk_test AS SELECT * FROM customers;
SELECT count(*) FROM customers_bk_test;
ROLLBACK;

SELECT count(*) FROM customers_bk_test;
```

**【問1】** 最後の `SELECT` はどうなりますか。

**【問2】** なぜそうなるのか説明してください。

**【問3】** 正しい順番を書いてください。

### 解答:

**【問1】** **エラーになります。** 退避テーブルが存在しません。

**【問2】** PostgreSQL では **`CREATE TABLE` もトランザクションに含まれる**ので、`ROLLBACK` すると
テーブルの作成そのものが取り消されます。

**【問3】** **退避 → `BEGIN` → 更新 → 確認 → `COMMIT`**

```sql
CREATE TABLE customers_bk_20220421 AS SELECT * FROM customers;  -- BEGIN の前

BEGIN;
UPDATE ...;
SELECT ...;   -- 確認
COMMIT;
```

### 期待結果:

```
BEGIN
SELECT 11
 count
-------
    11
(1 row)

ROLLBACK
ERROR:  relation "customers_bk_test" does not exist
LINE 1: SELECT count(*) FROM customers_bk_test;
                             ^
```

### 解説:

退避の目的は「`COMMIT` してしまった後でも戻せるようにする」ことです。
`BEGIN` の中で作ると、**戻したい場面（`ROLLBACK`）で退避も一緒に消える**ので、保険になりません。

> 🐘 **これは PostgreSQL の性質です。Oracle は逆で、`CREATE TABLE` が実行された時点で暗黙的に確定します**（`ROLLBACK` しても退避は残る）。
> どちらのDBでも **「退避は `BEGIN` の前」** にしておけば安全なので、そう覚えてください。

## 問題 8: 制約の端を疑う
- **目的**: 「今のデータでは通る」が「正しい」ではないことを確認する

### 問題:

問題3の「東京の顧客のランクを1つ上げる」は、今のデータでは成功しました。
では、東京に **Platinum（`membership_id = 4`）の顧客が1人いたら**どうなるでしょうか。

```sql
BEGIN;
UPDATE customers SET membership_id = 4 WHERE customer_id = 1;   -- Alice を Platinum にする
UPDATE customers SET membership_id = membership_id + 1 WHERE city = 'Tokyo';
ROLLBACK;
```

**【問1】** 2つめの `UPDATE` はどうなりますか。

**【問2】** なぜそうなるのか、`memberships` テーブルを見て説明してください。

**【問3】** この事故を実行前に見つけるには、どんな `SELECT` を書けばよいですか。

### 解答:

**【問1】** **外部キー制約違反でエラーになります。**

**【問2】** `memberships` に登録されているのは `membership_id` が **1〜4** の4件だけです。
Alice の `4 + 1 = 5` は存在しないランクを指すので、外部キー制約が拒否します。

**【問3】** 更新後の値が範囲を超えないか、実行前に確かめます。

```sql
SELECT customer_id, name, membership_id, membership_id + 1 AS after
FROM customers
WHERE city = 'Tokyo'
ORDER BY customer_id;
```

`after` が 4 を超える行があれば、その `UPDATE` は失敗します。

### 期待結果:

```
BEGIN
UPDATE 1
ERROR:  insert or update on table "customers" violates foreign key constraint "customers_membership_id_fkey"
DETAIL:  Key (membership_id)=(5) is not present in table "memberships".
ROLLBACK
```

### 解説:

**「開発環境のデータでは通った」は「正しい」ではありません。**
今回たまたま Platinum の顧客がいなかっただけで、本番に1人いれば止まります。

確認する端は決まっています。**上限・下限・0・マイナス・NULL・日付の初日と最終日。**

> ⚠️ **一度エラーになったトランザクションは、その先の文が全部失敗します。**
> `current transaction is aborted` が出たら、原因は**今打った文ではなく、もっと前のエラー**です。
> `ROLLBACK` してやり直してください。
