# 書いたSQLを自分で検証する

| 印 | 意味 |
| :--- | :--- |
| （無印） | **原理**。なぜそうなるかを理解する。手順はここから導ける |
| 🔑 | **覚えるところ**。理屈から出てこないので、覚えるか手元に置く |
| 🐘 | **PostgreSQL だけの話**。他のDBでは違う。名前は忘れてよい |

---

## この章のねらい

`SELECT` は間違っても誰も困りません。結果を見て、書き直せばいい。

`UPDATE` と `DELETE` は違います。**`COMMIT` した後は戻せません。**

だから実行する**前に**確かめるしかない。そのやり方を身につけるのがこの章です。
現場では、これができる人は「分かっているエンジニア」として扱われます。

### 原理はひとつだけ

> **変える前に、変わる範囲を見る。**

このあと手順が5つ出てきますが、**全部この1文から導けます。** 暗記する必要はありません。
「変わる範囲ってどこだ」「見るってどうやるんだ」を順番に詰めていくだけです。

---

## 1. 同じ `WHERE` で `SELECT` する

「変わる範囲」を決めているのは `WHERE` です。
ということは、**`UPDATE` の `WHERE` をそのまま `SELECT` に付ければ、変わる行が見える。**

たとえば「東京の顧客のランクを1つ上げたい」とき。書きたいのはこれです。

```sql
UPDATE customers SET membership_id = membership_id + 1
WHERE city = 'Tokyo';
```

先に、`WHERE` だけ同じにして `SELECT` します。

```sql
SELECT customer_id, name, city, membership_id
FROM customers
WHERE city = 'Tokyo'
ORDER BY customer_id;
```

```
 customer_id | name  | city  | membership_id
-------------+-------+-------+---------------
           1 | Alice | Tokyo |             2
           4 | Diana | Tokyo |             3
           5 | Ellen | Tokyo |             2
           7 | Hank  | Tokyo |             1
          10 | Kevin | Tokyo |             3
(5 rows)
```

**5件。** これが「変わる範囲」です。ここで顔ぶれを見ておくと、「あれ、この人も入るのか」に気づけます。

> ⚠️ **`SET` の中身は変えない。`WHERE` だけを写す。**
> `SET` を `SELECT` に混ぜようとすると別のクエリになってしまいます。見たいのは**どの行が対象か**です。

---

## 2. 件数を先に見積もる

`SELECT` で 5件だと分かったので、`UPDATE` は **5件のはず**です。

実行するとこう返ります。

```
UPDATE 5
```

**この数字と、さっきの件数を照合します。** 合っていれば狙いどおり。

- **5件のはずが 0件** → `WHERE` が誰にも当たっていない。条件のスペルミスか、値が違う
- **5件のはずが 11件** → `WHERE` を書き忘れた可能性がある。**全件更新は事故のいちばん多い形**

> ⚠️ **`UPDATE 0` はエラーではありません。**
> エラーが出ないので「成功した」と思ってしまいがちですが、**1件も変わっていない**という意味です。
> **件数を見ないコードは、検証していないのと同じ**です。

---

## 3. `BEGIN` で囲む

1と2をやっても、**実行してから間違いに気づくこと**はあります。そのときに戻せるようにしておきます。

```sql
BEGIN;

UPDATE customers SET membership_id = membership_id + 1
WHERE city = 'Tokyo';
-- UPDATE 5  ← ここで件数を確認

SELECT customer_id, name, membership_id
FROM customers WHERE city = 'Tokyo' ORDER BY customer_id;
-- 中身も確認

COMMIT;   -- 良ければ確定
-- ROLLBACK;  -- 違っていたら戻す
```

`ROLLBACK` した場合の実測です。

```
BEGIN
UPDATE 5
 customer_id | name  | membership_id      ← 更新後（1つ増えている）
-------------+-------+---------------
           1 | Alice |             3
           4 | Diana |             4
           5 | Ellen |             3
           7 | Hank  |             2
          10 | Kevin |             4
(5 rows)

ROLLBACK
 customer_id | name  | membership_id      ← 元に戻っている
-------------+-------+---------------
           1 | Alice |             2
           4 | Diana |             3
           5 | Ellen |             2
           7 | Hank  |             1
          10 | Kevin |             3
(5 rows)
```

**`BEGIN` の中なら、実際に更新した結果を見てから決められます。** これが一番強い検証です。

トランザクションそのものの話は [[15-1_導入_トランザクションとACID|15-1 トランザクションとACID]] で扱います。ここでは「囲むと戻せる」だけ押さえてください。

> ⚠️ **`BEGIN` と打ったら、必ず `COMMIT` か `ROLLBACK` で閉じる。**
> 開いたまま放置すると、その行を他の人が更新できずに待たされます（[[15-2_実践_ロックとMVCC|15-2 ロックとMVCC]]）。

---

## 4. 消す・変える前に退避する

`BEGIN` で囲んでも守れない場面があります。**`COMMIT` してしまった後**です。

そこで、変える前に元のデータをコピーしておきます。

```sql
CREATE TABLE customers_bk_20220421 AS SELECT * FROM customers;
```

```
SELECT 11
```

11行がコピーされました。これで、あとから元の値を照会できます。

```sql
-- 元の値を読む
SELECT customer_id, membership_id FROM customers_bk_20220421 WHERE customer_id = 1;
```

```
 customer_id | membership_id
-------------+---------------
           1 |             2
```

```sql
-- 見えた値で戻す
UPDATE customers SET membership_id = 2 WHERE customer_id = 1;
```

**名前に日付を入れておく**と、いつの退避か分かります。作業が終わったら消してください。

> 退避テーブルを使って**まとめて戻す**書き方（結合を使った更新）は、[[03-1_更新系SQLの実務パターン|03-1 更新系SQLの実務パターン]] で扱います。ここでは「元の値が残っていれば戻せる」ことだけ押さえてください。

> ⚠️ **退避は `BEGIN` の前にやる。**
> PostgreSQL では `CREATE TABLE` もトランザクションに含まれるので、`BEGIN` の中で作った退避テーブルは `ROLLBACK` で**一緒に消えます。**
>
> ```
> BEGIN
> SELECT 11                          ← 退避テーブルを作った
>  count
> -------
>     11
> ROLLBACK
> ERROR:  relation "customers_bk_test" does not exist   ← 消えている
> ```
>
> **退避 → `BEGIN` → 更新 → 確認 → `COMMIT`** の順です。

## 5. 境界を疑う

1〜4は「狙った範囲が合っているか」の確認でした。5は**「狙いそのものが間違っていないか」**の確認です。

事故はいつも同じ4か所で起きます。

### NULL — 「〜ではない」で消える

「Bronze 以外の顧客」を出したいとして、こう書いたとします。

```sql
SELECT count(*) FROM customers WHERE membership_id <> 1;
```

```
 count
-------
     6
```

ところが全体は11件で、Bronze（`= 1`）は4件です。

```
全件 11 ＝ Bronze 4 ＋ Bronze以外 6 ＋ ??? 1
```

**1件足りません。** 消えたのは `membership_id` が NULL の顧客です。

```sql
SELECT count(*) FROM customers WHERE membership_id IS NULL;
```

```
 count
-------
     1
```

`NULL <> 1` は「真」ではなく**「わからない」**になるので、`WHERE` に選ばれません。
`UPDATE` の `WHERE` でこれが起きると、**更新されるべき行が黙って残ります。**

さらに `= NULL` は常に0件です。

```sql
SELECT count(*) FROM customers WHERE membership_id = NULL;   -- → 0
SELECT count(*) FROM customers WHERE membership_id IS NULL;  -- → 1
```

**NULL の比較は `IS NULL` / `IS NOT NULL` を使います。** 詳しくは [[02_演算子|02 演算子]]。

### 0件 — エラーが出ないので気づかない

`WHERE` の値を間違えると、当たる行がゼロになります。

```sql
UPDATE customers SET membership_id = 2 WHERE city = 'tokyo';  -- 小文字
```

```
UPDATE 0
```

**エラーは出ません。** 1で `SELECT` していれば「0件だ」と気づけます。これが手順1をやる理由です。

### 重複 — 結合すると行が増える

`UPDATE` の対象を結合で決めるとき、**結合先が複数行あると同じ行を何度も更新します。**
「5件のはずが 12件更新された」はこれです。行の増殖は [[08_補足_結合|08 補足 結合]] で扱います。

### 端 — 制約に当たる値がないか

「東京の顧客のランクを1つ上げる」は、今のデータでは通ります。
でも **Platinum（`membership_id = 4`）の顧客が東京に1人でもいたら**、`4 + 1 = 5` になり、存在しないランクを指すのでエラーになります。

```
ERROR:  insert or update on table "customers" violates foreign key constraint "customers_membership_id_fkey"
DETAIL:  Key (membership_id)=(5) is not present in table "memberships".
```

**「今のデータでは通る」は「正しい」ではありません。** 上限・下限・0・マイナス・日付の初日と最終日を確認してください。

> ⚠️ **一度エラーになったトランザクションは、その先の文が全部失敗します。**
> `current transaction is aborted` が出たら、原因は**今打った文ではなく、もっと前のエラー**です。
> `ROLLBACK` してやり直してください（→ [[15-1_導入_トランザクションとACID|15-1 トランザクションとACID]]）。

## 🐘 他のDBではどうか

原理（変える前に見る）はどのDBでも同じです。違うのは名前と既定値だけです。

| | PostgreSQL | 他のDB |
| :--- | :--- | :--- |
| `BEGIN` / `COMMIT` / `ROLLBACK` | 使える | **標準SQL。どこでも使える** |
| 退避テーブルの作成 | `CREATE TABLE 退避 AS SELECT ...` | Oracle も同じ。**SQL Server は `SELECT * INTO 退避 FROM ...`** |
| `CREATE TABLE` は `ROLLBACK` で戻るか | **戻る**（トランザクションに含まれる） | **Oracle は戻らない**（DDL が暗黙コミットする）。だから Oracle では `BEGIN` の中で退避すると、そこで確定してしまう |
| 更新件数の表示 | `UPDATE 5` | ツールによって「5 rows affected」など。**表示形式が違うだけで、件数を見るのは同じ** |
| 自動コミット | ツールの設定次第 | **同じくツール次第。** 自分の環境がどちらか、最初に確かめること |

**どのDBでも「退避は `BEGIN` の前」にしておけば安全です。** PostgreSQL の挙動に合わせて覚えると Oracle で事故います。

## 🔑 手元に置くチェックリスト

原理から導けるものですが、**本番作業の前は考えずに手が動くほうが安全**なので、そのまま貼って使ってください。

```
□ 1. UPDATE / DELETE の WHERE をそのまま SELECT に付けて、対象と件数を見た
□ 2. 件数を覚えた。実行後の「UPDATE n」と照合する
□ 3. 退避を取った（BEGIN の前に）
□ 4. BEGIN で囲んだ
□ 5. 実行した。件数が一致した
□ 6. SELECT で中身も見た
□ 7. COMMIT した（違っていたら ROLLBACK）
```

### 🔑 よくやる間違い

| やりがちなこと | 正しくは |
| :--- | :--- |
| `UPDATE 0` を見て「エラーが出ていないから成功」と判断する | **1件も変わっていない。** 件数を見ないコードは検証していないのと同じ |
| `WHERE` を書き忘れて全件更新する | 手順1で件数を見れば気づける |
| 「〜ではない」を `<> 値` で書いて、NULL の行を落とす | `IS NULL` を使うか、`OR 列 IS NULL` を足す |
| `BEGIN` の中で退避テーブルを作る | `ROLLBACK` で退避も消える。**`BEGIN` の前に作る** |
| 開発データで通ったから本番でも通ると考える | 上限・下限・NULL・0件・日付の端を確認する |
| `BEGIN` したまま席を離れる | その行を触りたい人が待たされる。必ず `COMMIT` か `ROLLBACK` で閉じる |
