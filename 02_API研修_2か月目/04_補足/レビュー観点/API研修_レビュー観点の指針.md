# 1. SQL発行とパフォーマンス（N+1問題）

### 【レビュー観点】
**「for文の中でSQL（SELECT）を呼び出していないか？」**

*   **研修環境での最善（現実的な落とし所）**
    *   件数が数件（10件未満など）と分かっている場合は、for文での実装も「動作」としては許容する。
    *   ただし、**「なぜIN句やJOINを使わなかったのか？」**という質問に対し、「実装の容易さを優先した」などの理由を答えられるようにさせる。
    *   MyBatisの`<foreach>`を使ったIN句の実装を一度は経験させる。

*   **実務でのベストプラクティス**
    *   **原則、for文内でのSQL発行は禁止（N+1問題）。** 1000件、1万件と増えた際にDB往復コスト（RTT）でレスポンスが致命的に遅くなるため。
    *   **「DBに集合処理（JOINやIN）を任せる」**のが鉄則。
    *   **ディスクI/Oの勘違いを正す：** 「for文が遅いのはディスクアクセスのせい」ではなく、「AP⇔DB間のネットワーク往復回数」と「DB側のSQLパース/実行オーバーヘッド」が主因。同一TX内ならDBのバッファキャッシュが効くため、実はディスクI/Oはそれほど増えないことが多い。

# 2. Service層の責務と存在チェック

### 【レビュー観点】
**「存在チェック（SELECT）をしてから登録（INSERT）するロジックになっていないか？」**

*   **研修環境での最善（現実的な落とし所）**
    *   **外部キー制約がない前提**なので、Serviceでの存在チェックは「必須」として教える。
    *   ただし、チェックと登録の間にタイムラグがあるため、厳密には整合性が壊れる可能性がある（TOCTOU問題）ことを口頭で補足する。

*   **実務でのベストプラクティス**
    *   **DB制約（FK, UNIQUE）を活用し、例外をキャッチする：** 「SELECT → INSERT」の2ステップではなく、いきなりINSERTして制約違反例外（`DuplicateKeyException`など）をハンドリングする方が、並列実行時の整合性が担保され、かつDB往復も減る。
    *   **Serviceは「業務ルール」を判定する場所：** 「親が存在するか」はDBに任せ、「Todoが完了状態ならタグ追加不可」といった**DB制約だけでは表現できない業務判断**をServiceに書く。
    *   **「存在するかどうかは業務ルールではない」**と意識する。

# 3. DB設計と制約の考え方

### 【レビュー観点】
**「DBを単なる“箱”として扱っていないか？」**

*   **研修環境での最善（現実的な落とし所）**
    *   保守性やデータの修正しやすさを考慮し、あえて外部キー制約を外した状態で「アプリ側で整合性を守る苦労」を体験させる。
    *   ~~その代わり、中間テーブルには最低限**複合主キー（PRIMARY KEY）**を設定させ、物理的な重複だけは防がせる。~~

*   **実務でのベストプラクティス**
    *   **「アプリがバグってもDBがデータを守る」**というスタンス。外部キー制約、UNIQUE制約は必須。
    *   外部キーを張らない現場の理由（バッチ処理の高速化、論理削除との兼ね合い等）も理解しつつ、新規開発では整合性を優先する。
    *   **「外部キーを使わないのは自由ではなく、制約を自分で実装する責任を引き受けているだけ」**と認識する。

# 4. アーキテクチャとDTO・Entityの分離

### 【レビュー観点】
**「APIの型（Form）とDBの型（Entity）が混ざっていないか？」**

*   **研修環境での最善（現実的な落とし所）**
    *   FormからEntityへの詰め替えをControllerで行う現在の構成は、**「境界（Controller）で翻訳する」**という原則を守っているため合格。
    *   DTOを端折るのは「学習コスト」の観点から合理的だが、EntityにWebの都合（バリデーション注釈など）が入り込まないよう注意する。
    *   `new Entity(form)`のようにEntityがFormを直接知る実装は避け、getterで値を詰め替える。

*   **実務でのベストプラクティス**
    *   **Request DTO / Entity / Response DTO はすべて分ける：** API仕様の変更（フロント都合）がDB構造に波及するのを防ぐため。
    *   **Entityは「DBと会話するための型」：** APIのレスポンス形式に合わせてEntityを加工するのはNG。
    *   **CQRS的アプローチ：** 参照系（Query）ではEntityを使わず、JOIN結果を直接格納する`ReadModel`（または`XxxRow`, `XxxView`）をMyBatisのResultMapで作成し、それをResponseDTOに変換する。

# 5. トランザクション設計

### 【レビュー観点】
**「@Transactionalが適切な場所（Serviceのpublicメソッド）に付いているか？」**

*   **研修環境での最善（現実的な落とし所）**
    *   Serviceクラス単位、またはpublicメソッド単位で付与されていればOK。
    *   「どこからどこまでが失敗したときにロールバックされるべきか業務単位」を意識させる。

*   **実務でのベストプラクティス**
    *   **最小単位かつ業務単位：** トランザクションが長すぎるとDB接続やロックを占有し、他処理を待たせる原因になる。特に外部API呼出などはトランザクションに含めない。

# テーマ1：N+1問題（研修では正確にはループ内クエリ）の真実

「for文の中でSQLを叩く」という行為は、プログラミングの世界では最も有名なアンチパターンの一つですが、なぜそれがダメなのか、いつなら許されるのかを正確に理解することが重要です。

## 1. 何が問題なのか（エンジニア視点での言語化）

一般的に「N+1問題」と呼ばれます。
- **1回**：親データの一覧取得（例：Todo 100件）
- **N回**：各親データに紐づく子データの取得（例：各Todoに紐づくTagの取得 × 100回）

結果として、100件のデータを表示するだけで**合計101回のSQL**が発行されます。

### なぜこれが「地雷」なのか？
アプリ単体で見ると「数ミリ秒のSELECTを回しているだけ」に見えますが、システム全体では以下のコストが積み重なります。

1.  **AP⇔DB間の通信往復コスト（RTT: Round Trip Time）**：
    実務ではAPサーバとDBサーバは別々のマシンであることが多いです。1回のSQLごとにネットワークをパースし、パケットを送り、結果を受け取るという往復が発生します。（物理的な距離）これが100回重なると、クエリ実行時間よりも「通信待ち」が支配的になります。
2.  **DBのCPUオーバーヘッド**：
    DB側でも1回ごとに「SQLの構文解析（パース）」「実行計画の作成」「コネクションの管理」などの処理が走ります。1回で済む仕事を100回に分けるのは、DBにとって非常に非効率です。
3.  **スケーラビリティの欠如**：
    開発環境（データ数件）では爆速で動きますが、本番環境でデータが1000件、1万件になった瞬間にレスポンスが数十秒待ちになり、システムが火を吹きます。

---

## 2. ディスクI/Oに関する「誤解」と「真実」

よくある誤解として「100回SQLを投げると、100回ディスクに読み取りに行くから遅い」というものがありますが、これは少し違います。

- **真実**：
  DBには**「バッファキャッシュ」**という仕組みがあります。一度読み取ったインデックスやデータブロックはメモリ上に保持されます。そのため、同じテーブルに対して連続でSELECTを投げても、2回目以降はメモリから読み取ることが多く、**必ずしも「ディスクI/O」が100回発生するわけではありません。**
- **本当の問題**：
  ディスクI/Oよりも、先述した**「ネットワーク通信の回数」と「DB側のCPU処理回数」**が速度低下の主因です。インデックスが効いていてメモリに乗っていても、100回呼び出すオーバーヘッドは無視できません。

---

## 3. 「やっていいケース」と「ダメなケース」の判断基準

「for文の中のSQL ＝ 即アウト」ではありません。実務では以下の基準で判断します。

### ❌ NG（絶対に避けるべき）
*   **Web API（同期処理）内での実行**：ユーザーを待たせるため、N+1は致命傷になります。
*   **JOINやIN句で代替可能な場合**：SQL一発で取れるものを、わざわざJava側でループさせる理由は（技術的には）ありません。⇒ **「集約はSQLに任せろ」案件**
*   **データ量が不明、または増える可能性がある場合**：今は数件でも、将来的に増えるなら設計段階で潰すべきです。

### ⭕ OK（理由があれば許容される）
*   **バッチ処理で件数が限定的な場合**：夜間バッチなどで、対象が数十件と保証されており、1件ずつ処理を確定（コミット）させたい場合。ただ今回のAPIは同期処理。
*   **1件ずつ独立したエラーハンドリングが必要な場合**：100件中、5件目が失敗しても、残りの95件を処理し続けたいという業務要件がある場合。
*   **DB往復コストをまとめる仕組み（JDBC Batch / MyBatis Batch）を使っている場合**：コード上はfor文に見えても、ライブラリ側で通信をまとめてくれるモードを使っているならOKです。ただしselectでは使えない。

---

## 4. MyBatisでのベストプラクティス（解決策）

ループを回避するためには、以下の2パターンのいずれかを選択します。

### パターンA：IN句でまとめて取得する（2回SQL）
1.  Todoのリストを取得する。
2.  そのIDリストをIN句に渡し、Tagを一気に取得する。
3.  Java側でマッピングする。

```xml
<!-- MyBatisのforeachを利用した例 -->
<select id="selectTagsByTodoIds" resultType="Tag">
  SELECT * FROM tags
  WHERE todo_id IN
  <foreach collection="todoIds" item="id" open="(" separator="," close=")">
    #{id}
  </foreach>
</select>
```

### パターンB：JOINで一発で取得する（1回SQL）
SQLのJOINを使い、TodoとTagを結合した状態で取得します。MyBatisの`resultMap`を使えば、ネストした構造（Todoの中にList\<Tag>がある状態）に自動でマッピングしてくれます。

## 5. 研修環境での指導と実務の差

研修生には、この「ニュアンスの差」を伝えてください。

### 研修での最善（現実的な指導）
*   「今はデータが数件だから動いているけれど、**実務のコードレビューでは必ずNGが出るコードだよ**」と指摘してください。
*   研修では「外部キーがないからJavaでループしてチェックする」という回避策を採っていますが、それは**「DBの制約をアプリが肩代わりしている過渡期な状態」**であることを意識させます。

### 実際のベストプラクティス
*   **「DBに集合処理を任せる（SQLに任せる）」**のが、性能面でも保守面でも正義です。
*   「for文でSQLを書くときは、必ず**『なぜJOINやIN句を使わないのか』**を他人に説明できる理由（1件ずつコミットしたい等）を持て」と教えるのが、実務教育としての到達点になります。

# テーマ2：Service層の責務と存在チェック（厚すぎるService問題）

研修では「Service層にロジックを書きましょう」と教えますが、何でもかんでもServiceに詰め込むと、コードは冗長になり、かつ並列実行に弱い不安定なシステムになってしまいます。

## 1. 「厚すぎるService」の典型例：SELECT → INSERT

レビューで最もよく指摘されるのが、データの整合性を守るための「事前チェック」をJava側で愚直に書いてしまうケースです。

```java
// 指摘されやすい「厚すぎる」実装例
@Transactional
public void addTagToTodo(Long todoId, Long tagId) {
    // 1. Todoが存在するかチェック
    if (!todoMapper.exists(todoId)) {
        throw new NotFoundException("Todoが見つかりません");
    }
    // 2. Tagが存在するかチェック
    if (!tagMapper.exists(tagId)) {
        throw new NotFoundException("Tagが見つかりません");
    }
    // 3. 既に紐付いていないかチェック
    if (todoTagMapper.exists(todoId, tagId)) {
        throw new AlreadyExistsException("既に紐付いています");
    }
    // 4. 登録
    todoTagMapper.insert(todoId, tagId);
}
```

### なぜこれが実務で「NG」とされるのか？

1.  **TOCTOU問題（Time-of-Check to Time-of-Use）**：
    「チェックした時点」と「実行する時点」の間にタイムラグがあります。例えば、ステップ1で「Todoがある」と確認した直後、別のユーザーがそのTodoを削除したとします。するとステップ4では、存在しないTodoに対して紐付けを行おうとしてしまい、整合性が崩れます（あるいはエラーになります）。
2.  **DB往復回数の無駄**：
    登録1回のために、SELECTを3回、計4回のSQLを発行しています。前述のN+1問題と同様、通信コストが膨らみます。
3.  **責務の逆転**：
    「データの整合性（一意性や参照整合性）」を守るのはDB本来の仕事です。それをJava側が奪い取って一生懸命管理している状態は、DBの機能を信頼していない「過保護な設計」と言えます。

---

## 2. 業務ルール（Service） vs データの整合性（DB）

Service層が「本当にやるべきチェック」と「DBに任せるべきチェック」を切り分けるのがプロの設計です。

### ⭕ Service層（Java）でやるべきチェック：業務ルール
DBの制約だけでは表現できない、**「業務的な判断」**です。
*   「完了済みのTodoにはタグを追加できない」
*   「公開期間外のタグは使用できない」
*   「一般ユーザーは他人のTodoを編集できない」

### ❌ DB側（制約）に任せるべきチェック：データの整合性
DBが標準機能として持っている、**「データの正しさの保証」**です。
*   「親（Todo/Tag）が存在するか」（外部キー制約）
*   「既に同じ紐付けがないか」（一意制約 / UNIQUE）
*   「必須項目が埋まっているか」（NOT NULL制約）

※ただし、例外的にokなケースとしては、API仕様で「Todoが無い」「Tagが無い」を厳密に返したいというような更新系SQLのエラーからは原因を切り分けられないケースかな。

---

## 3. 実務でのベストプラクティス：制約と例外ハンドリング

実務では、**「あえてチェックせずに突っ込み、エラーが出たら対処する」**というアプローチを採ります。

```java
// 実務レベルの洗練された実装例
@Transactional
public void addTagToTodo(Long todoId, Long tagId) {
    // 業務ルールのチェックのみ行う
    if (todoMapper.isCompleted(todoId)) {
        throw new BusinessException("完了済みTodoは編集できません");
    }

    try {
        // いきなり登録する（DB制約に任せる）
        todoTagMapper.insert(todoId, tagId);
    } catch (DuplicateKeyException e) {
        // UNIQUE制約違反：既に登録されている場合
        throw new AlreadyExistsException("このタグは既に登録済みです");
    } catch (DataIntegrityViolationException e) {
        // FK制約違反：TodoやTagが存在しない場合
        throw new NotFoundException("指定されたTodoまたはTagが存在しません");
    }
}
```

この方法のメリットは以下の通りです。
*   **確実**：DBがロックをかけて担保するため、並列実行されても絶対に整合性が崩れない。
*   **高速**：SQL発行回数が最小限で済む。
*   **簡潔**：Serviceのコードが本来の「業務ロジック」だけに集中できる。

---

## 4. 研修環境（外部キーなし）での向き合い方

研修では「外部キー制約を張っていない」という前提があります。この場合、研修生はどうすべきでしょうか。

### 研修での現実的な回答
*   **Javaでチェックするしかない**：DBが守ってくれない以上、Java側でSELECTしてチェックを書くことは「正解」になります。
*   **ただし「代償」を理解させる**：
    「本来はDBでやるべきことを、今はこの環境の制約（FKなし）のためにJavaで肩代わりしているんだよ。そのせいでコードが長くなり、並列実行にも弱くなっているという『痛み』を自覚してね」と伝えます。

### 実務で「外部キーなし」の現場に遭遇したら？
実務でも、古いシステムや超大規模システムでは「パフォーマンスのため」「運用の柔軟性のため」という理由で外部キーがない現場があります。保守しやすいのよね。。。
*   その場合、**「整合性を守る責任をアプリ側が引き受けている」**という覚悟が必要です。
*   共通ライブラリでチェック機能を共通化したり、定期的なバッチ処理で不整合なデータ（孤児行）を探して削除するなどの、追加の運用コストを支払うことになります。

---

## 5. @Transactional の位置と範囲

Service層のメソッドを「業務の1単位」とするため、`@Transactional`はServiceに付けます。

*   **Controllerに付けない理由**：
    Controllerは「HTTPリクエストの受付」が仕事です。JSONのパースや認証チェック、外部API呼び出しなど、DBトランザクションとは無関係な（かつ時間の掛かる）処理を多く含みます。そこにトランザクションを張ると、DBの接続を不必要に長く占有してしまいます。
*   **内部メソッド呼び出しの注意点**：
    Springの`@Transactional`はAOP（プロキシ）を利用しています。**同じクラス内のメソッドを呼び出した場合、プロキシを通らないため、呼び出された側の`@Transactional`（REQUIRES_NEWなど）は無視される**という「Springの罠」は、実務レビューで頻出するポイントです。逆に内部メソッドは外から呼ばれないようprivateがいいですね。

---

### 補足：「例外キャッチって雑じゃない？」
- 例外 = 想定外ではない
- **制約違反は業務上の分岐**
つまり：
> **例外はエラーではなく、状態の通知**

**個人的見解：**
例外って上司へのエスカレーションに似てると思ってて、新人は「やべ例外発生した」となって、自己解決できないから命令元の上司（呼び出し元）にエスカレーションするんだけど、上司は「はいはい、この場合はこうして」と想定していたように業務を処理すると思います。こんな風に誰かにとってはイレギュラーだけど視座の高い人から見たらレギュラーというイメージがいいのではないでしょうか。

# テーマ3：DTO / Entity / Mapperの分離（境界を溶かさない設計）

研修では効率化のために一部を端折っていますが、実務では「なぜ分けるのか」という明確な理由があります。キーワードは**「関心の分離」**と**「境界線」**です。

## 1. 研修での構成と「許容されるショートカット」

研修では以下のフローを採っています。
- **[HTTP]** → **Form**（リクエストを受ける）
- **[Controller]** → **FormからEntityへ詰め替え**
- **[Service / Mapper]** → **Entity** を使って処理

### なぜこれでOK（研修的判断）なのか？
TodoアプリのようなシンプルなCRUDでは、リクエスト項目とDBのテーブル定義がほぼ1対1で一致します。そのため、ロジック専用のDTO（Application DTO）を定義してもEntityと全く同じ構造になり、コードが増えるだけの「過剰な設計」になりがちだからです。

### 守るべき最低限のルール
ショートカットをしても良いですが、以下の「境界線」だけは死守させます。
*   **EntityにWebの都合を持ち込まない**：
    Entityのフィールドに `@JsonProperty` や `@NotBlank`（バリデーション用注釈）を付けない。これらはFormの責務です。
*   **EntityにFormを食わせない**：
    `new TodoTag(form)` のようなコンストラクタはNGです。EntityがForm（Web層のクラス）に依存してしまい、層が溶けてしまいます。必ずControllerで `form.getXXX()` を使って詰め替えます。

---

## 2. 実務で「型を細かく分ける」4つの理由

実務では、`Request` / `Entity` / `Response` / `ReadModel` と型をバラバラにします。

### ① 変更の理由が違う（独立性）
*   **API仕様（Request/Response）の変更理由**：フロントエンドのUI変更、モバイルアプリ対応、外部連携のためのフォーマット変更。
*   **DB（Entity）の変更理由**：テーブル正規化、パフォーマンス向上のためのインデックス調整、物理削除から論理削除への移行。

これらが同じ型を使っていると、「画面に1項目追加したいだけなのに、DBの定義まで変えなきゃいけない（あるいはその逆）」という連鎖事故が起きます。

### ② セキュリティ（意図しない更新の防止）
Entity = Request だと、リクエストJSONに「adminフラグ」や「作成日時」をこっそり混ぜて送られた際、そのままDBに登録（オーバーポスティング）されてしまうリスクがあります。Request DTOを分けることで、**「ユーザーが触っていい項目」だけを明示的に制限**できます。

### ③ ヌル（null）の意味が違う
*   **Requestでのnull**： 「更新しない」という意味かもしれない。
*   **DBでのnull**： 「未設定（データがない）」という意味。
これらを1つの型で表現しようとすると、`if (value == null)` の判断が非常に複雑になります。

### ④ CQRS（参照と更新の分離）
特に参照系（Query）では、複数のテーブルをJOINした結果を返したいことが多いです。これは「1テーブル = 1Entity」という構造には収まりません。そこで**「参照専用のモデル（ReadModel）」**を定義し、MyBatisの `resultMap` でそこに詰め込むのが実務の王道です。

---

## 3. クラス構成と詰め替え場所の「常識」

実務における標準的なクラス構成と、データの流れを整理します。

### 構成イメージ
| レイヤ | オブジェクト名例 | 役割 |
| :--- | :--- | :--- |
| **Presentation** | `TodoForm` / `TodoResponse` | 外界（HTTP）との通訳。 |
| **Application** | `TodoCommand` / `TodoDto` | ユースケースを遂行するためのデータ。 |
| **Domain** | `Todo` (Entity) | 業務のルールとDBの構造。 |
| **Persistence** | `TodoMapper` | DBへの永続化。 |

### 詰め替え（マッピング）は「境界」でやる
*   **Controllerの仕事**： `Form` を受け取り、内部用の `Entity` や `Command` に翻訳してServiceに渡す。
*   **Serviceの仕事**： 業務処理を行い、結果を `Response DTO` に翻訳して返す。（またはReadModelをMapperから受け取る）
*   **Mapperの仕事**： `Entity` や `ReadModel` をDBとやり取りする。**MapperのXMLの中で `resultType="TodoResponse"`（API用DTO）を直接指定するのは、DB層がWeb層を知ってしまうため実務では「悪」とされます。**

---

## 4. CQRS（コマンド・クエリ責務分離）におけるQueryの流れ

ログで盛り上がった「参照系のベストプラクティス」です。

**[Queryフロー]**
`DB` → `Mapper` → **`ReadModel`** → `Service` → **`ResponseDTO`** → `JSON`

*   **ReadModel（XxxReadModel, XxxRow, XxxView）**：
    MyBatisのJOIN結果など、DB都合で効率的に取ってきたデータ。
*   **ResponseDTO（XxxResponse）**：
    API利用者が使いやすいように整形されたデータ（日付のフォーマット、表示順の制御、不要なIDの削除など）。

これらを分けることで、「SQLの最適化」と「APIの使いやすさ」を両立できます。

---


# テーマ4：トランザクション設計と例外処理（整合性を守る型）

「データが壊れないこと」を保証するために、Springの機能（`@Transactional`）とDBの制約、そして例外のハンドリングをどう組み合わせるか。

## 1. トランザクションの境界線：なぜ「Service」なのか

`@Transactional` を付与する場所には明確な理由があります。

### ❌ Controller に付けるのがダメな理由
Controllerは、HTTPリクエストのパース、認証チェック、外部API呼び出し、レスポンスのJSON変換など、**「DB操作以外の重い処理」**をたくさん含みます。
*   **問題点**：トランザクションが不必要に長くなり、DBの接続（コネクション）を長時間占有します。また、長時間ロックを保持することで、他のユーザーの処理を待たせてしまい、システム全体のパフォーマンスが低下します。

### ❌ Mapper に付けるのがダメな理由
Mapperのメソッド（SQL一発）にトランザクションを張っても意味がありません。
*   **問題点**：実務では「Todoを登録し、その後にTagを紐付ける」というように、複数のSQLを組み合わせて1つの業務を完了させます。Mapper単位だと、2手目のSQLで失敗したときに1手目のSQLがロールバックされず、不整合なデータが残ってしまいます。

### ⭕ Service に付ける理由：業務の1単位（Unit of Work）
Serviceのメソッドは、**「業務的にこれ以上分割できない一塊の作業」**を表現します。
*   **考え方**： 「Todo登録からTag紐付けまで全部成功するか、さもなくば最初から何もなかったことにするか」という**業務の整合性単位**でトランザクションを管理するのが正解です。

---

## 2. Spring AOP の仕組みと「プロキシの罠」

`@Transactional` を使う上で、絶対に知っておかなければならない技術的な挙動があります。Springのトランザクションは **「AOP（プロキシ）」** という仕組みで動いています。

*   **外部から呼ばれたときだけ効く**：
    Springが管理するBean（Serviceなど）が**外部のクラス（Controllerなど）から呼ばれた際**、Springが間に入ってトランザクションを開始します。
*   **「this（自分自身）呼び出し」は無視される**：
    同じServiceクラス内の `methodA()` から、`@Transactional` が付いた `methodB()` を呼び出しても、トランザクションは開始（または伝播）されません。なぜなら、Springのプロキシを経由せずに直接自分を呼んでいるからです。
*   **public メソッドのみ**：
    プロキシの仕組み上、`private` や `protected` のメソッドに注釈を付けても無視されます。トランザクションの入り口は必ず `public` メソッドである必要があります。


---

## 3. 例外処理：SQLException をそのまま返してはいけない

DBでエラー（制約違反など）が起きた際、それをそのままAPIのレスポンスとして返すのは「素人」の実装です。

### なぜ SQLException（または MyBatis の例外）を隠すのか？
1.  **セキュリティ**： エラーメッセージにテーブル名やカラム名、SQLの構文が含まれていると、悪意のあるユーザーにDB構造を教えることになり、攻撃のヒントを与えてしまいます。
2.  **APIの抽象度**： 「Duplicate key value...」というDBの生メッセージは、APIの利用者（フロントエンドなど）にとって不親切です。「既にその名前のタグは登録されています」という**業務的なメッセージ**に変換すべきです。
3.  **カプセル化**： DBを将来PostgreSQLからMySQLに変えたり、APIの構成を変えたりしても、利用者に影響が出ないようにします。

### 理想的な例外の「翻訳」フロー
実務では、以下のように例外を「バケツリレー」しながら翻訳していきます。

1.  **[DB層]**： 一意制約違反が発生。
2.  **[Persistence層]**： SpringがDB固有のエラーを `DuplicateKeyException`（Springの共通例外）に変換。
3.  **[Service層]**： 業務に合わせてさらに翻訳。
    `throw new AlreadyExistsException("そのタグは登録済みです")`
4.  **[Presentation層]**： `@ControllerAdvice` などでキャッチし、HTTPステータスコードを決定。
    `409 Conflict` + `{ "message": "登録済みです" }`

---

## 4. 「例外」を「業務の分岐」として使う

テーマ2でも触れましたが、**「チェックしてから実行する」のではなく「実行して失敗（例外）したら対処する」**という考え方が、トランザクション設計では非常に強力です。

*   **不整合を防ぐ最強の手段**：
    Javaの `if` 文によるチェックは、並列実行時にはすり抜ける可能性があります。しかし、DBの制約（UNIQUEなど）による例外は、100万分の1秒の狂いもなく重複を防ぎます。
*   **例外は「エラー（異常）」ではなく「通知」**：
    「登録に失敗した ＝ 既にデータがあるという通知がDBから来た」と捉え、それをServiceで適切にキャッチして業務的なレスポンスに変換するのが、実務レベルの例外設計です。

---

## 5. 研修 vs 実務のまとめ

| 観点 | 研修（現実解） | 実務（ベストプラクティス） |
| :--- | :--- | :--- |
| **TXの位置** | Serviceに付ける | Serviceのpublicメソッドに付ける |
| **TXの長さ** | あまり気にしない | DB接続を占有しないよう、最小限に保つ |
| **例外の扱い** | エラーが出なければOK | 業務例外に変換し、適切なHTTPコードで返す |
| **整合性担保** | Serviceでの `if` チェック | **DB制約 ＋ 例外キャッチ** |

# テーマ5：なぜ `SELECT *` は「不吉な臭い」がするのか

プロの現場で `SELECT *` が忌避されるには、単なる「行儀の良さ」を超えた、物理的・論理的な理由があります。

## 1. ネットワークとメモリの「無駄遣い」を避ける

アプリが `id` と `title` だけを必要としているのに、テーブルに `description`（長文）や `image_data`（大容量）が含まれていた場合、`*` を使うとそれら全てがネットワークを流れます。

*   **DBサーバ ➡ APサーバの通信負荷**：データ量が増えれば増えるほど、ネットワーク帯域を圧迫し、レスポンスが悪化します。
*   **Java側のメモリ消費**：MyBatisは取得した全カラム分、Entityオブジェクトにデータを詰め込もうとします。1,000件、10,000件と取得した際、使わないデータのためにヒープメモリが浪費され、GC（ガベージコレクション）が頻発する原因になります。

## 2. インデックスを無効化させない（カバリングインデックス）

DBには、**「インデックスだけ見て、テーブル（データ本体）を見に行かない」**という高速な検索モードがあります。
例えば、`todo_id` にインデックスが張られている場合：
- `SELECT todo_id FROM todos ...` ➡ インデックスだけで完結（爆速）
- `SELECT * FROM todos ...` ➡ インデックスを見てから、さらに「他のカラム」を取りにテーブル本体へアクセス（ディスクI/Oが発生）

`*` を使うことで、DBがせっかく用意した「ショートカット（インデックス）」を使えなくなるケースがあるのです。

## 3. 「将来の変更」に対する脆弱性

開発時はカラムが少なくても、1年後に誰かが「1MBくらいあるログ用テキストカラム」を追加するかもしれません。その瞬間、`SELECT *` を書いている全ての箇所のパフォーマンスが急落します。
**「必要なものを、必要な時に、必要な分だけ」** 指定する設計は、未来の変更に対する防波堤になります。

## 4. 結合（JOIN）時の「カラム名衝突」のリスク

複数のテーブルをJOINする場合、どちらのテーブルにも `id` や `created_at` という名前のカラムがあることはよくあります。
`SELECT *` で取得すると、MyBatisが「どの `id` をどのフィールドに詰めればいいか」混乱し、意図しないデータがセットされたり、エラーになったりします。

---

## MyBatisでの賢い書き方（`<sql>` タグの活用）

「いちいち列挙するのは面倒だ」という研修生には、MyBatisの共通化機能を教えます。

```xml
<!-- 1. カラム名のリストを定義しておく -->
<sql id="todoColumns">
  id,
  title,
  content,
  status,
  created_at
</sql>

<!-- 2. 必要に応じて呼び出す -->
<select id="findById" resultType="Todo">
  SELECT
    <include refid="todoColumns" />
  FROM todos
  WHERE id = #{id}
</select>
```
このように、**「定義は一箇所、利用は明示的」**にすることで、保守性とパフォーマンスを両立させるのが実務のスタイルです。
